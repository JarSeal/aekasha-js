Notes for the terrain category's material generator (`src/toolkit/terrain/material/`, `nodes/`, `debug/`; `createTerrainMaterial` and the JSON route `terrain`, p305), its decal material, its runtime decals and its decal generators (`decals/`, p309); the category's other parts (the texture set decode, the noise, the surface generators, the shared textures) are in the root's toolkit catalogue, the texture sets themselves in `src/_engine/features/texturesets/CLAUDE.md`; the root `.claude/CLAUDE.md` keeps the project-wide rules, commands and workflow.

## Terrain materials

One `MeshStandardNodeMaterial` built from a declarative config (`docs/plans/_DONE_p305_terrain-material-generator.md`, its Design and each phase's As built): layers of texture sets blended by a source (`SINGLE`, `VERTEX_COLOR`, `SPLAT_MAP`, `RULES` and the two `_AND_RULES` combos), each with anti-tiling (`NONE`, `DUAL_SCALE`, `HEX`), projection (`PLANAR`, `BIPLANAR`, `TRIPLANAR`, slope-gated), a macro variation, sparse sampling, a colour map (`DETAIL`, `FAR_ONLY`), a far surface (`AVERAGE_COLOR`, `COLOR_MAP`), object space and live procedural layers. **Every technique is a build-time branch on the config, its numbers uniforms**: a single-layer material compiles to what a single-layer material costs. The handbook pages (`docs/techniques/terrain-*.md`, `structure-materials.md`, `procedural-textures.md`'s live layers) are how to use it; the Hub's terrain page is the API.

- **Where the parts are.** `material/`: `TerrainMaterialConfig.ts` (the Zod schemas and types: the code route's config, the JSON route's define, a tier's overrides), `TerrainDefine.ts` (the define read by hand), `TerrainMaterial.ts` (both routes, `setupTerrainMaterial`, `buildTerrainGraph`, the variant per tier), `TerrainInputs.ts` (the inputs from a config, their reading and storage), `TerrainStorage.ts` (the binding budget), `TerrainSurface.ts` (the near surface, which every path builds), `TerrainLayers.ts` (a layer's UV, frame and sample), `TerrainSlots.ts` (the sparse slots), `TerrainFar.ts` (the far branch), `TerrainLive.ts` (live layers), `TerrainColorMapBake.ts`, `StructureMaterial.ts`, `TerrainQualityPreset.ts`, `TerrainWet.ts` (the wet response's inputs), `TerrainDebugViews.ts` (the views' loader). `nodes/`: one technique a module (`AntiTiling`, `Macro`, `Distance`, `ColorMap`, `Weights`, `HeightBlend`, `Rules`, `Projection`, `SlopeGate`, `Sparse`, `SurfaceSpace`, `BranchInputs`, `TerrainNormals`, `Wet`, `Ripples`, `Streaks`, `Shoreline`, `Snow`, `Frost`). `debug/_dbg__DebugViews.ts`. The JSON route's TSL file is `src/toolkit/materials/terrain/terrain.tsl.ts` (`setup = setupTerrainMaterial`); the rule type is `geometry/generate/terrain/TerrainRules.ts` (`terrain` imports `geometry`, never the reverse).
- **Two routes, one graph.** The code route's config (`TerrainMaterialConfig`) becomes the JSON route's props through `getTerrainMaterialProps`: the static define `staticDefines.terrain` (`TerrainMaterialDefine`: the config without `id`, `packing`, the layers' `set`, `splatMaps`, `noiseTexture`, `storage` and the texture ids) and the inputs (`layer<i>` `{ textureSet, packing? }` or the set array `layers` `{ textureSetArray, packing }`, `splat0` / `splat1`, `macro`, `colorMap`, `{ texture }` each). **The sets are inputs, not define fields:** the gather's texture closure reads `inputs` and `nodes`, never `staticDefines`, and a variant swaps a block's set or splat map without another shader. A variant's `staticDefines` replace the base's key by key (`terrain` whole), its inputs merge over the base's (so a `SEPARATE` base can't become `ARRAY`: an array material is its own base). An app material JSON needs its own two-line TSL file: a `tslFile` resolves from the JSON's top folder.
- **No zod in a build.** The graph imports only types from the schema; `readTerrainDefine` checks the define by hand (unknown keys, enums, ranges, the cross-field refusals, each error naming its path) and resolves it (defaults, a tier's overrides, `slotCount`, each layer's anti-tiling and projection). `TerrainDefine.test.ts` keeps the reader and the schema in step (keys, values, a shared list of defines both take and refuse), so **a new field goes in both**, and a refusal in one is a refusal in the other.
- **Resolution order:** a tier's `layers[i]` entry over the layer's own over the tier's material-wide field over the material's (`antiTiling`, `projection`, a layer's `source`); a tier's other fields replace the material's whole object (`blend`, `distance`, `sparse`, `uv`, `ao`). `macro`, `colorMap` and `space` aren't tier overrides (inputs, or the whole space). `getTerrainMaterialVariant(id, level)` is `getMaterialVariant` with the material's own define (`userData.terrainDefine`) and `qualityLevel`.
- **Storage and the budget** (`TerrainStorage.ts`): `SEPARATE` binds a packing's slots per layer, `ARRAY` one array per slot; the setup counts the layers, splat maps, macro and colour map against the renderer's limit (WebGPU: the lower of `maxSampledTexturesPerShaderStage` and `maxSamplersPerShaderStage`; WebGL2: `MAX_TEXTURE_IMAGE_UNITS`; 16 before the renderer) less `reservedTextures` (default 6) and throws listing them. The code route's `AUTO` takes `ARRAY` when `SEPARATE` is over or anything samples in slots (the material or any tier: a tier's variant shares the base's inputs). Under `ARRAY` a procedural set's layer and a live layer keep their own `layer<i>` beside the array (a set array takes imported sets only), the others mapping onto the array in order.
- **Slots** (sparse `maxLayers` under the sampled layer count, or `HEX`'s `apply: 'DOMINANT'` over two layers): the top K of the array's layers' raw weights by an insertion network of vars (`nodes/Sparse.ts`: an expression is built once per path to it, so each step is a var); a slot's uniforms picked by its layer (`pickByLayer`), every tap with the continuous coordinates' gradients (a slot's UV jumps where its layer changes). Every sampled layer's anti-tiling mode alike, the projected layers' projection alike; the layers of their own inputs beside the slots.
- **The TSL traps** (the slope gate's and the far branch's `If`s, the sky box's trap): a TSL `If` runs inside a `Fn` returning a struct var (`Fn(…).once()().toVar()`, three's `normalView` pattern); **every value the branch reads from outside is a zero var with an explicit `.assign()` before it** (`nodes/BranchInputs.ts`), since three declares a read-only `toVar()` at its first use, which put `dpdx(positionWorld)` into non-uniform control flow (WGSL forbids it; Chrome didn't refuse). No implicit-derivative sample in a branch: the taps take explicit gradients. Every uniform is made at setup (a `Fn` body runs at build time). The tests run the `Fn` and `If` bodies on stacks of their own (`setCurrentStack`) and walk from the statements built (a stack lists every node made in it), each node once (three's `traverse` is exponential on a hex graph).
- **Normals:** world space per layer (planar: an analytic frame; `MESH_UV`: the derivative frame; `MINIMAL`: a bump), blended by weight, converted to view once (`cameraViewMatrix`). Front faces only. `OBJECT` space works in the mesh's space × its scale and goes back to world once.
- **The far surface and the bake:** a material with a far mode builds the far surface as the struct's initializer and the near surface inside the branch (share under 1); a dense `MINIMAL` material bumps after the branch. A material with a debug view is built without the branch. `bakeTerrainColorMap` builds the graph again from the material's inputs (kept in a `WeakMap` by the setup: `userData` is cloned as JSON) without the distance effects, the colour map and the debug view, at view distance 0, in the mesh's UV space (`bakeTexture`'s `mesh`).
- **Live layers** (`TerrainLive.ts`): the set of a `{ textureSet }` bundle is `getTextureSetOfInput` (`aekasha/texturesets`); its generator must be loaded (`getTextureSetGenerator`) and a toolkit one (`build`); `prepareSurfaceGraph` makes its uniforms once for every plane and tap. No anti-tiling; in the far branch a `BUMP` normal takes two taps at the UV's gradients. A weight branch around it was measured dearer and dropped.
- **The wet response** (p307 D2, `wet`): `nodes/Wet.ts`' `applySurfaceWetness` (public: any TSL material) over the blended surface after the far branch and the macro, before the detail normals' fade (`material/TerrainWet.ts`); the conditions are `aekasha/surface`'s stable uniforms (`getSurfaceConditionNodes()`; without the feature the material builds dry, warned once a page load). Each layer's surface carries its sample's height, its set's `porosity`, `wetDarkening`, `wetRoughness` and `dryingSpeed` (one vec4, `getWetResponse`) and its `puddleResponse` (`LayerSurface.wet`), blended by the final weights; a far branch carries them as struct members (`wetHeight`, `wetResponse`, `wetPuddleResponse`), its far side the response by the raw weights at height 0.5. The sets' values are their category's unless given (`TEXTURE_SET_WET_RESPONSES`, the gatherer's); the gallery's Wet/dry row (`wetRow.ts`) is the check. Cavities are 1 − the material's `aoNode`. `SIMPLE` reads no height, cavity or normal (and refuses `puddles`). **Puddles** (`wet.puddles`, p307 T3): the waterline `puddleLevel × puddleResponse` (× the patches' share) over the blended height (the far side's 0.5), on ground flatter than `maxSlope`; under a puddle the pores and film are full, the roughness 0.02, the normal the geometry's. Their patches (`puddles.patches`) are the macro texture's B at their own scale: the one fetch the wet response makes (`TAPS` counts it), the input `macro` taken for it like rule noise (`takesMacroTexture`; the code route's `noiseTexture`, default `macroNoise`). **Regional wetness** (`wet.regional`, T7): a float vertex attribute (default `_wetness`, glTF's `_WETNESS`) or the first splat map's A (`PaintedWeights.splatAlpha`; a splat source painting at most 4 layers), the least wetness and puddle level shown. **Rain ripples** (`wet.ripples`, T4; `nodes/Ripples.ts`): the input `ripples` (a ripple atlas; the code route's `rippleTexture`, default `rippleAtlas`; `takesRippleTexture` like the macro's) sampled twice at the material's XZ, at two scales half a ring's lifetime apart, on the surface clock (`conditions.time`), each drop kept with the rain's chance; the normal tilted where water stands (the puddle, or the film × the puddles' flat gate) within `distance` (default 10-30 m). Both taps are in a branch on the rain and that weight (`masks.ripple`: `TAPS` gates its two fetches by it), with the slope gate's trap rules (inputs declared before the `If`, explicit gradients). `SIMPLE` refuses `ripples` too. **Rain streaks** (`wet.streaks`, T5; `nodes/Streaks.ts`): rivulets down faces steeper than `minSlope` (default 60°) that the rain reaches (the exposure × 2: a vertical face's full, an underside's none), one fetch of the macro texture's R (the input `macro`, taken like the patches') stretched `length` times down the face, its horizontal coordinate the space's x or z, whichever the face's normal turns from (each axis's own gradients), the two cross-fading over about 40-50° with a second fetch in a nested branch there alone (a hard switch showed a seam on a rounded rock). Damp (the pores' floor alone, never the film: a damp rivulet isn't glossy) full down to an overall wetness of 0.15, so they dry last; running (the film's floor, not × `puddleResponse`: running water is a film on a cliff too, and 25 % darker, the cue on a face whose pores the rain filled already) while it rains, a pulse moving down on the surface clock. The fetch is in a branch on the weight and the rain or wetness (`masks.streak`, which `TAPS` gates its one fetch by; the band's second isn't counted), with the slope gate's trap rules. Both qualities take them (they leave the normal to the film). **The shoreline** (`wet.shoreline`, T8; `nodes/Shoreline.ts`): bands over the height above the surface conditions' `waterLevel` (the world's Y whatever the material's space; none without a water level, whose uniform is far below any world), the waterline wandering ±`noise` by two octaves of value noise at the world's XZ: the wash (standing water up to the run-up's current reach: a puddle, so soaked, 0.02 rough and flat), the saturated sand 15 cm over the higher of the reach now and 1.5 s ago (a film's floor: its glossy edge is what shows a wave) and the damp band to `band` metres (a regional wetness's floor: the least wetness and puddle level shown, dried by the set's `dryingSpeed`); all full under the water. `runUp` (`{ height, period }`) moves the reach on the surface clock, out of step along the shore. Arithmetic only (no fetch, no branch), both qualities (`SIMPLE` leaves the normal alone). **Snow** (`wet.snow`, T10; `nodes/Snow.ts`): the input `snow` (a `{ textureSet }` bundle; the code route's `snowSet`, default `snow01`, in its default packing; `takesSnowSet` like the ripples'; under `ARRAY` storage it keeps its own input beside the array, its slots in the budget and in `AUTO`) covers the surface before the wet math by the surface conditions' `snowCoverage`: each pixel's resistance is half its slope over `maxSlope` (default 55°), a quarter its relief (`FULL`; the stones stick out last) and a quarter a drift noise (two octaves of value noise over `noiseScale`, ALU), and at least the slope alone (nothing past `maxSlope`); the coverage × (1 + `edge`) rises past it, faded over `edge`. The set is sampled top-down at the material's `(x, −z)` (its normal through the planar frame), mixed in by the cover with its albedo, roughness, normal (`FULL`), relief and its set's wet response, so the wet response wets the snow by its own: frozen below 0 °C (the wetness × 1 − cover × (1 − melt), so it doesn't show on frozen snow), slush from 0 to 3 °C (grey-blue, smoother, wet), its meltwater (a wider fringe of the mask × the melt) a regional wetness's floor around it. The whole of it is in a branch on the coverage (a snowless frame computes nothing), the taps in one on the cover, with the slope gate's trap rules; past a far mode's band (its share) the set's average colour, no tap (the reader refuses a snow set without one there). `masks.snow` is the cover: `TAPS` gates the set's slots by it, `WETNESS` mixes pale blue in by it. Both qualities. **Frost** (`wet.frost`, T11; `nodes/Frost.ts`): after the wetness, from `temperature[0]` (default 0 °C) to full at `temperature[1]` (−5 °C) × `strength` × 1 − the blended porosity (no set data of its own: ice fully, sand little) × the facing (an underside half), the albedo 12 % toward a cold white and the roughness raised toward 0.6 (never lowered: ice loses its mirror); arithmetic, both qualities, `masks.frost`. Its `sparkle` (`FULL` only; the reader refuses it with `SIMPLE`): 3D cells of the material's position (`density` a metre, default 50), each a random facet (the noise library's hashes) and a spot, glinting where the facet turns to the camera, × the frost or the frozen snow (the cover × 1 − the melt) × the view distance's fade (`distance`, default 4-10 m), added to the albedo × `strength` (default 3: lit by the scene, dimmer in shade); in a branch on that weight (the slope gate's trap rules), no fetch. **Rain occlusion** (`wet.rainOcclusion`, T12: `NORMAL_Y`, the default, the facing alone; `MAP` also the `rainOcclusion()` feature's map, `aekasha/surface`'s `getRainOcclusionNode()` at the world's position and geometry normal, whatever the material's space): the share of open sky scales the exposure (so the wetness, the streaks and the frost's facing), the puddle level, the ripples' rain and the snow coverage, never the regional wetness, the shoreline or the meltwater (not rain); one compare fetch every pixel makes (`TAPS` counts it), outside any branch (a compare fetch needs uniform control flow: the wet response runs at the graph's top level); no uniform of its own; both qualities; without the feature `MAP` builds with the facing alone, warned once a page load. The map's occluders are what casts shadows or has `userData.rainOccluder` (the gallery's pieces: the row casts no shadows). The colour-map bake strips `wet` (the dry surface), the ripple atlas, the snow set, and the macro input when only the patches or the streaks read it.
- **The rock material** (`material/RockMaterial.ts`' `setupRockMaterial`, p308 D5; the toolkit material `rockScatter`, `materials/rockScatter/`, its two-line TSL file): not a terrain material config but its own graph over the category's nodes, since a scatter rock is an `InstancedMesh` instance, whose `OBJECT` space would be the cell's. `TRIPLANAR` samples the input `surface`'s set at three's `positionGeometry` (the rock's own space; the texel density follows the instance's scale), each plane through `sampleAntiTiled` (`DUAL_SCALE` without the macro patches) and its normal to view space by `transformTangentNormalToView` at the plane's UV (the instance matrix isn't a node, so no `toWorld`), blended by the facing to `sharpness`; `UV` samples an imported rock's own maps once at the mesh's UV. Then the macro (`sampleMacroTexture` at `positionWorld`), a dust blend toward `dustColor` or the set's `averageColor` on faces turned up, and `applySurfaceWetness` with frost and `rainOcclusion` (geometry normal `normalViewGeometry`, the shaded normal's space). Its modes are flat static defines read by hand (`readRockDefine`); its numbers optional inputs, else uniforms of their defaults, all at `userData.uniforms.rock_<name>`. A scatter item can't override a material's inputs, so rocks on another ground set are a material JSON of their own (and its two-line TSL file).
- **The decal material** (`decals/DecalMaterial.ts`' `setupDecalMaterial`, p309 D2; the toolkit's `decalsGround_blend`, `decalsGround_cutout`, `decalsStructure_blend`, `decalsStructure_cutout`, `materials/decal/`, over one two-line TSL file): not a terrain material config but its own graph, like the rock's. A decal is a mesh UV'd into its cell of a `DECAL` atlas (`albedoAlpha` RGB + opacity, `normalRough` normal XY + roughness + puddle mask; p309 D1), sampled at the mesh's `uv` (atlas space: one material draws every cell, so a merge group of any cells shares it), its normal in the frame of that UV's derivatives (an `{ atlas }` input's UV is its cell's). `mode` (`BLEND`: transparent, no depth writes; `CUTOUT`: opaque, `alphaTest` 0.5, alpha to coverage) is set by the setup, a polygon offset on both (factor −1, units −4: a `CUTOUT` quad is as coplanar as a `BLEND` one); the JSON's `params` give `alphaTest`, `polygonOffsetFactor` and `polygonOffsetUnits` where they aren't 0. `edgeFade: 'UV1'` (the toolkit JSONs; the reader's default `NONE`) fades by the mesh's second UV set, 0..1 over the decal, over a vec2 share at each edge (a strip's along-length 0): **a mesh without `uv1` reads 0 there and draws nothing.** A `BATCHED` merge member's `setMergeMemberColor` opacity fades it with no code here (three multiplies a batch's colour, alpha too, into the diffuse colour before the opacity). `wet` (`FULL`, `SIMPLE`, `NONE`): `applySurfaceWetness` by its own response uniforms; the puddle mask is a relief, `0.5 − mask × puddleDepth`, under `FULL`'s puddles, so with `puddleResponse` 0.5 a full mask is under water from a puddle level of 0.1 and an unmasked texel never (flat ground's relief, as the terrain material's; 1 would flood the whole quad at the gallery's 0.6). `frost`, `rainOcclusion`, the optional inputs `ripples` (`FULL`) and `snow` as the rock's; the toolkit JSONs have no `snow` (it would pull `snow01` into every scene), so a decal shows over snow-covered ground unless an app's own JSON adds it. A logarithmic depth buffer writes fragment depth, which the offset doesn't move. The gallery's Decals stage (`decalsStage.ts`) is the check: every cell of both atlases on quads coplanar with a flat block and a wall, `BLEND` beside `CUTOUT`, `renderOrder` 10. **A decal's albedo replaces the ground's**, so it reads only on grounds it suits: the tyre tracks' darkened sand reads pressed into the gallery's `mud02` but as pale strips on `terrainBlockTest`'s darker `mud01` (lit about 2.6 times as bright), where the walk tints its trail (a spawn's `color`, × 0.4); a material's `tint` input does it for a mesh decal set. A decal mode keeping the ground's colour is a p309 follow-up.
- **Decal generators** (`decals/DecalGenerator.ts`, `decals/BakeDecal.ts`, `decals/generators/`, p309 D5; on `aekasha/toolkit/terrain`: `defineDecalGenerator`, `bakeDecalGenerator` and the nine, `decalCracks`, `decalStain`, `decalScorch`, `decalMudSplatter`, `decalFootprint`, `decalWetPatch`, `decalIceCrack`, `decalLeafPatch`, `decalFormwork`, each its own module and named export, so an unused one tree-shakes): not p304 surface generators (those have no opacity or puddle mask, pack only into a texture set packing, are gathered by their `<id>.generator.ts` file name, and tile where a decal fades out), but built on their parts by generics: `SurfaceGenerator.ts`' graph source (`SurfaceGraphSource`: a decal generator is one as it is), the params as uniforms (a number or colour rebakes without a rebuild; a static number, toggle or `choice`, a build-time string such as `decalFootprint`'s `shape`, rebuilds), `createSurfaceContext`'s `cells` and `seed`, the height layout function. `build(ctx, params)` returns `{ albedo, opacity, height, roughness, puddle?, normal? }`, packed into the `DECAL` slots (`packDecalOutputs`: `albedoAlpha` the albedo and opacity, `normalRough` the normal's XY × 0.5 + 0.5, the roughness and the puddle mask or 0, each clamped); without a `normal` it's `heightToNormal` over 4 taps, `heightScale / physicalSize[0]` deep. No AO: a generator darkens its own albedo. **The albedo over the whole decal, never black where the opacity is 0:** the atlas stores straight alpha, and its padding, mips and bilinear taps mix a transparent texel's RGB into the edge. **The roughness is the dry surface's:** the wet response brings the gloss (a print's inside at 0.5 glinted white under a low sun, its lugs averaged flat in the far mips; 0.75 since p309 Phase 5). `generators/DecalShapes.ts` holds the shared shapes (`centredPoint`, the SDFs, `edgeGuard`: a round decal's opacity gone past 0.44-0.5 of its radius, so the padding stays transparent whatever the noise). `bakeDecalGenerator` makes both slots in one MRT `bakeTexture` (`<id>.albedoAlpha` sRGB, `<id>.normalRough` linear; 512² by default) with the surface bake's controls and reuse by id (`BakeSurface.ts`' `startControlledBakeAsync`, `reuseOrStartBakeAsync`). **A generated cell's `data` is its recipe** (`generator`, `seed`, `params`), its `sources` the two PNGs baked from it at the cell's content size (480²: the rect less the padding; no mips, so the pipeline never resamples them), `source/<cellId>_albedoAlpha.png` and `_normalRough.png`, already in the `DECAL` packing. The gallery's Decals tab (`_dbg__terrainGalleryDecalBakes.ts`) is the tool: a cell baked from its data onto the bench (as `BLEND` and `CUTOUT` decals, lit and wet), its seed and params edited, its data copied as JSON, a cell or all exported on WebGPU (a PNG with the same pixels is left alone, one with other pixels asks first); then `yarn assets`. Editing a cell's `data` alone changes no output. The checks: the stage (wet footprints fill in a rain shower, Phase 5's figures) and `terrainBlockTest`'s walk (the boot print in a pool of 128).
- **Runtime decals** (`decals/RuntimeDecals.ts`, `DecalPatch.ts`, `MeshDecals.ts`, `DecalRibbons.ts`, `DecalRibbonPatch.ts`, p309 D4; on `aekasha/toolkit/terrain`: `createDecalPool`, `spawnDecal`, `spawnMeshDecalAsync`, `spawnRibbonDecal`, `createDecalTrail`): a pool is an explicit `BATCHED` merge group (`aekasha/merging`), one render object for every decal: one multi-draw on WebGL2, a draw per decal on WebGPU (r187 merges only instances of one geometry). Each decal is a mesh entity of the pool's material (app id `decalPool/<id>/<place>`) at the origin with its patch in world space, so a respawn is its slot's rewrite alone (`updateMergeMember`) from any stage: a `TRANSFORM` written outside `MAIN` would reach the batch a frame after the rewrite. A spawn takes a free place (one never used, or a decal whose lifetime ended), else the oldest drawn (FIFO), writes the patch into the place's own typed arrays, which its geometry's attributes span whole (made once per arrays: a spawn allocates nothing; the batch copies a vertex attribute's whole array anyway), the index's `count` set to the patch's (three types it read-only; both the batch's copy and a draw read it) and **the positions past the patch's set to its first vertex**: three bounds a batch's slot by every vertex, so a tail at the origin stretched a decal's bounds there (its instance never culled, and drawn into the sun's VSM shadow map as a receiver: a draw more for every decal, found in section 5), and keeps every slot within the group's `geometryReserve` (`maxPatchVertices`, default 169, and `getDecalPatchMaxIndices`), so the batch's buffers stop growing; a mesh decal past it gets arrays of its size and its slot grows the buffers once. **The patch** on a block is the block's own grid (`blocks/BlockSurface.ts`' `readBlockSurface`, read once per geometry, a `WeakMap`): the window of grid points under the decal's rect, the cells wholly outside it left out, its triangles the block's (each cell split along its (col + 1, row)–(col, row + 1) diagonal), so it conforms exactly at any spacing; its UVs projected along the decal's `normal` (`getDecalFrame`), `uv1` 0..1 over the decal (outside it the edge fade draws 0), lifted along the block's normals (`lift`, default 5 mm; the polygon offset does the coplanar work). A window past the reserve takes every n-th grid line (warned once a pool). A mesh decal is three's `DecalGeometry`, loaded by `import()` with the first one (`writeMeshDecalPatch`). **Ribbons** (`writeRibbonPatch`): rows along the path at most `step` apart (half the block's spacing), each vertex sampled on the block (`sampleBlockSurface`) and lifted 15 mm (its faces aren't the block's); the cell repeats along U (`tileLength`) with its rows doubled where a tile ends; `uv1.u` is a fade coordinate (0.5 inside, 0 → the material's edge share over `endFadeMeters` at a faded end), so the decal materials fade a strip's ends over metres. A trail stamps a segment every `segmentLength` (2 m) of path, joined to the last one (the same row at the joint, its tiles running on): the track lags the point by up to a segment. **Fades:** a decal's opacity is its own × its FIFO factor (the pool's oldest `fifoFade`, default `maxDecals / 8`, fading by place while the pool is full, written on a spawn and an expiry) × its lifetime's (its last `fadeSec`, by time, written by the pool's `APP_LOGIC` system for the fading decals only), through `setMergeMemberColor` only past 1e-3 of the last write (with `CUTOUT` it erodes the cut-out). Visual only: the cell and a missing rotation come from the named stream `decals` (`randomStream`). **Measured** (Phase 4 section 5, `terrainBlockTest`'s decal block walk and `devTools/bench/terrainBlockTestDecals.ts`; Windows Chrome, RDNA 3): 128 footprints and 64 track segments are 2 render objects (192 unmerged), the CPU frame 1.0-2.6 ms lower than the decals drawn by their own meshes on both backends, the buffers the same over 10 minutes of 60 spawns a simulated second, and WebGL2's GPU time the same as separate meshes at a walk's rate (0.56 ms the whole render) and 5 % more under ~1.2 rewrites a frame (0.59 against 0.56). WebGL2's GPU figures need the bench's own timer queries around the whole render on a GPU nothing else uses: the stats panel's timer and per-object queries around the uploads read wrong, and a light load's GPU reads at two levels by the minute (0.56 or ~2.3 ms).
