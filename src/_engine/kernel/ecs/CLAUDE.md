Notes for the ECS core (`src/_engine/kernel/ecs/`: `ECSWorld`, the registries, the core components and systems; and `kernel/loop/`'s system stages and main loop): the ECS core's detail, moved from the root, where the stage order stays; the root `.claude/CLAUDE.md` keeps the project-wide rules, commands and workflow.

## ECS core

`src/_engine/kernel/ecs/ECS.ts` defines `ECSWorld`, a bitwise-packed (index + generation) entity/component store. Key patterns:

- **Plugin registration**: `ECSWorld.registerPlugin(fn)` (and `registerCorePlugin`, also for worlds created with `applyGlobalPlugins: false`) and `ECSWorld.registerComponentHooks(type, { onAddComponent, onRemoveComponent, onDeleteEntity })` are static (all current/future worlds) and are called from an install, never at module load (see Engine features): the kernel's in `installKernel`, each feature's in its `install` through the `FeatureContext`, and the app's in `src/AppECSPlugins.ts`'s `appECSPlugins` feature (`id: 'app'`), which `src/index.ts` lists last in `features` — this is where you wire up new app/toolkit ECS managers/effects (or give a bigger part of the app a feature of its own). Registration order, so install order, breaks ties within a stage and order. `onRemoveComponent` runs only when the entity has the component, and a hook that removes the same component from the same entity again while it runs (two entities linked to each other) is ignored (p612).
- **Component types**: core types live in `src/_engine/kernel/ecs/ECSRegistry.ts` + `ECSCoreComponents.ts`, whose `ComponentDataMap` interface is the whole key → data map. An app or toolkit module adds its components in its own file, with a key object (`HoverToolComponentType`) and `declare module 'aekasha' { interface ComponentDataMap { [Key.X]: Data } }`; code uses that key object, since the `ComponentType` value holds only the engine's keys. Augment only `'aekasha'` (a second path to the same interface drops keys silently). `src/AppECSRegistry.ts` holds the app-wide keys. Debug listings read `ECSWorld.getComponentTypes()` (values, eg. `CORE_TRANSFORM`, `APP_SPIN`). `CoreComponentType` is the same object, `@deprecated` (removed in engine 6.0.0): write `ComponentType`.
- **App ids**: `getEntityIdByAppId` (and `ECSWorld.getEntityIdByAppId`) is one lookup in the world's map, kept where `APP_ID` is added, removed and its entity deleted (p612 D6). The first entity created with an id keeps it until it's deleted or its `APP_ID` removed or replaced, then the next live one with the id takes over (only ids taken twice are scanned); a second entity given a fixed id (`isFixed`) warns in the debug env. Never change `APP_ID.id` in place: add a new `APP_ID`.
- **Managed entities**: `CoreEntityOpts.managedBy` (code only) adds a `MANAGED_BY` component (`{ manager, ownerId, role }`) to an entity its manager creates, drives and deletes (eg. the sky box's lights). `createLightEntity` then skips the saved debug overrides, and the Lights tab shows the light read-only with a link to the manager's tab (registered with `_registerManagerDebugInfo` in `debug/_dbg__ManagedEntities.ts`), without LS writes or undo entries.
- **System stages**, defined in `src/_engine/kernel/loop/SystemStages.ts` (`ECSSystemStage`, with the `APP_RENDER_SYNC_ORDER` constants), run in this fixed order every frame: `MAIN → APP_PRE_PHYSICS → APP_POST_PHYSICS → APP_LOGIC → APP_RENDER_SYNC → LATE_MAIN`. `APP_PHYSICS_STEP` is the exception: it runs 0-N times per frame, once right before each fixed physics sub-step (dt = the fixed timestep), from inside `stepPhysics` (between `APP_PRE_PHYSICS` and `APP_POST_PHYSICS`) — use it for anything that must move in lockstep with the simulation (kinematic platforms, character controllers). In `WORKER_THREAD` mode the one-way worker commands those systems issue are carried in that frame's single STEP message and replayed before their own sub-step. Collision/contact-force events (both modes) are delivered by `flushPhysicsEvents` at the start of the next sub-step — after held-key polling, before `APP_PHYSICS_STEP` — an order gameplay code (e.g. the dynamic character's moving-platform logic, `features/character/controllers/dynamic/`) depends on. `APP_POST_PHYSICS` is where physics state syncs into ECS transforms; `APP_RENDER_SYNC` is where ECS transforms sync into Three.js `Object3D`s.
- **The loop** (`kernel/loop/MainLoop.ts`, p612 D10): one frame function, `runFrame`, in every build (not `async`; the stats behind `IS_DEBUG_ENV`, which a production build folds, the editor view branch a boolean check). Every frame request goes through `requestMainLoopFrame()` (`@internal`), which asks for one unless one is queued or the loop is stopped (`stopMainLoop()`), so the start, `toggleMainPlay` and the Loop controls tab never run two chains. The max FPS cap (`VITE_MAX_FPS`, or the Loop controls tab's `maxFPS`) skips only the render, `LATE_MAIN` and the late scene loopers of a frame it holds back: the stages before them run on every frame, so no game time is lost. Worlds are iterated from `getAllECSWorlds()`, a read-only array rebuilt on world create and delete (no copy per frame). The window listeners are `onVisibilityChange(fn)`, `onBeforeUnload(fn)` and `onWindowBlur(fn)` (`@internal`, Sets, each returning its remover).
