Notes for input (`src/_engine/kernel/input/`: the device bindings, the action layer and the gamepad); the root `.claude/CLAUDE.md` keeps the project-wide rules, commands and workflow.

## Input devices

One module per device, no barrel, so an app bundles only the devices it uses: `KeyboardInput.ts`, `MouseInput.ts` (raycast picking through `InputPicking.ts`, each binding's own `targets` only), `TouchInput.ts`, `GamepadInput.ts` (see Gamepad). `InputSharedTypes.ts` and `ActionTypes.ts` are type-only. Each module adds its DOM listeners on its first binding or action source, never at load.

- Input scope (`InputState.ts`' `setInputScope`, `@internal`, p611 D6): where the devices listen, read when a module adds its listeners. `WINDOW` (default, the full-page boot): as always. `CANVAS` (an engine mounted into a host page, `mountAekasha`): the mouse's and touch's listeners on the canvas (`mouseup` stays on the window, passive, so a press made on the canvas ends wherever it's released), the keys on the canvas, which gets `tabindex="0"` and clears the held keys on `blur` (attached once the renderer exists, `onRendererCreated`), and the gamepads read only while the canvas has focus (released when it loses it). `NONE`: no listeners and no gamepad reads, so bindings and maps never fire. Each device has an `@internal` remover (`removeKeyListeners`, `removeMouseListeners`, `removeTouchListeners`, `removeGamepadListeners`, the unmount's); the next binding or source adds them again by the scope then.

- The device bindings (`createKeyBinding`, `createMouseBinding`, `createTouchBinding`, on `aekasha`) are the low-level API: a callback on a device event, no sampling, unchanged by p610 and documented as such. Gameplay goes on action maps; a binding stays right for picking (`MOUSE_CLICK` / `MOUSE_HOVER` targets), a pinch, or a tool that wants the raw event (`scene01`'s D reads the binding's `time`). `KEY_HELD` bindings are polled per fixed step (`pollHeldKeyBindings`, after the action sample) or once per frame without stepping.
- Master switches (`InputState.ts`, its own tiny file so a scene load pulls no device module): `setAllInputsEnabled` (off during a scene load) and `setAppInputsSuspended` (an editor view, apart from it so a load's end doesn't lift it). The bindings honour both (`isDebugKey` bindings only the first); the action contexts read them (see Action maps). The per-device `set*InputsEnabled` switches are the bindings' own; nothing in `src/` calls them, and they don't apply to action maps.
- Device timing reads `performance.now()` (tap and double-click windows): the input modules aren't simulation code and aren't on the simulation lint. What the simulation reads is the per-step action sample.
- Reserved chords (the debug keys, `debug/DefaultDebugKeyBindings.ts`): `markChordReserved(id, chord, mapId?)`, and `warnIfKeyChordReserved` (`@internal`) warns in the debug env for a key binding or an action map binding on one (a binding that ignores modifiers collides on the key alone). `isKeyEventTakenByBindings` and `Actions.ts`' `isKeyEventInActiveMaps` (both `@internal`) let a yielding debug key give way.

## Action maps

The action layer (p610 D4, p603 C5; `Actions.ts`: maps, contexts, sampling, events; `ActionBindings.ts`: compiling bindings and reading the devices through them; `ActionRecording.ts`). Public on `aekasha`: `createActionMap`, `getActionMap(s)`, `setActionContextEnabled`, `isActionContextEnabled`, `recordActions`, `playActionRecording` and the types. The Hub's Input page is the user guide.

- **Two ways to read.** `sampleActions(stepIndex)` runs in `MainLoop.runFixedSubStep` right after the debug pre-step hook and before `pollHeldKeyBindings`, and `sample(-1)` once per frame without stepping (numbered by a count of its own); `map.read()` returns that sample (one object per action, updated in place). Presses and releases between samples are counted, so a tap shorter than a step isn't lost and an edge lands on one step. `onPressed` / `onReleased` fire at the device event (also paused, in editor views; a replay's at its sample). Simulation code reads; UI and debug keys use the callbacks.
- **The loop hook** (smallest build): `MainLoop`'s `@internal` `setActionSampler({ pollFrame, sample, skip })`, set by the first `createActionMap`, so an app without maps bundles none of the layer. `pollFrame` right after the latch in every loop variant (gamepads, while a map has a gamepad binding); `skip` in `noteFixedStepPause` (paused or suspended), so a press made meanwhile doesn't land on the first step after it. The step index comes from `FixedStepDriver.step`'s `onBeforeStep(stepDelta, stepIndex)`: the number `getPhysicsSubStepIndex()` gives, so recordings and brains share one step clock.
- **Contexts.** `GAMEPLAY` (default) and app contexts follow `areAppInputsEnabled()` (off during a load and in editor views); `DEBUG` follows `areAllInputsEnabled()` (runs in every view). A map is active when enabled, its context on, its `sceneId` current (if any) and its `enabledInDebugCam` rule met (default `NOT_ENABLED_IN_DEBUG`, `DEBUG` maps `ENABLED_IN_DEBUG`), and no replay stands in for it.
- **Live state vs. activity.** Every device's state is followed all the time; the counts, deltas and callbacks only while the map is active. So a key held through an inactive spell reads down afterwards without a press.
- **Map defaults outside `DEBUG`:** `ignoreModifiers` true, `preventDefault` true (a bound key's press while active, never in a text field, and never with Ctrl / Alt / Meta for a binding that ignores modifiers: copy, paste and back stay the browser's). `DEBUG`: exact modifiers, no `preventDefault` (the debug key maps set it themselves). A taken id replaces the old map (a scene's map made on every visit).
- **Types and state.** `createActionMap` has a `const` type parameter: action ids typed, each action's bindings checked against its type (`ActionBindingOf<T>`); a wrong-kind binding from plain data is left out with a warning. One `ActionState` shape for every type (`isDown`, `pressedCount`, `releasedCount`, `value`, `x`, `y`); `AXIS_2D` / `DELTA_2D` right and up positive (the gamepad's and the mouse's Y flipped). Several bindings: a button is down while any is, an axis takes the one pushed furthest, a delta sums them. A new keydown (not a repeat) of a key bound to a `BUTTON` that's already down counts as a press (macOS sends no keyup for Z while ⌘ is held), so `pressedCount` can exceed `releasedCount`.
- **Recording** (`ActionRecording.ts`, its own module): `recordActions(map).stop()` gives `{ mapId, firstStep, lastStep, frames }`, a frame per step with the non-idle fields of the non-idle actions (JSON as is). `playActionRecording` stands in for the map's devices (which neither count nor call back meanwhile) whatever its context, until `lastStep`; `from: 'RECORDED_STEPS'` (default, starts over when the step goes back: a scene loaded again) or `'NEXT_SAMPLE'`. Deleting the map ends both. The scene runner's input scripts are device-level key events instead (the test bridge's `playInput`, `devTools/verify/CLAUDE.md`), so they check the whole input path.
- Tests: `Actions.test.ts` (window, document and navigator stubbed): sampling and edge counts, contexts, the composites, the gamepad, recording and replay. The `MainLoop` hook itself isn't unit-tested (driving the loop needs a renderer): the scene runner's path hashes cover it.
- Users: the player brains (`features/character/brains/`), the debug keys (three `DEBUG` maps), the example scenes and `physicsTiers`, `largeWorld`, `assetCompare` (p610 Phase 5).

## Gamepad

`GamepadInput.ts` (p610 D4). The Gamepad API has no button events: `navigator.getGamepads()` is polled once per frame by the action layer's `pollFrame`, only while a map has a gamepad binding, and each pad's buttons and axes are kept as `Float64Array`s (the API's doubles: a `Float32Array` turned a trigger's 0.3 into 0.30000001, which a recording would carry). `gamepadconnected` / `gamepaddisconnected` drive `onGamepadConnected` / `onGamepadDisconnected` without polling; `getConnectedGamepads()` lists the pads.

- Names (`GAMEPAD_BUTTON_NAMES`, the standard mapping in index order): buttons by position (`SOUTH` is A / Cross), `LEFT_X`… axes and `LEFT` / `RIGHT` / `DPAD` sticks, up and right positive. Deadzones: an axis's and a stick's radial one default to 0.15, the rest rescaled to 0-1; the d-pad has none. A trigger is a `BUTTON` with its analog `value`.
- A map's `gamepadIndex` reads one pad; by default any, the furthest pushed for an axis. No gamepad binding on `DELTA_2D`: a stick look is an `AXIS_2D` rate action.
- Chrome reports a pad only after a button on it was pressed (a privacy rule). The scene runner has no pad, so gamepad bindings (the gym's `TANK` player) are checked by hand.
