Notes for the render area (`src/_engine/kernel/render/`): snapshots, pre-warm compiles, texture bakes, the drawing pipeline seam and the views; the root `.claude/CLAUDE.md` keeps the project-wide rules, commands and workflow.

## Snapshots

`kernel/render/Snapshot.ts`: `takeSnapshotAsync({ width, height, scene?, camera?, postFx?, hideDebugHelpers?, transparent?, samples? })` renders a scene through a camera into an image off screen and reads it back as a `Snapshot` (`{ width, height, data, postFx }`: RGBA8, sRGB encoded as the canvas shows it, straight alpha, top row first), for thumbnails, the Hub's example images (the debug drawer's Hub tab) and save game pictures. By default it's what the canvas shows: the current view's scene and camera (the debug camera too), through the scene's PostFX, without the viewports, and with the debug helpers hidden (`isDebugHelperObject`, `kernel/render/Object3DHelpers.ts`: `markDebugHelper`'s flag, the 3D symbols, three's `*Helper`s; the profiler's census reads the same predicate). `snapshotToBlobAsync` encodes one through a canvas (PNG, WebP, JPEG; a fully transparent pixel loses its colour), the dev files' `encodePNG` byte for byte. `readRenderTargetRGBA8Async` (`@internal`) is its readback (top row first on both backends), which the texture preview shares.

- Direct path (any scene and camera, PostFX off, or `transparent`): the scene renders into a HalfFloat target, then a quad with `renderOutput()` and the renderer's tone mapping and output colour space (the viewports' contract) into an RGBA8 target. The canvas isn't touched. `transparent` clears to alpha 0 and leaves the scene's background out for the render.
- PostFX path (the root scene with the active camera, its pipeline on): three's `pass()` sizes itself from the drawing buffer, so the renderer is resized to the snapshot (pixel ratio 1) for the render and put back, and `renderFrameNow()` (`MainLoop.ts`) draws the canvas again in the same task, so the browser never shows it cleared.
- Both start a new node frame first: three (r186, r187) updates `FRAME` nodes (a `pass()`, a shadow map) once per node frame, so a snapshot after the frame's own render would reuse them at the canvas's size and aspect (the PostFX snapshot came out stretched).
- The camera's aspect (an orthographic camera's width, keeping its height) is set for the snapshot and put back, like everything else it changes, before the readback starts.

## Pre-warm compiles

`preWarmMesh` (`kernel/mesh/Mesh.ts`: `createMeshEntity`'s `preWarm`, every level of a pre-warmed mesh's LOD) and `prewarmGeometry` (`kernel/assets/Geometry.ts`) compile with three's `renderer.compileAsync` ahead of the first draw (p057 Phase 3 step 3).

- `preWarmObjectsAsync(objects, label)` (`kernel/mesh/Mesh.ts`, p353 Phase 2: streaming's priming): objects already in the root scene, compiled in one `compileAsync` of the root scene (three r187 builds up to 16 pipelines at once only within one call), each made visible and unculled for the call's synchronous part only, so held objects (`TAG_DRAW_HELD`) compile without a frame showing them; the rest of the scene in view compiles too (a lookup for what's compiled). It compiles the real objects, never stand-ins: three (r187) counts a pipeline's users and releases it with its last render object, so a disposed stand-in takes its compile with it.
- During a scene load, a pre-warm from scene code runs before the load creates the scene data's lights and meshes (after the scene code), so a lit material compiles a variant without lights that no frame draws: an instance set's waits with `runWhenSceneLoadSettled` (`kernel/scene/SceneLoader.ts`, p354 Phase 5 step 6); `preWarmMesh` doesn't (likely the same for a lit mesh from scene code, not checked).
- Unculled: `compileAsync` culls against its camera, and the pre-warm camera is a default `PerspectiveCamera` at the origin, so a mesh elsewhere compiled nothing. `frustumCulled` is off for the call's synchronous part (the projection; the job awaits `renderer.init()` first so it is synchronous), the geometry's stand-in always.
- Under a render pipeline: while the pipeline provider's compiler (`RenderPipelineCompiler`, `FeatureContext.setRenderPipeline`'s second argument) returns a promise, the mesh compiles for the pipeline's own scene renders instead of the direct one. PostFX's (`compilePostFxScenePasses`) compiles in the scene pass's target, then the pre-pass's with its MRT, configured as their renders configure them. A depth-0 compile doesn't serve them: three r187 shares the node build across call depths (#35014), but the pipeline key differs by colour space (`srgb-linear` for the frame buffer target, none for a pass's) and the pre-pass has its own MRT build. Measured on the Gym (fresh shaders): no pre-warm 440-640 ms of hitch, depth 0 ~200 ms, through the passes none, with 16-18 ms frames during the ~500 ms compile. The shadow pass is never pre-warmed (its depth-only pipeline is cheap), and a chain switched on or off after the pre-warm compiles on its first frame.
- **The renderer state trap** (`CompileQueue.ts`): node builds read the renderer's global render target and MRT (`MRTNode.setup`, `NodeBuilder.getOutputType`), and `compileAsync` yields to the next frame every 8 ms, putting back the MRT that was set at its call (not a non-canvas target: that one simply stays). So a compile in a pass's target holds that target and MRT on the renderer across frames; three's own `PassNode.compileAsync` too. Fixed on three's dev by #35359 (after r187); what the engine changes with the release that has it (PostFX's `compileInScenePassAsync` first) is in `docs/issues/three-pass-compile-holds-renderer-state.md`. Two rules follow:
  - Engine compiles run one at a time (`runCompileAsync`): one started while another holds a target compiles for it, and its end puts that MRT back after the other has cleared it.
  - Every engine render runs with no target and no MRT set (`runWithClearRenderState`, free when nothing is set): `MainLoop`'s `runFrame` (the scene, the sky's env and static layer bakes, the viewports) and `renderScene` outside a frame, snapshots, the texture bakes and the impostor bakes (`withBakeRendererState`, the texture preview's too) and the sky box's PMREM bakes at registration. A render that sets its own target still reads the MRT: during a pre-pass compile it would write normals into its colour. A new render outside a frame goes through it too. It saves its own previous target inside the call, or it would put the held one back mid-render.

## Texture bakes

`kernel/render/TextureBaker.ts` (p304 D1): `bakeTexture({ id, size, outputs, layers?, build?, mipmaps?, wrap?, anisotropy?, isPersistent? })` (on `aekasha`) renders a TSL node graph once into a mipmapped render target that is then sampled like any texture, so a material pays one fetch a pixel instead of the graph's maths every frame. It resolves a `BakedTexture` (`{ id, textures, memoryBytes, rebake(), isDisposed(), dispose() }`) once rendered. Its users: the texture sets' procedural sets (`features/texturesets/TextureSetBakes.ts`, `src/_engine/features/texturesets/CLAUDE.md`), and the toolkit's `bakeSurfaceGenerator`, `bakeMacroNoise` and `bakeRippleAtlas` (`aekasha/toolkit/terrain`); its checks are `testDebugScene`'s two bake strips and tiles, the `noiseLibrary` and `proceduralSurfaces` verification scenes and the terrain gallery's Procedural row. The handbook is `docs/techniques/procedural-textures.md`.

- **The render:** one target for the whole bake, `count` the outputs (1 to 4: WebGPU's default `maxColorAttachmentBytesPerSample` is 32 and an RGBA8 attachment counts 8 there, like an RGBA16F one) and `depth` the layers (1 to 256, its default `maxTextureArrayLayers`). Each texture gets its output's `type` (`UNSIGNED_BYTE` | `HALF_FLOAT`) and `colorSpace` (`SRGB`, the attachment format `rgba8unorm-srgb`, so outputs mix; it needs `UNSIGNED_BYTE`), and its registry id `<id>.<name>` as its `name`: several outputs are `fragmentNode = mrt({ '<id>.<name>': node })`, since three's `MRTNode` finds an output's attachment by its texture's name. An output's graph is its `node` or what `build(ctx)` returns under its name (one with neither throws); `ctx` is `{ uv, layer, texel }`, `uv` the texel's centre with (0, 0) the first texel, so a material sampling the bake at a uv reads what the graph wrote at that uv (a render target's v = 0 is the top of the rendered image on both backends).
- **Its own triangle:** the material carries three's `QuadMesh` full-screen triangle as its `vertexNode`, and the bake calls `renderer.render(quad, quad.camera)`, not `quad.render()`: `QuadMesh.render()` swaps in its own `vertexNode` for the call, which the compile wouldn't see, so the compile would build a pipeline the render never uses.
- **The compile** runs before the first render (`compileAsync`, so the render doesn't stall a frame), in the bake's target with no MRT, through `runCompileAsync` (the renderer state trap above), and puts the target and MRT back: the node build reads the target's colour space and type (PostFX's `compileInScenePassAsync` pattern).
- **Layers and mips:** three r187 renders into an array target's layer on both backends (`setRenderTarget(target, layer)`: WebGPU's `baseArrayLayer`, WebGL's `framebufferTextureLayer`), so the layers render one by one, `ctx.layer` an int uniform set before each (no 2D bakes assembled into a `DataArrayTexture`). three r187 also generates a render target's mips after every render into it on both backends (no downsample chain): `mipmapsAutoUpdate` is off until the last layer's render, so every layer's mips are built once (#34630; WebGPU's mip pass walks `depthOrArrayLayers`). An array bake is neither a `DataArrayTexture` nor a `CompressedArrayTexture`: `sampleArrayLayer` takes three's `isArrayTexture` too and samples its layers by index.
- **Clear once:** the target is cleared on allocation, every layer with the mips off (`clearBakeTarget`), before anything can sample it: the destroyed-texture trap (`src/_engine/features/skybox/CLAUDE.md`). The textures exist from the call on, transparent black until the first render.
- **Ownership:** the textures are registered (`saveTexture`) before the first `await`, so the scene loading (or current) owns them, unless `isPersistent`. Deleting any output's texture (the scene's release, `deleteTexture`) disposes the bake, one owner for the target, the material and the other outputs (`SceneAssetRelease.ts` skips a texture an earlier deletion took with it); a bake disposed during its compile never renders. `bakeTexture` with the id of a bake that's alive returns that bake, its options ignored (the debug env warns); a texture registered under an output's id by anything else throws (so the toolkit's committed `macroNoise` and `rippleAtlas` copies are ids of their own, not the bakes' `macroNoise.data`). It throws before `InitEngine` (`getBakeRenderer`).
- **When it renders:** during a scene load (`isCurrentlyLoading()`) right after its compile, inside the load (scene code awaiting it holds the load), counted for the loader's `updateBakeStatusFn` (`reportSceneLoadBakeStatus`, `src/_engine/kernel/scene/CLAUDE.md`; the counts start at the load's first bake and are dropped when it settles). Outside a load every render queues, the first one too, so `bakeTexture` resolves on the frame it runs: the queue (`TextureBakeQueue.ts`, pure, `TextureBakeQueue.test.ts`) holds one request per id, run in first-request order, one per frame from `textureBakeSystem` (`MAIN`); a rebake of an id waits `TEXTURE_BAKE_THROTTLE_MS` (150) of `getElapsedTime()` after its last run (the sky box's static layers' rule), and requests made before it runs join it, its latest `run` always running, so a slider can rebake on every change. The system is added to the default world (a `WeakSet` of worlds, again if it's replaced) by the first queued render, never at load or in the kernel's install, so an app that never bakes runs none of it. Queued renders wait while an editor view shows or the main loop is paused.
- **`rebake()`** takes no params: it renders the graph again with its uniforms' current values (set them first: a toolkit `BakedSurface`'s `setParams` / `setSeed` set its uniforms, then `bake.rebake()`). Before the first render it resolves with it, which reads the latest values.
- **Memory:** `getBakedTextureMemoryBytes({ size, outputs, layers?, mipmaps? })` (`TextureBakeMemory.ts`, pure, on `aekasha`; `getBakeSize` and `getMipChainTexels` `@internal`), `BakedTexture.memoryBytes` the bake's: uncompressed, an RGBA8 1K output with its mips about 5.6 MB, `HALF_FLOAT` twice that. Baked textures are registered textures, so the GPU memory tab lists them with no source of their own.
- **Stats (debug env):** `kernel/render/debug/_dbg__TextureBakeStats.ts` keeps a tracker per id for the page's life (`createBakeStats`, `debug/_dbg__BakeStats.ts`, shared with the sky box's bakes: `src/_engine/debug/CLAUDE.md`'s GPU timing), loaded through `loadDebugModuleAsync` before a bake's first render; every render (all its layers) is timed. `getTextureBakeStats(id)` (on `aekasha`, `TextureBakeStats`: `bakes`, `cpuMs`, `gpuMs`, `bakesPerSec`) is undefined outside the debug env; GPU ms on WebGPU only. The profiler figure (`registerStatsSource`) isn't built.
- **Export (debug env, p304 D5):** `exportBakedTexture({ id, output, dir, fileName?, overwrite? })` (on `aekasha`) loads `kernel/render/debug/_dbg__TextureBaker.ts` through the debug loader and rejects outside the debug env. It finds the bake through the texture registry (`<id>.<output>`, its `renderTarget` and its index among the target's textures), reads level 0 back (`readRenderTargetRGBA8Async`'s `textureIndex`; a `HALF_FLOAT` output read as half floats and clamped to 0..1 with a warning) and writes `<dir>/<id>_<output>.png` through the dev files, the rows flipped (an imported PNG's top row is sampled at v = 1; `noiseLibrary`'s committed-copy check settles it). It resolves `CREATED`, `UPDATED`, `UNCHANGED` (the file has these bytes), `EXISTS` (other pixels and no `overwrite`: nothing written, so a tool asks and calls again) or `DOWNLOADED` (no dev files); a write passes the read's hash as `expectedHash`. An array bake is refused. Export committed copies from one backend (WebGPU): SwiftShader's WebGL2 rounds an fbm differently in places.
- **The bake helpers** (`BakeRenderer.ts`, `@internal`; moved from `features/lod/impostors/ImpostorBake.ts` by p304 Phase 1, since the kernel imports a feature's types only): `getBakeRenderer(caller)` (the renderer, or a throw before `InitEngine`), `withBakeRendererState(renderer, fn)` (`fn` inside `runWithClearRenderState`, the target with its cube face and mip level, the clear colour and auto clear put back) and `clearBakeTarget(renderer, target, layer?)` (the clear-once rule). The texture baker, the impostor bakes and the Assets tab's texture preview (`kernel/assets/debug/_dbg__TexturePreview.ts`) use them. None touches the scissor test (a leaked scissor breaks PMREM, three #31777; `Viewports.ts`' rule).
- **Readbacks:** three's `readRenderTargetPixelsAsync` is bottom row first on WebGL2 and top row first (rows padded to 256 bytes) on WebGPU, which only a check with a side sees; the kernel's `readRenderTargetRGBA8Async` is top row first on both.
- **Visual only:** GPUs differ in float precision, so a baked texture never feeds gameplay or colliders.

## Drawing pipeline

`kernel/render/DrawingPipeline.ts` (p354 D5): the engine's seam on three's `renderer.drawingPipeline` (a `StandardDrawingPipeline`, experimental in three r187), which decides what each render draws. Every render goes through it: a nested one (a shadow map, rendered while the outer render's list is drawn), the VSM blur and output quads, and a `compileAsync`'s projection. `addDrawingPipelineHook(renderer, { begin?, isCulled?, finishRenderList? })` (`@internal`) returns an idempotent remover; three's interface stays behind this one file, and every user adds a hook (instance sets; later p370's indirect draws, p375). It takes the renderer rather than importing `Renderer.ts`, so the Node tests drive it with a stub (`DrawingPipeline.test.ts`), and only lazy modules import it (an instance set's GPU backend): it's in no first download.

- The first hook installs one `StandardDrawingPipeline` subclass on the renderer, and the last one's remover puts back the pipeline it replaced. Installing over anything but three's standard pipeline warns (it comes back with the last remover); a pipeline set over the engine's meanwhile (`instanceStress`' `?stressPipeline=meshlet`) stays, the remover warns, and the hooks stop being called.
- The hooks run in the order they were added; the list is replaced on every change, never edited, so a hook removed during a render doesn't shift the others' calls. `getDrawingPipelineHooks(renderer)` lists them, for tests and tools.
- `begin(camera, renderer)`: a render's projection starts. `isCulled(object, camera)` is tri-state, per object and render (keep it a `userData` lookup): `true` or `false` decides, `undefined` passes to the next hook, and after the last to three's frustum test. three projects an object's children after the object's own `isCulled`, so a hook can choose an object's children for the render before they're projected (the set's probe and its slot's draws). `finishRenderList(camera, renderer)`: the render's list is complete and nothing of it is drawn yet, where a GPU-driven draw dispatches its cull (three's `MeshletDrawingPipeline` does too). It fires for the render's own list only, the first one begun after `begin`: three also finishes a `BundleGroup`'s list inside the projection.
- The order holds for nested renders (traced, p354 Phase 3 step 2): the view's `finishRenderList`, and its dispatch, run before `ShadowNode.renderShadow` starts the shadow map's render inside the view's draws, and three submits each `compute` call and each render on its own, in call order, so each render's draws read its own dispatch (a point light's six faces too).
- **The drawn object's nodes** (p354 D8, Phase 5 step 4): two per-object nodes let a draw that isn't an `InstancedMesh` feed the materials that read per-instance data, keyed on the drawn object (not the material: the shadow pass builds the drawn object with its own shadow material, which takes the source's `maskNode` and `positionNode`), set before the object's first build. `InstanceMatrix.ts`' `drawnInstanceMatrix` (`@internal`, its own lazy chunk) resolves at setup to an InstancedMesh's `instanceMatrix` (three's `referenceAttribute`, one node for every InstancedMesh: p058's shared build), an object's own node (`setObjectInstanceMatrixNode`: an instance set's draws, whose fetch gives the matrix), else the identity. `setMaterialPositionsInstances` / `doesMaterialPositionInstances` mark a material whose `positionNode` places each instance itself from it (the octahedral impostor's billboard, `features/lod/impostors/`): a set keeps such a material's `positionNode` and replaces any other's with its fetch. The other is `LodFade.ts`' `setObjectLodFadeNode`, the dither's per-object fade (`features/lod/CLAUDE.md`, LOD selection). Both live in the kernel so `lod()` and `instancing()` reach them without importing each other.

## Views

`kernel/render/Views.ts` (`_DONE_p083`, the editor/creator view epic): a view is what the whole canvas shows and what the main loop ticks, and exactly one is active. The built-in **Runtime** view (`RUNTIME_VIEW_ID = 'runtime'`, no `ViewDef`) is the loaded scene with the game/app debugger. Editor views (the material editor, `_DONE_p084`, `_DONE_p085`) are registered by debug modules with `registerView({ id, title, icon, orderNr?, scene, getCamera, getCameraRig?, onEnter?, onExit?, mainUpdate?, update?, toggleDrawer? })` and switched with `setActiveView(id)`: calls run one after another, and a failed `onEnter` returns to the Runtime view and resolves `false`. Views aren't viewports: viewports are composited over whichever view is active. Only the debug env registers views so far; in production the loop pays one boolean check.

- Suspension: while an editor view is active (`loopState.isSceneSuspended`, from the start of a switch to one until the switch back has finished; `isRuntimeViewActive()`), the frame (`runFrame`) runs none of the scene's per-frame work. That means no world's ECS stages (`MAIN` and `LATE_MAIN` included, so `object3DSyncSystem`, `skyBoxSystem` and `debugCameraSystem` stop too), no scene loopers, no held keys, and no physics: `stepPhysics` treats it as a pause and resumes without catching up, so a switch keeps a scene deterministic. `getElapsedTime()` stands still. The loop instead runs the view's `mainUpdate(delta)` and, while the view plays, `update(delta)`, then renders `view.scene` with `view.getCamera()` (no PostFX) and the viewports. Work outside the loop (timers, audio, DOM events, TSL's `time` node) keeps going, so per-frame game logic belongs in ECS systems or scene loopers. A scene loaded meanwhile (app code, HMR) is suspended as soon as it exists.
- Debug tools that must run in every view add `addViewFrameListener(fn, 'BEFORE_UPDATE' | 'AFTER_RENDER')`, called only in editor views (the axes gizmo, the env ball, the profiler's frame and GPU memory samplers), next to their ECS system for the Runtime view. `addViewChangeListener` runs after every finished switch.
- Input: `setAppInputsSuspended` (`kernel/input/InputState.ts`; apart from `setAllInputsEnabled`, so a scene load's end doesn't lift it) stops mouse, touch, held keys, every key binding without `isDebugKey` and every action map outside the `DEBUG` context (the engine's debug keys and CONFIG.ts `debugKeys` are `DEBUG` maps). The scene debug camera's OrbitControls are gated off (`setSceneDebugCameraInputEnabled`). `h` calls `toggleActiveViewDrawer()` (the view's `toggleDrawer`). F1 and F5 do nothing. F7 and the pause button call `toggleViewPlay()`, the view's own play flag (in the Runtime view, `toggleAppPlay`). The master loop button stops every view.
- HUD: `<body>` gets `aekEditorView` and `aekView_<id>`, and `body.aekEditorView #hudRoot > :not(.aekKeepInViews)` hides the scene's HUD (drawer, switch tools, draggable windows, scene loader, app HUD) with `display: none`, so it comes back as it was. `KEEP_IN_VIEWS_CLASS` (`ui/core/HUD.ts`) keeps an element: the top on-screen rows (centred and top left), stats, the toaster, the viewports layer, debug dialogs with a backdrop, and windows of a kind registered with `keepInViews: true` (the profiler). An editor view's own UI needs it too. The scene drawer keeps its open state (`setDrawerSuspendedByView`) and leaves `debugDrawerOpen` to the editor view, whose own right drawer sets it, so the rules keyed on that class (top row, viewport stack) shift for it too.
- On-screen tools: the view tools group (tool type `'VIEW'`, an exclusive kit toolbar, p806 D7) sits right of the About and undo / redo group in the top left row (`onScreenTopLeftRow`); the play group is alone in the centred top row (`onScreenTopRow`). Runtime comes first, then `getViews()` (by `orderNr`, then registration order; a `ViewDef`'s `iconSize: 'small'` shrinks an icon that fills its box). The group shows only when an editor view is registered, and every switch shows a toast (a switch `setActiveView` refuses puts the pressed button back). An editor view builds no prod-test play button and no switch tools (the bottom row, `onScreenBottomRow`). The tools themselves: `src/_engine/debug/CLAUDE.md`.
- Camera rig: `ViewCameraRig` (`{ camera, controls, setControlsSuspended, onMoveEnd? }`). The gizmo and the env ball resolve the camera they follow and drive through `kernel/camera/debug/_dbg__CameraRig.ts`: in the Runtime view the active camera, and the debug camera's rig while it is active; in an editor view its `getCameraRig()`, or its `getCamera()` treated like the main camera. The profiler census reads `getActiveViewCamera()` (`Views.ts`) instead, since it also loads in prodTest.
- Undo: `perScene` actions recorded in an editor view go to the bucket `__view:<id>`; `global` ones show in every view.
- Refresh: `AEK_debugViews` (`{ activeViewId, viewPlay }`) is written on every finished switch and every editor view play toggle. `restoreSavedView()` runs at the end of `InitEngine` (debug env, not awaited), after the first scene and the debug GUIs exist, so register views before that (in `kernel/init/InitEngine.ts`'s debug block). A saved view that isn't registered falls back to the Runtime view and clears the key. Each view restores its own state.
- The editor views' own code (`createViewCamera`, the material editor): `src/_engine/debug/editors/CLAUDE.md`.
