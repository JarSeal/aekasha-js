Notes for the sky box (`src/_engine/features/skybox/`, its debug tab in `debug/`); the root `.claude/CLAUDE.md` keeps the project-wide rules, commands and workflow.

## Sky box

`features/skybox/` shows at most one sky box, as the root scene's `backgroundNode` and `environmentNode`. A definition (`SkyBoxDef` in `SkyBoxTypes.ts`, typed from `SkyBoxSchema.ts`) is a set of layers: `base` (`COLOR` | `EQUIRECTANGULAR` | `CUBE_TEXTURE`, with `rotate` in radians, cube `flipY` = a half turn about X, `intensity`) and `env` (background roughness and intensity, environment intensity, and the env bake's `size` 64-512 and `dynamic`; `nebulaSize` is the nebula cube's). The procedural layers are `atmosphere` (a port of three's `SkyMesh`, driven by `suns[0]`), `suns[]` (up to 4, disc and halo; `suns[0]` is the primary: it alone drives the atmosphere, star fade, clouds, ground and ambient light; `suns[i].light` is a managed directional light, shadows on by default for `suns[0]` only), `moons[]` (up to 2; a sphere lit into its `phase`, optional texture; `moons[i].light` shines only at night), `stars` (procedural, cube-projected, optional `milkyWay`; faded out by day by `fadeRange`, never baked), `nebulae[]` (up to 8, baked; see below), `clouds` (need the atmosphere; moonlit at night), `ground` and `ambientLight`; each is on when its key is there, unless `enabled: false`. `dayNight` (same rule) places the suns and moons from a time of day; an extra sun with `rotateWithSky` (default) turns with the sky from where it stands at the start time, and `moons[1]` has its own orbit. `preset` (`DAY_SKY` | `NIGHT_SKY` | `DAY_NIGHT` | `SPACE`, `Presets.ts`) is a template the definition merges over (its arrays and `base` replace the template's); `gatherAppData` resolves it at build time, so runtime definitions never carry it, and code definitions go through `resolveSkyBoxPreset` (on the entry, with `SKYBOX_PRESET_NAMES`; `mergeSkyBoxPreset` is its untyped form, for the schema and the gatherer). A preset template change is a visible change: bump its template version and note it in the changelog. Colours (`toSkyColor`, `SkyColor.ts`) read `'#rrggbb'` and `{ r, g, b }` (0-255) both as sRGB, as the kernel's `toThreeColor` does.

- The `skyBox()` feature (`SkyBoxFeature.ts`, id `'skybox'`, on `aekasha/skybox`, p607) installs `skyBoxSystem` (`installSkyBoxSystem`, `SkyDayNight.ts`) and `skyBoxSceneHooks`: `sceneRegistered` registers a scene's JSON `skyboxes` when `InitEngine` registers the scenes, `retainedTextures` keeps the active texture through a scene's asset release, `exit` clears the sky box and `created` calls `activateSceneDefaultSkyBox` (the last one registered with `isDefault: true`, else the first) once the scene code has run; its `onDebug` / `onDebugAfterStart` register and create the tab. Its `onUnmount` is `stopSkyBox` (p615 D8): the updates waiting for an activation settle with null, `clearSkyBox` runs (an activation in flight is superseded, the bakes disposed, the lights deleted, the root scene's background, environment and their intensities reset, the listeners told `'clear'` once more) and the listener set is cleared, before `deleteRenderer()`; the registry and the definitions stay (nothing mounts again in the page load). Without the feature a scene's sky boxes aren't registered, and a scene whose JSON lists `skyboxes` fails the boot (the feature manifest).
- The public API is the entry (`index.ts`); every other export is `@internal`, its summary naming who uses it (the feature, the debug tab, the env ball, GPU memory, the test bridge). A change listener (`onSkyBoxChange`) gets a `SkyBoxState` (`{ id, sceneId, def }`, read-only) and a `SkyBoxChangeReason`, and `setActiveSkyBox`, `createSkyBox` and `updateSkyBox` resolve with one: `ActiveSkyBox` (the uniforms, nodes, textures and running time) is internal.
- State flow: `registerSkyBox(def, sceneId?)` stores definitions per scene (default: the loading scene, else the current one); a definition still carrying a `preset` warns in the debug env and the preset is ignored. `setActiveSkyBox(id | null)` resolves one (plus its debug overrides from `AEK_debugSkyBox`, debug env only), loads its texture, builds its nodes and shows it; when calls overlap, the latest wins (`activate` keeps the latest in flight and wraps `loadAndShow`). A texture that fails to load never fails it (p615 S2): `loadSkyTextureAsync` (`layers/Base.ts`) loads with `throwOnError: true` in every env and turns a failure into `null` with a promise `catch` (not a `try`: the debug toast's gate would stay in the bundle), `reportSkyTextureFailure` logs it (and toasts in the debug env), and the base shows black, a moon a plain disc, so a scene load never fails on a sky texture. `createSkyBox` registers and, for the current scene, shows it; its `isDefault` defaults to true, so the last one created is the default. An `updateSkyBox` made while an activation loads its textures is queued by sky box id and applied once that activation has shown (p615 S1): the queued changes are `deepMerge`d in call order (a drag is one update), a structural one among them starts another activation (the ones after it queue again), and one for a sky box no longer active by then resolves with the active one and changes nothing. Otherwise `updateSkyBox(id, partial)` re-activates on a base structural key (`BASE_STRUCTURAL_KEYS` in `layers/Base.ts`), rebuilds the nodes when the set of layers changes (`getCompositeSignature`), or `env.size`, or the background blur crossing 0; anything else is a uniform or scene property write. Overrides address one sun as `{ suns: { "0": { ... } } }` (`deepMerge` merges an index object into an array by index); a list edit (adding or removing a sun, moon or nebula) stores the whole array, and adding or removing an entry is structural (a rebuild). Activation owns `scene.environmentIntensity`, `backgroundIntensity` and `environmentRotation`: set them in the definition, not by hand.
- Both nodes sample one PMREM (`getPMREMTexture` in `SkyEnvironment.ts`: baked once per texture, disposed with it) in the same world direction, so reflections match the background. The background looks up `normalWorldGeometry` (not `normalWorld`, which is negated on the back-side background box), and the environment is a bare `pmremTexture` so the lighting context drives its direction and level. Rotation: PMREMNode applies `scene.environmentRotation` to the environment only (it skips materials without an `envMap` property, like the background box's plain `NodeMaterial`), so the background applies the same transposed rotation itself, in `layers/Base.ts`.
- Two paths. A texture-only or colour-only sky box takes the direct path (above). One with a procedural layer takes the composite path (`SkyComposite.ts`): `buildSkyComposite` stacks the layers (base, nebula cube, stars, sun and moon discs, atmosphere with clouds, ground, back to front; discs and lights are unrolled per index) into one node, used as the background (`VIEW`) and as the background of a private bake scene (`ENV_BAKE`: wider clamped disc, no disc when the sun has a light, frozen clouds). `SkyEnvironment.ts`'s env bake runs `fromScene` into a fixed target (allocated at activation; `rootScene.environmentNode` is `pmremTexture` of it, a new node only on a size change) with one long-lived `PMREMGenerator`. Rotation and flip are baked in, so `environmentRotation` is 0 there. A blurred background samples the bake.
- Static layers (`SkyStaticLayers.ts`): the nebulae are too costly per pixel, so they are baked into one HalfFloat cube (`env.nebulaSize` per face, no mipmaps, cleared on allocation) by a `CubeCamera` over a private back-side sphere (`NoBlending`, so the cube's alpha keeps the `starBoost` mask the stars read). The composite samples it with its own rotation uniform (the sidereal rotation with day-night), in both `VIEW` and `ENV_BAKE`. It bakes on activation and structural changes, and a param change is throttled to one bake per 150 ms of the loop's elapsed time (`STATIC_LAYERS_THROTTLE_MS`; the latest request always runs); it runs before the env bake in the same `skyBoxSystem` tick and requests one. Whether a sky box has static layers is part of the composite signature.
- `skyBoxSystem` (MAIN, order 1, default world only, `SkyDayNight.ts`) steps the day-night cycle, moves the sky lights and runs a requested bake: at most one per frame, never while a scene loads. Value changes request a bake (`env.dynamic: false` turns that off; `bakeEnvironment()` always does). Layer uniforms are created once per activation (`createSkyUniforms`); the atmosphere's vertex-stage terms are computed on the CPU in `layers/Atmosphere.ts`.
- The sky clock (p615 D5, `skyClockSec` in `SkyDayNight.ts`): `skyBoxSystem` adds `getElapsedTime()`'s change to it unless a scene is loading, and writes it to the clouds' `time` uniform every frame (`layers/Clouds.ts`; the env bake's frozen clouds take `bakeTime` from it right before a bake). So the clouds stop with the master loop, in editor views and during a load, and keep drifting while only the app is paused. It lives in the module, not the uniforms, so a rebuild or a structural update doesn't make the clouds jump, and `clearSkyBox` (a scene's exit) restarts it at 0 through `_setSkyBoxClearHook` (`SkyBox.ts` imports nothing from `SkyDayNight.ts`), so a scene's clouds start in the same place on every visit. Never read three's `time` node or the renderer's node frame for anything a snapshot shows: the stars' twinkle is the one layer left on `time` (ambient; the test bridge pins three's node frame time, `_dbg__TestBridge.ts`). The bake schedules read the loop's clock too: the day-night re-bake's rate limit and the static layers' throttle use `getElapsedTime()` (monotonic, never reset), so under the test clock the bakes before a snapshot are the same on every run; only the bake stats' CPU timing reads `performance.now()`, and only while the stats' hooks are set (`_setEnvBakeHooks`, `_setStaticLayersBakeHooks`).
- Day-night (p113, `SkyTime.ts`): the time model and the sun, moon and star (sidereal) directions, CPU only. The running time lives on `ActiveSkyBox.time`, never in the definition; games drive it with `setTimeOfDay`/`getTimeOfDay`, `playDayNight`/`pauseDayNight`/`isDayNightPlaying`, `setDayNightSpeed`/`getDayNightSpeed`, `setDayNightCycleDuration`, and read `getSunDirection`, `getSunElevation`, `getMoonDirection`, `getMoonPhase` (all in `SkyDayNight.ts`, with `skyBoxSystem`, the sky clock and the bake schedule; the setters are no-ops without day-night). It advances in `skyBoxSystem` by the change in `getElapsedTime()` (so a master pause never jumps it), per `dayNight.timeSource`: `APP` (default: stops with the app loop, `isAppPlaying()`), `MAIN` or `MANUAL`; it stands still while a scene loads. A moved time writes only the sun-dependent uniforms and lights (`applySkyTimeUniforms`, `updateSkyLightsForTime`), with no allocations. While it moves, it re-bakes once the sun or moon has turned `env.updateAngleDeg` (1°) and at most `env.maxUpdatesPerSec` (1/s), plus once when it stops or reverses. `env.size` defaults to 128 with day-night. `updateSkyBox`'s `dayNight` runtime keys (timeOfDay, speed, playing, cycleDurationSec) also set the running cycle.
- Two traps the layers hit: a TSL `If` must not be the first to build a node other layers share (the stars build their lookup direction before their night-only branch, or the whole sky reads an unassigned direction by day); and a render target sampled before anything rendered into it gets its GPU texture destroyed in place by its first render, without its bind groups being invalidated (three r186, a WebGPU "Destroyed texture used in a submit" every frame). New env bake targets are cleared once on allocation, and a new shadow-casting sky light renders its map once, for that reason. Each trap is a `@remarks` on the function that guards it (`starsNode` in `layers/Stars.ts`, `setEnvBake` with B1's activation before `createRenderer`, `setStaticLayers`, `syncSkyLights` with the `castShadow` crash below), and the two direction notes above are on `buildBaseLayer` (`layers/Base.ts`).
- Sky lights (`SkyLights.ts`): ordinary ECS lights made by `createLightEntity` with `managedBy: { manager: 'SKYBOX', ownerId, role }`, created on activation and deleted by `clearSkyBox`. The sky only writes what it owns (transform, colour, intensity, shadow settings and intensity, `shadow.autoUpdate`) and reads the light from `OBJECT3D` every time. The sun light follows the active camera, snapped to shadow texels in light space, and fades out below the horizon (`horizonFade`) without touching `castShadow`; a `castShadow` change re-creates the light (toggling it back on in place crashed with PostFX on, WebGPU).
- The pre-3.0 `{ type, params }` shape (code and JSON) still converts through `LegacySkyBox.ts`, with a dev warning. It's `@deprecated`, removed in engine 6.0.0 with the schema's two conversions, `createSkyBox`'s legacy overload, the gatherer's `warnOnLegacySkyBox` and the debug tab's `migrateLegacySkyBoxLS` (each says so; `p622_engine-6-major.md` lists them). Legacy equirects get `rotate: π` and legacy cubes `flipY: true`: that reproduces their old look in the standard orientation.
- Debug tab: `features/skybox/debug/_dbg__SkyBox.ts` plus one `debug/_dbg__*Folder.ts` per layer. Bindings call `setSkyBoxParam(path, ...)`, which renders the value, stores it as an override (only values that differ from the definition) and records the `skybox.param` undo action; a new layer's controls need no new action type. Layer paths, proxy keys, defaults and the override store live in `_dbg__SkyBoxShared.ts`, the undoable edits (`setSkyBoxParam`, `setSkyBoxArray`, `resetSkyBoxLayer`, "Apply preset") in `_dbg__SkyBoxEdits.ts`; `_dbg__LayerFolderItems.ts` has the slider, auto/custom colour and 2-tuple helpers. The Environment folder's bake stats time GPU only on WebGPU (`_dbg__GPUTimer.ts`, shared with the PostFX profiler). The Day-night folder's Transport is runtime only (the public API, no overrides, no undo); its Config is ordinary overrides. The tab refreshes every 250 ms while visible, and with day-night on the Suns and Moons folders' disabled position sliders show where the time puts them. Suns, Moons and Nebulae are lists (`_dbg__ListFolderItems.ts`; `selectListEntry` repoints a list's layer paths, `setSkyBoxArray` records a list edit as one undo step). "Apply preset" writes a computed override (a diff against the definition: missing layers get `enabled: false`) and records `skybox.applyPreset`.
- The app's `skyShowcase` scene (`dayNight.skybox.json`, every layer on a 5-minute day) is the verification scene for the sky box plans; it also lists the `space` sky box. largeWorld lists `dayNight` too (its default stays `basicSkybox`), and turns its own sun and ambient light off while the active sky box has a sun light (`onSkyBoxChange`, `getSkyLightIds`). A scene's JSON lights are created after its scene file runs (`createNextSceneObject3Ds`), so scene code that touches them does it on enter. The `space` scene (`space.ts`: SPACE sky box, toolkit asteroids with mutual gravity at zero world gravity, a scene-scoped "Space demo" debug tab) is the space demo.
