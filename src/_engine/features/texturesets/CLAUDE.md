Notes for texture sets (`src/_engine/features/texturesets/`, the `textureSets()` feature, p303); the root `.claude/CLAUDE.md` keeps the project-wide rules, commands and workflow.

## Texture sets

A texture set (`*.textureSet.json`, `docs/plans/_DONE_p303_texture-sets-and-terrain-texture-library.md` D1, D2) is a named group of packed PBR maps, each slot a texture asset's id, in up to three packings (`FULL`: `albedoHeight`, `normal`, `orm`; `LITE`: `albedoRough`, `normalHeight`; `MINIMAL`: `albedoHeight`), with the surface's physical facts (`physicalSize`, `heightScale`) and `surface` defaults a terrain material copies into uniforms. A set is plain data; its textures are ordinary registered textures, owned and released as any other (nothing of the set itself is registered or released).

- **Where the parts are.** The asset schema, the input form's schema and the packings' slots (`TEXTURE_SET_PACKINGS`, the slot order a packing's textures are listed and loaded in) are `schemas/TextureSetSchema.ts` (a schema imports no feature, and the material schema checks the form); the scene's `textureSets` field is the feature's part, `TextureSetsSchema.ts` (both on `aekasha/schemas`). `TextureSetRefs.ts` is import-free (the gather's closure and streaming manifest import it, `devTools/engineImports.test.ts`): the form `{ textureSet, packing? }`, its predicate and `getTextureSetInputDependencies(value, getSet)`, which reads the set through a lookup since a slot's texture id is any id. The runtime is `TextureSets.ts` (the sets) and `TextureSetArrays.ts` (D4's set arrays), the install `TextureSetsFeature.ts`.
- **The data.** The gatherer (`devTools/gather/textureSets.ts`, `devTools/gather/CLAUDE.md`) fills the defaults (`defaultPacking`, every `surface` field; `averageColor`, sRGB `#rrggbb`, the JSON's or else the asset pipeline's measure of the default packing's albedo, `devTools/assetPipeline/CLAUDE.md`'s Average colour: none when that texture wasn't encoded), so the runtime has no defaults table, and writes each set inline into every scene that lists it (`textureSets`, its default packing's textures appended to the scene's `textures`) or whose material names it (the closure appends the packing the input samples); the development data also has a `textureSets` section by id. `getTextureSet(id)` reads that section first, else the first scene that has the set (`SceneData.textureSets`): a production build has only the scenes' data, so a set no scene lists or names isn't there.
- **The input.** `textureSets()`'s install registers the `{ textureSet }` resolver (`ctx.registerMaterialInputResolver`, kind `textureSet`): a bundle (`TextureSetInput`) of the packing's texture nodes by slot, plus uniforms `physicalSize` (vec2), `heightScale` and each `surface` field (`tint` a linear colour from the JSON's sRGB, the rest floats), flat (the slot and field names don't collide), kept at `userData.uniforms[<group>_<key>_<field>]`. An unknown set or a packing the set lacks throws naming the input; a slot texture that isn't registered samples the white texel with the missing texture's warning. Its `dependencies` pass `getTextureSet` as the lookup, so `ensureMaterialDependencies` loads a code-made material's set textures.
- **Why a feature** (p303 Phase 1's decision 1): p299's lazy pattern (the resolver `import()`ed by the load that needs it) has no load to hang on, since the gather turns a set into plain texture ids in the scene's `textures`, and a built-in dependency form in the kernel's `MaterialInputRefs.ts` would have put bytes into the banner's `_engine/kernel/assets` group (15 B of headroom then). So nothing of texture sets is in the kernel but `SceneData.textureSets`' type. Without `textureSets()`, a scene whose data names a set fails the boot (the gather's feature manifest), and a code-made material with a `{ textureSet }` input fails to build (the kernel's "Unknown object footprint" error: no kernel bytes name the feature). The lookups and the load work without it.
- **The load from code.** `loadTextureSetAsync(id, { packing? })` loads the packing's textures that aren't registered, from their declarations (`findTextureDeclaration`: the development texture section, else a scene's entry), and re-tags the registered ones, all in the caller's owner scope (every load starts before the first await), and rejects for an unknown set, a packing it lacks or a texture no data declares. `getTextureSetPackingTextures(id, { packing? })` returns the registered ones by slot, or undefined unless all are. Both type their result by packing (`TextureSetTextures<P>`).
- **Set arrays** (`TextureSetArrays.ts`, p303 D4). `buildTextureSetArray({ id?, sets, packing, swappable?, isPersistent? })` makes one array texture per slot of the packing with the kernel's `buildTextureArray` (registered as `<id>.<slot>`, layer `i` from `sets[i]`; the assembly, the uncompressed fallback, the size, mip, codec and colour space checks are `kernel/assets/TextureArray.ts`' p299 code), and a `TextureSetArray` (`id`, `packing`, `sets`, `arrays` by slot, `layerCount`, `layerParams`, `swappable`) kept in the feature's map until any of its arrays is disposed (its `dispose` event: deleted or released with its scene). A slot texture that's registered is borrowed by id; one that isn't goes in as its declaration's props (`findTextureDeclaration`), loaded for the array alone, never registered nor uploaded. Every member is resolved before any build starts, and every build starts before the first await (the caller's owner scope); a failed slot deletes the arrays this call registered, and the error names the slot and each layer's set. The id is `tsa:<hash>` of the packing and the list (two builds share one), unique for a swappable one; a build of a registered id returns it, re-tagged (a swappable one as swapped: only its packing and layer count must match). `setTextureSetArrayLayer(id, layer, setId)` swaps every slot with `setTextureArrayLayer`, queued per set array, then writes the layer's params; when a slot fails, the slots already swapped get the previous set back. **The layer params are one uniform array** (`layerParams`, vec4 × 4 per layer: `physicalSize`, `heightScale`, `heightContrast` / `tint` (linear), `normalStrength` / `roughnessScale`, `aoStrength`, `porosity`, `wetDarkening` / `wetRoughness`), read by name with `getTextureSetLayerParams(layerParams, layer)` (an index or an int node): three makes each `uniformArray` its own uniform buffer binding, and a stage has 12 by default (WebGPU's `maxUniformBuffersPerShaderStage`), so one array per field would have run out. The node is the set array's, shared by every material sampling it, so a swap updates them all.
- **The set array input** (p303 D4). `{ "textureSetArray": ["sand01", "grass01"], "packing": "LITE" }` (`packing` required: the sets' defaults may differ) or `{ "textureSetArray": "gallery" }` (a set array the scene lists with that `id`, or in code one built by id): a bundle (`TextureSetArrayInput`) of the packing's array texture nodes by slot (`.sample(uv).depth(layer)`), the set array's `layerParams` node (shared) and `layerCount` (an int). The schema is `schemas/TextureSetSchema.ts`' `TextureSetArrayInputSchema`, one of `MaterialSchema.ts`' checked forms; the predicate `isTextureSetArrayInputRef` is `TextureSetRefs.ts`'. The resolver (kind `textureSetArray`) is `TextureSetArrays.ts`', registered by its first `buildTextureSetArray` (the install doesn't load the module); its `dependencies` are none (the arrays aren't textures a load gets). A list's derived id (`getTextureSetArrayId`) finds the scene's array. A list whose array isn't built (its build failed, or code didn't await `buildTextureSetArray`) samples white stand-in arrays (a 1 × 1 `DataArrayTexture` per layer count, shared) with the sets' own params, warned: `.depth()` on the kernel's 2D white texel wouldn't compile. An id no set array has throws naming the input.
- **The scene load** (no kernel bytes). The gatherer writes a scene's `textureSetArrays` (the scene part's field: `{ id?, sets, packing, swappable? }`, listed, then the lists its materials' inputs name, `devTools/gather/textureSetArrays.ts`) with their sets in its `textureSets` (inline, no textures), and each member texture its `textures` doesn't hold into the first array's `__textures` (resolved as a listed texture: in a production build the array's only declaration, and the scene never loads it on its own). `installTextureSets` adds two scene hooks: `worldCleared` (the next scene's data, its owner already set) starts `buildSceneTextureSetArraysAsync`, through `import('./TextureSetArrays')` the first time and synchronously after (so a set array the next scene shares is re-tagged before the previous scene's assets are released), and `beforeAssets` awaits it: the scene's JSON materials are created right after its textures, synchronously, with no hook between. **The cost:** the scene's own textures start after its set arrays are built. **Trap:** the runtime modules import only types from `schemas/TextureSetSchema.ts` (a value, eg. `TEXTURE_SET_PACKINGS`, brings zod with it: Phase 3 section 2's first build put 22 kB gzip of it into the lazy `TextureSetArrays` chunk); a packing's slots come from the gathered set (`Object.keys(set.packings[packing])`, in the schema's order). A failed build is logged and the load goes on (its materials sample white). The member lookup (`getMember`) reads `findTextureDeclaration`, then the scenes' `__textures`. A cell's material needs nothing more: the arrays are the scene's, built with its load, and the closure sees the cells' materials before the cut.
- **Debugging.** The material editor builds a material's set arrays before its copy (`debug/_dbg__TextureSets.ts`, loaded by `registerTextureSetsDebug`, the install's `onDebug`): a set array is built by its scene's load, so elsewhere (or before any build in the page load, the resolver not registered yet) the copy of a `{ textureSetArray }` material failed with the kernel's "Unknown object footprint". Its preparer (the editor's `registerMaterialEditorPreparer`) builds each array a material's `inputs` or sockets name that isn't built: a list's own sets, an id's `textureSetArrays` entry from any scene in the generated data (an id no scene lists is left to the resolver's error), in the scene current then, and the editor's exit re-tags the ones it built to the current scene, as its textures. The Assets tab's texture info window has a Texture set folder naming each set, packing and slot the texture fills (`kernel/assets/debug/`' `getTextureSetSlotsOf`: the development data's `textureSets` section, else the scenes' inline sets, so the kernel's debug code imports no feature code). The verification scene is `textureSets` (`src/app/scenes/textureSets/`, p303 Phase 1's exit): the hand-made `p303TestSet` (PNGs passed through with `optimize: false`, made by `devTools/assetPipeline/fixtures/textureSetsFiles.ts`; its mortar's height, the albedo's alpha, is 0, so a premultiplying decode would show black) through `{ textureSet }` in each packing, one TSL file branching on the bundle's slots (the top row). Below it, p303 Phase 3's exit: four `LITE` sets (`p303TestSet` and three more from the same script in `arraySets/`, each with its own `physicalSize`, `tint`, `normalStrength` and `roughnessScale`, and a KTX2 copy of each, `*Ktx`) in 1 m quads, a column per layer: the PNG sets through `{ textureSet }` above the same four through one `{ textureSetArray }` material by list (`p303ArrayPngMat`: the uncompressed path, from the scene's registered textures), then the KTX2 ones likewise by id (`p303ArrayKtxMat`, the scene's listed `p303KtxArray`: the compressed path, its members loaded for the array alone). The layer is each quad's `setLayer` attribute, and both inputs shade through one graph (`liteSurface.ts`). An orthographic snapshot at whole pixels (256 px a metre, no MSAA, no PostFX) compares each array quad with its set's. `window.__textureSets.results` holds the lookups' checks, the set arrays' shapes, the textures each material samples (`sampledTextures`: 2 for an array material, 8 for the four sets') and the comparison (`compare`, per layer the largest channel difference, the mean and the pixels off, and a `control` against another set), and `checkReleaseAsync()` leaves the scene and lists the sets' textures and set arrays still registered (none). Measured (2026-11-13): the KTX2 array matches its sets exactly on WebGPU (1 / 255 on 0.1 % of the pixels on WebGL2's SwiftShader); the PNG array within 2 / 255 on both, from the kernel's 2D canvas readback of image members, which rounds the colour where the alpha (here roughness) is under 1 (`docs/issues/texture-array-image-layers-premultiplied.md`). **Trap:** three's `bumpMap` normalizes the surface derivatives, so its scale is height per screen pixel and changes with the distance; a bump in metres (`heightScale`, MINIMAL's normal) is the unnormalized form, as the scene's `bumpNormal` and the toolkit's asteroid material do.
- **The toolkit's side** (p303 D7, D8). `aekasha/toolkit/terrain` (`src/toolkit/terrain/nodes/SampleTextureSet.ts`): `sampleTextureSet(bundle, uv, { layer?, grad? })` decodes a `{ textureSet }` bundle, or a `{ textureSetArray }` bundle's layer, into `{ packing, albedo, normalTS, roughness, ao, isAoBaked, height }` (the packing read from the bundle's slots; null where the packing has none; no `surface` field applied), `transformTangentNormalToView(normalTS, uv)` and `bumpNormalView(height)` (the unnormalized bump in metres, the trap above). **Trap:** three's `normalMap()` without a `tangent` attribute builds its frame from the mesh's `uv()` derivatives (`tangentViewFrame`), so a normal map sampled at another UV (world tiling, a triplanar plane, a turned anti-tiling tap) gets the mesh UV's orientation; `transformTangentNormalToView` is the same construction from the UV actually sampled. World tiling from above is `(x, −z) / physicalSize` (`(x, z)` shows the map mirrored, though it shades right). The baseline material is `src/toolkit/materials/textureSetSurface/` (one set, any packing; static defines `tiling` `WORLD_XZ` / `UV` and `minimalNormal` `BUMP` / `FLAT`; roughness × `roughnessScale` capped at 1). Measured (2026-11-13, the gallery's top-down close-ups of `sand01` and `cliffs01`): the high-passed shading of `FULL` and `LITE` correlates with `MINIMAL`'s frame-free bump at 0.90-0.91 on WebGPU and WebGL2, a deliberately mirrored frame at 0.35 (`sand01`) and 0.78 (`cliffs01`, its albedo carrying the rest).
- **The gallery** (`src/app/scenes/terrainGallery/`, a debug scene): the 16 library sets on generated 12 m blocks with a 35° ramp each, the cliffs with a wall tiled at its UVs in metres, `textureSetSurface` per block through `matOverrides.inputs`, the scene's own DAY_NIGHT sky standing at 10:00, no shadows (`docs/issues/vsm-stripes-on-unshadowed-slopes.md`: the engine's VSM draws stripes down an unshadowed slope). Its tab (`_dbg__terrainGallery.ts`, "Terrain gallery"): the set list (a row flies the scene's camera to the block; in the debug camera the scene's camera moves, not the view), the packing of `sand01`, `grass01` and `cliffs01` (loads that packing's textures, the scene's from then on; the latest pick wins), and a 1 m world checker over the blocks (made on first use; not the walls). Both saved (`AEK_debugTerrainGallery`). The scene runner shoots the tab (`scenes.config.ts`' `debugger`).
