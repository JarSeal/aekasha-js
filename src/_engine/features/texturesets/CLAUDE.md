## Texture sets

A texture set (`*.textureSet.json`, `docs/plans/p303_texture-sets-and-terrain-texture-library.md` D1, D2) is a named group of packed PBR maps, each slot a texture asset's id, in up to three packings (`FULL`: `albedoHeight`, `normal`, `orm`; `LITE`: `albedoRough`, `normalHeight`; `MINIMAL`: `albedoHeight`), with the surface's physical facts (`physicalSize`, `heightScale`) and `surface` defaults a terrain material copies into uniforms. A set is plain data; its textures are ordinary registered textures, owned and released as any other (nothing of the set itself is registered or released).

- **Where the parts are.** The asset schema, the input form's schema and the packings' slots (`TEXTURE_SET_PACKINGS`, the slot order a packing's textures are listed and loaded in) are `schemas/TextureSetSchema.ts` (a schema imports no feature, and the material schema checks the form); the scene's `textureSets` field is the feature's part, `TextureSetsSchema.ts` (both on `aekasha/schemas`). `TextureSetRefs.ts` is import-free (the gather's closure and streaming manifest import it, `devTools/engineImports.test.ts`): the form `{ textureSet, packing? }`, its predicate and `getTextureSetInputDependencies(value, getSet)`, which reads the set through a lookup since a slot's texture id is any id. The runtime is `TextureSets.ts`, the install `TextureSetsFeature.ts`.
- **The data.** The gatherer (`devTools/gather/textureSets.ts`, `devTools/gather/CLAUDE.md`) fills the defaults (`defaultPacking`, every `surface` field), so the runtime has no defaults table, and writes each set inline into every scene that lists it (`textureSets`, its default packing's textures appended to the scene's `textures`) or whose material names it (the closure appends the packing the input samples); the development data also has a `textureSets` section by id. `getTextureSet(id)` reads that section first, else the first scene that has the set (`SceneData.textureSets`): a production build has only the scenes' data, so a set no scene lists or names isn't there.
- **The input.** `textureSets()`'s install registers the `{ textureSet }` resolver (`ctx.registerMaterialInputResolver`, kind `textureSet`): a bundle (`TextureSetInput`) of the packing's texture nodes by slot, plus uniforms `physicalSize` (vec2), `heightScale` and each `surface` field (`tint` a linear colour from the JSON's sRGB, the rest floats), flat (the slot and field names don't collide), kept at `userData.uniforms[<group>_<key>_<field>]`. An unknown set or a packing the set lacks throws naming the input; a slot texture that isn't registered samples the white texel with the missing texture's warning. Its `dependencies` pass `getTextureSet` as the lookup, so `ensureMaterialDependencies` loads a code-made material's set textures.
- **Why a feature** (p303 Phase 1's decision 1): p299's lazy pattern (the resolver `import()`ed by the load that needs it) has no load to hang on, since the gather turns a set into plain texture ids in the scene's `textures`, and a built-in dependency form in the kernel's `MaterialInputRefs.ts` would have put bytes into the banner's `_engine/kernel/assets` group (15 B of headroom then). So nothing of texture sets is in the kernel but `SceneData.textureSets`' type. Without `textureSets()`, a scene whose data names a set fails the boot (the gather's feature manifest), and a code-made material with a `{ textureSet }` input fails to build (the kernel's "Unknown object footprint" error: no kernel bytes name the feature). The lookups and the load work without it.
- **The load from code.** `loadTextureSetAsync(id, { packing? })` loads the packing's textures that aren't registered, from their declarations (`findTextureDeclaration`: the development texture section, else a scene's entry), and re-tags the registered ones, all in the caller's owner scope (every load starts before the first await), and rejects for an unknown set, a packing it lacks or a texture no data declares. `getTextureSetPackingTextures(id, { packing? })` returns the registered ones by slot, or undefined unless all are. Both type their result by packing (`TextureSetTextures<P>`).
- **Debugging.** The Assets tab's texture info window has a Texture set folder naming each set, packing and slot the texture fills (`kernel/assets/debug/`' `getTextureSetSlotsOf`: the development data's `textureSets` section, else the scenes' inline sets, so the kernel's debug code imports no feature code). The verification scene is `textureSets` (`src/app/scenes/textureSets/`, p303 Phase 1's exit): the hand-made `p303TestSet` (PNGs passed through with `optimize: false`, made by `devTools/assetPipeline/fixtures/textureSetsFiles.ts`; its mortar's height, the albedo's alpha, is 0, so a premultiplying decode would show black) through `{ textureSet }` in each packing, one TSL file branching on the bundle's slots; `window.__textureSets.results` holds the lookups' checks and `checkReleaseAsync()` leaves the scene and lists the set's textures still registered (none). **Trap:** three's `bumpMap` normalizes the surface derivatives, so its scale is height per screen pixel and changes with the distance; a bump in metres (`heightScale`, MINIMAL's normal) is the unnormalized form, as the scene's `bumpNormal` and the toolkit's asteroid material do.
