Notes for the characters (`src/_engine/features/character/`: actors, brains, the dynamic controller and their debug tools); the root `.claude/CLAUDE.md` keeps the project-wide rules, commands and workflow.

## Characters

The `character()` feature (`CharacterFeature.ts`, on `aekasha/character`, requires `physics()`; p610 built it on p603's contracts C1, C2, C4): `installCharacters` (`Character.ts`: the two systems and the `CHARACTER` delete hook), the `DYNAMIC_CHARACTER` controller kind, the player brain kinds, the `exit` scene hook (`deleteAllCharacters`: exit hooks run in reverse install order, so characters go before their physics entities) and the debug tools (`onDebug` / `onDebugAfterStart`).

- Actors (`ActorTypes.ts`, type-only): `ActorController<TIntent>` (`kind`, `tick(dt, intent, step)`, `attach` / `detach` typed but never called until a controller is swapped on a live actor (p421, p420), `dispose`) and `ActorBrain<TIntent>` (`kind`, `think(intent, step, dt)`, `configDefaults`, `dispose`). Named generically so p423's vehicles can lift them. A character is the actor record of kind `'CHARACTER'`: its entity's `CHARACTER` component (`CharacterObject`: `id`, `bodyKind`, `entityId`, `visualId`, `intent`, `controlMode`, `controller`, `brain`).
- Kinds (`ActorKinds.ts`): `registerBrainKind` / `registerControllerKind` (and `unregister*`, `get*Kinds`), from a feature's install, never at module load. The kinds and their params are interfaces filled by declaration merging on `'aekasha/character'` (`CharacterBrainKinds`, `CharacterControllerKinds`, as `ComponentDataMap`), so `{ kind, params }` (`CharacterBrainSpec`, `CharacterControllerSpec`) is type-checked per kind, `params` optional when all its fields are. An unknown kind throws, naming the registered ones. `createCharacterOfKind({ id, visual (Object3D or app id), controller, brain? })` makes a character from data (a save, a network message). The `DYNAMIC_CHARACTER` factory `import()`s `controllers/dynamic/DynamicCharacter.ts`, so the controller is its own chunk; the player brains, registered at install, keep the action layer in the main chunk.
- The step order, both systems at `APP_PHYSICS_STEP` with `getPhysicsSubStepIndex()` as `step`: the app's systems (order 0), `characterBrainSystem` (-5), `characterControllerSystem` (-10). So what code writes to an intent in its step applies in that step, and a brain sees it (a `turn` overriding a heading). The intent's moves, turn and jump last one step (the controller clears them after reading); `faceYaw`, `run` and `crouch` stay.
- Brains go with their character: the delete hook disposes the brain, then the controller, and deletes the deprecated `controls` bindings, however the entity goes. `setCharacterBrain(id, spec | null)` makes the new brain before disposing the old one and applies its `configDefaults`.
- `configDefaults` (a player brain's `turnToMoveDirection`): the controller's `config.applyDefaults` sets each key the creation `config` didn't give, at creation (before `config.initial` is snapshotted, so a saved debug edit still wins) and on `setCharacterBrain` (which then overwrites a debug edit of that key). A key the controller doesn't have is skipped.
- Body plans (`CharacterBodyPlans.ts`, `HUMANOID_CAPSULE` the default): the colliders, their roles (`MAIN`, `CROUCH`, the sensors) and sizes from the configuration (`CharacterBodyData`, unprefixed). `bodyKind` names the body's kind (`getBodyKind` reads it or the deprecated `kind`).
- Deprecated, removed in engine 6.0.0 (p610 D5, Phase 4): `DynamicCharacterOpts.input` (`CharacterInputSchemes.ts`' `getInputBrainSpec` maps it to the same kind's player brain, its `mappings` to keyboard bindings; `brain` wins, with a warning), `CharacterObject.kind`, `keyBindingIds`, `mouseBindingIds`, `data` and `initialConfig`, `CreateCharacterOpts.controls` and `data`, `charData`, `DynamicCharacter.data`. Nothing in the engine reads the flat `data` view any more (keep it so: the view can't go while something reads it). `controlFns` stays: it's the script brain's API.

## Character brains

`brains/PlayerBrains.ts` registers `TANK`, `WORLD_FIXED` and `CAMERA_RELATIVE` (`registerPlayerBrains`, the feature's install). A brain writes the intent and never touches the body; it counts durations in steps (`step`, `dt`) and draws randomness from a named stream, so it decides the same way on every run. Brains are on the simulation lint (the character folder, and the app's `GymDummyBrain.ts` by name in `SIMULATION_FILES`).

- Each player brain owns an action map, `<characterId>:input` (`GAMEPLAY`, so `NOT_ENABLED_IN_DEBUG`: the players stand still while the debug camera is on), built from its `bindings` param, deleted in `dispose`. `TANK`'s actions: `turn` (`AXIS_1D`, positive left) and `forward`; the others' `move` (`AXIS_2D`, up = North, -Z, or screen-up); all `jump`, `run`, `crouch`. `think` reads `map.read()`, the sample taken right before the step. `runMode` / `crouchMode`: `TOGGLE` flips on an odd `pressedCount`, `HOLD` follows `isDown`.
- `CAMERA_RELATIVE` reads the main camera at `think`, so its intent depends on the camera's pose (deterministic only under the scene runner's test clock); the intent carries the result.
- `turnToLastMoveDirection` (`WORLD_FIXED`, `CAMERA_RELATIVE`; p610 D10): a closure made only when it's on. While `move` isn't idle it remembers the world move's yaw (and the last diagonal's: both axes non-zero, a stick too) and clears a `faceYaw` it wrote; on the first idle step it writes the heading to `faceYaw`, the last diagonal when the move's last step is within `releaseGraceMs` (default 80, counted in steps) of it, else the last move. A turn in the intent cancels it; a `faceYaw` someone else wrote is never cleared nor replaced. Tested in `brains/PlayerBrains.test.ts` through replayed recordings of the brain's map.
- An app's brain kind: declaration merging plus `registerBrainKind` in its feature's install (the gym's `GYM_DUMMY`, `thirdPersonGymScene/GymDummyBrain.ts`, registered in `AppECSPlugins.ts`).

## Dynamic character controller

`controllers/dynamic/` (p610 Phase 4): `DynamicCharacter.ts` (the factory and `tickDynamicCharacter`, the tick's order as calls), `DynamicCharacterData.ts` (the three types, their defaults, `BAKED_CONFIG_KEYS`, `DERIVED_CONFIG`, the flat view, the context type), `Locomotion.ts`, `Floor.ts`, `Wall.ts`, `Tumble.ts`, `Platform.ts`, `Casts.ts`, `Jump.ts`, `Crouch.ts`. Keep each under the size standard; a new behaviour gets its own file and a call in the tick.

- One `DynamicCharacterContext` per character: the body, its colliders, the three objects, the intent, the dims, the casts, the pose and velocity scratch (13 doubles). Each part is a function of it; the sensor handlers are closures over it, made once. Its body fields are set once `createCharacter` resolves (the sensors fire and the tick runs only after). The vector scratch is module-level in the file that uses it (ticks never interleave).
- The data, on the controller: `state` (written by the tick), `config` (`{ values, initial, bakedKeys, onChange, applyDefaults }`, values unprefixed) and `internal` (the tick's memory). The nested objects are mutated in place. The `config` option (`Partial<DynamicCharacterConfig>`) wins over the deprecated `charData`'s `_` keys; `character.data` is a view of accessors defined once at creation (state, `_` config, `__` internal: the old key order), nothing per frame.
- The tick's order: the pending tumble, the body read (pose, velocities, once), the pending landing, the control mode, the intent read and cleared, crouch, turn, move, tumbling, getting up, falling, the velocity and motion state, the moving platform, the floor ray, the jump phase, the jump, the locomotion state. **Only the tick writes the body**: the sensors record (`internal.pendingTumble`, `pendingLanding`) in the events' flush at the sub-step's start, and the tick applies them where the callbacks used to.
- Step time (p610 D2): the configured durations stay in ms (`jumpCooldown: 100`) and are compared against `(step - stampStep) * stepMs`, so they are whole steps; the stamps are `…Step` step indices with `-1` for "not set" (step 0 is real). `CharacterCastRecord.resolvedAtStep` (`resolvedAt`, deprecated, is `resolvedAtStep * timestepMs`). The tumble start draws from `getRandomStream('character:<id>')`.
- Casts (`Casts.ts`): on `MAIN_THREAD` the floor ray and wall cast are synchronous (`castRayAndGetNormalSync`, `castShapeSync`) and used in the step that fires them; in the worker targets they're async (`inFlight`, the result lands a frame or more later), and the wall sensor reads the body type through the worker proxy's cached type (`bodyTypeSync()`). So characters are deterministic on `MAIN_THREAD` only (p428 owns the worker targets). The floor ray fires every step, idle too (a skip at rest would change the hashes).
- The step path allocates nothing (`perf-auditor`, Phase 4); the physics backend's per-cast `RAPIER.Ray` and shape are p614's.
- Known limit: a crouched character can't pass under a low ceiling (the wall sensor keeps the standing size, so `slideAlongWall` cancels the move): p421 or the p070 prompt.
- The checks: the probe hash leaves characters out; the scene runner's path hash (`getCharacterPaths`, `MAIN_THREAD`) covers them, driven in the gym by `devTools/verify/inputs/thirdPersonGymScene.json` (`devTools/verify/CLAUDE.md`). A change that must keep behaviour keeps the gym's and `topDownTestScene`'s path hashes.

## Character debugging

`debug/` (`_dbg__Character.ts`: the Characters tab and tools; loaded through `registerCharacterTools` / `createCharactersDebuggerGUI`). The Character state window (`_dbg__CharacterStateWindow.ts`, opened from a character's edit window or its row toggle in the Characters tab) shows the controller's `state`, `config.values` and `internal` as groups (`getGroupSource`, no allocation), with step stamps as "N steps (M ms) ago", and its second header row toggles in-world gizmos (`_dbg__CharacterGizmos.ts`) drawn from `CharacterController.probes`, the controller's last floor ray and wall cast as it used them (the wall-cast hold counted in steps from `getPhysicsSnapshotStepIndex()`).

- A character's gizmo lines belong to its owners, the window and the pin (the window's pin button or the Characters tab's row toggle), and are disposed with the last one. They are refilled by a system at `APP_RENDER_SYNC` / `POSE_CONSUMERS`, so they start from the visual's pose of the frame being drawn. Pins are per character id and session only: restored on character creation, dropped at a scene enter without the character.
- The configuration rows are editable: every write goes through `applyConfigValues` (into `config.values`, then the controller's `config.onChange` recomputes derived values; `config.bakedKeys` are shown locked), is undoable (`character.config`) and is saved per scene and character id in `AEK_debugCharConfig` (`_dbg__CharacterConfigOverrides.ts`, values that differ from `config.initial` only). The saved format keeps the `_` keys (`toSavedKey` / `fromSavedKey` at the LS boundary), so tuning saved before p610 applies; an unknown saved key is skipped with a warning. A controller applies the saved values with `applySavedCharacterConfig(character)` right after assigning `character.controller`. "Copy changes" gives a `config` snippet for the scene code, the data copy (`copyDataAsJson`) `{ state, config: values, internal }` as JSON.
- The hints (`_dbg__CharacterConfigHints.ts`) and the window's formats are keyed by the unprefixed names; read only the three objects here, never the flat `data` view.
