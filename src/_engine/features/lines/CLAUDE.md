## Lines

The `lines()` feature (`LinesFeature.ts`, on `aekasha/lines`, p607) draws line segments, 1px or thick, with pulses and dashes. `Lines.ts` is the API (`createLines`, `createLineEntity`, `bindLineToEntity`, `getLine`, `getLineForEntity`, the thick backend's preload) and the install (the `LINE` component hooks and the time system); `LineObject.ts` is the handle, which owns every piece of a line's state (the segment buffer, colour, width, dash, transform, attachment); `LineBackend.ts` is the backend contract and the thick backend's loader, `LineBackendThin.ts` (`THREE.LineSegments`, always 1px) and `LineBackendFat.ts` (instanced screen-space quads, a trimmed port of three's `Line2NodeMaterial`) the two renderers; `LineWriter.ts` the allocation-free cursor and `LineBuilders.ts` the shapes (`write*` into a writer, `*ToSegments` into a new array); `LinePulse.ts` the colour graph; `LineEntity.ts` the entity side; `LineRegistry.ts` the live lines by id. Without the feature, `createLines` throws naming it, and the engine's debug drawing that uses lines (ray helpers, collider wireframes, the LOD and spatial overlays, the character gizmos) is off with one log line each (`isLinesInstalledFor`).

- A line belongs to no ECS world: the registry is module-wide, and `createLines` returns a plain handle. Its one per-frame system, `lineTimeSystem` (`LineSystem.ts`, a core plugin on `MAIN`), writes the main loop time into the one uniform every pulse reads, so pulsing costs no CPU per line. Nothing else runs per frame: a consumer refills on its own cadence.
- Two ways to feed a line: build once (`segments`, `setSegments`, a `*ToSegments` builder), or refill per frame (`beginWrite()` → the writer, or the `write*` builders → `endWrite()`), which writes into the retained buffer and uploads only the written range. `growth: 'FIXED'` drops an overflow with one warning instead of reallocating, which a per-frame refill with a known ceiling wants; `GROW` doubles the buffer.
- Backends: `AUTO` picks `THIN` at width ≤ 1 and `FAT` above. The thick backend is its own chunk, loaded on first need: until it arrives a wide line draws 1px and then swaps itself (await `preloadFatLineBackend()` for the right width on the first frame). A swap (that, or `setWidth` across 1px on an `AUTO` line) replaces `object3D`, keeping its parent, child index, transform, visibility and children: never cache `object3D`. Dashes are `FAT` only and fixed at creation (`dash`), so pin `backend: 'FAT'` with them.
- Bounds are the committed segments' own (not the buffer's unused tail), computed on the first commit, or on every `endWrite()` with `recomputeBounds`. `frustumCulled` defaults to false: a refilled line culled against stale bounds vanishes at some camera angles.
- Entities: `createLineEntity` makes the line an entity (its object the entity's `OBJECT3D`, placed by the ECS transform); `bindLineToEntity` ties an existing line's lifetime to an entity, and `attach({ to: 'ENTITY' })` only parents it. Deleting the entity or removing its `LINE` component disposes the line, and disposing the line deletes the entity (or removes the component). A backend swap re-points the entity's `OBJECT3D` (`repointLineEntity`).
- Trap: a thick line is a `Mesh`, so the `OBJECT3D` auto-tagger stamps it `TAG_IS_MESH`; `retagLineEntity` swaps it for `TAG_IS_LINE`, else the mesh delete hook would dispose the line's object too.
- Scene exit (the feature's `exit` hook, `disposeNonPersistentLines`) disposes every line that is neither `persistent` nor bound to an entity; an entity's line goes with its entity.
