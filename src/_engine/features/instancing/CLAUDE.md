## Instanced mesh pools

`features/instancing/InstancedMeshPool.ts` (`_DONE_p348` Phase 3; it was `toolkit/ecs/`, whose deprecated re-exports p606 removed with the toolkit's next major): `createInstancedMeshPool` draws many instances with one `InstancedMesh`, each instance an entity with a `Transform` and `INSTANCED_MESH_SLOT` (`{ mesh, index }`), baked into the instance matrix by `instancedMeshPoolSyncSystem` (`APP_RENDER_SYNC`) when its `Transform` changed (`MAP` storage: its version; `TYPED_ARRAY`: the store's dirty flag, which this system clears for instances, since they have no `OBJECT3D` for `object3DSyncSystem` to clear it). The `instancing()` feature (`InstancingFeature.ts`, on `aekasha/instancing`, p607) installs it, the slot hooks, the instances' spatial radius and the LOD target. Add `pool.mesh` to the scene yourself; its owning entity (`TAG_IS_MESH`) disposes it and releases the pool's registry refs. Freeing a slot (`despawn`, deleting the entity or removing the slot) is a swap-remove, so an instance's `index` can change: read it from the component. `createInstancedLodPool` has one mesh per level and moves instances between them through the LOD system's `registerLodTarget` seam; a LOD-culled instance is in no mesh (`index -1`), and a cross-fading one is in two (see LOD selection, `features/lod/CLAUDE.md`). A pool's bounds are computed at spawn (a LOD pool's: the union of all placements, copied to each level mesh), and `instancedMeshPoolSyncSystem` grows them when an instance it bakes (or one coming back from LOD culling) leaves them, so three never frustum-culls the whole mesh while a moved instance is on screen; they never shrink. A pool's `spatialDomain` joins its instances to a domain; in `DEFAULT` they aren't light receivers (see Spatial index, `features/spatial/CLAUDE.md`).
