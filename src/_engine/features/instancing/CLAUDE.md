Notes for the instanced mesh pools and the instance sets (`src/_engine/features/instancing/`); the root `.claude/CLAUDE.md` keeps the project-wide rules, commands and workflow.

## Instanced mesh pools

`features/instancing/InstancedMeshPool.ts` (`_DONE_p348` Phase 3; it was `toolkit/ecs/`, whose deprecated re-exports p606 removed with the toolkit's next major): `createInstancedMeshPool` draws many instances with one `InstancedMesh`, each instance an entity with a `Transform` and `INSTANCED_MESH_SLOT` (`{ mesh, index }`), baked into the instance matrix by `instancedMeshPoolSyncSystem` (`APP_RENDER_SYNC`) when its `Transform` changed (`MAP` storage: its version; `TYPED_ARRAY`: the store's dirty flag, which this system clears for instances, since they have no `OBJECT3D` for `object3DSyncSystem` to clear it). The `instancing()` feature (`InstancingFeature.ts`, on `aekasha/instancing`, p607) installs it, the slot hooks, the instances' spatial radius and the LOD target. A pool lives in one world, its `opts.world`: `spawn(placements, entityOpts?)` and `despawn(entityId)` take no world (p622 D5: an instance spawned into another world outlived the mesh's scene there and kept a slot in a disposed mesh). Add `pool.mesh` to the scene yourself; its owning entity (`TAG_IS_MESH`) disposes it and releases the pool's registry refs. Freeing a slot (`despawn`, deleting the entity or removing the slot) is a swap-remove, so an instance's `index` can change: read it from the component. `createInstancedLodPool` has one mesh per level and moves instances between them through the LOD system's `registerLodTarget` seam; a LOD-culled instance is in no mesh (`index -1`), and a cross-fading one is in two (see LOD selection, `features/lod/CLAUDE.md`). A pool's bounds are computed at spawn (a LOD pool's: the union of all placements, copied to each level mesh), and `instancedMeshPoolSyncSystem` grows them when an instance it bakes (or one coming back from LOD culling) leaves them, so three never frustum-culls the whole mesh while a moved instance is on screen; they never shrink. A pool's `spatialDomain` joins its instances to a domain; in `DEFAULT` they aren't light receivers (see Spatial index, `features/spatial/CLAUDE.md`).

## Instance sets

`features/instancing/InstanceSet.ts` (p354, `docs/plans/p354_gpu-driven-culling.md`): `createInstanceSetAsync({ world, levels, maxInstances, lod?, receiveShadow?, maxVisible?, entityOpts? })` on `aekasha/instancing` draws an instanced LOD pool's levels (`InstancedLodPoolLevel[]`, the same `LodDef` settings) for instances that are plain data, with no entity per instance, culled and LOD-selected per instance by a backend. The front (the options' checks, the owning entity, the ranges) is on the entry; each backend is an `import()` of its own (`InstanceSetGpu.ts` with its TSL in `InstanceSetNodes.ts`; the CPU one is p354 Phase 4), against the contract in `InstanceSetTypes.ts`.

- The owning entity is created before the backend's `import()`, and the promise resolves `null` when it was deleted meanwhile (a scene exit). It holds `INSTANCE_SET` (a core component, its data `InstanceSetData`), whose hooks (`instancing()`'s install) dispose the set once: the group leaves its parent, the backend frees its draws and buffers, and the registry refs on the levels' geometries and materials are released. `entityOpts.persistent` is applied by the set itself (`createEntity` leaves it to the creators, `docs/issues/entity-persistent-flag-not-applied.md`). Without `instancing()` a set warns once and its deletion frees nothing.
- `addInstances(placements | Float32Array)` appends (16 floats a matrix, column major, uniform scale: a non-uniform one warns in the debug env) and returns the `InstanceRange`, or `null` and adds nothing past `maxInstances` (at most 2^24: a list entry packs the instance in 24 bits). The backend keeps the only copy (`writeInstances`).
- `backend` is `'GPU'` where `isWebGPURenderer()`, else `'CPU'`, which draws nothing and warns once until Phase 4.
- The GPU backend's buffers: the affine matrices (three `vec4` rows), the cull records (the origin and scale × level 0's `getConservativeGeometryRadius`, the CPU path's measure), a state word per instance (the level in bits 0-7, the level a cross-fade dissolves out of in 8-15; `LEVEL_NONE` 0xfe, `LEVEL_CULLED` 0xff) and its fade's progress (an `f32`, 1 when none runs, read only while one does), the visible lists (`maxVisible` per level, default `maxInstances` up to 65,536; an entry is the instance in bits 0-23 and its copy's signed fade in 24-31: 127 + round(t × 127) for the incoming copy, round(t × 127) for the outgoing one, so both decode from one rounded `t` and split the pixels exactly; 254 is whole), a counter per level (atomic) and the indirect args per (level, group), 32 B each. CPU copies of the matrices and records upload by `updateRanges`.
- Each dispatch runs three passes (`createInstanceSetPasses`): the reset zeroes the counters; the cull, one thread per instance up to the highest added (its compute node's `count`, set before each dispatch: three recomputes the dispatch, 2D past the per-dimension limit), first moves the state and then tests the record's sphere (grown by the largest level's conservative radius over level 0's) against the render camera's frustum and appends a copy per drawn level within the budget (past it only counted: the overflow): a fading instance's level at `t` and its outgoing level at `t - 1`, one copy for a fade to or from culled; the finalize writes `min(count, maxVisible)` into every group's args.
- The state's move is `utils/LodRules.ts`' `selectLodTarget` and `stepLodInstanceState` ported line by line (their tests are the port's reference; Node can't run TSL, so `instanceStress` checks the parity, below): the target, a fade's start (never a first selection; a change mid-fade fades from the incoming level) and its advance in the same frame, ending at 1 − `LOD_FADE_END_EPSILON`. It runs in the frame's first dispatch only (`getMainLoopFrame`, p354 D7), from the LOD frame inputs (`getLodFrameInputs`, `kernel/ecs/LodTargets.ts`, which `lod()`'s selection writes): a mode uniform says `SELECT`, `FORCE` (the `forceLevel` debug option, which fades as the ECS path's does, or level 0 without `lod()`, unfaded, which warns once when there are levels to select), `ADVANCE` (`freeze` or no selection camera: the levels hold, the fades run) or `HOLD` (a later dispatch in the frame, a frame the selection didn't run: the app loop paused). The fade's delta is `getLodFadeDelta(inputs.fadeStep, lod.fadeSeconds ?? inputs.fadeSeconds)`, a uniform, so `fadeTimeScale` and the global fade seconds reach it. At 20k on `instanceStress`' held orbit the state per level and the fading count are the pool's exactly, with fades off, 0.25 s and 1 s (p354 Phase 2).
- The draws: a plain `Mesh` per (level, geometry group), one per level for a single material, its geometry the level's attributes and index with its own `setIndirect` offset. The wrappers aren't disposed: three frees a geometry's attributes with it, which the level geometries share. Each source material gets `enableLodDither` (as a pool's level materials) and one node variant (`renderer.library.fromMaterial`, its values copied once: a later change to the source doesn't reach it), its `maskNode` kept (the dither and any other mask) and the instance fetch as its `positionNode` (a source's own `positionNode` is replaced, with a debug warning). The variant's dither reads the drawn copy's fade from its list entry, a flat varying from the vertex stage (`setMaterialLodFade`, `kernel/render/LodFade.ts`'s third source), ANDed with the object's visibility fade. The list a mesh reads is a per-object uniform (`LIST_BASE_KEY`), so every draw of a material shares one build: `instanceStress` builds 3 node builds and 3 render pipelines, as the pools, plus 3 compute pipelines.
- The dispatch: one drawing pipeline hook for every GPU set (`kernel/render/DrawingPipeline.ts`' `addDrawingPipelineHook`, added with the first set and removed with the last). Its `isCulled` keeps a set's draws to renders of the main camera (every other camera, a shadow or the debug camera included, draws none of it until p354 Phase 3) and notes the sets the render reached; its `finishRenderList` dispatches those, after the projection and before any draw. A render that never reaches a set costs it nothing.
- `object` (a `Group`) goes directly under the root scene: the instances are in world space, and its draws have no bounds and no raycast. three's `info.render` doesn't count their draws or triangles: read the set's (below). A drawing pipeline set over the engine's (`instanceStress`' `?stressPipeline=meshlet`, which refuses on its set path) stops every set's dispatch.
- Debug: `readInstanceSetStatsAsync(set, { state? })` (on the entry; debug env and prod test mode, `debug/_dbg__InstanceSet.ts`): the last dispatch's drawn and overflowed instances per level (a fading instance's two copies in both), and with `state: true` every instance's level counted (a fading one in both its levels, as a pool's level meshes hold it) and the fading ones (a readback of the whole state buffer). The LOD tab lists the live sets through the kernel's debug source seam (`registerLodContentDebugSource`, `kernel/ecs/LodTargets.ts`; the tab is `lod()`'s): `instancing()`'s `onDebug` loads `_dbg__InstanceSet.ts`, which registers a source reading the front's live sets (`getLiveInstanceSets`, kept in the debug env only), and the tab's "Force level" options cover their levels. The tab's `freeze`, `forceLevel` and `fadeTimeScale` drive a set through the frame inputs.
- Verification: `instanceStress` (`src/app/scenes/instanceStress/`) draws the same forest with pools or, with `?stressPath=gpu`, a set; the scene runner runs it as `instanceStress@pools` and `instanceStress@set` (20k trees, still camera, no fades), and `npx tsx devTools/bench/instanceStress.ts` measures both paths at any count on a dev server or a `yarn build:test` build (its options in the file's header; prod test mode has no stats panels, so no GPU figures there). `npx tsx devTools/bench/instanceStressLodTab.ts` drives the LOD tab's controls on both paths (time scale, force level, freeze; the held fade's keys dispatched in the page around `measure()`, so it's frame exact) and compares their states at six checkpoints and a snapshot pair at a fade held at 0.5 (p354 Phase 2 step 3).
- Later phases (the plan's): the debug tab folder (Phase 2), a slot per camera with shadows, viewports and the debug camera (3), the CPU backend for WebGL2 (4), removing and moving instances, impostor levels, the GPU memory tab and `preWarm` (5).
