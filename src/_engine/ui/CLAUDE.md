## UI kit

The DOM UI the app's HUD and the debug tools are built from, public on `aekasha/ui` (p617 D6). The Hub's UI kit section is the user guide (`hub/pages/features/ui-kit/`: the overview with CMP, the HUD root and a build's size, `core/`, `forms/` (the fields, value editors and containers, the drop-down among them), `data/` (p805: the lists, trees, tables, graphs and stat tiles), `overlays/`, `styling/` and the component library, `library/`; each component with its live demo, parts, custom properties and keys), and its example scene (`src/app/examples/uiKit/`) builds an app HUD from every piece. p803 restyled the kit onto the tokens (layered, accessible: p800 D3, D8) and added the core components; p804-p808 add the forms, the data display, the debugger's migration and the game pieces.

The layout (p803 D2, `devTools/layout/layoutRules.ts`' rule per folder, so a module directly in `ui/` fails `layout.test.ts`): `core/` (CMP, the HUD root, the bounds, motion, the theme watch, the icons), `components/` (one module per component, its stylesheet and test next to it), `overlays/` (the windows and dialogs in `windows/`, the toaster, and the overlay layer: the stack, the focus trap, the anchor, the tooltip, the popover, the menu, the context menu and the command palette), `forms/` (p804's fields, value editors and containers, the drop-down among them: their binding and scheduler in `forms/binding/`, the pieces of several modules in `color/`, `rotation/`, `gradient/` and `curve/`), `data/` (p805's data display: the table, list, tree, graphs and stat tile; so far the list, `List.ts` with `ListTypes.ts` and `ListRow.ts`, its opt-in `VirtualRows.ts` and `Reorder.ts`, the tree, `Tree.ts` with `TreeTypes.ts`, `TreeNodes.ts` and `TreeRow.ts`, the table, `Table.ts` with `TableTypes.ts`, `TableRows.ts` and `TableGrid.ts`, what the collections share, `CollectionParts.ts`, `Filter.ts` and `Selection.ts`, the graphs in `graphs/` (`Sparkline.ts`, `Donut.ts`, `StackedBar.ts`, `Chart.ts` with its scale, `ChartScale.ts`, `TimeSeries.ts`, and the parts they share, `GraphParts.ts`) and the stat tile, `StatTile.ts`), `styles/`, `fonts/` and `testing/` (the tests' shared helpers). Only the entry `index.ts` and this file sit directly in `ui/`. A piece with more than one module gets its own folder (the windows).

- **CMP** (`core/CMP.ts`; its types in `core/CMPTypes.ts`, the animation chain in `core/CMPAnim.ts`, which writes the CMP through its methods and imports only the types): `CMP(props, wrapper?, wrapperProps?)` makes an element from its props (`tag`, `text`, `html`, `class`, `style`, `attr`, the `on*` listener props and `listeners`, `anim`, `onCreateCmp` / `onRemoveCmp`) and returns its handle, `CMPHandle` (`add`, `remove`, `update`, `updateText`, `updateClass`, `updateStyle`, `updateAttr`, `focus`, …). `classes(...)` joins class arguments.
  - It's in the DOM once it's added under a CMP that is: an app's UI goes under the HUD root (`getHUDRootCMP().add(…)`). The one root is the CMP made with `attach` (the boot's HUD root): a second one throws, and so does a taken id. A generated id is a counter (`aekCmp_N`).
  - Templates: a CMP's `toString()` is a `<cmp>` placeholder, so another CMP's `html` places it (`` html: () => `<h2>${star} Scores</h2>` ``). The parent's `update()` makes its template children again, so an `html` that names them is a function. `html` is raw HTML: user text goes in `text`, or through the root's `settings.sanitizer` (`sanitize`, `sanitizeAll`).
  - Props are copied once, at create and at `update()` (`style` and `attr` too, so a style constant several CMPs share is never written). The update methods write that copy in place, with no allocation per call (a HUD value updated every frame), and the next `update()` keeps what they set.
  - `onCreateCmp` runs once when the CMP is mounted (added, attached, or put in place of its placeholder by its parent's `html`) and after each `update()`; `onRemoveCmp` after `remove()` has removed its children, listeners, timers and element. Per-CMP state kept in a module map is cleaned up there.
  - Every listener is a capture listener (a `listeners` entry is added with `{ capture: true, ...options }`): a parent's `onClick` runs before its child's, and a child's `stopPropagation()` doesn't stop it.
  - A style key that is a custom property (`--x`) goes through `setProperty` / `removeProperty`; `null` removes a style.
- **The HUD root** (`core/HUD.ts`): `createHudRoot({ slot? })` (p803 D4) makes it, a fixed, zero-size kit root over the canvas in place of `slot` or the page's `#hudRoot` / `#guiContainer`, and returns its handle. The boot calls it with a mount's slot in its container (whose `contain: layout` makes the HUD's fixed elements relative to the container) or none; a page without the engine calls it itself (see Outside the engine). One per page: a second call throws, naming the boot. `hasHudRoot()` says whether it exists, `getHUDRootCMP()` throws before. Each child places itself. In an editor view only the root's direct children with `KEEP_IN_VIEWS_CLASS` stay visible (Views, `src/_engine/kernel/render/CLAUDE.md`).
- **Draggable windows** (`overlays/windows/`: `DraggableWindow.ts` (the stacks, the DOM build, the hooks and the public functions, over 800 lines with its header saying why), `DraggableWindowTypes.ts`, `DraggableWindowStore.ts` (config resolution, LS, the kinds' geometry), `DraggableWindowGeometry.ts` (styles, clamps, fits, cascade), `DraggableWindowDrag.ts`, `DraggableWindowDom.ts` (the parts without state: the header with its buttons, tooltips and keys, the attributes, the names) and `DraggableWindowKeys.ts` (the header's keys and the cycle keys), none of which imports `DraggableWindow.ts`; `DraggableWindow.scss`):
  - `openDraggableWindow({ id, title, content, … })` opens a window, or reopens and updates the one with its id. `closeDraggableWindow` keeps its state (a reopen restores its layout), `removeDraggableWindow` drops it. Two layers: the app's windows, and the debug windows (`isDebugWindow`) above them, opened only in the debug env (`showInProdTest`: prodTest too).
  - An edit window per entity is a window kind. Register the kind once with `registerDraggableWindowKind(kind, { content, onClose, sceneTargetResolver, keepInViews })`, before the boot restores the saved windows (its step after the app's `start`): in `start` or a feature's install, or at a `_dbg__` module's load (anywhere else a registration at load is a module side effect). It also covers the windows restored from LS; a single window uses `registerDraggableWindow(id, …)`. Open a window with `kind` and `id: getKindWindowId(kind, key)`, from a list row through `toggleDraggableWindow` (open, bring to front, close when on top), and select the rows from `getDraggableWindowsOfKind`. Rebuild one with `updateDraggableWindow(id)`, all with `updateDraggableWindowsOfKind(kind)`, and keep per-window module state in a map cleaned up in the content's `onRemoveCmp`. Double-clicking a header fits the window to the screen (`fitDraggableWindowToScreen`), and the Debug tools tab's "Center and fit all windows" fits them all (`fitAllDraggableWindowsToScreen`).
  - LS: the `saveToLS` windows and the kinds' geometry are in `AEK_popupWindows`, written on finished changes and restored by the boot's after-start hook; a restored window's content comes from its registered function, which is why registering comes first. The format is unchanged since before p617's split (`DraggableWindow.test.ts`' round trip).
  - Scene loads: at a load's start a `removeOnSceneChange` window is removed, and a `closeOnSceneChange` one closes, unless its kind has a `sceneTargetResolver`: then it's torn down and rebuilt after the `entered` hooks when the resolver finds its target in the next scene (closed otherwise, and after a failed load, at `loadSettled`).
  - The kernel names it uses (p617 D7, the only ui → kernel imports the layout check allows, `devTools/layout/layout.ts`' `UI_KERNEL_HOOKS`): `addSceneHooks`, `addBootAfterStartHook`, added on the windows' first use, never at load, and `Config.ts`' env flags (and `AppConfig.draggableWindows`, the deprecated fallback for a content function, until 6.0.0). None of them imports anything heavy. A resize reaches the windows' clamp through `core/Window.ts`' `onBoundsResize` (p803 D4), not the main loop's resizers: the main loop brings three, the renderer and both workers into any bundle that imports it, so no kit module may (the Hub's `scripts.test.ts` fails on a kernel module outside `UI_KERNEL_HOOKS`).
  - A window's `icon` is a registered icon's name (see Icons), drawn before the title in a `1em` box of its own (`.aekWindow__title .aekIcon`, `aek.components`), set off from it and on its line.
  - Accessible (p803 D8): the window is `role="dialog"` (non-modal), named by its title (`aria-labelledby`) or by `ariaLabel` (default 'Window'; an empty title's heading is `aria-hidden`). Its header is a `<div>` (a `<header>` would be a second banner landmark): a tab stop (`role="group"`, "movable window" when it moves, its keys in a hidden `aria-describedby` text) when it has a key to act on, which `DraggableWindowKeys.ts` gives it: the arrows move the window a step (`--aek-base` × 16 / 14, 16 px at the defaults, kept grabbable as a drag), Alt+arrows resize it (in px from then on, as a drag), Shift is four steps, Enter toggles the collapse; a key it uses goes no further, and the change is committed (recorded, LS) on the arrow's keyup or the header's focusout. The collapse button has `aria-expanded`, `aria-controls` (the content) and the title as its name, the close button `aria-label="Close"`; both have tooltips (the close button's repeats its label, so it describes nothing: `createTooltip`'s rule), and the title a tooltip only while it's cut (`onlyWhenTruncated`). A content with no focusable element is a tab stop itself (`tabindex="0"`, read at the mount and a rebuild: axe's `scrollable-region-focusable`); a collapsed window's content is `visibility: hidden` once the collapse ends, so Tab skips it. The focus moving into a window (`focusin`) brings it to the front, as a press does.
  - The cycle keys (p803 D8): F6 / Shift+F6 by default, `setWindowCycleKeys({ next, previous } | null)` (public; chords like `'Ctrl+Shift+F6'`). A capture `keydown` listener on the HUD root's **parent** (the page's body, or a mount's container with the canvas: decided in Phase 5 over the plan's HUD root, so a key pressed on the canvas reaches the windows), added at the first mount and kept: it focuses the next window's first focusable element (its content's, else its header) and brings it to the front, then stops the key (`preventDefault`, no key binding gets it, its keyup swallowed). The order is the HUD root's children (the mount order, which a bring-to-front doesn't change), the app's windows and then the debug windows, skipping an inert or unrendered one; from outside every window F6 takes the first, Shift+F6 the last. With no window open the key is left alone. The debug key `sc-toggle-main-loop` moved to Shift+F7 for it.
- **Dialogs** (`overlays/windows/DialogWindow.ts`): `openDialog` is a window centred over a backdrop that doesn't move, resize or collapse, reset on every open. It takes the focus (the window's first focusable element) and pushes a modal entry on the overlay stack, which Escape inside the HUD closes with `closeOnEscape` and otherwise stops at; however it closes, its entry goes in the window's unmount hook (`onDraggableWindowUnmount`, `@internal`, run before its DOM goes, so the focus is still in it) and the focus returns to the opener. A reopen keeps the first opener and goes on top. A dialog rebuilt by a scene load's `sceneTargetResolver` has no entry (dialogs are `removeOnSceneChange` in practice). Modal (p803 Phase 5): `role="dialog"` (`"alertdialog"` with `alert`) and `aria-modal="true"` written on every open, `initialFocus` (a selector) over the windows' first focus, a focus trap (`trapFocus`, removed in the unmount hook and on a reopen), and its stack entry asks for `inert` with its backdrop in `keep` and `isDebug` for a debug dialog. It stacks in its own layer (`setDraggableWindowModal`, `@internal`, before the open; kept until the window is removed): an app's dialogs from `--aek-z-dialog` (5000: above the app's windows and a loading overlay over the bounds, `--aek-z-loading`, below the debugger, so the debugger stays clickable over a pause menu, decided in Phase 5 over D7's "above the debug windows"), a debug dialog from `--aek-z-debug-dialog` (30000); `DraggableWindow.ts`' `Z_INDEX_BASES` (`@internal`) equals the tokens (`DialogWindow.test.ts`).
- **Toasters** (`overlays/Toaster.ts`, `Toaster.scss`): `createToaster` returns the toaster's CMP (add it under the HUD root); the first one made is the default for `addToast` (`setAsDefaultToaster` moves it). One timer per toast at a time; `removeToaster` clears its toasts' timers and, with the last toaster, the page's `visibilitychange` listener. The engine makes a toaster only in the debug env (the debug toaster, kept in every view, which follows the system's theme), so an app that shows toasts makes its own. p803 Phase 5 (D5, D9): nothing goes into the page's head any more: `Toaster.scss` (on the tokens, layered) has the styles and a toaster's size settings are custom properties on its element (`--aek-toast-min-width`, `-max-width`, `-min-height`, `-max-height`), a toast's animation time `--aek-toast-time` on it; the toaster at `--aek-z-toast`. Its classes are `aekToaster` and `aekToast` with `__icon`, `__content`, `__title`, `__message`, `__close` (the old unprefixed `toast*` classes went: a host page's `.toast` would match), `data-type` and `data-phase` (`entering`, `appearing`, `showing`, `removing`). Kinds: `info`, `success` (new), `warning`, `alert`, each a status colour (a 3 px stripe, `--aek-toast-status`) and an icon: `settings.icons`' HTML or, without one, a glyph in CSS (`data-glyph`: i, a check mark, !, a multiplication sign, as CSS escapes: a non-ASCII character in the output would make Sass write `@charset`), never the colour alone. Two visually hidden live regions per toaster (`role="status"` polite, `role="alert"` assertive for an alert) read a toast's title and message once, emptied first and filled 50 ms later so a repeated text is read again; the toaster itself isn't live. The showing time pauses while a toast is hovered or holds the focus, and while the page is hidden (one `visibilitychange` listener, added with the first toaster). The close button is `aria-label="Close"`, a 24 px target; with the focus in a toast it has an overlay stack entry, so Escape closes it and the focus goes back to what had it (`removeToast` with the focus inside does the same). A long text scrolls in `__content` (the close button keeps its column), a tab stop when it overflows (measured at the add). Under reduced motion (a factor of 0) a toast doesn't slide or push the queue: it fades in place in the setting's time, unscaled. A down or right toaster's new toast is prepended (it settled at the far end before). `aekVisuallyHidden` (`kit.scss`, `aek.utilities`) is the kit's visually hidden class.
- **Icons** (`core/icons/`): `registerIcon(name, svg)` and `getSvgIcon(name, size?)`; the built-ins are named SVG strings (`BuiltInIcons.ts`, from `icons/svg/`, Bootstrap Icons' licence). The boot registers them all (`registerBuiltInIcons`, about 10 kB gzip) only in the debug env and prodTest: a production app registers the ones it shows, or gets `??` and a warning. p803 Phase 5 (D5): `getSvgIcon` writes `<span class="aekIcon uiIcon">` (and `smallIcon` at `'sm'`: the debugger's old classes, which no style reads since p806 D9; p622 stops writing them), `1em` square in `aek.base` (`kit.scss`), in the debugger's roots too (p806 Phase 5 removed their inline, auto-width reset), so an icon follows its text, or at `size` `'sm'` / `'md'` / `'lg'` (`data-size`, `--aek-icon-size-*`: 12 / 16 / 20 px, 11 / 13 / 16 compact, in the type scale's group and the compact block; `Tokens.test.ts` counts them in the density's scales; `SvgIconSize` on `aekasha/ui`). `'small'` is the deprecated name of `'sm'`.
- **Buttons** (`components/Button.ts`, `Button.scss`, p803 D10): `createButton({ label, variant?, size?, icon?, iconPosition?, iconOnly?, tooltip?, kbd?, pressed?, onPressedChange?, holdToConfirmMs?, onUnheldClick?, disabled?, focusableWhenDisabled?, type?, onClick?, class?, attr?, id? })` returns `{ cmp, setLabel, setDisabled, isDisabled, setLoading, isLoading, setPressed, isPressed }`, each setter writing the element in place. Disabled (p806 D7): `disabled`, or with `focusableWhenDisabled` `aria-disabled="true"` (still a tab stop: a toolbar's button, which the arrows still stop on), whose clicks, holds and `onUnheldClick` are ignored (`canAct`); `setDisabled(isDisabled, reason?)` makes the reason its tooltip while it's disabled (`syncTooltip`: the reason, else `tooltip`, else an icon-only label; the tooltip made or removed as needed), and the disabled look is `:disabled` or `[aria-disabled='true']`. A native `<button>` (`type="button"`), its parts `.aekButton__icon` (`aria-hidden`), `__label` (none with `iconOnly`: the label is the `aria-label` and, without `tooltip`, the tooltip, which then describes nothing), `__kbd` (the `kbd` prop's Kbd handle, which the app makes with `createKbd` (p804 D13), `aria-hidden`; the button's `aria-keyshortcuts` is the handle's `getAriaKeyShortcuts()`, ARIA's names (`Control`, `Plus`), rewritten on its `onKeysChange`; the button removes the handle with itself), `__hold` (the hold's fill) and the hidden "Hold to confirm" text its `aria-describedby` names (a `hidden` element inside: left out of the name, read as the description). Variants `primary` / `secondary` (default) / `ghost` / `danger` / `link` and sizes as `data-variant` / `data-size`; the states as attributes (`disabled`, `aria-pressed`, `aria-busy`, `data-holding="filling" | "confirmed"`, `data-hold-steps`). The size is on the button (`--aek-button-font-size`, `--aek-button-height`, set per `data-size`; p803 put it on the parts while the full page's unlayered normalize beat it, and p804 D13 moved it back once normalize went into `aek.page`). Loading: the parts fade to `opacity: 0` (the width kept) and the button's `::after` turns (`kit.scss`' `aekSpin`; `aekPulse` under `prefers-reduced-motion`, a still ring at `--aek-motion: 0`); clicks are ignored. Hold to confirm: a primary pointerdown (captured), Space or Enter (no repeats; their default prevented, so no click) starts a timer of `holdToConfirmMs`, which acts and leaves the fill full until the release; a release, `pointercancel`, a lost capture or a blur before cancels; every click is ignored (the timer acts); a click no press on the button started (a pointer's `pointerdown`, a hold key's keydown; a `pointercancel`, the key's keyup and a blur end one, the click after a pointer's release takes it) calls `onUnheldClick` (p804 D13: a screen reader's browse mode, where the app confirms another way) and is ignored without it. The fill takes `--aek-button-hold-time` linearly, in `steps(4)` when `getMotionFactor` is 0 at the press (information, not motion). `cmp.remove()` clears the timer and removes the tooltip. Custom properties: `--aek-button-radius`, `--aek-button-hold-color`.
- **Button groups** (`components/ButtonGroup.ts`; its joined styles are in `Button.scss`, after the button's own, so no order between two stylesheets decides them): `createButtonGroup({ label, buttons, exclusive?, toolbar?, orientation?, onChange?, class?, attr?, id? })` returns `{ cmp, buttons, getPressedIndex, setPressedIndex }` and adds the `createButton` handles it's given (generic over `ButtonGroupItem`, `Button | DropDown`, default `Button`). `toolbar` (p806 D7) is the same toolbar's keys and tab stop (the first item) for items that act alone: toggles, actions and `createDropDown`s (the trigger takes the focus, `getDropDownTrigger`, `@internal`; the arrows act only on an item's own element, so an open list keeps its keys); a `disabled` item is skipped, an `aria-disabled` one (`focusableWhenDisabled`) is a stop. `role="group"` named by `label`, each button a tab stop. `exclusive` makes it a toolbar (`role="toolbar"`, `aria-orientation` when vertical) of toggles, one pressed: a capture `click` on the group stops a press of the pressed button before it (nothing changes, its `onPressedChange` isn't called), and a bubble `click` after a button pressed itself releases the others and calls `onChange(index)`. One tab stop (roving `tabindex`: the pressed button, else the first enabled; moved by `focusin`, so Tab comes back to the last one focused, as the APG toolbar): the arrows along the orientation move the focus to the next enabled button (wrapping), Home and End to the ends; a used key is stopped (`swallowNextKeyUp` for its keyup). `setPressedIndex` doesn't call `onChange`. The keys and the tab stop are `RovingFocus.ts`' (below).
- **Roving focus** (`components/RovingFocus.ts`, `@internal`, p805 D4; the menu's keys and typeahead and the button group's tab stop moved here unchanged, for the list, the tree and the tabs): `getMoveTarget(key, from, { count, orientation?, wrap?, pageSize?, isSkipped? })` (the arrows along `'vertical'` (default) or `'horizontal'`, Home / End, PageUp / PageDown by `pageSize` (clamped, never wrapping; without it they aren't move keys), each passing over `isSkipped` items; from -1 the next is the first and the previous the last; returns the index, -1 for a move key with nowhere to go (an end without `wrap`, all skipped: the caller still uses the key up), null for another key). `createTypeahead({ getCount, getText })` returns `{ type(letter, from), clear }` (the APG's: letters within 500 ms one search, one letter or one repeated looking past `from`, more including it, going round; `getText` lowercased) and `isTypeaheadKey(e)` (one character, no Ctrl / ⌘ / Alt). `createRovingTabStop({ getElems, indexOf? })` returns `{ reset(index), setIndex(index), getIndex, onFocusIn }`: `reset` writes every item's `tabindex` (0 the stop, -1 the rest; at creation and after the items changed), `setIndex` only the old stop and the new, `onFocusIn` the composite's `focusin` listener (no listener of its own to remove).

(TabBadge: a count, a word, or { label, tone?, spokenLabel? }), disabled?, separatorBefore?, content: CMPHandle | () => CMPHandle }` (`separatorBefore`, p806 D6: `data-separator-before`, a line the stylesheet draws in a gap before the tab, across the list's run; no element, since a `tablist` holds tabs alone, and the arrows go on across it: the debugger's scene tabs). The selected tab's line is `--aek-tabs-indicator-color` (a shape, not only a colour).

- **Splitters** (`components/Splitter.ts`, `Splitter.scss`, p805 D10): `createSplitter({ first, second, orientation?, size?, unit?, min?, max?, step?, collapsible?, collapsed?, onSizeChange?, onCollapsedChange?, label, class?, attr?, id? })` returns `{ cmp, setSize, getSize, collapse, restore, isCollapsed }`. `orientation` is the panes' ('horizontal', the default: side by side, so the separator's `aria-orientation` is vertical). ## Writing a component

How a kit component is written (p803 D2; `components/Button.ts` is the model): the coding standards page points here.

- **The shape**: `createX(props: XProps): X` in its group's folder (`components/`, `overlays/`, `forms/`; a piece with more than one module gets a folder of its own), returning its handle `{ cmp, …setters, …getters }`. The caller adds `cmp` where it goes; `cmp.remove()` disposes of it, and its `onRemoveCmp` clears every listener, timer and observer the piece added, its overlay stack entry and its tooltip. Every component takes `class`, `attr` and `id`; events are `on*` props; a setter writes the element in place, with no rebuild and no allocation (a HUD value set every frame). An options object, never positional optionals (the coding standards' Public API).
- **ARIA and keys**: a native element where one exists (`<button>`, `<a>`, `<hr>`), the APG pattern where none does; ARIA, `inert` and `popover` written as attributes (linkedom doesn't reflect the properties); a key the piece uses goes no further (`stopPropagation`, `swallowNextKeyUp` for its keyup); an overlay pushes an overlay stack entry and anchors with `showAnchored` (see The overlay layer); never colour alone; a target at least 24 px in both densities.
- **Styles**: its own stylesheet next to it, imported by the module with `styles/kit.scss` (D4: the kit's global styles come with any module), in `@layer aek.components` with `:where()` selectors (a pseudo-element goes after it, `:where(.aekX)::before`: inside, it makes the whole rule invalid, which p804's checkbox drew nothing from); global classes `aek<Name>` with `__part`s, states and variants as attributes (`data-variant`, `data-state`, `aria-pressed`); every colour a role, every size a token (no `rem`); its custom properties (`--aek-<name>-*`) read with the token as the fallback, so an app sets them on any ancestor. A rule on another kit piece put inside it (a menu item's key hint, a part's number box) takes one class of specificity (`.aekMenu :where(.aekMenu__kbd)`): zero against the piece's own zero is decided by the stylesheets' load order, which an import anywhere else changes (p804 Phase 6 section 3: the curve editor's import of the menu moved `Menu.scss` before `Kbd.scss`, and the menu's hints took the item's font size). The full page's normalize is in `aek.page`, below the kit's layers (p804 D13), so a component's rule on its own `button` or `input` needs no workaround. Motion through the duration tokens, or `getMotionFactor` for a JS timing; reduced motion keeps what's information (a hold's fill steps).
- **JSDoc** (the coding standards' JSDoc): the summary lists its parts, custom properties, keys, ARIA and motion, each prop is documented, and an `@example` that type-checks (`examples.test.ts`). Nothing at module load (`moduleSideEffects.test.ts`).
- **Tests**: `<Name>.test.ts` next to it, on `testing/KitDom.ts`: each key of its JSDoc, the ARIA after each action, and its disposal (`countListeners`: none left after `cmp.remove()`, mid-interaction too).
- **With it, in the same branch**: its names on `aekasha/ui` (`index.ts`; `yarn verify:baselines --update` records them), its box in both component library pages with its texts, its group's demos map and checks (`hub/_assets/ts/_library/`) and `COMPONENT_USES` (`hub/CLAUDE.md`), its section on the Hub's UI kit pages with `::: demo <key>` and its reference table, a line in this file, and `yarn verify:ui --only <key>`.

## The overlay layer

Every open overlay (a dialog, a drop-down's list, a tooltip, a popover, a menu; p803 D7) is an entry of one stack: Escape pressed inside the HUD goes to the top entry alone, a closed entry gives the focus back, and an anchored overlay shows in the browser's top layer, so no window clips it. The Hub's UI kit section's Windows and overlays page (`features/ui-kit/overlays/`, its `aek:covers`) is the user guide.

- **The stack** (`overlays/OverlayStack.ts`, `@internal`): every open overlay pushes `{ elem, close?, returnFocus?, inert?, keep?, isDebug? }` and gets its remover. One capture `keydown` listener on the HUD root's element, added on the first push and kept, takes Escape for the top entry still in the document (`close`, or nothing for an entry without one) and stops it, so the piece's own listeners, the input system's (bubble phase on the window) and anything else miss it; `swallowNextKeyUp` (a one-off capture listener on the window, where the keyup goes after a close moved the focus) takes its keyup. A key pressed outside the HUD root (an embed's host page) never reaches it. The remover gives the focus back to `returnFocus` (default: what had it at the push) when the focus is in the overlay or nowhere, unless called with `false` (a focusout close). An `inert` entry, the top one, sets `inert` on the HUD root's other children (not its own, its `keep` or the entries above it; an app's entry spares the children with `DEBUGGER_ROOT_ATTR`, `data-aek-debugger`: the drawer, the editor drawer, the on-screen tools' rows and switch tools, the stats panels, the debug toaster and a debug window with its backdrop), removed with it; a child with `KEEP_LIVE_ATTR` (`data-aek-keep-live`, `@internal`: the announcer's region) is never covered; the app's own `inert` is never touched, and a child added while it's open stays live (no observer, decided in Phase 5: a child added then is code's on purpose, a window or toast the dialog opened, a tooltip or a fallback list above it).
- **The focus trap** (`overlays/FocusTrap.ts`, `@internal`): `trapFocus(elem)` (Tab and Shift+Tab wrap, the dialog's from Phase 5) and `getFocusableElements` / `getFirstFocusable` (by selector, rendered only), which the windows use.
- **The anchor** (`overlays/Anchor.ts`, `@internal`): `computeAnchorPlacement` (pure: a side of an anchor rect, flipped when it doesn't fit and the other side has more room, aligned `start` / `center` / `end` and shifted inside the bounds, the space left as the max size; viewport px) and `showAnchored({ elem, anchor, side?, align?, gap?, matchAnchorWidth?, themeFrom? })`, which shows an element already in the document in the top layer (`popover="manual"`: the browser closes it on nothing, the stack does) or, without the Popover API (`hasTopLayer`; linkedom, some WebGL 2 browsers), moves it to the HUD root at `--aek-z-tooltip` with its old place's `data-aek-theme` / `data-aek-density` (a dialog's centring transform would make a fixed element inside it relative to the dialog). It sets `position: fixed`, the place (viewport px in the top layer, which ignores a mount's `contain: layout`; minus the bounds' corner in the HUD root), the max size and `data-side`, and repositions in one rAF on a scroll anywhere (a capture listener on the document: a host page's scroll moves the anchor, not a top-layer overlay) and on the window's and the bounds' resizes; its remover stops that and hides the popover (removing the element is the caller's). A top-layer overlay keeps its DOM place, so it inherits the tokens, the theme and `inert` from there. `anchor` may be a point (`AnchorPoint`, `{ x, y }` in viewport px, p805 D11: a context menu at the pointer), a box of no size there that a scroll doesn't move, with no anchor watch and no `matchAnchorWidth`; the forced theme and density come from `themeFrom` (default the anchor element; a point's overlay takes none without it).
- **Tooltips** (`overlays/Tooltip.ts`, `Tooltip.scss`, on `aekasha/ui`): `createTooltip({ anchor, text, side?, onlyWhenTruncated?, class?, attr?, id? })` returns `{ cmp, show, hide, isShown, setText }`. The anchor's `aria-describedby` gets the tooltip's id (added to the ids there, taken off by `cmp.remove()`; not while its text is the anchor's `aria-label`, an icon button's name, nor with `onlyWhenTruncated`, which shows it only while the anchor's text is cut: a cut title's whole text). It shows after `--aek-tooltip-delay` of hover (500 ms, read on the anchor; a delay, not motion, so reduced motion keeps it: its own table in the design document's motion section) and at once on a keyboard focus (`:focus-visible`: a click's focus shows none), and hides on blur, a press of the anchor, Escape (the stack's, or the anchor's own outside the HUD root), the pointer leaving (100 ms to reach the tooltip, which can be hovered: WCAG 1.4.13) and its anchor leaving the document (`onAnchorRemoved`). Its element is in the HUD root only while it shows, never in the anchor (its text would join the anchor's name), with `role="tooltip"`; `cmp.remove()` disposes of it (its anchor listeners, timers, the stack entry and the ARIA). Never interactive: that's a popover.
- **Popovers** (`overlays/Popover.ts`, `Popover.scss`, on `aekasha/ui`): `createPopover({ anchor, content, label?, side?, align?, onOpen?, onClose?, class?, attr?, id? })` returns `{ cmp, open, close, toggle, isOpen }`. A click on the trigger (Enter, Space on a button) toggles it; the trigger has `aria-haspopup="dialog"`, `aria-expanded` and `aria-controls`. Open, its element (`role="dialog"`, non-modal, `tabindex="-1"`, `aria-label` from `label`) is in the HUD root with the focus on its first focusable element (else itself); Escape closes it with the focus back on the trigger (the stack entry's `returnFocus`, so also where a click doesn't focus a button); a `pointerdown` outside it and the trigger (a capture listener on the document while open) or the focus leaving both closes it and leaves the focus there. `content` is a CMP added once, or a function built on every open and removed on close. `cmp.remove()` disposes of it.
- **Menus** (`overlays/Menu.ts`, `overlays/MenuItems.ts`, `Menu.scss`, on `aekasha/ui`; p803 D10, the APG menu button; submenus p805 D11): `createMenu({ anchor, items, label?, side?, align?, onOpen?, onClose?, class?, attr?, id? })` returns `{ cmp, open(focus?), close, toggle, isOpen }`. `items` (or a getter read on every open, so checked states and values stay the app's) are `MenuItem`s: an action (`menuitem`: `onSelect`, `icon`, `kbd` (a Kbd handle, p804 D13, drawn by `addShortcutHint` with its `aria-keyshortcuts`; the menu removes it, its submenus' too: a getter's at each close, drawn or not (`findMenuHintHandles` over the open's items), an array's with the menu), `disabled`), `type: 'checkbox'` (`menuitemcheckbox`, `checked`, `onCheckedChange`), `type: 'radio'` (a `role="group"` of `menuitemradio`s: `label`, `value`, `options`, `onValueChange`, called only for a new value), `type: 'submenu'` (`MenuSubmenuItem`: `label`, `icon`, `disabled`, `items`, any of a menu's, a submenu too; also in a group), `type: 'group'` (`role="group"` named by `aria-label`, its visible name a `::before` from `data-label`: no DOM child that isn't an item) and `type: 'separator'`. Built on each open into its element (`role="menu"`, named by `label`, else the trigger's `aria-label` or text), shown like the popover (in the HUD root, `showAnchored` with `matchAnchorWidth`, a stack entry returning the focus to the trigger, a capture `pointerdown` on the document for a press outside, a focusout leaving it and the trigger); emptied on close. The trigger gets `aria-haspopup="menu"`, `aria-expanded`, `aria-controls`; its click toggles, ArrowDown / ArrowUp open on the first / last item. In the menu the items take the real focus (`tabindex="-1"`, not `aria-activedescendant`): the arrows (wrapping), Home, End, typeahead (letters within 500 ms; one letter, or one repeated, cycles from the next item), Enter picks and closes, Space flips a checkable item and stays open (an action it picks and closes), Tab closes with the focus on the trigger; a used key is stopped, its keyup swallowed. A disabled item (`aria-disabled`) is focusable and picks nothing. The arrows' targets and the typeahead are `RovingFocus.ts`' (`getMoveTarget` with `wrap`, `createTypeahead`). **Submenus** (p805 D11): a submenu item is a `menuitem` with `aria-haspopup="menu"`, `aria-expanded` and, while open, `aria-controls`, its `__submenuMark` a CSS chevron (`aria-hidden`), kept `surface-hover` while open. Its submenu is a level of its own: an `.aekMenu[data-submenu]` (`role="menu"`, named by the item's label, id `{menu id}-{depth}`), appended next to the root, built on open and removed on close, anchored to the item (`showAnchored`, `side: 'right'`, `align: 'start'`, `gap: 0`: flipped at the bounds), with its own overlay stack entry returning the focus to its item (so Escape closes one level) and its own typeahead, listeners (capture, as the root's CMP's) and hints. ArrowRight, Enter or Space on the item opens it on its first item, a click too; ArrowLeft in it closes it back to the item; Tab and a pick close every level (deepest first, the root last with the focus back on the trigger); a disabled submenu item opens nothing. A press or the focus anywhere in any level, or in the trigger, keeps the menu. The pointer: hovering a submenu item focuses it and opens its submenu after `--aek-submenu-delay` (150 ms in `tokens.css`, a delay not scaled by motion; read on the menu at each open, default 150), the focus staying on the item; hovering another item of the level closes an open submenu at once, unless the pointer is heading for it (`MenuItems.ts`' `isInPointerPath(from, to, box)`: the move's end inside the triangle from its start to the submenu's near edge), when the submenu stays and the item under the pointer is acted on after the delay (a diagonal move across the other items). `MenuItems.ts` (`@internal`, out of `Menu.ts` for its size) builds a level's items (`buildMenuItems`), returning its `MenuEntry`s. `createMenuSurface({ items, getLabel, side?, align?, matchAnchorWidth?, isInside?, onOpen?, onClose?, onRemove?, class?, attr?, id? })` (`@internal`) is the menu without a trigger, returning `{ cmp, open({ anchor, focus?, returnFocus?, themeFrom? }), close(returnFocus?), focusItem, isOpen }`: its `anchor` an element or a point, its `returnFocus` (default what had it) the root's stack entry's; `createMenu` is it with the trigger wired (its ARIA, click and arrows, `isInside` the trigger), p805's context menu opens it at the pointer. A pick that closes closes first, then runs, so a dialog it opens returns the focus to the trigger. Hovering an item (`pointermove`) focuses it. The check marks are CSS shapes in the accent; a focused item is `surface-hover` with its ring inside. `cmp.remove()` disposes of it (the trigger's listeners and ARIA, the document listener, the stack entry, the typeahead timer).
- **Context menus** (`overlays/ContextMenu.ts`, on `aekasha/ui`; p805 D11): `createContextMenu({ target, items, label?, onOpen?, onClose?, class?, attr?, id? })` returns `{ cmp, close, isOpen }`: `createMenuSurface` opened over `target`'s descendants. `items` is an array or `(elem, source) => MenuItem[]` (`ContextMenuSource`: `'pointer'`, `'keyboard'`, `'touch'`), read at each open with the element it opens on (one menu serves a list: the row is found from the element); none opens nothing and leaves the browser's menu. `label` a string or a function of the element (default 'Context menu'). ## Forms and bindings

The fields, value editors and containers (p804, Tweakpane's replacement: the debugger moves onto them in p806), all on one binding (`{ target, key }`, `{ get, set }` or `{ value }`, D3) read by one refresh scheduler (D4), each piece its own module in `forms/`, so a form with a number field carries no colour or editor code (D12). The Hub's UI kit section's Forms and fields page (`features/ui-kit/forms/`, its `aek:covers`) is the user guide: each piece with its demo, parts, custom properties and keys.

- **The binding core** (`forms/binding/`, p804 D3-D6): `Binding.ts` (`@internal`; its `BindingSource` and `BindingChange` types are public with the first field) binds a field's value as `{ target, key }` (an object value written in place, key by key: a `THREE.Vector3` stays the instance), `{ get, set }` (`set` gets a copy it may keep), `{ value }` (held) or `{ get }` alone (`ReadonlyBindingSource`, public, Phase 4 section 1: a monitor's, or a field's with `readonly: true`; a write keeps the value until the next read), compared and copied by a `BindingValueKind` (`getPrimitiveValueKind`, `createObjectValueKind(keys, create?)`: no allocation when a read fills the kept copy; a copy is a plain object, or `create`'s, an array for a number array's indices). ## Data display

The pieces that show an app's data (p805, on `aekasha/ui`, the Hub's `features/ui-kit/data/` page): the list, the tree and the table (the collections), the graphs in `data/graphs/` and the stat tile, all in `data/` (its layout rule); the tabs, the accordion and the splitter are components (above), the context menu and the command palette overlays (The overlay layer). What the collections share (p805 D3, D4, D8): the rows are the app's objects kept by key (`getKey`, default `id`), so a refresh (`setRows` / `setItems` / `setRoots`, or `rows` as a function read on `refresh()` and on a scheduler's tick, `forms/binding/BindingScheduler.ts`' `addScheduledRefresh`) keeps a row's element, focus and selection and writes only the text that changed, and a live figure (`setCell`, `setItem`, `setNode`) writes one text node with nothing allocated; one tab stop per collection with the arrows inside (`RovingFocus.ts`), the APG pattern its mode needs (a list, a listbox, a grid; a tree; a native table, or a grid with a selection or `onRowActivate`); sorts, filters' counts, moves and lazy loads' ends read by the announcer; a context menu is the app's `createContextMenu` on the collection's `cmp.elem`, its row found by `getKeyAt`; virtual rows and reorder are values the app passes (`createVirtualRows()`, `createListReorder()`), not imports, and so is a stat tile's sparkline, so a piece without them carries none of their code. None registers anything at load, and `_engine/ui/data/` is budgeted at 0 in the first download of the `app` and `uiKit` profiles (`sbp.config.ts`); the `uiKit` profile's data window (`src/app/profiles/uiKit/uiKitEmbedData.ts`, a chunk its button's first press loads) is what a table, a list, tabs, a stat tile and a sparkline cost together. The UI kit example's inspector (`src/app/examples/uiKit/exampleUiKitInspector.ts`) uses the tree, splitter, tabs, table, stat tiles, time series, context menu and fields' menu together.

## Tokens and units

The design tokens the kit, the debugger and the Hub share (p801), in `styles/tokens.css`: plain CSS (ASCII only: a non-ASCII character makes Sass write `@charset`), so the Hub's Sass `@use`s it as is and `Tokens.test.ts` parses it. The Hub's UI kit section's Styling page (`features/ui-kit/styling/`, its `aek:covers`) is the user guide; the roles and their values are p801 D2.

- **The kit root**: every token is on the class `aekUi` (`KIT_ROOT_CLASS`, public) through `:where(.aekUi)`, never `:root` (an embed leaves the host page alone). The HUD root has it (`core/HUD.ts`), the Hub's `<html>` too, and an app puts it on a container of its own UI outside the HUD. It sets `font-size: medium` (the user's browser default, which a host's root can't change) and `font-family: var(--aek-font-sans)`; its `color-scheme` comes from the theme blocks (see Themes). `kit.scss`' `aek.base` gives it and each forced theme under it `color: var(--aek-text)` (a computed colour inherits as it is, so a forced subtree sets its own), and its controls `font: inherit; color: inherit` (p803 D5: Phase 0 found no pixel change on the debugger).
- **Units** (p801 D4): a registered length (`@property`, `inherits: true`), computed on the kit root, so it inherits as pixels and never compounds: `--aek-base` (`calc(var(--aek-ui-font-size, 0.875em) * var(--aek-ui-scale, 1))`, 14 px at the defaults). p801's second one, `--aek-rem` (10 px, the old 62.5 % root's `rem`, `@internal`), went in p806 D9 with its last users, the debugger's styles and `Viewports.module.scss`. The type and space scales are lengths from `--aek-base` (`calc(var(--aek-base) * 12 / 14)`), not `em`s, so a density can re-declare them. `--aek-ui-font-size` and `--aek-ui-scale` are public and read only on the kit root.
  - Every style is on the tokens: don't write a `rem`. `page.scss`' `body` (`1rem`) is the one `rem` left; media queries are px (one can't read a custom property, so they don't follow the UI scale).
  - Without `@property` an `em` in `--aek-base` would resolve again in every descendant: the kit root declares fixed `calc(14px * scale)` / `calc(10px * scale)` first and the computed values only inside `@supports (transition-behavior: allow-discrete)` (every browser passing it has `@property`; `@supports` can't test an at-rule). Those browsers follow the UI scale but not the browser's font size.
  - CSS has no scoped registration: the two names are on every element of a host page too, at their `initial-value`. `yarn verify:embed`'s host style check leaves out exactly the names `tokens.css` registers (`devTools/verify/CLAUDE.md`).
- **Themes** (p801 D3): dark by default, light under `prefers-color-scheme: light`, and `data-aek-theme="dark" | "light"` on any element forces its subtree (the nearest forced ancestor wins; a kit root inside a forced element declares no colours). Each theme's values are written twice (the media query, the attribute), and a token that reads another (the ring's colour, the shadows, the backdrop) is declared in each theme block, since a `var()` resolves where it's declared. Each block also sets `color-scheme` (`dark` / `light`, p803 D5), so native scrollbars and controls follow the kit's theme; `Tokens.test.ts` checks it, and counts only `--aek-*` names as roles. The kit's colours are on the roles (p803 Phase 5, from p801's inventory, §4), and the debugger's since p806.
  - The debugger's roots take its theme setting (p806 D8, `overlays/DebuggerRoot.ts`, `@internal`): `getDebuggerRootProps()` gives a root `DEBUGGER_ROOT_ATTR`, `data-aek-theme` (dark by default, light, or none for `'app'`) and the compact density, and hooks that keep it in a set while mounted, which `setDebuggerTheme(theme)` rewrites through each CMP's `updateAttr` / `removeAttr` (an `update()` then keeps it; `onCreateCmp` writes it again, for a root made before a change and mounted after). A root put in a plain element (an editor view's HUD) goes there with `appendDebuggerRoot(parent, cmp)`, which runs the mount hook an add would. The drawer, the editor drawer, the on-screen tools' rows and switch tools, and a debug window (`isDebugWindow`, the profiler's and the debug dialogs too) with its backdrop (`DraggableWindowDom.ts`' `getDebugRootProps`). The debug toaster and the scene loader follow the system: they're the kit's (Phase 5's toaster, Phase 7's loading overlay). `DebuggerRoot.test.ts` covers it.
- **Density**: `data-aek-density="compact"` on any element re-declares the type and space scales (only those) for its subtree; the debugger's roots set it (p806 D8).
- **Motion** (p801 D7): `--aek-motion-fast / -base / -slow` are `calc(Nms * var(--aek-motion, 1))`; `prefers-reduced-motion: reduce` sets `--aek-motion: 0` on the kit root, layered, so an app's own value there wins. Transitions take a duration token; a longer animation multiplies its own by `var(--aek-motion, 1)`. JS-timed ones (the toaster, the debug scene loader's fades) multiply by `core/Motion.ts`' `getMotionFactor(elem)` (public since p803 D4: the element's computed `--aek-motion`, so an app's setting stops them too). CMP's `anim` phases don't scale on their own (an app's animation can carry meaning): an app scales them with the factor.
- **Focus** (p801 D6): `:where(.aekUi :focus-visible)` in `aek.base` draws the ring from `--aek-focus-ring-width / -offset / -color`. Any unlayered style beats it: never remove `outline` in a kit or debugger style (p801 Phase 2 removed the six there were).
- **Layers** (p801 D5): `@layer aek.page, aek.tokens, aek.base, aek.components, aek.utilities;` first in `tokens.css` (`aek.page` is the full page's normalize, p804 D13: named here so either stylesheet may load first; empty in an embed and the Hub). The tokens, the ring, `kit.scss`' base rules and every kit component's styles are layered (p803 D5), with `:where()` selectors, so an app's unlayered rule always wins (the Hub's Styling page: a broad `button { … }` reaches the kit too). The debugger's own styles stay unlayered (p806 D9: a dev tool's layout survives an app's element rules).
- **Contrast** (`styles/Tokens.test.ts`, reading the file with `fs`: Vitest turns a CSS import into an empty string): the layer order first, each `@property` once with its fixed fallback, the same tokens in both themes with matching copies, a WCAG pair or a reason for every theme token (4.5 for text, the accent and the status colours on the four surfaces, 3 for `border-control` and the ring, 3 for the chart series `chart-1` to `chart-6` on `surface` and `surface-raised` (p805 D9: `CONTRAST_SERIES`, in Phase 0's order, which the design document's colour section shows in its own table); `text-disabled` exempt, `border` / `border-strong` decorative), the fonts' opt-in, and the compact density setting every type and space token and nothing else. A new role gets a pair or a reason there.
- **Fonts** (p801 D8, `fonts/`): IBM Plex Sans (variable, `wght` 100-700, normal and italic) and IBM Plex Mono (400, 500, 600, 400 italic), Latin woff2 from Fontsource 5.3.0 with both OFL licences. `fonts.css` declares the faces and, in `aek.tokens` on `.aekUi` (not `:where()`, so it beats `tokens.css`' kit root whichever loads first), puts each family in front of the default stack. The default tokens are the system stacks, so an app that doesn't opt in downloads nothing; a face is fetched only when text uses it. The `aekasha/ui/fonts` entry (`fonts/index.ts`) is `import './fonts.css'` alone: `package.json`'s `sideEffects` lists it (a build drops a side-effect-free module's stylesheet with it) and `aliases.test.ts` allows a `.css`-only entry only then. `InitEngine.ts` imports `fonts.css` (the full page), `_dbg__DebuggerGUI.ts` too (the debugger, also in a debug embed). The Hub can't load `fonts.css` (its URLs would resolve against `hub.css`), so `hub/_assets/scss/_base.scss` repeats the faces and the opt-in, and `devTools/hub/fonts.test.ts` keeps them the same.
- **Bounds in an embed** (p801 D4, closing `docs/issues/ui-kit-in-an-embed.md`): `core/Window.ts`' `getWindowSize` (`@internal`) is the HUD's containing block: the browser window, or the container `mountAekasha` sets with `setWindowBoundsElement` (its padding box and viewport position; `contain: layout` makes it the fixed elements' containing block). A position from a viewport rect subtracts the bounds' `left` / `top` (a window's open and a drag's start). The windows' default max size and the dialog's backdrop are `100%` of it; a window's `'%'` unit is of the bounds, `'vw'` / `'vh'` the browser window's, as in CSS. A bounds resize reaches the windows' clamp through `onBoundsResize` (`@internal`, p803 D4): with the first listener it attaches a `ResizeObserver` on the bounds element, or the window's `resize` without one, moves it when `setWindowBoundsElement` changes the bounds (a mount, an unmount), and stops with the last listener (the windows keep theirs). The `uiKit` embed profile (`src/app/profiles/uiKit/`, its scene `uiKitEmbed`) opens a window with a kit button and its tooltip, a second button that opens a dialog with a small form (opened at load, the dialog took a host page's focus as it mounted: the Hub's UI kit page shows it live, p803 Phase 8; the form, p804 D12, a property grid of five fields bound to the box, is a module the dialog's first open imports, so a build gives it its own chunk), a third button that opens a data window (p805 D13: tabs of a table, a list and a stat tile, a module of its own too; `verify:embed` doesn't open it), and a toast, and `yarn verify:embed` checks them, after clicking the button and the form's select's trigger, at a 16 px and a 62.5 % host root (`devTools/verify/CLAUDE.md`). The scene's dialog is `closeOnEscape`: Escape on the host page leaves it open, Escape inside it closes it (p803 D7). The list overflows the dialog there (the top layer), and the check reads its last option as shown. The toast's text colour and the buttons' font are the kit's (p803 D5's kit root colour and controls' reset), and the check also counts the host head's `<style>` elements before and after the mount: the kit writes none (Phase 5 section 4).
