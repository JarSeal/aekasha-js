Notes for the UI kit (`src/_engine/ui/`, `aekasha/ui`: CMP, the HUD root, the draggable windows, dialogs, the drop-down, toasters, icons, the overlay layer with tooltips and popovers, the styles, and the design tokens, units and fonts); the root `.claude/CLAUDE.md` keeps the project-wide rules, commands and workflow.

## UI kit

The DOM UI the app's HUD and the debug tools are built from, public on `aekasha/ui` (p617 D6). The Hub's UI kit page is the user guide, and its example scene (`src/app/examples/uiKit/`) builds an app HUD from every piece. p800 restyles the kit and adds components; until then a change here keeps its look.

The layout (p803 D2, `devTools/layout/layoutRules.ts`' rule per folder, so a module directly in `ui/` fails `layout.test.ts`): `core/` (CMP, the HUD root, the bounds, motion, the icons), `components/` (one module per component, its stylesheet and test next to it), `overlays/` (the windows and dialogs in `windows/`, the toaster, and the overlay layer: the stack, the focus trap, the anchor, the tooltip and the popover), `forms/` (the drop-down), `styles/`, `fonts/` and `testing/` (the tests' shared helpers). Only the entry `index.ts` and this file sit directly in `ui/`. A piece with more than one module gets its own folder (the windows).

- **CMP** (`core/CMP.ts`; its types in `core/CMPTypes.ts`, the animation chain in `core/CMPAnim.ts`, which writes the CMP through its methods and imports only the types): `CMP(props, wrapper?, wrapperProps?)` makes an element from its props (`tag`, `text`, `html`, `class`, `style`, `attr`, the `on*` listener props and `listeners`, `anim`, `onCreateCmp` / `onRemoveCmp`) and returns its handle, `CMPHandle` (`add`, `remove`, `update`, `updateText`, `updateClass`, `updateStyle`, `updateAttr`, `focus`, …). `classes(...)` joins class arguments.
  - It's in the DOM once it's added under a CMP that is: an app's UI goes under the HUD root (`getHUDRootCMP().add(…)`). The one root is the CMP made with `attach` (the boot's HUD root): a second one throws, and so does a taken id. A generated id is a counter (`aekCmp_N`).
  - Templates: a CMP's `toString()` is a `<cmp>` placeholder, so another CMP's `html` places it (`` html: () => `<h2>${star} Scores</h2>` ``). The parent's `update()` makes its template children again, so an `html` that names them is a function. `html` is raw HTML: user text goes in `text`, or through the root's `settings.sanitizer` (`sanitize`, `sanitizeAll`).
  - Props are copied once, at create and at `update()` (`style` and `attr` too, so a style constant several CMPs share is never written). The update methods write that copy in place, with no allocation per call (a HUD value updated every frame), and the next `update()` keeps what they set.
  - `onCreateCmp` runs once when the CMP is mounted (added, attached, or put in place of its placeholder by its parent's `html`) and after each `update()`; `onRemoveCmp` after `remove()` has removed its children, listeners, timers and element. Per-CMP state kept in a module map is cleaned up there.
  - Every listener is a capture listener (a `listeners` entry is added with `{ capture: true, ...options }`): a parent's `onClick` runs before its child's, and a child's `stopPropagation()` doesn't stop it.
  - A style key that is a custom property (`--x`) goes through `setProperty` / `removeProperty`; `null` removes a style.
- **The HUD root** (`core/HUD.ts`): `createHudRoot({ slot? })` (p803 D4) makes it, a fixed, zero-size kit root over the canvas in place of `slot` or the page's `#hudRoot` / `#guiContainer`, and returns its handle. The boot calls it with a mount's slot in its container (whose `contain: layout` makes the HUD's fixed elements relative to the container) or none; a page without the engine calls it itself (see Outside the engine). One per page: a second call throws, naming the boot. `hasHudRoot()` says whether it exists, `getHUDRootCMP()` throws before. Each child places itself. In an editor view only the root's direct children with `KEEP_IN_VIEWS_CLASS` stay visible (Views, `src/_engine/kernel/render/CLAUDE.md`).
- **Draggable windows** (`overlays/windows/`: `DraggableWindow.ts` (the stacks, the DOM build, the hooks and the public functions, over 800 lines with its header saying why), `DraggableWindowTypes.ts`, `DraggableWindowStore.ts` (config resolution, LS, the kinds' geometry), `DraggableWindowGeometry.ts` (styles, clamps, fits, cascade) and `DraggableWindowDrag.ts`, none of which imports `DraggableWindow.ts`; `DraggableWindow.module.scss`):
  - `openDraggableWindow({ id, title, content, … })` opens a window, or reopens and updates the one with its id. `closeDraggableWindow` keeps its state (a reopen restores its layout), `removeDraggableWindow` drops it. Two layers: the app's windows, and the debug windows (`isDebugWindow`) above them, opened only in the debug env (`showInProdTest`: prodTest too).
  - An edit window per entity is a window kind. Register the kind once with `registerDraggableWindowKind(kind, { content, onClose, sceneTargetResolver, keepInViews })`, before the boot restores the saved windows (its step after the app's `start`): in `start` or a feature's install, or at a `_dbg__` module's load (anywhere else a registration at load is a module side effect). It also covers the windows restored from LS; a single window uses `registerDraggableWindow(id, …)`. Open a window with `kind` and `id: getKindWindowId(kind, key)`, from a list row through `toggleDraggableWindow` (open, bring to front, close when on top), and select the rows from `getDraggableWindowsOfKind`. Rebuild one with `updateDraggableWindow(id)`, all with `updateDraggableWindowsOfKind(kind)`, and keep per-window module state in a map cleaned up in the content's `onRemoveCmp`. Double-clicking a header fits the window to the screen (`fitDraggableWindowToScreen`), and the Debug tools tab's "Center and fit all windows" fits them all (`fitAllDraggableWindowsToScreen`).
  - LS: the `saveToLS` windows and the kinds' geometry are in `AEK_popupWindows`, written on finished changes and restored by the boot's after-start hook; a restored window's content comes from its registered function, which is why registering comes first. The format is unchanged since before p617's split (`DraggableWindow.test.ts`' round trip).
  - Scene loads: at a load's start a `removeOnSceneChange` window is removed, and a `closeOnSceneChange` one closes, unless its kind has a `sceneTargetResolver`: then it's torn down and rebuilt after the `entered` hooks when the resolver finds its target in the next scene (closed otherwise, and after a failed load, at `loadSettled`).
  - The kernel names it uses (p617 D7, the only ui → kernel imports the layout check allows, `devTools/layout/layout.ts`' `UI_KERNEL_HOOKS`): `addSceneHooks`, `addBootAfterStartHook`, added on the windows' first use, never at load, and `Config.ts`' env flags (and `AppConfig.draggableWindows`, the deprecated fallback for a content function, until 6.0.0). None of them imports anything heavy. A resize reaches the windows' clamp through `core/Window.ts`' `onBoundsResize` (p803 D4), not the main loop's resizers: the main loop brings three, the renderer and both workers into any bundle that imports it, so no kit module may (the Hub's `scripts.test.ts` fails on a kernel module outside `UI_KERNEL_HOOKS`).
  - A window's `icon` is a registered icon's name (see Icons).
- **Dialogs** (`overlays/windows/DialogWindow.ts`): `openDialog` is a window centred over a backdrop that doesn't move, resize or collapse, reset on every open. It takes the focus (the window's first focusable element) and pushes a modal entry on the overlay stack, which Escape inside the HUD closes with `closeOnEscape` and otherwise stops at; however it closes, its entry goes in the window's unmount hook (`onDraggableWindowUnmount`, `@internal`, run before its DOM goes, so the focus is still in it) and the focus returns to the opener. A reopen keeps the first opener and goes on top. A dialog rebuilt by a scene load's `sceneTargetResolver` has no entry (dialogs are `removeOnSceneChange` in practice). No `inert`, trap or modal ARIA until p803 Phase 5.
- **The drop-down** (`forms/DropDown.ts`, `forms/DropDown.scss`): `createDropDown` returns `{ cmp, open, close, toggle, isOpen, refresh }`; add its `cmp` where it goes. Keyboard, focus and ARIA are its own, and the list's keys reach no key binding. The open list pushes an overlay stack entry (its Escape is the stack's under the HUD root; its own Escape handles a list outside it), and a pick, Escape or Tab returns the focus to what had it at the open (the trigger, opened by its keys); a focusout close leaves the focus where it went. The list is anchored to the trigger (`showAnchored`, see The overlay layer): in the top layer, on `placement`'s side when it fits (else the other), inside the HUD's bounds and as tall as the space left (no `40vh`, nothing clips it). Its highlighted option has `data-active`, which shows the ring while the list is `:focus-visible` (the list keeps the focus for `aria-activedescendant`, p803 D7), and `yarn verify:ui`'s outline check reads that option. The trigger's label re-reads `value` after `onChange` returns (p617 Phase 6); `refresh()` is for a change made elsewhere.
- **Toasters** (`overlays/Toaster.ts`): `createToaster` returns the toaster's CMP (add it under the HUD root) and puts its CSS in the head; the first one made is the default for `addToast` (`setAsDefaultToaster` moves it). One timer per toast at a time; `removeToaster` clears its toasts' timers and its styles. The engine makes a toaster only in the debug env (the debug toaster, kept in every view), so an app that shows toasts makes its own.
- **Icons** (`core/icons/`): `registerIcon(name, svg)` and `getSvgIcon(name, size?)`; the built-ins are named SVG strings (`BuiltInIcons.ts`, from `icons/svg/`, Bootstrap Icons' licence). The boot registers them all (`registerBuiltInIcons`, about 10 kB gzip) only in the debug env and prodTest: a production app registers the ones it shows, or gets `??` and a warning.
- **Styles** (`styles/`): `kit.scss` (p803 D4) holds the kit's global styles: the design tokens (`tokens.css`, `@use`d: see Tokens and units) with the ring, `aek.base`'s kit root `color` and controls' reset (D5), and `.uiIcon` (unlayered until Phase 5's `.aekIcon`). `HUD.ts` and every kit module with styles import it (`DraggableWindow.ts`, `Toaster.ts`, `DropDown.ts`, `SvgIcon.ts`; a new component too, D2), so `aekasha/ui` brings it without the boot and Vite emits one copy. No stylesheet `@use`s it (a second copy): a stylesheet that needs the tokens reads them as custom properties. `index.scss`, which `Boot.ts` imports in every build, holds only the editor views' HUD rule. Neither has anything on an element a host page owns, nor of the debug tools (each debug module imports its own, p617 S1). `page.scss` (`InitEngine` only): normalize and the `*` and `body` rules, the page's `#mainCanvas` and `#guiContainer`; no root size and no font (both are the kit root's). A component's styles come with its module (`DraggableWindow.module.scss`, `DropDown.scss`, the toaster's injected CSS). `variables.scss` is mostly the debugger's colours (p800's).
- Tests (Node, linkedom; `testing/KitDom.ts`' `stubKitDomAsync` in `beforeAll` (p803 D11) for the tests that need focus or the event order: the browser's capture, target and bubble order (linkedom calls every listener from the target up, so a capture listener's `stopPropagation()` wouldn't keep the event from the target), `activeElement`, the focus events, `[inert]` refusing focus, `getClientRects`, plus `dispatchKey` and `countListeners` (a piece's disposal check); the others still stub linkedom per file): `OverlayStack.test.ts`, `FocusTrap.test.ts`, `CMP.test.ts`, `HUD.test.ts` (one root, in its slot, a kit root), `Window.test.ts` (`onBoundsResize`'s sources), `DraggableWindow.test.ts` (the hooks added on first use and never at load, the reopen rules, kinds, scene loads, the LS round trip), `DraggableWindowGeometry.test.ts` (the bounds: the window, a mount's container), `DialogWindow.test.ts`, `Toaster.test.ts`, `DropDown.test.ts`, `Motion.test.ts`, and `styles/Tokens.test.ts` (see Tokens and units). linkedom takes `style['--x']`, which browsers ignore, so the custom-property path is checked in a browser only. In a browser, `yarn verify:ui` (p803 D11, `devTools/verify/CLAUDE.md`) runs the component library's demos through axe-core, their keyboard scripts and their screenshots in both themes and densities: a piece's change shows there.
- **Outside the engine** (the Hub's component library, `project/aekasha/components/`, p802 D9: `hub/CLAUDE.md`'s Project section, `devTools/hub/CLAUDE.md`'s Scripts): the kit's pieces run on a page with no boot. Its script makes the HUD root with `createHudRoot` (which brings `kit.scss`) and registers the built-in icons, both from `aekasha/ui`. The Hub's script build resolves one engine module to a stand-in (`hub/_assets/ts/_kit/`): `utils/LocalAndSessionStorage.ts` (in memory: the dev Hub shares the app's origin, and the windows write all of `AEK_popupWindows` on every finished change). A new storage function fails that build until the stand-in exports it. The other hooks are added and never run, and the env flags stay false (no debug window). The page's "Used by" lists read the kit's functions from `src/`, so a renamed public function goes into `devTools/hub/generated/components.ts`' `COMPONENT_USES`.
- **Left for p803** (found by the component library, p802 Phase 4; the embed's are under Bounds in an embed): the kit sizes no icon (`.uiIcon`'s SVG fills its box, and `'small'` adds `smallIcon`, which only the on-screen tools style); the window header clips its title's descenders; a long toast runs past its `toastMaxHeight` (100 px by default) under its close button. Both themes and both densities look the same on the kit until p803 maps its colours (`variables.scss`) and sizes (`--aek-rem`) to the tokens.
- Waiting for engine 6.0.0 (p622): the `T`-prefixed type names' deprecated aliases (p803 D3: `TCMP` for `CMPHandle`, `TProps` for `CMPProps`, …, `TDropDown` for `DropDown`; at the end of `core/CMPTypes.ts` and next to `DropDown`), `AppConfig.draggableWindows`, `AddToastResponse.timeout` and `CMPSettings.doCheckIsInDom`.

## The overlay layer

Every open overlay (a dialog, a drop-down's list, a tooltip, a popover; p803 D7) is an entry of one stack: Escape pressed inside the HUD goes to the top entry alone, a closed entry gives the focus back, and an anchored overlay shows in the browser's top layer, so no window clips it. The Hub's UI kit page (Dialogs, Tooltips and popovers) is the user guide.

- **The stack** (`overlays/OverlayStack.ts`, `@internal`): every open overlay pushes `{ elem, close?, returnFocus?, inert?, keep?, isDebug? }` and gets its remover. One capture `keydown` listener on the HUD root's element, added on the first push and kept, takes Escape for the top entry still in the document (`close`, or nothing for an entry without one) and stops it, so the piece's own listeners, the input system's (bubble phase on the window) and anything else miss it; `swallowNextKeyUp` (a one-off capture listener on the window, where the keyup goes after a close moved the focus) takes its keyup. A key pressed outside the HUD root (an embed's host page) never reaches it. The remover gives the focus back to `returnFocus` (default: what had it at the push) when the focus is in the overlay or nowhere, unless called with `false` (a focusout close). An `inert` entry, the top one, sets `inert` on the HUD root's other children (not its own, its `keep` or the entries above it; an app's entry spares the children with `DEBUGGER_ROOT_ATTR`, `data-aek-debugger`), removed with it; the app's own `inert` is never touched, and a child added while it's open stays live.
- **The focus trap** (`overlays/FocusTrap.ts`, `@internal`): `trapFocus(elem)` (Tab and Shift+Tab wrap, the dialog's from Phase 5) and `getFocusableElements` / `getFirstFocusable` (by selector, rendered only), which the windows use.
- **The anchor** (`overlays/Anchor.ts`, `@internal`): `computeAnchorPlacement` (pure: a side of an anchor rect, flipped when it doesn't fit and the other side has more room, aligned `start` / `center` / `end` and shifted inside the bounds, the space left as the max size; viewport px) and `showAnchored({ elem, anchor, side?, align?, gap?, matchAnchorWidth? })`, which shows an element already in the document in the top layer (`popover="manual"`: the browser closes it on nothing, the stack does) or, without the Popover API (`hasTopLayer`; linkedom, some WebGL 2 browsers), moves it to the HUD root at `--aek-z-tooltip` with its old place's `data-aek-theme` / `data-aek-density` (a dialog's centring transform would make a fixed element inside it relative to the dialog). It sets `position: fixed`, the place (viewport px in the top layer, which ignores a mount's `contain: layout`; minus the bounds' corner in the HUD root), the max size and `data-side`, and repositions in one rAF on a scroll anywhere (a capture listener on the document: a host page's scroll moves the anchor, not a top-layer overlay) and on the window's and the bounds' resizes; its remover stops that and hides the popover (removing the element is the caller's). A top-layer overlay keeps its DOM place, so it inherits the tokens, the theme and `inert` from there.
- **Tooltips** (`overlays/Tooltip.ts`, `Tooltip.scss`, on `aekasha/ui`): `createTooltip({ anchor, text, side?, class?, attr?, id? })` returns `{ cmp, show, hide, isShown, setText }`. The anchor's `aria-describedby` gets the tooltip's id (added to the ids there, taken off by `cmp.remove()`). It shows after `--aek-tooltip-delay` of hover (500 ms, read on the anchor; a delay, not motion, so reduced motion keeps it: its own table in the design document's motion section) and at once on a keyboard focus (`:focus-visible`: a click's focus shows none), and hides on blur, a press of the anchor, Escape (the stack's, or the anchor's own outside the HUD root), the pointer leaving (100 ms to reach the tooltip, which can be hovered: WCAG 1.4.13) and its anchor leaving the document (`onAnchorRemoved`). Its element is in the HUD root only while it shows, never in the anchor (its text would join the anchor's name), with `role="tooltip"`; `cmp.remove()` disposes of it (its anchor listeners, timers, the stack entry and the ARIA). Never interactive: that's a popover.
- **Popovers** (`overlays/Popover.ts`, `Popover.scss`, on `aekasha/ui`): `createPopover({ anchor, content, label?, side?, align?, onOpen?, onClose?, class?, attr?, id? })` returns `{ cmp, open, close, toggle, isOpen }`. A click on the trigger (Enter, Space on a button) toggles it; the trigger has `aria-haspopup="dialog"`, `aria-expanded` and `aria-controls`. Open, its element (`role="dialog"`, non-modal, `tabindex="-1"`, `aria-label` from `label`) is in the HUD root with the focus on its first focusable element (else itself); Escape closes it with the focus back on the trigger (the stack entry's `returnFocus`, so also where a click doesn't focus a button); a `pointerdown` outside it and the trigger (a capture listener on the document while open) or the focus leaving both closes it and leaves the focus there. `content` is a CMP added once, or a function built on every open and removed on close. `cmp.remove()` disposes of it.
- **Styles**: both new pieces' stylesheets are on the tokens and in `@layer aek.components` with `:where()` selectors (p803 D5: an app's unlayered rule wins), and read their max size from `showAnchored`'s `--aek-anchor-max-width` / `-height` (the tooltip caps its width at 32ch). The windows, the drop-down and the toaster move onto the tokens and the layer in Phase 5.

## Tokens and units

The design tokens the kit, the debugger and the Hub share (p801), in `styles/tokens.css`: plain CSS (ASCII only: a non-ASCII character makes Sass write `@charset`), so the Hub's Sass `@use`s it as is and `Tokens.test.ts` parses it. The Hub's UI kit page (Styling) is the user guide; the roles and their values are p801 D2.

- **The kit root**: every token is on the class `aekUi` (`KIT_ROOT_CLASS`, public) through `:where(.aekUi)`, never `:root` (an embed leaves the host page alone). The HUD root has it (`core/HUD.ts`), the Hub's `<html>` too, and an app puts it on a container of its own UI outside the HUD. It sets `font-size: medium` (the user's browser default, which a host's root can't change) and `font-family: var(--aek-font-sans)`; its `color-scheme` comes from the theme blocks (see Themes). `kit.scss`' `aek.base` gives it and each forced theme under it `color: var(--aek-text)` (a computed colour inherits as it is, so a forced subtree sets its own), and its controls `font: inherit; color: inherit` (p803 D5: Phase 0 found no pixel change on the debugger).
- **Units** (p801 D4): two registered lengths (`@property`, `inherits: true`), computed on the kit root, so they inherit as pixels and never compound: `--aek-base` (`calc(var(--aek-ui-font-size, 0.875em) * var(--aek-ui-scale, 1))`, 14 px at the defaults) and `--aek-rem` (`--aek-base / 1.4`, 10 px: the old 62.5 % root's `rem`). The type and space scales are lengths from `--aek-base` (`calc(var(--aek-base) * 12 / 14)`), not `em`s, so a density can re-declare them. `--aek-ui-font-size` and `--aek-ui-scale` are public and read only on the kit root.
  - The kit's and the debugger's existing styles are `calc(N * var(--aek-rem))` (p801 Phase 2's conversion of every `Nrem`, the toaster's CSS and `_dbg__Assets.ts`' inline styles included): they look as they did at the defaults, follow the browser's font size and the UI scale, and ignore the host's root. `--aek-rem` is `@internal` (not in the Hub's guide); p803 / p806 replace it with the scale tokens as they restyle, and it goes with its last user. Don't write a new `rem` or `--aek-rem`: a new style uses the tokens. `page.scss`' `body` (`1rem`) is the one `rem` left; media queries are px (one can't read `--aek-rem`, so they don't follow the UI scale).
  - Without `@property` an `em` in `--aek-base` would resolve again in every descendant: the kit root declares fixed `calc(14px * scale)` / `calc(10px * scale)` first and the computed values only inside `@supports (transition-behavior: allow-discrete)` (every browser passing it has `@property`; `@supports` can't test an at-rule). Those browsers follow the UI scale but not the browser's font size.
  - CSS has no scoped registration: the two names are on every element of a host page too, at their `initial-value`. `yarn verify:embed`'s host style check leaves out exactly the names `tokens.css` registers (`devTools/verify/CLAUDE.md`).
- **Themes** (p801 D3): dark by default, light under `prefers-color-scheme: light`, and `data-aek-theme="dark" | "light"` on any element forces its subtree (the nearest forced ancestor wins; a kit root inside a forced element declares no colours). Each theme's values are written twice (the media query, the attribute), and a token that reads another (the ring's colour, the shadows, the backdrop) is declared in each theme block, since a `var()` resolves where it's declared. Each block also sets `color-scheme` (`dark` / `light`, p803 D5), so native scrollbars and controls follow the kit's theme; `Tokens.test.ts` checks it, and counts only `--aek-*` names as roles. The kit's and the debugger's colours aren't on the roles yet (p801 D1): p803 / p806 map them from p801's inventory (§4).
  - The debugger forces `data-aek-theme="dark"` on its roots until p806 gives it a theme setting (p803 D6): the drawer, the editor drawer, the on-screen tools' rows and switch tools, and a debug window (`isDebugWindow`, the profiler's too) with its backdrop (`DraggableWindow.ts`' `getThemeAttr`). So on a light system a debug window's kit frame doesn't turn light around the debugger's dark panels, and their text and native controls stay dark-themed. The debug toaster and the scene loader follow the system: they're the kit's (Phase 5's toaster, Phase 7's loading overlay).
- **Density**: `data-aek-density="compact"` on any element re-declares the type and space scales (only those) for its subtree; the debugger opts in in p806.
- **Motion** (p801 D7): `--aek-motion-fast / -base / -slow` are `calc(Nms * var(--aek-motion, 1))`; `prefers-reduced-motion: reduce` sets `--aek-motion: 0` on the kit root, layered, so an app's own value there wins. Transitions take a duration token; a longer animation multiplies its own by `var(--aek-motion, 1)`. JS-timed ones (the toaster, the debug scene loader's fades) multiply by `core/Motion.ts`' `getMotionFactor(elem)` (public since p803 D4: the element's computed `--aek-motion`, so an app's setting stops them too). CMP's `anim` phases don't scale on their own (an app's animation can carry meaning): an app scales them with the factor.
- **Focus** (p801 D6): `:where(.aekUi :focus-visible)` in `aek.base` draws the ring from `--aek-focus-ring-width / -offset / -color`. Any unlayered style beats it: never remove `outline` in a kit or debugger style (p801 Phase 2 removed the six there were).
- **Layers** (p801 D5): `@layer aek.tokens, aek.base, aek.components, aek.utilities;` first in `tokens.css`. Only the tokens, the ring and `kit.scss`' base rules are layered; the components' styles stay unlayered until p803 / p806 restyle them (layered now, an app's broad unlayered rules would beat them).
- **Contrast** (`styles/Tokens.test.ts`, reading the file with `fs`: Vitest turns a CSS import into an empty string): the layer order first, each `@property` once with its fixed fallback, the same tokens in both themes with matching copies, a WCAG pair or a reason for every theme token (4.5 for text, the accent and the status colours on the four surfaces, 3 for `border-control` and the ring; `text-disabled` exempt, `border` / `border-strong` decorative), the fonts' opt-in, and the compact density setting every type and space token and nothing else. A new role gets a pair or a reason there.
- **Fonts** (p801 D8, `fonts/`): IBM Plex Sans (variable, `wght` 100-700, normal and italic) and IBM Plex Mono (400, 500, 600, 400 italic), Latin woff2 from Fontsource 5.3.0 with both OFL licences. `fonts.css` declares the faces and, in `aek.tokens` on `.aekUi` (not `:where()`, so it beats `tokens.css`' kit root whichever loads first), puts each family in front of the default stack. The default tokens are the system stacks, so an app that doesn't opt in downloads nothing; a face is fetched only when text uses it. The `aekasha/ui/fonts` entry (`fonts/index.ts`) is `import './fonts.css'` alone: `package.json`'s `sideEffects` lists it (a build drops a side-effect-free module's stylesheet with it) and `aliases.test.ts` allows a `.css`-only entry only then. `InitEngine.ts` imports `fonts.css` (the full page), `_dbg__DebuggerGUI.ts` too (the debugger, also in a debug embed). The Hub can't load `fonts.css` (its URLs would resolve against `hub.css`), so `hub/_assets/scss/_base.scss` repeats the faces and the opt-in, and `devTools/hub/fonts.test.ts` keeps them the same.
- **Bounds in an embed** (p801 D4, closing `docs/issues/ui-kit-in-an-embed.md`): `core/Window.ts`' `getWindowSize` (`@internal`) is the HUD's containing block: the browser window, or the container `mountAekasha` sets with `setWindowBoundsElement` (its padding box and viewport position; `contain: layout` makes it the fixed elements' containing block). A position from a viewport rect subtracts the bounds' `left` / `top` (a window's open and a drag's start). The windows' default max size and the dialog's backdrop are `100%` of it; a window's `'%'` unit is of the bounds, `'vw'` / `'vh'` the browser window's, as in CSS. A bounds resize reaches the windows' clamp through `onBoundsResize` (`@internal`, p803 D4): with the first listener it attaches a `ResizeObserver` on the bounds element, or the window's `resize` without one, moves it when `setWindowBoundsElement` changes the bounds (a mount, an unmount), and stops with the last listener (the windows keep theirs). The `uiKit` embed profile (`src/app/profiles/uiKit/`, its scene `uiKitEmbed`) opens a window, a dialog with an open drop-down and a toast, and `yarn verify:embed` checks them at a 16 px and a 62.5 % host root (`devTools/verify/CLAUDE.md`). The scene's dialog is `closeOnEscape`: Escape on the host page leaves it open, Escape inside it closes it (p803 D7). The list overflows the dialog there (the top layer), and the check reads its last option as shown. Left for p803: the toast's text colour and the buttons' font from the host.
