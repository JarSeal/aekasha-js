Notes for the debug tooling (the debugger framework in `src/_engine/debug/`, its public entry points and `_dbg__` modules; a kernel area's or a feature's own debug modules in its `debug/` subfolder): the Debug system's detail, moved from the root, where its dual-layer pattern stays; the root `.claude/CLAUDE.md` keeps the project-wide rules, commands and workflow.

## Debug system

- The public API (`aekasha/debug`, `debug/index.ts`; p618): drawer and profiler tabs, lists, toasts, stats and GPU memory sources, `markDebugHelper`, entity window openers, undo / redo, the dev files client and `loadDebugModuleAsync`, with the pane item types `DebuggerTabDef` names. Every other export of a thin module is `@internal`, its summary naming its user (the boot, a debug key, the on-screen tools). The dev files protocol's route, header and meta constants, `AEK_GATHER_EVENT`, three protocol bodies and the test bridge's three result types are on the entry only for `devTools/` (which imports them by path): `@deprecated`, leaving it in engine 6.0.0 (p622), as do `createDebuggerTab`'s second parameter and `DebugGUIOpts`. The pane types' Tweakpane fields (a binding's passed-through params and `onCreate`'s `BindingApi`, `custom`'s `Pane | FolderApi`) are Tweakpane's: p800 replaces it, a major.
- Registrations work at any time (p618 B1, B4): the thin module keeps what's registered before its implementation loads and hands it over in its `register*` (the boot's debug step, after the features' installs). `UndoRedo.ts` keeps the undo handlers (the implementation reads them, `_getUndoRedoActionHandler`), `DebuggerGUI.ts` and `Profiler.ts` the tabs created early (pending, in creation order; `remove*Tab` drops a pending one), `Profiler.ts` the stats sources and entity window openers, `GPUMemory.ts` the GPU memory sources. A new public registration follows the pattern, never `useDebug(ref)?.register(…)`, which drops a call made before the load without a word.
- The loader (`kernel/config/DebugModules.ts`): `loadDebugModuleAsync` (public; debug env, prod test mode too with `includeInProdTestMode`, a failed import logged) and `useDebug` (`@internal`, how a thin module calls its loaded `_dbg__` module), plus `loadDebugModule`, the sync form, for the three engine callers that can't await (`Camera.ts`' debug camera, `PhysicsQueryStats.ts`' ray helpers, `_dbg__OnScreenTools.ts`' physics draw). An app's own debug module needs neither: `if (IS_DEBUG_ENV) await import('./_dbg__x')` folds the same way (the debug tab example); the loader adds the prod test opt-in and the log. Either way the `import()` sits inside the call or the `if`.
- Placement (p608 D4, p618 D5 / D7): a kernel area's or a feature's thin debug wrapper sits in its own public module (`kernel/assets/AssetsAPI.ts`' `createAssetsDebugGUI`, `features/postfx/PostFX.ts`' PostFX profiler functions next to `createPostFXDebugGUI`, `Renderer.ts`' `createRendererDebugGUI`), not in `debug/`. A debug-only module has the `_dbg__` name even when only a `_dbg__` module imports it (`debug/_dbg__SceneHelpers.ts`, the Debug tools tab's grid and axes; `debug/_dbg__PercentagePie.ts`, the ray cast stats' pie). `initECSStressTest` (on `aekasha`, a debug-only stress test) is the thin `kernel/ecs/ECSStressTest.ts`, which loads `kernel/ecs/debug/_dbg__ECSStressTest.ts` (the ECS tab's benchmark imports it directly). Each debug file over 800 lines or with a function over 150 has a header line saying why it isn't split (p618 D8): the Tweakpane panels and the editors are p800's to replace; the physics wireframes and the character gizmos were reviewed for correctness only, to be split when next reworked.
- About Ækasha dialog (`debug/_dbg__About.ts`, `openAboutDialog()`): the Æ button left of undo / redo (`_dbg__OnScreenTools.ts`) opens it. It shows `PROJECT_METADATA` (versions, `packages`, `buildTools`, `build`: commit and time, read from git and package.json by `getProjectMetadata` in `devTools/projectMetadata.ts`, which `vite.config.ts` and the Hub share) the runtime (renderer, GPU, browser) and physics (the backends, thread, transport, SharedArrayBuffer, stepping settings, body counts), with a "Copy info" button for bug reports. A new runtime package shows up by itself (`dependencies`), and a new physics backend through its `ENGINES` entry's `name` and `packageName`; a new runtime fact goes in its Runtime or Physics section.
- The other default debug keys (`debug/DefaultDebugKeyBindings.ts`, rebindable through `AppConfig.debugKeys`; p610 Phase 5): action maps in the `DEBUG` context (`aek:debugKeys`, the CONFIG.ts keys that add a key in `aek:appDebugKeys`, `aek:prodTestKeys`), so they run in every view and while the loop is paused, and stop during a scene load. The definitions stay `KeyUpDownBinding` data: a `KEY_DOWN` key runs at its action's `onPressed`, a `KEY_UP` key at its `onReleased`, each only for its own key's event (`runDebugKey`: not an edge a modifier made, a blur's release, a key-repeat or a replay), then by its `sceneId`, `enabledInDebugCam`, `caseInsensitive` and `yieldToOtherBindings`. The maps prevent the default of their keys' keydowns outside a text field (key-repeats included). The engine keys' chords are reserved (`markChordReserved` with the map's id), so an app key binding or action map binding one warns (`warnIfKeyChordReserved`). The keys: F1 debug camera, u / i the Debug key shortcuts dialog's App / Aekasha tab, o / p the on-screen camera / scene dropdown (`createDropDown` in `ui/DropDown.ts`: an in-page list, not a native select, so Escape cancels; its default styles in `DropDown.scss` are in `:where()`, so any class overrides them), F5 play in prod test mode, F6 main loop, F7 app loop pause, F8 profiler window, F9 env ball, F10 axes gizmo. F1 (and the on-screen camera switch) and F6/F7 and the gizmo keys show a toast (`addDebugToast` in `debug/DebuggerGUI.ts`, a no-op before the debug toaster exists); with the main camera active, a gizmo key on a hidden gizmo also turns on its "in main camera" option. Production test mode has F5 (stop), F6, F7 (no toasts) and F8 (when the profiler is enabled there), which give way to an app key binding or active action map of the same key (`yieldToOtherBindings`: `isKeyEventTakenByBindings`, `isKeyEventInActiveMaps`). The Debug tools tab's "Debug key shortcuts" buttons open a dialog (`debug/_dbg__DebugKeyShortcuts.ts`) listing the app's key bindings and action maps' actions for the current scene and every engine key by `category` (the definitions' field, joined to the map's action by id), with what CONFIG.ts or app code changed about it (the map's live bindings: rebound, unbound, disabled); give a new default key a `category`. It opens with `closeOnEscape` (an `openDialog` opt-in, `ui/DialogWindow.ts`): while such a dialog is open, Escape only closes the topmost one and no key binding or other Escape listener gets the press (its keyup included).
- Debug assets (p611 Phase 2): Rollup loads every `import()`, and Vite emits a `?url` (or `new URL`) file when it loads the module naming it, before tree-shaking, so a debug module's asset ships in `dist/` unless the `import()` that reaches it sits inside `if (__AEK_DEBUG__) { … }` or `__AEK_DEBUG__ ? … : null` (an `import()` in `loadDebugModuleAsync`'s closure, or after `if (!__AEK_DEBUG__) return`, still emits). So the 3D symbols' `?url` imports live in `debug/symbols/_dbg__Symbols.ts`, which `load3DSymbols` loads with `__AEK_DEBUG__ ? await loadDebugModuleAsync(() => import('./_dbg__Symbols')) : null`. `yarn verify:baselines` fails on a debug asset in a production build (`devTools/verify/CLAUDE.md`).
- Character debugging: the feature's own (`features/character/debug/`), in `src/_engine/features/character/CLAUDE.md`.
- Test bridge (`debug/TestBridge.ts` → `debug/_dbg__TestBridge.ts`, `_DONE_p601` Phase 2): `window.__AEK_TEST__`, installed with `?aekTest=true` in the debug env and prod test mode (never in a production build), from `InitEngine` right before the app's start callback, so it sees the first load. It's what `yarn verify:scenes` drives: `whenSceneReady()` (the first load finished, physics hold released, two frames; reports the `backend`), `whenProbeDone({ freeze? })` (the probe's report through `onPhysicsProbeReport`; `freeze: true` freezes in the report's own frame), `freeze()` (pins physics interpolation to the newest snapshot for two frames, `setPhysicsInterpolationPinnedToNewest`, then pauses the app and master loops and the day-night cycle), `snapshot({ width, height })` (`takeSnapshotAsync`, a byte-exact PNG, base64) and `getCharacterPaths()` (p610 D6, `_dbg__TestBridgeInput.ts`: every character's pose and locomotion state hashed per step over the probe's steps, from `MainLoop`'s `setPreStepHook`; in the same hook it plays `window.__AEK_TEST_INPUT__`, the runner's input script, as key events right before the given steps of the first scene's world). Bump `TEST_BRIDGE_VERSION` when a method's arguments or results change. On install it starts the test clock: every frame advances 1/60 s (`setFixedFrameDelta` in `MainLoop.ts`, which physics stepping follows too, so one step per frame), and it replaces `NodeFrame.prototype.update` so TSL `time` does the same and stops on freeze (three r186's fields: re-check on a three upgrade). So what a page shows depends on how many frames ran, not how long they took.
- Undo / redo (`debug/UndoRedo.ts` public API, implementation `debug/_dbg__UndoRedo.ts`): a recorded entry is plain JSON (`AEK_debugUndoRedo`), in its scene's bucket (`'perScene'`, the default: undone only while the scene is current), the global one (`'global'`: settings that aren't a scene's, eg. the renderer's) or, for a `'perScene'` entry recorded in an editor view, `__view:<id>` (see the root's Views); undo and redo walk the current scene's and the global bucket as one timeline by timestamp. `recordOrCoalesceUndoRedoAction` (what a binding's `onChange` calls) merges the ticks with the same type and key within 800 ms into one entry (the first tick's `prev`, the last's `next`). An undo stops at an entry whose handler isn't registered (warned, the pointer kept) until it is: skipping it would apply the rest out of order. The settings (`AEK_debugUndoRedoSettings`: the history size per bucket, defaulting to `AppConfig.undoRedo.historySize`, and the toasts) and the history list are the Debug tools tab's. The engine's own debug modules import `_dbg__UndoRedo.ts` directly; its `_registerUndoRedoActionHandler` is the public function. A handler that changes a tab's state saves it with `persistDebuggerTabValue` and refreshes the tab with `updateDebuggerTab`.
- Profiler window (`debug/Profiler.ts` public API, implementation `debug/profiler/`, `_DONE_p344`): a draggable window (`aekProfiler`) opened by `toggleProfilerWindow()` from the on-screen stats panels (setting `openFromStatsPanels`), the Statistics tab, the speedometer button in the top on-screen tools and F8. Its tabs are `DebuggerTabDef`s with the drawer's contract minus `sceneId`: `createProfilerTab` / `openProfilerTab` / `updateProfilerTab` / `isProfilerTabOpen`, ordered by `orderNr` (Overview 0, Objects 10, GPU memory 20, Settings 100). The drawer and the window each mount tabs through a `createTabHost` (`debug/_dbg__TabHost.ts`). Settings are in `AEK_debugProfiler`, the open tab in `AEK_debugProfilerUI`. It loads in the debug env, and in prodTest when its stored `enabledInProdTest` is on (`isProfilerLoadedInThisMode`, read from LS at boot); gate profiler-only registrations on that, not on `IS_DEBUG_ENV`.
  - A closed profiler measures nothing: the frame probe (`setFrameProbe` in `MainLoop.ts`, read by `runFrame`) is set only while the window is open, and a tab holds its stats sources only while mounted. Code adds figures with `registerStatsSource({ id, label, acquire?, release?, read, availability?, format? })`: refcounted, `release` turns off only what `acquire` turned on, and `availability` returns why it is n/a ("WebGPU only"). A source that isn't a built-in one gets an Overview row under "App" (p618 D14: `app:<sourceId>` entries in the settings' `overviewMetrics`, after the engine's, kept while the source isn't registered and appended when a new one is; the Settings tab moves them only within their group); `format` writes its value (default: a number with two decimals, a string as is, else JSON), and a throwing `format` logs once and reads n/a. The built-in ones are in `profiler/_dbg__ProfilerSources.ts` (GPU frame time through `_dbg__GPUTimer`, draw counters from a `LATE_MAIN` sampler, physics step stats through the runtime `setPhysicsStepStatsEnabled`, memory, rays, PostFX, long tasks, scene).
  - The in-view census (`profiler/_dbg__Census.ts`) repeats three r186's `_projectObject` culling against the active camera, at the update rate; a three upgrade can make it drift, and `info.render` ("drawn") stays the ground truth. Debug code that adds objects to the root scene marks them with `markDebugHelper(obj)`, so the census counts them in their own row. `registerEntityWindowOpener` lets the Objects tab's heaviest rows open an entity's edit window.
- GPU memory tab (`debug/gpuMemory/_dbg__GPUMemory.ts`, `_DONE_p345`): a tab of the profiler window (`createProfilerTab`, id `gpuMemory`; open it with `openProfilerTab(GPU_MEMORY_TAB_ID)`), not the drawer. It loads where the profiler does (`isProfilerLoadedInThisMode`: the debug env, and prodTest when the profiler is enabled there; prodTest has no budget toast and no links to drawer tabs). Its sampler and peaks run with the window closed too. three's own `renderer.info` bookkeeping, not a driver figure. Frame counters are read by a debug `LATE_MAIN` system right after the render (three resets `info.render` in its own animation frame). "By owner" sums registered assets (`AssetOwners`) and sources with three's per-object bytes (`info.memoryMap`), so they and "untracked" add up to `info.memory.total`. A GPU resource that isn't a registered asset (a render target, an instance buffer) should be named with `registerGPUMemorySource({ id, label, getResources, owner? })` (`debug/GPUMemory.ts`, a no-op where the profiler doesn't load, returns its remover): `getResources` returns the three objects (textures, render targets, geometries, attributes), never a byte estimate. The snapshot diff names what a scene visit left allocated, through an allocation tracker that wraps `renderer.info`'s create / destroy calls (installed by `onRendererCreated` in `kernel/render/Renderer.ts`, before `renderer.init()`). three r186 counts compressed textures as 1 B and cube faces as 1×1. The tab fixes the first at the source: `installCompressedTextureSizer` (`_dbg__GPUMemoryOwners.ts`, also before `init()`) replaces `info._getTextureMemorySize` so a compressed texture counts its uploaded mip bytes, in every figure. The cube part is estimated separately, outside the totals.
- Drawer tabs are one declarative `createDebuggerTab({ id, title, icon, content, ... })` call (`debug/DebuggerGUI.ts`; implementation `debug/_dbg__DebuggerGUI.ts`), at any time (one created before the drawer loads waits for it, see above). `content` is a factory (re-run on every mount/rebuild) returning sections: CMPs, `{ pane: true, content: [...] }` declarative Tweakpane panes (`_dbg__DebuggerPaneBuilder.ts`: bindings, folders, buttons, separators, a `custom` escape hatch) and `debuggerListCMP` lists (`_dbg__DebuggerList.ts`, with optional per-row icon toggles). Menu order is `AppConfig.debugDrawer.tabOrder` (engine default `DEFAULT_DEBUG_DRAWER_TAB_ORDER` in `kernel/config/Config.ts`), overridable per tab with `orderNr` (same 0-based scale). An `icon` (a tab's, a view's, a draggable window's) names a registered icon (`ui/icons/SvgIcon.ts`, p607 D12): `InitEngine` registers every built-in in the debug env and prod test mode (`registerBuiltInIcons`), so debug code uses any built-in name; a new built-in gets its export in `BuiltInIcons.ts` and its name in `BUILT_IN_ICONS`, and an app's own icon is `registerIcon`ed.
  - `openDebuggerTab(id)` opens the drawer on a tab. Refresh with `updateDebuggerTab(id, { rebuild? })`: it's a no-op unless that tab is visible (`isDebuggerTabOpen(id)`, false while an editor view hides the drawer); a closed tab is rebuilt from `content` on its next mount. A scene change updates the drawer's title in place and rebuilds only the open tab (`onRefresh`, then `content`), so a tab that builds from the current scene's data (cameras, lights, characters, ray casts) shows the new scene's; the drawer itself is rebuilt only when a tab is created or removed (the menu changes). A `content()` or `onRefresh` that throws is logged and leaves an error line in the tab's place (`_dbg__TabHost.ts`), never a broken drawer or scene load. Use `refreshIntervalMs` (runs only while visible) and `onOpen` (returns its cleanup) instead of hand-rolled intervals/teardown, and `onRefresh` to sync live values into the objects panes bind to.
  - Scene-scoped tabs: `sceneId` removes the tab on that scene's exit (one drawer rebuild); the saved open tab id is kept, so the drawer lands on the tab again when the scene re-creates it, also after a reload. Create them from the scene file, debug env only, via a dynamic `import()` of an `_dbg__` module (eg. `app/scenes/space/_dbg__spaceDemo.ts`).
  - Persistence: `lsKey` + `state` + `persistKeys` — only those state keys are hydrated (synchronously at registration, also in prod test mode) and written (on a finished change) as a flat object; bindings can use one-level paths (`'helpers.showGrid'`). Folder open states go to `uiLsKey` (default `${lsKey}UI`). Binding `onChange` fires on user input only (never on hydration/refresh/rebuild) and gets `e.prev`/`e.last` for undo recording. Scene-scoped, boot-time and deviation-only keys stay module-owned (custom `headerButtons` for their clear-LS buttons).

Legacy (pre-ECS) Camera/Light/Mesh managers have been fully removed in favor of the ECS-based `kernel/camera/Camera.ts`, `kernel/light/Light.ts` and `kernel/mesh/Mesh.ts`; favor ECS patterns for any new manager-like code rather than reintroducing non-ECS managers.
