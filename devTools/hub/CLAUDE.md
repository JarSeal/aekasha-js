Notes for the Ækasha Hub's generator (`devTools/hub/`, `devTools/hubPlugin.ts`, `devTools/hubBuild.ts`, `devTools/hubPreview.ts`; authoring is in `hub/CLAUDE.md`); the root `.claude/CLAUDE.md` keeps the project-wide rules, commands and workflow.

## Ækasha Hub

- `yarn hub:build`: Any error (a dead `hub:` or `api:` link, an `.md` without a slot, …) is printed with its file and line, the last output is left as it was, and it exits 1: a public build writes into `<out>.tmp-<pid>` and renames it over `<out>` only when nothing failed, a write step's throw included (`outDir.ts`). `--out` takes a missing or empty folder or an earlier Hub output (one holding `_headers`, `404.html` and `_assets/`), and refuses the repo root and every folder above it, `src/`, `hub/`, `devTools/`, `docs/`, `node_modules/`, `.git/`, a file and any other non-empty folder, before the build starts (`getHubOutDirError`). It prints the API docs' stats and whether their model was reused. `--no-api` skips TypeDoc, for fast content work: the Documentation page says the API isn't built, and neither `api:` links nor `hub:` links to API pages are checked (one warning). Embeds (p611 D9, `embed.ts`): before the build, an embed profile with no `dist-embed/<id>/` or no entry in the `yarn sbp` report is built and measured (`yarn sbp --profile <ids> --brief`; exit 1, a budget over, still builds the Hub), and the profiles the pages' `::: embed`s use are copied into `_assets/embed/<id>/` without `.vite/` (`copyHubEmbeds`; the entry is referenced with its `?v=`, the rest is hashed, so `_headers`' immutable cache holds; a profile that copies `basis/` or `draco/` would ship them unhashed). `--no-embed` skips both: the poster and a note. `{{sbp:…}}` reads `.cache/sbp/report.json` (`sbp.ts`), which `yarn build` writes right before. `AEK_HUB=false` skips it (so `AEK_HUB=false yarn build` builds no Hub; `tsc -p hub` still runs) and turns off the dev server's `/hub/`. `AEK_HUB_IN_DIST=true yarn build` also copies it into `dist/hub/`, so the app's site serves it at `/hub/` (off by default: the Hub isn't in production unless asked for).
- Search (`search.ts`, `searchProtocol.ts`, the browser side `hub/_assets/ts/_search.ts`): minisearch, one document per heading with an id plus each page's own section (its title, `aek:tags`, `aek:description` and the text before its first heading), built from the rendered bodies (the homepage isn't indexed); code blocks give their identifiers only, and indexed words also get their camelCase parts. `_assets/hub-search.js` is the whole payload (`HubSearchPayload`): the serialized index, the path table its ids point into, the menu and the searchable pages with their headings (the results' groups and breadcrumbs). Every page names its URL in `<meta name="aek-hub-search">`, whose `?v=` `diffBuilds` ignores, so a text edit only reloads its own page. A document's id is `<path index>#<anchor>`, so `path` and `anchor` aren't stored, and a heading is stored only when its page's headings don't give it (a heading in a page's own markup); `createHubSearchReader` decodes a result on both sides (`search.test.ts`'s round trip). The dialog is a chunk `hub.ts` imports on first use (⌘K / Ctrl+K, `/`, or the search button; its focus or hover preloads), so neither loads until someone searches. `hub:build` prints the payload's `gzip -9` and raw sizes (256 KiB and 954 KiB at p619 Phase 6) and warns over 450 KiB gzipped. The Version page's changelog is out of it (`hubSearchSkip`): it was a large share.
- Output (`.cache/hub/dev/` in dev, `dist-hub/`): the pages, `404.html`, `_assets/hub.css`, `hub.js` (and its lazy `chunks/`), `hub-search.js` (the search's payload, loaded on its first use; p619 D7 removed `hub-data.js`, which every page loaded for the search alone), the static assets, and the favicons copied from `hub/_assets/favicons/` (the Hub's own: the app's Æ in the Hub's accent, not `src/public/`'s). Every link is relative, so the site works at a domain root and under `/hub/`; the 404 page, served at any depth, resolves against `<base href>` (`rebaseNotFoundPage` moves it). Every `_assets/` reference carries `?v=<content hash>` and `_headers` caches `_assets/*` as immutable, so reference a static asset through `{{asset:…}}` (or `url(fonts/…)` in the SCSS, which gets its hash), never as a bare path.
- `yarn hub:preview` listens on `localhost` only; a malformed escape is a 400 and a NUL byte a 404 (`resolveHubRoute`), and no request ends the server. A link's malformed escape (`api:`, `repo:`, an image) is an error at its line, not a throw out of the build; two `docs/issues/` files whose names slug alike are an error, and the second gets no page.
- Modes: `public` (`yarn hub:build`: minified, no dev client; any error leaves the last output as it was) and `dev` (the plugin: unminified, the dev client; a page with an error is served as an error page listing it with its file and line, and errors outside every page, in the shell, SCSS or TS, go on every page and the 404 page; a failed SCSS or TS build keeps the last good assets).
- Dev plugin (`devTools/hubPlugin.ts`, `AEK_HUB=false` turns it off): lazy, the first `/hub` request empties `.cache/hub/dev/` and builds; the watching starts with it, so a save during that build is the next run's (p619 H3). A request during a rebuild waits for that run only, not for the runs saves queue after it. An editor's temporary or backup file (`.swp`, `4913`, `~`, `.#…`, `___jb_tmp___`, `.crswap`, a dot file) triggers no run. A static asset removed from `hub/_assets/` has its copy removed. The Version page keeps the first build's commit, "local changes" and time (an edit and its undo flipped "local changes" and reloaded it). The watcher closes with the HTTP server, or on Vite's `closeBundle` in middleware mode. `hub/` is watched with `fs.watch`, not Vite's watcher (Vite logs a watched `.html` save as a "page reload", clearing the terminal, and sends a `full-reload`); the build's sources outside it (`package.json`, `CHANGELOG.md`, `docs/issues/`, the files pages include with `<<<`, `tsconfig.json`) go through Vite's watcher. Other app, toolkit and engine saves never rebuild it (an engine or toolkit save only marks the API docs stale, see Documentation); the `yarn sbp` report is a source too (a run rebuilds the pages that show its numbers). In `dev`, `::: embed` imports the profile's entry source from the dev server: the page first imports `/@vite/env` (Vite's `define`s are globals the app page gets through Vite's client; without it `__PROJECT_METADATA__` throws), and removes the `page.scss` `<style>` the untree-shaken `aekasha` entry injects (the root font size, normalize). Its scss modules bring Vite's client, so that page reloads on the gatherer's `full-reload`s. Every run builds the whole Hub (tens of ms) and `diffBuilds` compares it with the last run to send the custom HMR event `aek:hub` (`HubDevEvent`, `devTools/hub/devProtocol.ts`): `css` (the stylesheet is swapped, no reload), `pages` (only those tabs reload) or `all` (scripts or static assets). It never sends `full-reload`, so open app tabs aren't touched. The dev client (`hub/_assets/ts/_devClient.ts`, dev builds only) opens its own socket to Vite's HMR server instead of importing `/@vite/client`, which reloads on the gatherer's `full-reload`s and shows the app's error overlay. The socket's token is filled into each page when it's served (never on disk), and `/hub` routes run `devTools/hostCheck.ts`' `getHostAndOriginError` (the dev files' check too). `hub/hub.config.ts` and `devTools/hub/*` are Vite config dependencies: a change restarts the server, and open Hub tabs reload when it's back.
- Generated sections (`devTools/hub/generated/`, `HubGeneratedSection`): a hand-written page whose `generated-*` slots and child pages a generator fills (an `.md` for such a slot is an error). Home (`''`, see Features and homepage in `hub/CLAUDE.md`). Issues (`issues/`): a page per `docs/issues/*.md` at `/hub/issues/<file name>/` (not in the nav), listed on the section's page grouped by status with the first paragraph of the first section as the summary. Version (`version/`): `package.json`'s versions and codenames and the build commit and time (the dev plugin keeps its first build's time), then `CHANGELOG.md` with its headings one level down and an anchor per entry (`#2026-10-07-impostor-billboard-lod`); its latest entry is the homepage's "What's new" (`latestChange`).
- Documentation (`devTools/hub/api/`, p553; per entry since p619 D6): the API reference under `/hub/documentation/`, generated from the engine's and the toolkit's JSDoc. `extract.ts` runs TypeDoc's API with `tsconfig.json`'s `typedocOptions` (so `_dbg__*`, the tests and the entries are left out, as in `yarn docs`) plus `skipErrorChecking`, then `linkNamedReferences` (a reference TypeDoc left by name to a declaration it has gets its id: the interfaces merged by `declare module 'aekasha'`, `ComponentDataMap`), and reads the entry files' names with the conversion (`ApiModel.entries`, through `importGraph.ts`' parser: TypeScript loads only then, never in a Hub build). It caches the JSON model in `.cache/hub/typedoc.json` under a hash of its inputs (the engine and toolkit `.ts`, the entry files, `src/*.ts`, `tsconfig.json`, `package.json`, `yarn.lock`, the TypeDoc version, `EXTRACT_VERSION`). The model stays per source module (the docs ratchet counts every export); the pages are the public entries': `entries.ts` maps each entry's names to their declarations, `publicApi.ts` lays out the pages, `render.ts` renders them (a symbol in `renderSymbol.ts`, the search documents in `apiSearch.ts`). A page per entry at its specifier (`documentation/aekasha/physics/`), an h2 per source module (`#module-<Name>`: its path and summary), each name an h3 with its anchor (members `#Owner.member`), its signature highlighted by shiki with its types linked, its comment through markdown-it (`html` off), tables for parameters and properties, and a source link (GitHub at the build commit in `public`, `/__open-in-editor` in `dev`). An entry over 150 names (`aekasha`) has a page per source folder (a kernel area or `utils`: `documentation/aekasha/scene/`), which its page lists; `documentation/aekasha/toolkit/` lists the toolkit's entries. A name on two entries is documented on the first (`ENTRY_FILES`' order) and listed on the second as a re-export. Internal exports (on no entry) have no page. Undocumented names are listed as "No description", and each page shows its coverage.
  - Links: `api:` in any page's Markdown or markup (`[loadScene](api:loadScene)`): a bare name is a public name, a member needs its owner (`api:ECSWorld.addSystem`), a name two declarations share needs a module path suffix (`api:PhysicsBodies.createRigidBody`). Unknown or ambiguous fails the build with the suggestions or candidates, and so does an internal name ("is internal: it's on no entry, so it has no page") (`links.ts`). A type in a signature links its nearest public owner, else stays text. A JSDoc `{@link X}` lands on the same anchor; in a public comment, one to an internal export or to nothing is code, with a warning at its line (three's own classes without one): write an internal name in backticks.
  - Search: a document per entry (kind `entry`, named by its specifier), public name and class / interface member, found by name only (`symbol`), its first sentence stored as the snippet, clipped at a word to 120 characters (`SEARCH_SUMMARY_MAX_LENGTH`, p605: the summaries were the largest stored field). A second entry's re-export has none. The API pages aren't in the payload's `pages`: a result's breadcrumb comes from its path.
  - Dev: TypeDoc runs in a child process (`extractProcess.ts`, about 6 s, never in the dev server's process: it blocks the event loop for seconds). An engine or toolkit save only marks the model stale; the next request for an API page (the landing page and the subtrees, not `documentation/code-blocks/`) starts the conversion and gets the "Rebuilding the API documentation…" page (503), which reloads on the `aek:hub` kind `api`. Other pages never wait, and their `api:` links resolve against the last good model (`buildHub({ api: 'last' })`). A failed conversion keeps that model and shows its errors on the API pages.
  - Rendering the whole API takes about a second, so each slot's output is memoized per model hash, mode and commit; a dev rebuild with an unchanged model adds about 25 ms.
  - The public API's checks (p619 R2, `entries.ts`, replacing TypeDoc's validation, which no longer runs): a type a public name names (in a signature, a property, a base type) that no entry exports is a `yarn hub:build` warning at the reference, once per type, with the types it names in turn (transitive); a private, `@internal` or inherited member, a type parameter, a `{@link}` and another package's type don't count. `ACCEPTED_LEAKS` keeps the deprecated names' own types until 6.0.0 (a key that no longer leaks warns). A name on an entry tagged `@internal` warns, and one the model lacks is an error. `typedoc-plugin-zod` (`typedocOptions.plugin`, so `yarn docs` too) expands a `z.infer` / `z.input` alias into its fields, giving it the schema constant's comment when it has none; a union alias gets a table per variant (`getTabledVariants`, labelled by a shared literal key: `type: 'PERSPECTIVE'`). Composed aliases (`SkyBoxDef`: `Omit<z.input<…>> & {…}`) stay references.
  - A TypeDoc upgrade re-checks the Documentation pages: the cache hash includes its version (so the model is rebuilt), `model.ts`'s `Kind` numbers are checked against `ReflectionKind` with `satisfies` (a renumbering fails `tsc`), and the renderer reads the serialized JSON model's shape (`JSONOutput`), so look at an entry page, a class, a Zod-derived type (`SkyBoxDef`, `CameraProps`), the `{@link}` warnings and the leaked type ones before and after (`linkNamedReferences` reads `symbolIdMap`). Bump `EXTRACT_VERSION` when what the extraction writes changes.
