Notes for the engine majors' codemods (`devTools/migrate/`: engine 6.0.0's, p622 D10); the entry-imports codemod of engine 5.0.0 is `devTools/layout/CLAUDE.md`'s, and the root `.claude/CLAUDE.md` keeps the project-wide rules, commands and workflow.

## Engine 6 codemod

- `npx tsx devTools/migrate/migrateEngine6.ts [--check] [--report] <folder | file>...` (eg. `src hub/_assets/ts`): migrates an app made from the template to engine 6.0.0 and toolkit 3.0.0, run after the app took the new `src/_engine/`, `src/toolkit/` and `devTools/` (the Hub's migration page, `hub/pages/documentation/migration/engine-6.md`, gives the order). Targets anywhere in the repo, `.ts` modules (not `.d.ts`), `src/generated/` skipped (the gather writes it again). The rewritten modules are formatted with Prettier. A module with an error is left as it was and every error is listed; the reports (what needs a person: file, line, the name, the migration page's anchor) always print, on stderr. `--check` writes nothing and exits 1 when a module would change; `--report` writes nothing and prints only the reports. Exits 2 on an error (a module left, a bad target or flag). About 7 s over the template's `src` and `hub/_assets/ts` (957 modules).
- The files: `migrateEngine6.ts` (the CLI: the targets, the program from the repo's `tsconfig.json`, Prettier, the exit codes), `engine6Rules.ts` (the rules as one table, `ENGINE6_RULES`: each with an `id`, the plan decision it comes from and its migration page anchor), `engine6.ts` (the logic without the file system: `createMigrationProgram`, a program over a base compiler host with virtual texts on top, and `migrateEngine6({ program, files, rules })` → `{ changed, errors, reports }`) and `engine6.test.ts`. Like every dev tool it imports nothing of the engine (`devTools/engineImports.test.ts`).
- It works on the checker's symbols, not on names: a rename never touches a local, a parameter or a property that only shares the name, and code that no longer compiles against the new engine is fine (an import of a removed name still binds in its module). Each touched import is written again whole (a value import left with only inline types becomes `import type`), so two rules on one import statement never collide; two overlapping edits elsewhere are an error.
- Kinds 1-2, renames and moves by import (`ImportRule`: `from` and `to`, each an entry and a name): a name imported by name from an entry gets its new name in the import and every reference (an aliased import keeps its local name; a shorthand property becomes `Old: New`, a local `export { Old }` becomes `export { New as Old }`), or moves to its new entry's import (merged into one the module has, else a new import after the old one). When the module imports the new name already, the two merge (the value import is kept over a type-only one). A namespace import's `ns.Old` and an `import('entry').Old` type are renamed too, and `export { Old } from` keeps the module's exported name (`export { New as Old } from`). A dynamic `import()` of an entry isn't followed. Errors: a renamed reference that another declaration would shadow, or a name the module declares itself; a move through a namespace import.
- Kind 3, the call reshapes (`ReshapeRule`, p622 Phase 3): a call whose callee resolves to an entry's function, in its old shape (more arguments than `newArgCount`, or its argument at `newHas.index` has no `newHas.member`, the new props' marker; an `any` there is reported, never guessed), gets the new one: `params` names the old arguments, `args` the new ones (an old argument as it was, or an object of them: `{ key, param }`, shorthand when the argument is an identifier of the key's name, or `{ spread }`, an object literal's properties merged in place, anything else `...x`). An old `undefined` or left-out argument is dropped, a trailing new argument left empty too, and an object of a single spread is that argument as it was (`createPhysicsEntity(c, b, t, opts)` → `({ colliders: c, body: b, target: t }, opts)`). The new arguments name the old ones in their order (a test checks it), so evaluation order stays; a reshape that reorders arguments needs a check of its own first. Comments go with their argument (the ones before it and after it on its line), a dropped placeholder's with the next argument kept. A spread argument is reported. The reshaped argument list is written last, innermost call first, with the edits inside its arguments applied to their text (`resolveReshapes`), so a renamed name or a reshaped call in an argument is no overlap. Each rule has a fixture in `engine6.test.ts`' `RESHAPE_FIXTURES`, keyed by its id.
- Kind 3, the member renames (`RenamedMemberRule`): `x.old` (a call of it, `?.` included) on a value whose type is one of `types` (or has it in a union or intersection, as the member reports' check) gets the new name: `WorldAPI.setMaxCcdSubstepsSync` → `setMaxCcdSubsteps`. A destructuring of the old name isn't followed.
- Kind 4, the reports (p622 Phase 2 section 5), each from the checker's symbols, never a name alone: `RemovedImportRule` (an import, `export … from` or `ns.Name` of a name the entry no longer exports), `RemovedMemberRule` (a member an entry's type lost: read as `x.member` or in a destructuring on a value of that type, or written in an object literal whose contextual type is it, a union's or an intersection's member included; `onlyString` reports only a string value, the `kbd` that became a Kbd) and `CallArgRule` (an entry function's argument at an index: any, an object literal's named properties, or a string literal, which `rewrite` replaces instead: `getSvgIcon`'s `'small'` → `'sm'`). An entry's exports are read through the first non-declaration module of the program that imports or re-exports from it (`createEntryExports`), so a project that never imports an entry gets none of its reports. A module's reports are sorted by line. A `RemovedImportRule` or `CallArgRule` with `withoutFeature` (p622 Phase 4: the tiers' setters and `createPhysicsEntity`'s `tierPolicy`, which need `physicsTiers()`) is for names that stay on their entry: it reports only when no module of the program calls that feature's factory (`createFeatureCalls`: by the checker, the declarations, libraries and `*.test.ts` modules aside; a reference that isn't a call doesn't count), so the CLI's whole program decides, not the modules a run rewrites; that program is the targets and what they import, so a run over a folder without the boot module (`src/index.ts`) reports them even when the app lists the feature.
- Reports' lines: `--check` and `--report` give the module as read; a writing run finds a rewritten module's reports again on a second program over its formatted text (the CLI's `migrate(texts, files)`), so the lines match the written file.
- Tests (`engine6.test.ts`): stand-in entries in engine 6's shape (the old names gone, as an app sees them) in a virtual `noLib` program with a minimal globals file (`GLOBALS`: without a global `Array` an array literal's elements get no contextual type), a generated fixture per rename rule, per removed import name and per removed member (a read and an object literal), a test per behaviour, each run twice (the second run must change nothing), and a check against the repo's entries today: every rename's target exported, every removed name not, every member rule's type and call rule's callee exported. A new rule gets its fixture through the generated ones, and a test of its own when it does more.
