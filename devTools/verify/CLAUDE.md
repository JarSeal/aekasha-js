Notes for the verify commands (`devTools/verify/`: the scene runner, the baselines, the embed check, the UI check and the `@example` check); the root `.claude/CLAUDE.md` keeps the project-wide rules, commands and workflow.

## Verify commands

- `yarn test` / `yarn test:watch` — the unit tests (Vitest, `_DONE_p601` Phase 1). `vitest.config.ts` is standalone (none of `vite.config.ts`'s plugins run under a test) with `environment: 'node'`, and defines `__PROJECT_METADATA__` and `__AEK_DEBUG__: true`. A test is a `*.test.ts` next to its module (`src/` or `devTools/`), importing `describe` / `it` / `expect` from `vitest` (no globals). No GPU: anything that needs a renderer belongs to the scene runner. No module reads a browser global at load: `src/_engine/ModuleLoad.test.ts` imports every engine module in Node and fails on one (the `IS_*` flags read as production until `initEnvironment`; a test that needs the debug env calls `initEnvironment({ search: '?isDebug=true', env: { VITE_APP_ENV: 'development' } })`, as `kernel/config/Config.test.ts` does; with no `VITE_APP_ENV` it's a production build, which ignores the URL). A test that needs a browser global stubs it in its own file (`vi.hoisted` + `vi.stubGlobal`), never in a global setup. The structural checks are tests too (p606): `features/physics/worker/PhysicsWorker.test.ts` (the worker bundles without three, `MainLoop`, `Config` or the facade's modules), `devTools/aliases.test.ts` (`tsconfig.json`'s `paths` match `devTools/aliases.ts`, and an entry file holds only named `export … from`), `devTools/engineImports.test.ts` (the devTools' imports from the engine, the root `CLAUDE.md`'s Coding standards), `devTools/layout/layout.test.ts` (the layout check, `devTools/layout/CLAUDE.md`), `devTools/verify/examples.test.ts` (every `@example` and the readme's examples type-check, see `devTools/verify/CLAUDE.md`) and `devTools/verify/moduleSideEffects.test.ts` (no statement runs at module load outside the debug loader's modules, the worker entries and `src/index.ts`; no allow-list). Tests are left out of TypeDoc and the Hub's API hash. The Stop hook runs them when `src/`, `devTools/` or `vitest.config.ts` changed. The schema tests are `devTools/gather/gatheredJson.test.ts`: every gathered JSON in `src/` through `validateGatheredJson`, and bad cases made by breaking one field of a repo asset (no fixture files: a fixture under `src/` would be gathered).
- `yarn verify:scenes`: It loads every scene of the generated data through the test bridge (see Debug system) in four configurations, `workerSab`, `workerMsg`, `mainThread` (debug env: errors, the determinism probe's hash, a 512 × 288 snapshot) and `prodTest` (errors only), and fails on a console or page error the config doesn't allow, a changed hash, a snapshot over the tolerance, a changed system order, a changed character path hash, or a load that ran in another physics configuration than it asked for. The probe hash leaves characters out; on `MAIN_THREAD` the runner compares the bridge's `getCharacterPaths()` hash instead (p610 D6: every character's pose per step, deterministic only there, p428). A scene's `inputScript` (`devTools/verify/inputs/<name>.json`, `{ frames: [{ step, down?, up? }] }`, keys as `KeyboardEvent.key`) is handed to the page by an init script and played as key events right before those fixed steps (0 = the first step after the load); the gym's runs 600 steps of the two players walking, turning, running, crouching and jumping (one tumbles), and the run's note lists the locomotion states each character went through. The system order (p607 Phase 1) is every world's systems per stage as `id@order`, read through the bridge's `getSystemOrder` last on the page (after the probe or the prod test settle, so lazily loaded debug systems are in) and compared by `systemOrder.ts` (Chromium only): registration order breaks ties, so a moved registration shows there first. `--config quick` is `workerSab` alone. It runs `yarn copyDecoders && yarn gatherAppData` first (a failed gather stops it before any page loads), and starts its own dev server on 8092 (or the next free port) unless `--url` (`devServer.ts`' `startVerifyServerAsync`, which `yarn verify:ui` shares; p619 V3: on `localhost`, with its own dependency cache `node_modules/.vite-verify`, never shared with a `yarn dev*`, and Vite's dependency, optimize and page reload lines in the progress log as `[vite] …`). A page whose main frame navigates again after its first load (a reload: Vite re-optimizing a dependency found only at runtime, or a source change without an HMR boundary), or whose page call a navigation cut off, runs once more in a fresh context with `RELOAD_RERUN_NOTE` (`sceneRun.ts`); a reload in that second run fails it. The run hashes `src/generated/generatedAppData.json` at its start and end and warns when it changed (a gather under the run: the pages after it loaded the new data). `vite.config.ts` has no `optimizeDeps`: Vite 6's scan from `index.html` finds the workers' dependencies too. Baselines are local and per backend (`.cache/verify/scenes/<webgpu|webgl>/`: snapshots depend on the GPU and the driver): `--update` records every run without errors as good, so update on `main`, then run on the branch; the last run, with a `*.diff.png` per failed snapshot, is in `last-run.json` and `last-run/`. On WSL2 headless WebGPU can't render, so the page renders on WebGL2 (SwiftShader) without `--headed` (logged): WebGPU-only regressions need a `--headed` run on a real GPU. `--browser firefox` (p605 Phase 6; Playwright's Firefox, `npx playwright-core install firefox` once) is the cross-browser determinism run: the debug configurations only, always WebGL2, probe hashes only (no snapshots), compared with Chromium's baseline for the same scene, configuration and steps (the `webgl` file's entry, else `webgpu`'s, which it checks agree), never `--update`, its last run in `.cache/verify/scenes/firefox/`. A difference means the simulation depends on the JS engine: an issue file and an `unstableHash` with `browsers: ['firefox']` (`skip` and `allowedErrors` take `browsers` too). Run it after the Chromium run passes on the same commit, and before the PR of a change to simulation code (p610, p614). The full matrix takes about an hour on SwiftShader. `playwright-core` is a project devDependency, pinned to the run-aekasha-js skill's version, so they share its downloaded Chromium. A baseline that's there but unreadable or of another format stops the run (exit 2, the run so far in `last-run.json`) unless `--update` records over it: it used to read as none, so every run was NEW and passed. A `scenes.config.ts` entry naming a scene the data doesn't have fails the start (a renamed scene would lose its settings), and so does a shell's `VITE_APP_ENV` other than `development` or `test` (its build has no test bridge). A missing or non-JSON input script fails its scene (its `frames` aren't checked). Every page call has a timeout (the bridge's own plus 60 s, or 60 s: a hung readback), and `baseline.json`, `last-run.json` and the committed baselines are written atomically (`devTools/files.ts`).
- `yarn verify:baselines [--update [--allow-docs-drop]] [--no-build] [--docs]` — diffs the committed files in `devTools/verify/baselines/` (`devTools/verify/baselines.ts`, `_DONE_p601` Phase 3): `bundle.json` and a `bundle.<id>.json` per embed profile (today `bundle.banner.json`) (every file in `dist/assets/` by its key, bytes and gzip, plus the main chunk's modules per group: a package, each engine folder, toolkit, app; minified, and the gzip of each group's code. The keys (a name without its hash, `@<worker>` or `@<source folder>` where two files share one) and the module sizes are `devTools/sbp/CLAUDE.md`'s, p619 B1, B2), `api.json` (every export of the documented API by module, with its kind, from the Hub's TypeDoc model, and each public entry's export names, read from its `index.ts`: the public surface, p606) and `docs.json` (documented / total exports and class and interface members per folder, the Hub's coverage rule, and each folder's undocumented ones by name, `SceneLoader#LoadSceneProps`, `ECS#ECSWorld.addSystem`). It exits 1 on a chunk whose gzip grew over 1 % or 2 kB (at least 100 B), a new chunk, an export added, removed, moved or of another kind, a name added to or removed from an entry, or a folder with more undocumented exports or members than recorded (the docs ratchet, p605: it names each new one with its file and line; a new folder starts at none); shrinking, better coverage and deleting documented code pass. `--update` writes the current state: commit it with the change that explains it. It refuses a grown undocumented count unless `--allow-docs-drop` is given too (say why in the commit; a move that renames folders needs it, as p608's did and p609's will, since the ratchet reads each moved folder as a new one). The bundle's measuring, its diff and the build steps are `devTools/sbp/`'s (`bundleModel.ts`, `bundleDiff.ts`, `appBuild.ts`), shared with `yarn sbp` (p611 D1). It runs the build's bundle steps first (decoders, production gather, `vite build`, each embed profile's `vite build` with `AEK_EMBED_PROFILE`, the dev gather again; no `tsc`, no Hub), 12-20 s; `--no-build` reuses `dist/`, `dist-embed/` and `dist-stats/`. `--docs` checks (or records) `docs.json` alone, without the build, `api.json` or the progress log, in about 1 s (6 s when TypeDoc converts): the Stop hook runs it. Gzip sizes shift by a byte or two between builds with new content hashes, within the tolerance: don't commit such a `bundle.json` without a change that explains it. The same build, and each embed profile's (`bundle.<id>.json`, p611), is checked for debug code (p607 D7, `debugInProduction.ts`, its test next to it): a `_dbg__*` file in `dist/assets/`, a debug module with rendered code in any chunk of the main build or a worker build (the module sizes, p619 V7; a finding in a worker names it), a debug asset (p611: an emitted file whose source is in a debug folder or whose every importer is a debug module, `listEmittedAssets`), or a feature's `ctx.onDebug` / `ctx.onDebugAfterStart` call left in a script (p612 D9: found by its text, `n.onDebug(`, since property names aren't minified; gate it with `if (IS_DEBUG_ENV)`) fails the run: a `_dbg__` module, or any module under an engine folder named `debug` in any case (`debug/`, `kernel/<area>/debug/`, `features/<name>/debug/`), the entry `debug/index.ts` aside (p608 D4: a debug folder holds nothing that ships, so a wrapper with rendered code is called from code that ships), and `--update` records nothing. The build sets `VITE_APP_ENV=production` itself, so a shell's `development` can't build the debug code in; a `dist/` from `yarn build:test` holds it by design, so `--no-build` after one fails.
- `yarn verify:embed [--profile <id>] [--no-build] [--headed] [--webgl]` (`devTools/verify/embed.ts`, p611 Phase 4): mounts each embed profile's build (`sbp.config.ts`, `dist-embed/<id>/`, built first unless `--no-build`) into a plain host page with its own styles (`embedHost.html`, served with the build at `/aekasha/` from its own server, on a free port of `localhost`), one page load per scenario since the engine mounts once per page load. `INLINE` at `width: '50%'`, `height: '80%'` of a 640 × 360 target: the container, the canvas and its drawing buffer at 320 × 288, something drawn, all following when the target grows to 800 × 400, `unmount()` leaving the target empty and a second mount throwing. `BACKGROUND`: the container and the canvas fill the viewport, drawn behind the content, a click on the heading reaching it and one in the middle not reaching the embed, nothing left after `unmount()`. In both, no computed style of the host's elements (`embedChecks.ts`' `HOST_STYLE_SELECTORS`) changes while mounted or after, and no console or page error; the custom properties `tokens.css` registers are left out (`readRegisteredProperties`: CSS puts a registered property with an `initial-value` on every element, the host's too, and has no scoped registration; p801 Phase 3 found the check failing for both profiles since Phase 1), so a token declared on the host's elements still fails it. For the banner (`EXAMPLE_PROFILE`), a third page load: the Hub's embed example (`embedExample.html` at `/example.html`, whose regions `hub/pages/examples/embed/` includes) mounts in its hero at the target's size, turns, and its pause button pauses (no change over 400 ms) and resumes it. For the `uiKit` profile (`UI_KIT_PROFILE`, p801 D9), two more page loads, `INLINE` in the 640 × 360 target on a host with a 16 px root and again with `html { font-size: 62.5% }` (`embedHost.html`'s `?root=`): the scene's window, dialog, backdrop, toast and open drop-down list inside the container (`checkInside`), the window at its px position from the container's corner, the dialog centred, the backdrop the container's box, the window's, the toast's and a list item's font sizes the same at both roots, and their font IBM Plex Sans with its face loaded (the scene imports `aekasha/ui/fonts`, p801 D8; the host's is Georgia); then Escape on the host page's button leaving the `closeOnEscape` dialog open and Escape inside it closing it (p803 D7: the overlay stack listens on the HUD root), a drag of the window's title moving it by the pointer's distance, and the window and the toast inside the container after the target shrinks to 320 × 200. The elements are found by the ids and classes the scene gives them (`UI_KIT`, kept in step with `src/app/profiles/uiKit/uiKitEmbed.ts`). Each check after a mount, a resize or a turn polls for its state for up to 10 s (p619 V5 replaced fixed 400 ms waits), and a page that never gets ready is that scenario's failure. A function named inside `page.evaluate` fails under tsx (its `__name` helper isn't in the page): inline it. Headless WebGPU (`launchChromium`, `browser.ts`, shared with the scene runner); `--webgl` (and WSL2 without `--headed`) is WebGL2 through SwiftShader. About 3 s without the build. Exits 1 on a failed scenario, 2 on an error.
- `yarn verify:ui [--url <hub url>] [--only <piece>[,…]] [--update] [--headed]` (`devTools/verify/ui.ts`, the CLI; `uiChecks.ts`, its pure parts, tested; `uiPage.ts`, the steps on a page; `uiSnapshots.ts`, the screenshots; `ui.config.ts`, the axe tags, the allow list and the screenshot tolerance; p803 D11): the UI kit's demos on the Hub's component library page (`project/aekasha/components/`, dev-only until p803 Phase 8, so it starts its own dev server, the scene runner's, and opens the dev Hub's page, unless `--url` names a Hub's root such as a running dev server's `http://localhost:8080/hub/`), in Chromium at 1440 × 900. Each demo box's states (the box as shown, each of its Hub buttons, a repeated text numbered, and the states its checks table adds: `hub/_assets/ts/_componentChecks.ts`, next to the demos, keyed like their `DEMOS`) run on their own page load in four settings (dark and light, each at the default and the compact density: a browser context per setting with the Hub's saved theme and the colour scheme emulated, then the page's theme and density radios on the HUD root), the four at once. After the steps the pointer moves to the viewport's bottom right corner (off the clicked button, whose hover would change in the shot) and it waits for the page to settle (no animation running and the HUD root's boxes the same on two polls, up to 5 s), then: a screenshot, of the HUD root's overlays alone (the page around them hidden, clipped to their union in the viewport; a backdrop's is the viewport) or of the box when nothing is open (pinned at the viewport's top left, its width rounded, the page hidden: where the page lays it out moves it by fractions of a pixel, which antialias its edges differently), compared with `.cache/verify/ui/baseline/<piece>/<state>.<setting>.png` (local, as the scene runner's: the fonts render differently per machine; `last-run/` has this run's shots and a `*.diff.png` over the tolerance; no baseline is a note, `--update` records the shots of the runs without problems); then axe-core (`axe-core`, injected with `addScriptTag`; WCAG 2.2 A and AA and `best-practice`) over the box and `#hudRoot`. A violation fails unless `UI_ALLOWED_VIOLATIONS` lists its rule on that piece with the phase that fixes it (a committed list, not a flag, so the plain command is each phase's check; one that ran and matched nothing is printed as one to remove). Then each keyboard script of the table (`UiKeyStep`: `click`, `clickHud`, `focusHud`, `focusBox` (a box button, focused without a click: the focus outside the HUD), `press` in Playwright's key names, and `expectFocus`, `expectFocusBox` (the focus on a box button: an overlay's opener), `expectAttr`, `expectCount`, `expectText`, `expectActiveOption`, with the page's selectors), on its own page load per setting: each expectation polls for up to 3 s and the script stops at the first that doesn't come, naming its step and what the page had; after every key the focused element (not the body) must show an outline (computed `outline-style` not `none`, within 500 ms; a script's focus after a click shows none, the next key turns `:focus-visible` on). A script says what's true of the piece today, and the phase that fixes a key changes its steps. A console or page error fails the state or script. A problem in all four settings prints once. About 50 s. Exits 1 on a failed state or script, 2 on an error. A function named inside `page.evaluate` fails under tsx, as in the embed check.
- The `@example` check (`devTools/verify/examples.ts`, run by `examples.test.ts` in `yarn test`, so the Stop hook runs it; p606 Phase 8): every `@example` in TypeDoc's scope (`src/_engine`, `src/toolkit`, minus `_dbg__*`, tests and `index.ts`) type-checks as app code, and so does every `ts` / `js` block of `readme.md` (p621 D3: `collectReadmeExamples`, each owned by the heading above it). The TS AST finds each tag and its code comes from the raw comment, so a finding has its source line. Each fenced block (ts / js; other languages skipped) is one example, an unfenced tag is all code. Each becomes a virtual module in `src/__examples__/` (a folder that doesn't exist) with one header line importing, from any entry, the entry names it uses but doesn't import or declare (values and `import type` apart, for `verbatimModuleSyntax`), and `export {}` (no shared scope). One in-memory program: the real `tsconfig.json` with its `.d.ts` roots, minus `noUnusedLocals` / `noUnusedParameters`; only the examples' diagnostics count. Free: 2304 / 2552 / 18004 (a name the reader has, `box`) and 2307 for a relative specifier (the reader's own `./CONFIG`); a misspelled entry fails. The test also checks four fixtures in the same program (about 1.3 s). Limits: an example's `declare module 'aekasha'` merges into the shared program (two conflicting ones would clash), and an internal name no entry exports passes as a free name.
- The module-level side effects test (`moduleSideEffects.test.ts`, p607 D8, in `yarn test`): no top-level statement that isn't a declaration (a call, an assignment, or an `if`, a loop, a block or a `try` around one: p617 G1 found a listener added in an `if`; an import, an export, a declaration and `export default` aren't read, nor is a declaration's initializer) in `src/_engine/`, `src/toolkit/`, `src/app/` or `src/*.ts`, except `_dbg__*` files (they run only through the debug loader's `import()`; found by name wherever they are, p608 D4), the two worker entries and `src/index.ts`. It has no allow-list: p607 moved every registration into an install, and p619 removed its empty `NOT_YET_INSTALLED`. A registration belongs in a feature's `install` (Engine features, `src/_engine/kernel/init/CLAUDE.md`).
