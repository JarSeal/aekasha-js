Notes for the verify commands (`devTools/verify/`: the scene runner, the baselines, the embed check and the `@example` check); the root `.claude/CLAUDE.md` keeps the project-wide rules, commands and workflow.

## Verify commands

- `yarn verify:scenes`: It loads every scene of the generated data through the test bridge (see Debug system) in four configurations, `workerSab`, `workerMsg`, `mainThread` (debug env: errors, the determinism probe's hash, a 512 × 288 snapshot) and `prodTest` (errors only), and fails on a console or page error the config doesn't allow, a changed hash, a snapshot over the tolerance, a changed system order, a changed character path hash, or a load that ran in another physics configuration than it asked for. The probe hash leaves characters out; on `MAIN_THREAD` the runner compares the bridge's `getCharacterPaths()` hash instead (p610 D6: every character's pose per step, deterministic only there, p428). A scene's `inputScript` (`devTools/verify/inputs/<name>.json`, `{ frames: [{ step, down?, up? }] }`, keys as `KeyboardEvent.key`) is handed to the page by an init script and played as key events right before those fixed steps (0 = the first step after the load); the gym's runs 600 steps of the two players walking, turning, running, crouching and jumping (one tumbles), and the run's note lists the locomotion states each character went through. The system order (p607 Phase 1) is every world's systems per stage as `id@order`, read through the bridge's `getSystemOrder` last on the page (after the probe or the prod test settle, so lazily loaded debug systems are in) and compared by `systemOrder.ts` (Chromium only): registration order breaks ties, so a moved registration shows there first. `--config quick` is `workerSab` alone. It starts its own dev server on 8092 unless `--url`. Baselines are local and per backend (`.cache/verify/scenes/<webgpu|webgl>/`: snapshots depend on the GPU and the driver): `--update` records every run without errors as good, so update on `main`, then run on the branch; the last run, with a `*.diff.png` per failed snapshot, is in `last-run.json` and `last-run/`. On WSL2 headless WebGPU can't render, so the page renders on WebGL2 (SwiftShader) without `--headed` (logged): WebGPU-only regressions need a `--headed` run on a real GPU. `--browser firefox` (p605 Phase 6; Playwright's Firefox, `npx playwright-core install firefox` once) is the cross-browser determinism run: the debug configurations only, always WebGL2, probe hashes only (no snapshots), compared with Chromium's baseline for the same scene, configuration and steps (the `webgl` file's entry, else `webgpu`'s, which it checks agree), never `--update`, its last run in `.cache/verify/scenes/firefox/`. A difference means the simulation depends on the JS engine: an issue file and an `unstableHash` with `browsers: ['firefox']` (`skip` and `allowedErrors` take `browsers` too). Run it after the Chromium run passes on the same commit, and before the PR of a change to simulation code (p610, p614). The full matrix takes about an hour on SwiftShader. `playwright-core` is a project devDependency, pinned to the run-aekasha-js skill's version, so they share its downloaded Chromium. A baseline that's there but unreadable or of another format stops the run (exit 2, the run so far in `last-run.json`) unless `--update` records over it: it used to read as none, so every run was NEW and passed. A `scenes.config.ts` entry naming a scene the data doesn't have fails the start (a renamed scene would lose its settings), and so does a shell's `VITE_APP_ENV` other than `development` or `test` (its build has no test bridge). A missing or invalid input script fails its scene. Every page call has a timeout (the bridge's own plus 60 s, or 60 s: a hung readback), and `baseline.json`, `last-run.json` and the committed baselines are written atomically (`devTools/files.ts`).
- `yarn verify:baselines [--update [--allow-docs-drop]] [--no-build] [--docs]` — diffs three committed files in `devTools/verify/baselines/` (`devTools/verify/baselines.ts`, `_DONE_p601` Phase 3): `bundle.json` (every file in `dist/assets/` by its name without the content hash, bytes and gzip, plus the main chunk's modules per group: a package, each engine folder, toolkit, app), `api.json` (every export of the documented API by module, with its kind, from the Hub's TypeDoc model, and each public entry's export names, read from its `index.ts`: the public surface, p606) and `docs.json` (documented / total exports and class and interface members per folder, the Hub's coverage rule, and each folder's undocumented ones by name, `SceneLoader#LoadSceneProps`, `ECS#ECSWorld.addSystem`). It exits 1 on a chunk whose gzip grew over 1 % or 2 kB (at least 100 B), a new chunk, an export added, removed, moved or of another kind, a name added to or removed from an entry, or a folder with more undocumented exports or members than recorded (the docs ratchet, p605: it names each new one with its file and line; a new folder starts at none); shrinking, better coverage and deleting documented code pass. `--update` writes the current state: commit it with the change that explains it. It refuses a grown undocumented count unless `--allow-docs-drop` is given too (say why in the commit; a move that renames folders needs it, as p608's did and p609's will, since the ratchet reads each moved folder as a new one). The bundle's measuring, its diff and the build steps are `devTools/sbp/`'s (`bundleModel.ts`, `bundleDiff.ts`, `appBuild.ts`), shared with `yarn sbp` (p611 D1). It runs the build's bundle steps first (decoders, production gather, `vite build`, the dev gather again; no `tsc`, no Hub), 12-20 s; `--no-build` reuses `dist/` and `dist-stats/`. `--docs` checks (or records) `docs.json` alone, without the build, `api.json` or the progress log, in about 1 s (6 s when TypeDoc converts): the Stop hook runs it. Gzip sizes shift by a byte or two between builds with new content hashes, within the tolerance: don't commit such a `bundle.json` without a change that explains it. The same build, and each embed profile's (`bundle.<id>.json`, p611), is checked for debug code (p607 D7, `debugInProduction.ts`, its test next to it): a `_dbg__*` file in `dist/assets/`, a debug module with rendered code in any chunk, a debug asset (p611: an emitted file whose source is in a debug folder or whose every importer is a debug module, `listEmittedAssets`), or a feature's `ctx.onDebug` / `ctx.onDebugAfterStart` call left in a script (p612 D9: found by its text, `n.onDebug(`, since property names aren't minified; gate it with `if (IS_DEBUG_ENV)`) fails the run: a `_dbg__` module, or any module under an engine folder named `debug` in any case (`debug/`, `kernel/<area>/debug/`, `features/<name>/debug/`), the entry `debug/index.ts` aside (p608 D4: a debug folder holds nothing that ships, so a wrapper with rendered code is called from code that ships), and `--update` records nothing. The build sets `VITE_APP_ENV=production` itself, so a shell's `development` can't build the debug code in; a `dist/` from `yarn build:test` holds it by design, so `--no-build` after one fails.
- `yarn verify:embed [--profile <id>] [--no-build] [--headed] [--webgl]` (`devTools/verify/embed.ts`, p611 Phase 4): mounts each embed profile's build (`sbp.config.ts`, `dist-embed/<id>/`, built first unless `--no-build`) into a plain host page with its own styles (`embedHost.html`, served with the build at `/aekasha/` from its own server, on a free port of `localhost`), one page load per scenario since the engine mounts once per page load. `INLINE` at `width: '50%'`, `height: '80%'` of a 640 × 360 target: the container, the canvas and its drawing buffer at 320 × 288, something drawn, all following when the target grows to 800 × 400, `unmount()` leaving the target empty and a second mount throwing. `BACKGROUND`: the container and the canvas fill the viewport, drawn behind the content, a click on the heading reaching it and one in the middle not reaching the embed, nothing left after `unmount()`. In both, no computed style of the host's elements (`embedChecks.ts`' `HOST_STYLE_SELECTORS`) changes while mounted or after, and no console or page error. For the banner (`EXAMPLE_PROFILE`), a third page load: the Hub's embed example (`embedExample.html` at `/example.html`, whose regions `hub/pages/examples/embed/` includes) mounts in its hero at the target's size, turns, and its pause button pauses (no change over 400 ms) and resumes it. Each check after a mount, a resize or a turn polls for its state for up to 10 s (p619 V5: fixed 400 ms waits), and a page that never gets ready is that scenario's failure. A function named inside `page.evaluate` fails under tsx (its `__name` helper isn't in the page): inline it. Headless WebGPU (`launchChromium`, `browser.ts`, shared with the scene runner); `--webgl` (and WSL2 without `--headed`) is WebGL2 through SwiftShader. About 3 s without the build. Exits 1 on a failed scenario, 2 on an error.
- The `@example` check (`devTools/verify/examples.ts`, run by `examples.test.ts` in `yarn test`, so the Stop hook runs it; p606 Phase 8): every `@example` in TypeDoc's scope (`src/_engine`, `src/toolkit`, minus `_dbg__*`, tests and `index.ts`) type-checks as app code. The TS AST finds each tag and its code comes from the raw comment, so a finding has its source line. Each fenced block (ts / js; other languages skipped) is one example, an unfenced tag is all code. Each becomes a virtual module in `src/__examples__/` (a folder that doesn't exist) with one header line importing, from any entry, the entry names it uses but doesn't import or declare (values and `import type` apart, for `verbatimModuleSyntax`), and `export {}` (no shared scope). One in-memory program: the real `tsconfig.json` with its `.d.ts` roots, minus `noUnusedLocals` / `noUnusedParameters`; only the examples' diagnostics count. Free: 2304 / 2552 / 18004 (a name the reader has, `box`) and 2307 for a relative specifier (the reader's own `./CONFIG`); a misspelled entry fails. The test also checks four fixtures in the same program (about 1.3 s). Limits: an example's `declare module 'aekasha'` merges into the shared program (two conflicting ones would clash), and an internal name no entry exports passes as a free name.
- The module-level side effects test (`moduleSideEffects.test.ts`, p607 D8, in `yarn test`): no top-level statement that isn't a declaration (a call, an assignment, or an `if`, a loop, a block or a `try` around one: p617 G1 found a listener added in an `if`; an import, an export, a declaration and `export default` aren't read, nor is a declaration's initializer) in `src/_engine/`, `src/toolkit/`, `src/app/` or `src/*.ts`, except `_dbg__*` files (they run only through the debug loader's `import()`; found by name wherever they are, p608 D4), the two worker entries and `src/index.ts`. It has no allow-list: p607 moved every registration into an install, and p619 removed its empty `NOT_YET_INSTALLED`. A registration belongs in a feature's `install` (root `CLAUDE.md`, Engine features).
