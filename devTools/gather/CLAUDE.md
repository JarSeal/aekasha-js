Notes for the scene/asset data pipeline (`devTools/gatherAppData.ts`, `devTools/gather/`, the dev plugin `devTools/sceneGathererPlugin.ts`): the gatherer, the generated files, the feature manifest and `__saveData`, moved from the root, where an outline stays; scene loads are in `src/_engine/kernel/scene/CLAUDE.md`; the root `.claude/CLAUDE.md` keeps the project-wide rules, commands and workflow.

## Scene/asset data pipeline (JSON → generated code)

Scenes and assets are authored as JSON files under `src/app/**` (and the toolkit's under `src/toolkit/**`), named by suffix (e.g. `*.scene.json`, `*.mesh.json`, `*.camera.json`, `*.light.json`, `*.geometry.json`, `*.texture.json`, `*.textureArray.json`, `*.textureAtlas.json`, `*.material.json`, `*.importedAsset.json`, `*.skybox.json`, `*.postFx.json`, `*.impostor.json`, `*.mergeMaterial.json`; `GATHERED_SUFFIXES`). `devTools/gatherAppData.ts` runs it (`gatherSceneData({ pipeline?, profiles?, isProduction?, srcDir?, outDir? })`, the repo's by default; its steps in `devTools/gather/`, one module each: `gatheredJson.ts` the suffixes, schemas and `validateGatheredJson`; `context.ts` the registries, the id spaces and `readAssetJsons`, the one pass-1 reader for every type, which `registries.ts` and `textures.ts` use; `scenePass.ts` and `sceneAssets.ts` the scenes, `sources.ts` the files an asset points at; `mergedGeometries.ts` a `MERGED` geometry's part ids (p371 D2: pass 1 fails on a geometry JSON's part that names neither a geometry JSON nor an import's piece, `<importId>/…`, or names a `MERGED` one; the scene pass checks the inline ones alike and warns, only, for a part whose geometry or import the scene doesn't list; a node name isn't known before the import, so a wrong one fails at load); `mergeMaterials.ts` the merge material palettes (p374, `src/_engine/features/merging/CLAUDE.md`'s Merge materials: pass 1 registers each palette after the materials, its class checked and its table's entries and agreed state baked by `devTools/assetPipeline/mergeMaterials.ts`' `resolveMergeMaterial`, and each slot's array as a texture `<paletteId>.<slot>` in `mergeMaterialSlots`; the scene pass inlines a scene's `mergeMaterials` as `SceneMergeMaterial`s, appends their slot arrays to its `textures` and fails on a `mergeGroups` palette the scene doesn't list, `checkMergeGroupPalettes`); `textureClosure.ts` the scene's texture closure (p302 D6, `addTextureClosure`: the textures the scene's resolved data names that its `textures` doesn't give, by id, inline or as a listed atlas's slots, appended to its `textures` each once, in the order named; from the listed materials, a mesh's inline `mat` and its `matOverrides` (their `params` texture slots, `textureMapKeys`, and their `inputs` and each `nodes` socket's values, `staticDefines` aside, through `INPUT_DEPENDENCY_FNS`: the runtime's import-free `getTextureInputDependencies`, `getTextureArrayInputDependencies` and `getAtlasCellInputDependencies` (p299 D5: `{ textureArray, layer }` names the array, `{ atlas, slot, cell }` the slot `<atlas>.<slot>`) in `kernel/assets/MaterialInputRefs.ts`, on `devTools/engineImports.test.ts`' list; a resolver with a texture form, p303's, adds its function there; an array layer or atlas cell value is first checked against pass 1's registries (`getInputRefError`: a layer name not in the array's `__layers` or an index past them, an id of another kind of texture, an atlas no JSON has, a slot or cell it doesn't have), failing the gather as the scene's error naming the material and the input, and adds no id then; an app's own resolver's values aren't known, so its scene lists their textures), a spot light's `map` and the `backgroundTexture`; an id no asset JSON has fails the gather naming what names it; no `__dependencies` key, no loader change: the added entries get the save entries, ship checks, atlas expansion, unknown-id failure and streaming cut of a listed one, and the Assets tab can't tell them apart); `sources.ts` also drops an import's `merge` (build time only, p371 D3) from the generated data and fails on `merge` with a remote `fileName`; `saveEntries.ts`; `shipChecks.ts`; `output.ts`; `jsonSchemas.ts`). The scene pass resolves a scene's lists in `resolveSceneAssets`' order (`sceneAssets.ts`): cameras, lights, geometries, impostors (their atlas slots appended to `textures`), merge materials (their slot arrays appended too), materials, meshes, then the texture closure (it reads the resolved materials and meshes with their save entries), then the textures (so the appended ones resolve as listed ones), imports, sky boxes and PostFX; nothing before the textures reads a resolved texture:

1. Walks `src/`, finds files matching those suffixes.
2. Validates each against a Zod schema in `src/_engine/schemas/*.ts`, or next to its feature (`features/skybox/SkyBoxSchema.ts`, `features/lod/LodSchema.ts`, `features/lod/impostors/ImpostorSchema.ts`; all on `aekasha/schemas`). The scene and mesh schemas are composed (p607 D10): the kernel's fields plus each feature's `FeatureSchemaPart` (`skyBoxSchemaPart`, `postFxSchemaPart`, `spatialSchemaPart`, `lodSchemaPart`, `streamingSchemaPart`, `mergingSchemaPart`; `createSceneAssetSchema` / `createMeshAssetSchema`, `schemas/FeatureSchemas.ts`, which throws on a field two owners give), composed for the gatherer in `devTools/gather/engineSchemas.ts` (`ENGINE_SCHEMA_PARTS`, in the JSON Schemas' property order, so `.schemas/` didn't change; its test fails on an engine `*SchemaPart` missing from it, whose fields zod would strip). The gather fails on a file that doesn't parse or validate, an id two files of a type give (the first file keeps it) and an id a scene lists that no asset JSON has (p619 G1, G2, G12).
3. Emits `src/generated/`: `generatedAppData.json`, `generatedAppFns.ts` (a loader per id, `() => import(…)`, for the scene, TSL material and PostFX files: a scene's file loads with its scene, a TSL material's with its scene load's assets or by `loadTslMaterialFileAsync` (`createMaterial` throws naming it for a file nobody loaded), a PostFX pass's in `postFx()`'s `created` hook; each its own chunk in a build) and `index.ts`, whose `appData` `src/index.ts` passes to `InitEngine({ data })`. Each embed profile of `sbp.config.ts` gets the same three files with only its scenes in `src/generated/profiles/<id>/`, which its entry module binds (p611 D7, `devTools/gather/output.ts`; see `devTools/sbp/CLAUDE.md`). The engine never imports the folder: it keeps the data in `kernel/scene/AppData.ts` (`getAppData`, `@internal`; apps read it with `getGeneratedAppData` / `getGeneratedSceneData`), and `kernel/scene/Scene.ts`'s `registerScenesFromGeneratedData()` builds the scenes from it. Each gathered scene gets the feature manifest `__features` (`getSceneFeatureIds` in `devTools/gather/engineSchemas.ts`: the features whose part's fields the resolved scene or one of its meshes uses, given and not an empty list; always written, `[]` included). `InitEngine`'s `checkSceneFeatures` throws on a scene that needs a feature `features` doesn't list, naming each scene and the factory; a scene without the key (data from before it) isn't checked. Only data counts: a sky box or LOD made in scene code isn't in it. Then a streaming scene's content is cut into cells (p353 Phase 3, `gather/streamingManifest.ts`, the scene pass's last step, after `__features`): its resolved meshes and point and spot lights, and the assets only they use, go into its `__streaming` manifest by position (an oversized mesh into every cell it overlaps, in their kept layers; a cell's mesh also gives its cell a far entry, its coarsest explicit LOD level, or without `lod` itself when it groups (p377 D1; `streaming.farEntries: 'LOD_LEVELS'` gives only the levels', D2), alike ones grouped into one `farMeshes` entry per cell, naming its near entries by their index in the manifest's `meshes` (`entries`, p377 D3); each cell's near, far and kept layers list the assets they reference and their estimates: p353 Phase 5 D7-D9), a material's textures are what its `params`, `inputs` and `nodes` name (`addMaterialFieldRefs`), its own lists keep the base, and `streaming.base` / `radii` / `farEntries` (build time only) are dropped; a mesh's `MERGED` geometry brings its parts' refs (one level), and has no extent the gather measures, so it's placed as a point (a large one needs `radii`); the rules are `src/_engine/features/streaming/CLAUDE.md`'s JSON content. An embed profile takes a cell-only TSL material's loader from the manifest.
4. Also compiles the Zod schemas to plain JSON Schema files in `.schemas/*.schema.json` (used for editor autocomplete/validation on the asset JSON files themselves): `writeJsonSchemas` (`gather/jsonSchemas.ts`), run by `yarn gatherAppData`, `yarn assets` and the dev plugin's (re)start, writing a file only when it changed; importing `gatherAppData.ts` writes nothing (nor does importing `copyDecoders.ts`).

Per-scene overrides live in each asset file's `__saveData` (`{ [sceneId]: [latest, ...older] }`; only the latest entry is applied, its fields replacing the asset's but for `params`, a TSL material's `inputs` and `nodes`, a sky box's definition (`applySkyBoxSaveEntry`) and a mesh's `geo` / `mat` props of the same type, merged key by key; a mesh's merged props are validated again). An entry's `__meta` can carry `engineVersion`/`toolkitVersion`/`appVersion` (`src/_engine/schemas/_SaveDataSchema.ts`); anything that writes save entries should stamp all three, and the gatherer warns when an applied entry comes from another major version.

This runs via `yarn gatherAppData`, and automatically on file add/change/delete during `yarn dev` through the custom `sceneGathererPlugin` Vite plugin (`devTools/sceneGathererPlugin.ts`, its queue `devTools/workQueue.ts`: debounced, one run at a time; triggers a full reload, or surfaces a Vite error overlay if validation or an asset fails). A gather writes a generated file only when its content changed (`writeFileIfChanged`, atomic, p619 G7; `gatherSceneData` returns `{ isGathered, changedFiles }`), so a gather that changes nothing reloads no page. Each gather the plugin runs first sends the custom HMR event `aek:gather` (`DevDataGatheredEvent` in `debug/DevFilesProtocol.ts`: `done` / `failed`, the changed files, the asset errors, `willReload`), which the dev files' `onDevDataGathered` delivers; the page reloads when the generated data changed or a source file did (one served as it is changes no `__url`), and a failed gather keeps it. Both run the asset pipeline (`_DONE_p300`) first, cached: the gather needs its run for the `__url`s. The plugin builds only what a change touched (an asset JSON, a source file, `assets.config.json`, `assets.optimization` in `src/CONFIG.ts`) and reuses its last run when nothing the pipeline reads changed.
