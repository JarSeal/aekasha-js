## Scene/asset data pipeline (JSON → generated code)

Scenes and assets are authored as JSON files under `src/app/**` (and the toolkit's under `src/toolkit/**`), named by suffix (e.g. `*.scene.json`, `*.mesh.json`, `*.camera.json`, `*.light.json`, `*.geometry.json`, `*.texture.json`, `*.textureArray.json`, `*.textureAtlas.json`, `*.material.json`, `*.importedAsset.json`, `*.skybox.json`, `*.postFx.json`, `*.impostor.json`; `GATHERED_SUFFIXES`). `devTools/gatherAppData.ts` runs it (`gatherSceneData({ pipeline?, profiles?, isProduction?, srcDir?, outDir? })`, the repo's by default; its steps in `devTools/gather/`, one module each: `gatheredJson.ts` the suffixes, schemas and `validateGatheredJson`; `context.ts` the registries, the id spaces and `readAssetJsons`, the one pass-1 reader for every type, which `registries.ts` and `textures.ts` use; `scenePass.ts` and `sceneAssets.ts` the scenes, `sources.ts` the files an asset points at; `saveEntries.ts`; `shipChecks.ts`; `output.ts`; `jsonSchemas.ts`):

1. Walks `src/`, finds files matching those suffixes.
2. Validates each against a Zod schema in `src/_engine/schemas/*.ts`, or next to its feature (`features/skybox/SkyBoxSchema.ts`, `features/lod/LodSchema.ts`, `features/lod/impostors/ImpostorSchema.ts`; all on `aekasha/schemas`). The scene and mesh schemas are composed (p607 D10): the kernel's fields plus each feature's `FeatureSchemaPart` (`skyBoxSchemaPart`, `postFxSchemaPart`, `spatialSchemaPart`, `lodSchemaPart`; `createSceneAssetSchema` / `createMeshAssetSchema`, `schemas/FeatureSchemas.ts`, which throws on a field two owners give), composed for the gatherer in `devTools/gather/engineSchemas.ts` (`ENGINE_SCHEMA_PARTS`, in the JSON Schemas' property order, so `.schemas/` didn't change; its test fails on an engine `*SchemaPart` missing from it, whose fields zod would strip). The gather fails on a file that doesn't parse or validate, an id two files of a type give (the first file keeps it) and an id a scene lists that no asset JSON has (p619 G1, G2, G12).
3. Emits `src/generated/`: `generatedAppData.json`, `generatedAppFns.ts` (a loader per id, `() => import(…)`, for the scene, TSL material and PostFX files: a scene's file loads with its scene, a TSL material's with its scene load's assets or by `loadTslMaterialFileAsync` (`createMaterial` throws naming it for a file nobody loaded), a PostFX pass's in `postFx()`'s `created` hook; each its own chunk in a build) and `index.ts`, whose `appData` `src/index.ts` passes to `InitEngine({ data })`. Each embed profile of `sbp.config.ts` gets the same three files with only its scenes in `src/generated/profiles/<id>/`, which its entry module binds (p611 D7, `devTools/gather/output.ts`; see `devTools/sbp/CLAUDE.md`). The engine never imports the folder: it keeps the data in `kernel/scene/AppData.ts` (`getAppData`, `@internal`; apps read it with `getGeneratedAppData` / `getGeneratedSceneData`), and `kernel/scene/Scene.ts`'s `registerScenesFromGeneratedData()` builds the scenes from it. Each gathered scene gets the feature manifest `__features` (`getSceneFeatureIds` in `devTools/gather/engineSchemas.ts`: the features whose part's fields the resolved scene or one of its meshes uses, given and not an empty list; always written, `[]` included). `InitEngine`'s `checkSceneFeatures` throws on a scene that needs a feature `features` doesn't list, naming each scene and the factory; a scene without the key (data from before it) isn't checked. Only data counts: a sky box or LOD made in scene code isn't in it.
4. Also compiles the Zod schemas to plain JSON Schema files in `.schemas/*.schema.json` (used for editor autocomplete/validation on the asset JSON files themselves): `writeJsonSchemas` (`gather/jsonSchemas.ts`), run by `yarn gatherAppData`, `yarn assets` and the dev plugin's (re)start, writing a file only when it changed; importing `gatherAppData.ts` writes nothing (nor does importing `copyDecoders.ts`).

Per-scene overrides live in each asset file's `__saveData` (`{ [sceneId]: [latest, ...older] }`; only the latest entry is applied, its fields replacing the asset's but for `params`, a TSL material's `nodes`, a sky box's definition (`applySkyBoxSaveEntry`) and a mesh's `geo` / `mat` props of the same type, merged key by key; a mesh's merged props are validated again). An entry's `__meta` can carry `engineVersion`/`toolkitVersion`/`appVersion` (`src/_engine/schemas/_SaveDataSchema.ts`); anything that writes save entries should stamp all three, and the gatherer warns when an applied entry comes from another major version.

This runs via `yarn gatherAppData`, and automatically on file add/change/delete during `yarn dev` through the custom `sceneGathererPlugin` Vite plugin (`devTools/sceneGathererPlugin.ts`, its queue `devTools/workQueue.ts`: debounced, one run at a time; triggers a full reload, or surfaces a Vite error overlay if validation or an asset fails). A gather writes a generated file only when its content changed (`writeFileIfChanged`, atomic, p619 G7; `gatherSceneData` returns `{ isGathered, changedFiles }`), so a gather that changes nothing reloads no page. Each gather the plugin runs first sends the custom HMR event `aek:gather` (`DevDataGatheredEvent` in `debug/DevFilesProtocol.ts`: `done` / `failed`, the changed files, the asset errors, `willReload`), which the dev files' `onDevDataGathered` delivers; the page reloads when the generated data changed or a source file did (one served as it is changes no `__url`), and a failed gather keeps it. Both run the asset pipeline (`_DONE_p300`) first, cached: the gather needs its run for the `__url`s. The plugin builds only what a change touched (an asset JSON, a source file, `assets.config.json`, `assets.optimization` in `src/CONFIG.ts`) and reuses its last run when nothing the pipeline reads changed.
