# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Aekasha (Ækasha) — a WebGPU/Three.js + Rapier physics game engine framework (package name `aekasha-js`). It's a "template" repo: an engine (`_engine`) plus one example app (`app`) built on top of it.

### Aekasha brand, feeling, and core principles

Ækasha is a high-performance WebGPU framework for the modern web. Driven by a modular ECS and a threaded physics core, it acts as the "fifth element" for developers — the invisible medium where complex data transforms into immersive reality.

Primordial Performance: Engineered from the ground up for WebGPU, Ækasha treats the GPU not as a peripheral, but as the primary canvas for logic and rendering.

Modular Infinity: Like the Akasha of myth, the framework is infinite and modular. You only bring into existence what you need, keeping the "memory space" clean and light.

Threaded Reality: By offloading heavy physics calculations and asset loading to dedicated threads via the physics API and asset loading API, Ækasha ensures that the "flow" of the user experience remains uninterrupted.

Smallest Build Possible: Every byte before the first frame is a wait. A build carries only what the app uses (features opt in, the heavy parts load on first use, debug code never ships), `yarn sbp` measures every build against its budgets, and a scene is light enough to embed in any page.

Maintain the brand, feeling, and core principles in creating the best UX for both, the developer and the end user!

### Three-folder split

- `src/_engine/` — the engine. Treat as stable/library code; changes here should be minimal and purposeful. Its folders (p602's map, applied by p608; `devTools/layout/layoutRules.ts` keeps them as rules, so `layout.test.ts` fails on a file outside them):
  - `kernel/` — what every app runs, one folder per area: `ecs/`, `loop/` (`MainLoop`, the stages), `config/` (`Config`, the env flags, the debug loaders in `DebugModules.ts`), `init/` (`InitEngine`, the feature contract, the kernel's install), `scene/`, `assets/` (with `import/` and the assets `worker/`), `render/` (`Renderer`, `Snapshot`, `Views`, the three maths), `camera/`, `light/`, `mesh/`, `input/`.
  - `features/` — the nine opt-in features (see Bootstrap flow), one folder each: its entry `index.ts`, its `<Name>Feature.ts`, its worker, its `debug/` modules and its nested `CLAUDE.md`.
  - `ui/` — the UI kit (`aekasha/ui`), by group (p803 D2, a layout rule per folder): `core/` (`CMP`, the HUD, the bounds, motion, the theme watch, the icons), `components/` (buttons, links, badges, tags, key hints, input glyphs, spinners, progress bars, skeletons, dividers, empty states, the loading overlay, tabs, the accordion, the splitter), `overlays/` (the windows and dialogs, the toaster, the overlay layer: its stack, the focus trap, the anchor, the tooltip, the popover, the menu, the context menu and the command palette), `forms/` (p804: the fields, value editors and containers on one binding and refresh scheduler, `forms/binding/`: number fields, sliders and range sliders, radio groups and segmented controls, selects (the drop-down), text fields, checkboxes and switches, monitors and graph monitors; the colour field with its lazy picker, vectors, rotations and quaternions, the angle dial, the 2D pad, the gradient and curve editors; folders, fieldsets, the property grid with its declarative items, and the form), `data/` (p805: the data display: the list with its opt-in virtual rows and reorder, the tree, the table, the parts, the filter and the selection its collections share, the graphs in `data/graphs/` (sparkline, donut, stacked bar, chart, time series) and the stat tile), `testing/` (the tests' helpers), the global styles (`ui/styles/`, with the design tokens the kit, the debugger and the Hub share: `tokens.css`, p801) and the opt-in fonts (`ui/fonts/`, the `aekasha/ui/fonts` entry: IBM Plex Sans and Mono).
  - `debug/` — the debugger framework (`aekasha/debug`): the drawer, the tab host, the pane builder, undo / redo, the profiler, GPU memory, the on-screen tools, the editor views, the 3D symbols and the dev files client. A kernel area's or a feature's own debug modules are in its `debug/` subfolder (see Debug system).
  - `utils/` (pure: no three, DOM or ECS; storage the exception), `schemas/` (the asset JSON schemas; a feature's own next to it), `types/` (global declarations). The engine root holds only the entry `index.ts` and `ModuleLoad.test.ts`.
- `src/toolkit/` — reusable ECS components/modules, models, textures, shaders, and assets meant to be imported as-is or copy-pasted into `app` and modified. A catalogue by category (p609 D1, kept as rules in `layoutRules.ts` like the engine's): the code categories have an entry each (`TOOLKIT_CATEGORIES`), the asset categories none (asset JSONs, reached by id through the gatherer). A piece that grows a second file gets its own folder inside its kind.
  - `ecs/` (`aekasha/toolkit/ecs`): `effects/` (a system registered once per world: `FollowTool`, `HoverEffect` and `SunShadowFit` act on an entity's component, `MutualGravity` on the bodies `addGravityBody` lists) and `gameplay/` (`FollowObjectCameraRig`, `MovingPlatform`).
  - `geometry/` (`aekasha/toolkit/geometry`): `generate/` (`Asteroid`, `Foliage`, `Terrain`), `scatter/` (`ScatterOnSurface`); the generators draw from the engine's `createSeededRandom` (`utils/SeededRandom.ts`, p610; the entry still exports one, `geometry/SeededRandom.ts`' `@deprecated` copy, until toolkit 3.0.0).
  - `materials/` (`aekasha/toolkit/materials`): a folder per material named by its id (`<id>.material.json`, `<id>.tsl.ts`), and `TriplanarProjection.ts`, the TSL helper they share.
  - `models/<category>/<id>/`, `textures/<id>/` and `skyboxes/<id>/`: assets, each source next to its JSON. Model categories: `brand/` (the Æ symbol); p450 (still a prompt in `docs/templates/todo-plan-prompts.txt`) adds `reference/` and `nature/`, and the first textures and sky boxes.
  - Models (`toolkit/models/<category>/<id>/`): the source GLB sits next to its `*.importedAsset.json` (a JSON-relative `fileName`); the asset pipeline writes the optimized output into `src/public/aek-assets/`. The first is the Ækasha symbol (`aekashaSymbol`): the Æ glyph of `src/public/favicon.svg` extruded with a small bevel, 1 unit high, centred, facing +z, Draco-compressed (the JSON's `optimize.mesh.codec: "draco"` keeps it so). `devTools/toolkit/buildAekashaSymbol.ts` builds the GLB (three's `SVGLoader` with `linkedom`'s `DOMParser`, `ExtrudeGeometry`, gltf-transform); run it with `npx tsx` when the glyph changes and commit the GLB. It fails when the glyph has no hole, and leaves the glTF scene unnamed (GLTFLoader makes scene and node names unique together, so a scene named like the node renames the node and its geometry id).
- `src/app/` — the actual game/app: scenes and asset JSON files, app-specific managers/components. One folder per scene (p609 D2, kept as rules in `layoutRules.ts`, so `layout.test.ts` fails on a file elsewhere):
  - `scenes/<sceneId>/`: `<sceneId>.scene.json`, `<sceneId>.ts` (its `sceneFile`), its `_dbg__` module and `<sceneId>.hub.png`, its own modules (`lodShowcase/lanes/`) and the asset JSONs only this scene uses, with their sources. File and folder names follow the scene id, which stays (it keys `__saveData`, the scene runner's baselines, the LS state and `?startScene=`).
  - `examples/<name>/`: the Hub's example scenes (see `hub/CLAUDE.md`).
  - `shared/`: app code several scenes use (`characterVisual.ts`, `largeWorldRock.ts`, the verification scenes' `verifyHarness.ts`); code one scene uses stays in its folder. The ECS example's `SpinComponent` / `SpinSystem` stay in `examples/ecs/` though another scene uses them: the ECS page shows them from there.
  - `profiles/<id>/`: an SBP embed profile (p611 D7, `sbp.config.ts`): its entry module (`<id>.embed.ts`, binding the profile's generated data, `src/generated/profiles/<id>/`, and exporting `mount`), and its scene with that scene's assets, laid out as a scene folder. `banner` is the floor: one code-made scene, no feature; `uiKit` (its scene `uiKitEmbed`) the UI kit in an embed, which `yarn verify:embed` checks (p801 D9). The app-wide registrations stay in `src/*.ts` (`AppECSPlugins.ts`, `AppECSRegistry.ts`).
  - The shared assets in their type's folder (`impostors/`, `skyboxes/`, `textures/`, `postFx/`, and `cameras/`, `lights/`, `materials/`, `meshes/`, `geometries/`, `importedAssets/` when one is shared). "Only this scene uses it" means no other scene JSON, scene file or asset JSON names its id: an asset a second scene starts using moves to its type's folder, one only a scene uses goes into that scene's folder. A moved asset JSON keeps its id, so the scenes naming it don't change; its `$schema` and relative paths (`image`, `fileName`) do, and a scene JSON's `sceneFile` is relative to `src/app/`.

The boundary is a lint rule (p606, errors everywhere, `eslint.config.js`):

- `import/no-restricted-paths` with `LAYER_ZONES`: the engine imports no toolkit, app, `src/generated/` or `src/*.ts` file; the toolkit no app, `src/generated/` or `src/*.ts` file; nothing outside the engine an `_engine/` path (only the `aekasha*` entries, see Build config notes); a toolkit category no other category's files (`TOOLKIT_CATEGORIES`, listed by hand: a new category goes there and in `devTools/aliases.ts`); the app and `src/*.ts` no toolkit file. It resolves the path (the node resolver with `.ts`; the aliases stay unresolved, so unchecked), so `import type` and `import()` are checked too. The one exception: the generated code's imports of the toolkit's `*.tsl.ts` materials (assets). Trap: in a zone whose `from` is a glob, `except` isn't resolved against `basePath` (the exceptions are absolute), and one zone's `from` is all globs or none.
- `@typescript-eslint/no-restricted-imports`: no `aekasha*` import inside the engine (an entry imported by the code it re-exports makes cycles), no kernel import of a `features/` path but `import type` (p612 D2: the kernel names a feature's types for the data it holds or carries for it, component data, config, scene and mesh definitions, import params and the assets worker's messages, and imports none of its code; the types stay in the feature, the layout report, `devTools/layout/layoutReport.ts`, lists each; a kernel `_dbg__` module isn't checked, an `import()` neither), and no static import of a `_dbg__` module outside `_dbg__*` files (debug code is found by name, p608 D4; `import type` is allowed; `import()` isn't checked, which is the point). `src/_engine/debug/*.ts`, the thin entries, aren't exempt, and the engine's debug files keep the `aekasha*` rule. A later config entry replaces the rule's options for its files, so each lists every pattern that applies there.

### ECS core

`src/_engine/kernel/ecs/ECS.ts` defines `ECSWorld`, a bitwise-packed (index + generation) entity/component store. Plugins and component hooks are static (every world) and register from an install, never at module load: the kernel's, each feature's through its `FeatureContext`, and the app's in `src/AppECSPlugins.ts`' `appECSPlugins` (listed last in `features`). An app or toolkit module adds its component keys with `declare module 'aekasha' { interface ComponentDataMap { … } }`. The stages (`kernel/loop/SystemStages.ts`) run in this order every frame: `MAIN → APP_PRE_PHYSICS → APP_POST_PHYSICS → APP_LOGIC → APP_RENDER_SYNC → LATE_MAIN`, plus `APP_PHYSICS_STEP` 0-N times per frame, right before each fixed physics sub-step; physics syncs into ECS transforms in `APP_POST_PHYSICS`, ECS into Three.js `Object3D`s in `APP_RENDER_SYNC`. Detail: `src/_engine/kernel/ecs/CLAUDE.md`.

### Scene/asset data pipeline (JSON → generated code)

Scenes and assets are JSON files under `src/app/**` and `src/toolkit/**`, named by suffix (`*.scene.json`, `*.mesh.json`, …; `GATHERED_SUFFIXES`), each validated against its Zod schema (`src/_engine/schemas/`, or next to its feature) and gathered by `devTools/gatherAppData.ts` into `src/generated/`, whose `appData` `src/index.ts` passes to `InitEngine({ data })`. It runs with `yarn gatherAppData`, before `dev` and `build`, and on every save in `yarn dev` (`sceneGathererPlugin`). Per-scene overrides live in each asset file's `__saveData`. Detail: `devTools/gather/CLAUDE.md`; scene loads: `src/_engine/kernel/scene/CLAUDE.md`.

### Bootstrap flow

`src/index.html` → `src/index.ts` → `InitEngine({ config, data, features, start })` (`kernel/init/InitEngine.ts`, once per page load), which reads the environment (`initEnvironment`), takes `config` (`src/CONFIG.ts`), checks `features` and the scenes' feature manifests, keeps `data`, installs the kernel (`installKernel`), creates the first ECS world, installs `features` in list order, registers the scenes, adds the debug tooling (debug env), awaits the app's `start` and starts the main loop once the root scene has children. A feature is an `EngineFeature` (`{ id, requires?, install(ctx) }`) that reaches the kernel only through its `FeatureContext`; the nine are `physics()`, `character()`, `skyBox()`, `lod()`, `spatial()`, `instancing()`, `lines()`, `postFx()` and `viewports()`, and the template lists all nine in that order, then `appECSPlugins`. `mountAekasha` (`kernel/init/Mount.ts`) runs the same boot into an element of a page it doesn't own. The boot step by step, the embed boot and the feature contract (Engine features): `src/_engine/kernel/init/CLAUDE.md`.

### Debug system (dual-layer, lazy-loaded)

Debug tooling (Tweakpane-based) is split into two layers so it tree-shakes out of production builds:

- `src/_engine/debug/*.ts` and other engine modules (e.g. `kernel/render/Renderer.ts`'s `createRendererDebugGUI`) are thin public entry points that, only when `IS_DEBUG_ENV` is true, dynamically `import()` the real implementation via `loadDebugModuleAsync`/`useDebug` (`src/_engine/kernel/config/DebugModules.ts`, next to `Config.ts`: shipping code calls them, so they aren't in a debug folder, p608 D2).
- `__AEK_DEBUG__` (p607 D7, see Build config) is false in a production build: `initEnvironment` never sets the debug flags there, so every `IS_DEBUG_ENV` branch, the `debug/*.ts` wrappers it was the only user of and their `_dbg__` chunks fold away (`yarn verify:baselines` fails on any left: a `_dbg__` module, or any module in an engine folder named `debug`, the entry aside), and both loaders return `null` first. A feature registers its debug tools with `ctx.onDebug` / `onDebugAfterStart` (`src/_engine/kernel/init/CLAUDE.md`, Engine features).
- The actual Tweakpane implementations live in files prefixed `_dbg__`, next to the code they debug: the debugger framework's in `debug/` (`_dbg__DebuggerGUI.ts`), a kernel area's or a feature's in its own `debug/` subfolder (`kernel/render/debug/_dbg__Renderer.ts`, `kernel/camera/debug/`, `features/skybox/debug/`). A debug folder holds nothing that ships (p608 D4: the production check above). Follow this `_dbg__` + dynamic-import pattern when adding new debug panels for engine-level features.
- The debug drawer itself is toggled in-app with the `h` key (the engine's default debug key `sc-toggle-debug-drawer`, rebindable in `src/CONFIG.ts`' `debugKeys`) via `toggleDrawer()`.
- Draggable windows are the UI kit's (`src/_engine/ui/CLAUDE.md`: kinds, registration, LS, scene loads). A debug module's edit window per entity is a window kind, registered at its `_dbg__` module's load.

Detail: `src/_engine/debug/CLAUDE.md` (the About dialog, debug keys, the test bridge, the profiler, GPU memory, drawer tabs) and `devTools/devFiles/CLAUDE.md` (dev files).

### Physics

The `physics()` feature (`features/physics/`, on `aekasha/physics`): Rapier behind an engine-agnostic Physics API, on a worker thread by default (`AppConfig.physics.workerTarget`, `'WORKER_THREAD'` or `'MAIN_THREAD'`), with every message through one transport and the transforms back through one shared triple buffer. Bodies are ECS components made by `createPhysicsEntity` (`async`, the entry point app code uses), and simulation tiers let a large world freeze, disable or remove bodies. The layout, the worker targets, the deterministic loads and the probe, the tiers and imported physics: `src/_engine/features/physics/CLAUDE.md`.

Scene loads are deterministic (p101): physics is held for the whole load, the world is replaced with a fresh one, and stepping resumes only after every `createPhysicsEntity` call of the load has finished. So a scene simulates identically on every visit, in both worker targets. The rules for simulation code:

- No physics entity survives a scene switch, and any body/collider reference from the previous scene is stale. Deleting one is a quiet no-op.
- Physics writes (poses, velocities, impulses, kinematic targets) go in `APP_PHYSICS_STEP` systems or in scene-load code. Writes from per-frame stages depend on frame timing. In `WORKER_THREAD` mode, `APP_PHYSICS_STEP` commands are captured per sub-step and cloned at capture, so reusing scratch vectors is safe.
- `getPhysicsSubStepIndex()` is the step clock for `APP_PHYSICS_STEP` systems (-1 outside a sub-step), and `addPhysicsStepGate(step)` makes stepping wait for something.
- Characters (the dynamic controller, `features/character/controllers/dynamic/`) are deterministic on `MAIN_THREAD` (p610): durations count fixed steps (`getPhysicsSubStepIndex`; the configured durations stay in ms), the tumble start draws from the seeded stream `character:<id>`, the casts are synchronous, and the sensor callbacks only record (the tick writes the body). Their brains run right before the controllers in the same step and read action maps sampled right before it (`kernel/input/`), so a recorded input replays step for step. In `WORKER_THREAD` mode they aren't: the tick runs on the main thread against the latched snapshot and async casts (p428). Detail: `src/_engine/features/character/CLAUDE.md`.
- Randomness in simulation code comes from a named stream (`getRandomStream(name)`, `utils/RandomStreams.ts`, on `aekasha`): seeded from the world seed (`setRandomSeed`) and the name, restarted by every `loadScene` (right before the physics world is replaced), so a scene draws the same numbers on every visit.
- The simulation lint (`SIMULATION_FILES` in `eslint.config.js`: the physics and character files (the engine's brains included), `movingPlatform/`, `MutualGravity.ts`, the gym's `GymDummyBrain.ts`, `physicsTiers.ts` (its plough); not the input devices, which time DOM events) makes `Math.random`, `performance.now()`, `Date.now()` and `new Date` errors there. Profiling reads go through `readStatsClock` (`utils/StatsClock.ts`, measurement only); the known violations are allow-listed per file with their plan (`features/physics/PhysicsWallClock.ts` under the deprecated `getPhysGameTime`, which no simulation code reads, removed in engine 6.0.0), never disabled inline. A new simulation file goes on the list.

### Build config notes (`vite.config.ts`)

- `root: './src'`, output to `../dist`.
- `vite-plugin-wasm` for Rapier's WASM binary.
- `worker: { format: 'es' }`: ES module workers, so a worker can load chunks on demand (an IIFE worker can't be code-split, and a dynamic `import()` in one fails `vite build`). The dev server loads workers as modules either way.
- `server.fs.allow: [<repo root>]`: `/@fs/` serves the repo (`node_modules`, `.tools/`) but nothing outside it, since the dev server is on the LAN (`--host`).
- `crossOriginIsolationPlugin`: the COOP / COEP headers on every dev server response (`SharedArrayBuffer`, physics' shared transform buffer); `basicSsl()` only under `AEK_DEV_HTTPS=true`.
- The dev-only `sceneGathererPlugin` (see data pipeline above), the dev-only `devFilesPlugin` (see Debug system), the dev-only `hubPlugin` (after `devFilesPlugin`; `/hub/`, see Ækasha Hub) and an `html-transform` plugin that injects `%APP_NAME%`/`%VERSION_CHECKSUM%`/etc. placeholders (sourced from `package.json`'s `app_metadata`/`engine_metadata`/`toolkit_metadata` through `devTools/projectMetadata.ts`) into `index.html`. In a build, `assetOutputsBuildPlugin` copies the asset outputs the production data loads into `dist/aek-assets/`; with `AEK_EMBED_PROFILE=<id>` the config is merged with the embed's (`getEmbedBuildConfig`, `embedOutputsPlugin` in its place; `devTools/sbp/CLAUDE.md`).
- `define`: `__PROJECT_METADATA__` and `__AEK_DEBUG__` (p607 D7): true when `VITE_APP_ENV` is `development` or `test` (read from `process.env`; `yarn build` sets none, which is production), false otherwise, dev server and workers included; `vitest.config.ts` defines it `true`, `types/typings.d.ts` declares it. False folds the debug flags and the code behind them (see Debug system).
- `rollup-plugin-visualizer` writes a bundle treemap to `dist-stats/bundle-stats.html`, and `devTools/sbp/moduleSizesPlugin.ts` (in `plugins` and `worker.plugins`, p619) each module's size after minification, the worker builds' too, to `dist-stats/module-sizes.json`: what `yarn sbp`'s groups and the production debug check read (`devTools/sbp/CLAUDE.md`).
- The public entries' aliases (`aekasha`, `aekasha/<feature>`, `aekasha/toolkit/<category>`, p606) come from one list, `devTools/aliases.ts`: `resolve.alias` here and in `vitest.config.ts`, and `tsconfig.json`'s `paths` (a copy `devTools/aliases.test.ts` checks). Each alias is exact (`^aekasha$`), so an entry not in the list fails to resolve. The toolkit, the app, `src/*.ts` and the generated code import the engine only through them; engine code imports engine code by relative path (both are lint rules, see Three-folder split).
- `package.json`'s `"sideEffects": ["**/*.scss", "**/*.css", "./src/_engine/ui/fonts/index.ts"]` (p607 D13): every other module is side-effect free, so the build keeps only what's used of a module (the entries' re-exports included) and drops a module none of whose names are used, with its top-level code. Vite applies it to the project's own files through its resolver (relative imports, in a build), and that wins over Rollup's `treeshake.moduleSideEffects` (the entries' function it replaced made no difference with it). So nothing may register at module load outside `_dbg__` modules (`moduleSideEffects.test.ts`), and an entry file holds only named `export … from` (`aliases.test.ts`). The one exception is the stylesheet entry `aekasha/ui/fonts` (p801 D8): `import './fonts.css'` alone, listed in `sideEffects` because a build drops a side-effect-free module's stylesheet import with it, and `aliases.test.ts` allows an entry of `.css` imports only when `sideEffects` lists it. esbuild reads the field too, where Vite bundles `vite.config.ts` with its `devTools/` imports, so a devTools module the config loads registers nothing at load either (p619 H6: the Hub's directives are a list `createHubMarkdown` takes; `./devTools/**` was listed for them). The dev server doesn't tree-shake, so there importing an entry runs every module it re-exports.

## Coding standards

The full text, with examples, is the Hub page `hub/pages/documentation/coding-standards/` (`intro.md`, `jsdoc.md`). In one line each:

- Layering: engine ← toolkit ← app, enforced by the lint; outside the engine only `aekasha*` entries, inside it only relative paths; the kernel imports a feature's types only (`import type`); a feature owns its folder; debug code in colocated `_dbg__` modules, reached only through the debug loader.
- Public API: entry points only (an entry file is named `export … from` lines only, the stylesheet entry `aekasha/ui/fonts` aside), everything else `@internal`; options objects past two parameters or any optional one; no internal types in public signatures; a UI kit component written as `src/_engine/ui/CLAUDE.md`'s Writing a component says.
- Naming: `create`/`delete`, `register`/`unregister`, `get`/`set`, `*Async`, `on*` returning the remover, `is`/`has`; PascalCase files (an asset id's file keeps the id); no `Manager` suffix; no names differing only in case.
- Size: about 800 lines per file and 150 per function or closure, or the file's header says why not.
- Async and disposal: re-check the scene / entity / request after every `await`, and say in the JSDoc which overlapping call wins; one owner disposes each resource; listeners and timers return or register their cleanup.
- Per-frame code: no allocations, storages read once per frame, no redundant GPU state changes (`perf-auditor` agent).
- Smallest build: no module-level side effects (register in an install; `moduleSideEffects.test.ts`, and a top-level `const x = register()` it can't see is still one), debug code behind the folded debug flags and out of `try` blocks, heavy dependencies behind `import()`, no `Addons.js` barrel.
- Simulation (`APP_PHYSICS_STEP`, physics, controllers, AI): step-index time, seeded RNG, intents as the only input, state read at the step (never synced `TRANSFORM`s or interpolated poses), plain-data messages, `import type` across the boundary, data components, one Rapier build.
- Type hygiene: no `any`; `eslint-disable` with `-- reason`; a TODO names its issue file or plan.
- Dev tools (p619 D8, K3): they import the engine by path, only the schemas entry file (`src/_engine/schemas/index.ts`; the `aekasha/schemas` alias doesn't resolve in Vite's bundle of `vite.config.ts`), the modules `devTools/engineImports.test.ts` lists with their reasons (each loads zod at most, or the packages its entry names; `TestBridge.ts` with `import type` only), and types from any entry with `import type`; the test fails on anything else. The repo's folders come from `devTools/paths.ts` (the Hub's from `devTools/hub/paths.ts`, built on it), `sha256`, atomic and changed-only writes and the source walk from `devTools/files.ts`, git from `devTools/git.ts`. A `never` helper is a `function` declaration (an arrow's call doesn't narrow). A command's `main()` runs only when its file is the script run (a test or the Vite config imports it). New tool code names promises `*Async` (K4: older tool code isn't renamed).
- JSDoc: a summary on every export saying what the signature can't; `@param name text` (no hyphen, no type) and `@returns` only where they add; `@example` on entry APIs; `@remarks` for traps; `@template` for type parameters; empty `@internal` on its own line; `@deprecated` with its replacement and removal major; `{@link}` only to public names (on an entry; an internal export in backticks, or the Hub warns); Zod types documented on the alias and on each shape key. `eslint-plugin-jsdoc` checks the shape as errors (`eslint.config.js`; no `require-*` rule: presence is the ratchet's). It's pinned at 63.3.3, the last version that runs on `.nvmrc`'s Node 22.13.0 (64+ needs ≥ 22.22.2). Its `empty-tags` and `no-types` fixers delete text, and the hooks run `--fix` on every edit: write an `@internal` reason in the summary and a `@returns` with words first (`@returns {@link X}` reads as a type, and its fix leaves `@returns` empty).

## Versioning

`package.json` holds four semver versions (`MAJOR.MINOR.PATCH`: major = breaking, minor = new feature, patch = fix):

- `engine_metadata.version` — the engine (`src/_engine/`).
- `toolkit_metadata.version` — the toolkit (`src/toolkit/`), which ships with the engine. Its own scale: additions are minor, fixes/updates are patch, and a major bump happens only when an engine-level change requires it.
- `app_metadata.version` — the example app (`src/app/` and the app-level files in `src/`: `AppECSPlugins.ts`, `AppECSRegistry.ts`, `CONFIG.ts`).
- `version` (the project/package version) — **always identical to `engine_metadata.version`**. App-only changes bump `app_metadata.version` and never touch the project version.

Rules:

- Bump once per branch merged to `main` (in the PR), not per commit, at the level of the biggest change on that side since the last merge. Reset the lower parts to 0 (e.g. `1.4.2` → minor bump → `1.5.0`).
- Engine, toolkit and app are bumped independently; a side with no changes keeps its version.
- A major bump gets a new codename. Engine codenames follow the sun's path (Dawn → Sunrise → Morning → Zenith → Afternoon → Golden Hour → …); toolkit codenames follow the moon's phases (Crescent → Half Moon → Gibbous → Full Moon → …); app codenames follow life stages (Toddler → Preschooler → Kid → Teen → …).
- Each PR adds an entry to `CHANGELOG.md` with a section per part it bumped (Engine / Toolkit / App, plus Project for repo tooling).
- Before opening the PR, `yarn checkVersions --against main` must pass. The Stop hook runs the base check (project version = engine version, valid semver) whenever `package.json` changes.
- After merging to `main`, run `yarn tagRelease` and push the tags it prints.
- The `x-version-checksum` meta tag hashes every part's version and codename plus the project version.

## Workflow

- **Always run Node with the version in `.nvmrc` (22.13.0).** The shell's default Node can be older than `package.json`'s `engines` (≥ 22.13.0); yarn then refuses to run, and checks fail or silently do nothing. Every Bash command that runs `yarn`, `npx`, `node` or `tsx` starts with `source .claude/hooks/use-node.sh &&` (from the repo root; it works in bash and zsh and stops the command when that Node isn't installed), eg. `source .claude/hooks/use-node.sh && yarn build`. The hooks source it too. Never report a check result from another Node version.
- **Watching a long run.** A command whose result you wait for and that takes more than a few seconds (`yarn verify:*`, `yarn build`, `yarn hub:build`, `yarn assets`, a long Vitest run) runs in the background with its output in a log under the gitignored `.cache/`: the verify commands write `.cache/verify/progress.log` themselves, anything else is redirected to `.cache/runs/<name>.log`. Give the user a command to copy that starts from the repo root's absolute path on the current machine (the user works on several), eg. `cd /path/to/repo && tail -f .cache/verify/progress.log`. Don't poll the log: the background task reports when it ends. `yarn test` takes about a second: run it in the foreground.
- A Stop hook runs lint (`--fix`, then fails on the errors left; warnings don't block) and type-check (`tsc` and `tsc -p hub`) when `src/`, `hub/`, `devTools/` or `vite.config.ts` changed, the unit tests when `src/`, `devTools/` or `vitest.config.ts` did, the docs ratchet (`yarn verify:baselines --docs`, naming each new undocumented export) when `src/_engine/` or `src/toolkit/` did, plus the version rule check when `package.json` changed. Leave the tree compiling and lint-clean. An edit to a `.ts` file is linted the same way right away (`tool-lint.sh`), showing the file's remaining errors.
- **Keep the Ækasha Hub current.** A change that adds, changes or removes an engine or toolkit feature or public API updates its Hub content (`hub/pages/`) in the same branch: the feature page, the example page and its scene, and the snippets they include. Run `yarn hub:build` after a Hub change: it fails on a dead `hub:` link.
- **Keep the nested `CLAUDE.md` files current.** A change to a subsystem that has one (the map under Architecture) updates it in the same branch; project-wide rules stay here. A new nested file starts with one line naming what it covers, gets a line in the map, and its `## ` sections are Hub sections like the Architecture ones (see Ækasha Hub).
- `readme.md` (root) is the project's public face. Update it in the same branch when a change alters what it lists: a new engine subsystem or toolkit module (Features), a new asset JSON type, a new command or URL flag, a changed runtime/browser requirement, a changed signature of an API its Examples use (`InitEngine`, `createRenderer`, `createSceneLoader`/`loadScene`, `createMeshEntity`, `createPhysicsEntity`, `addSystem`/`registerPlugin`, `AppConfig`), or a Roadmap item that lands (move it into Features). Physics objects in the scene JSON schema, the procedural sky/day-night cycle, the editor/material editor and the LOD system are the ones that call for a new highlight or example. Keep version numbers out of it (they live in `CHANGELOG.md`).
- `docs/plans/` holds specs for unstarted work. Never treat one as current state or implement one unless I reference it explicitly.
