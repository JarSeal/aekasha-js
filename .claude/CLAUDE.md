# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Aekasha (Ækasha) — a WebGPU/Three.js + Rapier physics game engine framework (package name `aekasha-js`). It's a "template" repo: an engine (`_engine`) plus one example app (`app`) built on top of it.

### Aekasha brand, feeling, and core principles

Ækasha is a high-performance WebGPU framework for the modern web. Driven by a modular ECS and a threaded physics core, it acts as the "fifth element" for developers — the invisible medium where complex data transforms into immersive reality.

Primordial Performance: Engineered from the ground up for WebGPU, Ækasha treats the GPU not as a peripheral, but as the primary canvas for logic and rendering.

Modular Infinity: Like the Akasha of myth, the framework is infinite and modular. You only bring into existence what you need, keeping the "memory space" clean and light.

Threaded Reality: By offloading heavy physics calculations and asset loading to dedicated threads via the physics API and asset loading API, Ækasha ensures that the "flow" of the user experience remains uninterrupted.

Smallest Build Possible: Every byte before the first frame is a wait. A build carries only what the app uses (features opt in, the heavy parts load on first use, debug code never ships), `yarn sbp` measures every build against its budgets, and a scene is light enough to embed in any page.

Maintain the brand, feeling, and core principles in creating the best UX for both, the developer and the end user!

In the browser, append query params to toggle modes: `?isDebug=true` (full debug tooling) and `?isProdTest=true` (production build with a subset of debug features). Next to either, `?startScene=<sceneId>` (`getStartSceneQueryParam`; null outside those two modes, so a production build never reads it) picks the first scene: `loadScene`'s first load (`kernel/scene/SceneLoader.ts`) uses it over the Debug tools' start scene and `src/index.ts`'s, with the scene code from `sceneFileObjects`. An id without both its scene data and its scene file warns (also as a debug toast, queued by `addDebugToastWhenReady` until the toaster exists) and loads the usual start scene. Later loads ignore it; the debugger's scene loader still applies only while the Debug tools' start scene is on. `?aekTest=true` installs the test bridge (see Debug system), and `?physicsProbe=N` arms the determinism probe (see `src/_engine/features/physics/CLAUDE.md`).

### Three-folder split

- `src/_engine/` — the engine. Treat as stable/library code; changes here should be minimal and purposeful. Its folders (p602's map, applied by p608; `devTools/layout/layoutRules.ts` keeps them as rules, so `layout.test.ts` fails on a file outside them):
  - `kernel/` — what every app runs, one folder per area: `ecs/`, `loop/` (`MainLoop`, the stages), `config/` (`Config`, the env flags, the debug loaders in `DebugModules.ts`), `init/` (`InitEngine`, the feature contract, the kernel's install), `scene/`, `assets/` (with `import/` and the assets `worker/`), `render/` (`Renderer`, `Snapshot`, `Views`, the three maths), `camera/`, `light/`, `mesh/`, `input/`.
  - `features/` — the nine opt-in features (see Engine features), one folder each: its entry `index.ts`, its `<Name>Feature.ts`, its worker, its `debug/` modules and its nested `CLAUDE.md`.
  - `ui/` — the UI kit (`aekasha/ui`): `CMP`, the HUD, the windows and dialogs, the drop-down, the toaster, the icons and the global styles (`ui/styles/`).
  - `debug/` — the debugger framework (`aekasha/debug`): the drawer, the tab host, the pane builder, undo / redo, the profiler, GPU memory, the on-screen tools, the editor views, the 3D symbols and the dev files client. A kernel area's or a feature's own debug modules are in its `debug/` subfolder (see Debug system).
  - `utils/` (pure: no three, DOM or ECS; storage the exception), `schemas/` (the asset JSON schemas; a feature's own next to it), `types/` (global declarations). The engine root holds only the entry `index.ts` and `ModuleLoad.test.ts`.
- `src/toolkit/` — reusable ECS components/modules, models, textures, shaders, and assets meant to be imported as-is or copy-pasted into `app` and modified. A catalogue by category (p609 D1, kept as rules in `layoutRules.ts` like the engine's): the code categories have an entry each (`TOOLKIT_CATEGORIES`), the asset categories none (asset JSONs, reached by id through the gatherer). A piece that grows a second file gets its own folder inside its kind.
  - `ecs/` (`aekasha/toolkit/ecs`): `effects/` (a component and its system, put on an entity: `FollowTool`, `HoverEffect`, `MutualGravity`, `SunShadowFit`) and `gameplay/` (`FollowObjectCameraRig`, `MovingPlatform`).
  - `geometry/` (`aekasha/toolkit/geometry`): `generate/` (`Asteroid`, `Foliage`, `Terrain`), `scatter/` (`ScatterOnSurface`); the generators draw from the engine's `createSeededRandom` (`utils/SeededRandom.ts`, p610; the entry still re-exports it, deprecated until toolkit 3.0.0).
  - `materials/` (`aekasha/toolkit/materials`): a folder per material named by its id (`<id>.material.json`, `<id>.tsl.ts`), and `TriplanarProjection.ts`, the TSL helper they share.
  - `models/<category>/<id>/`, `textures/<id>/` and `skyboxes/<id>/`: assets, each source next to its JSON. Model categories: `brand/` (the Æ symbol); p450 adds `reference/` and `nature/`, and the first textures and sky boxes.
  - Models (`toolkit/models/<category>/<id>/`): the source GLB sits next to its `*.importedAsset.json` (a JSON-relative `fileName`); the asset pipeline writes the optimized output into `src/public/aek-assets/`. The first is the Ækasha symbol (`aekashaSymbol`): the Æ glyph of `src/public/favicon.svg` extruded with a small bevel, 1 unit high, centred, facing +z, Draco-compressed (the JSON's `optimize.mesh.codec: "draco"` keeps it so). `devTools/toolkit/buildAekashaSymbol.ts` builds the GLB (three's `SVGLoader` with `linkedom`'s `DOMParser`, `ExtrudeGeometry`, gltf-transform); run it with `npx tsx` when the glyph changes and commit the GLB. It fails when the glyph has no hole, and leaves the glTF scene unnamed (GLTFLoader makes scene and node names unique together, so a scene named like the node renames the node and its geometry id).
- `src/app/` — the actual game/app: scenes and asset JSON files, app-specific managers/components. One folder per scene (p609 D2, kept as rules in `layoutRules.ts`, so `layout.test.ts` fails on a file elsewhere):
  - `scenes/<sceneId>/`: `<sceneId>.scene.json`, `<sceneId>.ts` (its `sceneFile`), its `_dbg__` module and `<sceneId>.hub.png`, its own modules (`lodShowcase/lanes/`) and the asset JSONs only this scene uses, with their sources. File and folder names follow the scene id, which stays (it keys `__saveData`, the scene runner's baselines, the LS state and `?startScene=`).
  - `examples/<name>/`: the Hub's example scenes (see `hub/CLAUDE.md`).
  - `shared/`: app code several scenes use (a copied toolkit piece among them); code one scene uses stays in its folder.
  - `profiles/<id>/`: an SBP embed profile (p611 D7, `sbp.config.ts`): its entry module (`<id>.embed.ts`, binding the profile's generated data, `src/generated/profiles/<id>/`, and exporting `mount`), and its scene with that scene's assets, laid out as a scene folder. `banner` is the floor: one code-made scene, no feature. The app-wide registrations stay in `src/*.ts` (`AppECSPlugins.ts`, `AppECSRegistry.ts`).
  - The shared assets in their type's folder (`cameras/`, `lights/`, `impostors/`, `skyboxes/`, `textures/`, `postFx/`, and `materials/`, `meshes/`, `geometries/`, `importedAssets/` when one is shared). "Only this scene uses it" means no other scene JSON, scene file or asset JSON names its id: an asset a second scene starts using moves to its type's folder, one only a scene uses goes into that scene's folder. A moved asset JSON keeps its id, so the scenes naming it don't change; its `$schema` and relative paths (`image`, `fileName`) do, and a scene JSON's `sceneFile` is relative to `src/app/`.

The boundary is a lint rule (p606, errors everywhere, `eslint.config.js`):

- `import/no-restricted-paths` with `LAYER_ZONES`: the engine imports no toolkit, app, `src/generated/` or `src/*.ts` file; the toolkit no app, `src/generated/` or `src/*.ts` file; nothing outside the engine an `_engine/` path (only the `aekasha*` entries, see Build config notes); a toolkit category no other category's files (`TOOLKIT_CATEGORIES`, listed by hand: a new category goes there and in `devTools/aliases.ts`); the app and `src/*.ts` no toolkit file. It resolves the path (the node resolver with `.ts`; the aliases stay unresolved, so unchecked), so `import type` and `import()` are checked too. The one exception: the generated code's imports of the toolkit's `*.tsl.ts` materials (assets). Trap: in a zone whose `from` is a glob, `except` isn't resolved against `basePath` (the exceptions are absolute), and one zone's `from` is all globs or none.
- `@typescript-eslint/no-restricted-imports`: no `aekasha*` import inside the engine (an entry imported by the code it re-exports makes cycles), no kernel import of a `features/` path but `import type` (p612 D2: the kernel names a feature's types for the data it holds or carries for it, component data, config, scene and mesh definitions, import params and the assets worker's messages, and imports none of its code; the types stay in the feature, the layout report, `devTools/layout/layoutReport.ts`, lists each; a kernel `_dbg__` module isn't checked, an `import()` neither), and no static import of a `_dbg__` module outside `_dbg__*` files (debug code is found by name, p608 D4; `import type` is allowed; `import()` isn't checked, which is the point). `src/_engine/debug/*.ts`, the thin entries, aren't exempt, and the engine's debug files keep the `aekasha*` rule. A later config entry replaces the rule's options for its files, so each lists every pattern that applies there.

### ECS core

`src/_engine/kernel/ecs/ECS.ts` defines `ECSWorld`, a bitwise-packed (index + generation) entity/component store. Key patterns:

- **Plugin registration**: `ECSWorld.registerPlugin(fn)` (and `registerCorePlugin`, also for worlds created with `applyGlobalPlugins: false`) and `ECSWorld.registerComponentHooks(type, { onAddComponent, onRemoveComponent, onDeleteEntity })` are static (all current/future worlds) and are called from an install, never at module load (see Engine features): the kernel's in `installKernel`, each feature's in its `install` through the `FeatureContext`, and the app's in `src/AppECSPlugins.ts`'s `appECSPlugins` feature (`id: 'app'`), which `src/index.ts` lists last in `features` — this is where you wire up new app/toolkit ECS managers/effects (or give a bigger part of the app a feature of its own). Registration order, so install order, breaks ties within a stage and order. `onRemoveComponent` runs only when the entity has the component, and a hook that removes the same component from the same entity again while it runs (two entities linked to each other) is ignored (p612).
- **Component types**: core types live in `src/_engine/kernel/ecs/ECSRegistry.ts` + `ECSCoreComponents.ts`, whose `ComponentDataMap` interface is the whole key → data map. An app or toolkit module adds its components in its own file, with a key object (`HoverToolComponentType`) and `declare module 'aekasha' { interface ComponentDataMap { [Key.X]: Data } }`; code uses that key object, since the `ComponentType` value holds only the engine's keys. Augment only `'aekasha'` (a second path to the same interface drops keys silently). `src/AppECSRegistry.ts` holds the app-wide keys. Debug listings read `ECSWorld.getComponentTypes()` (values, eg. `CORE_TRANSFORM`, `APP_SPIN`). `CoreComponentType` is the same object, `@deprecated` (removed in engine 6.0.0): write `ComponentType`.
- **App ids**: `getEntityIdByAppId` (and `ECSWorld.getEntityIdByAppId`) is one lookup in the world's map, kept where `APP_ID` is added, removed and its entity deleted (p612 D6). The first entity created with an id keeps it until it's deleted or its `APP_ID` removed or replaced, then the next live one with the id takes over (only ids taken twice are scanned); a second entity given a fixed id (`isFixed`) warns in the debug env. Never change `APP_ID.id` in place: add a new `APP_ID`.
- **Managed entities**: `CoreEntityOpts.managedBy` (code only) adds a `MANAGED_BY` component (`{ manager, ownerId, role }`) to an entity its manager creates, drives and deletes (eg. the sky box's lights). `createLightEntity` then skips the saved debug overrides, and the Lights tab shows the light read-only with a link to the manager's tab (registered with `_registerManagerDebugInfo` in `debug/_dbg__ManagedEntities.ts`), without LS writes or undo entries.
- **System stages**, defined in `src/_engine/kernel/loop/SystemStages.ts` (`ECSSystemStage`, with the `APP_RENDER_SYNC_ORDER` constants), run in this fixed order every frame: `MAIN → APP_PRE_PHYSICS → APP_POST_PHYSICS → APP_LOGIC → APP_RENDER_SYNC → LATE_MAIN`. `APP_PHYSICS_STEP` is the exception: it runs 0-N times per frame, once right before each fixed physics sub-step (dt = the fixed timestep), from inside `stepPhysics` (between `APP_PRE_PHYSICS` and `APP_POST_PHYSICS`) — use it for anything that must move in lockstep with the simulation (kinematic platforms, character controllers). In `WORKER_THREAD` mode the one-way worker commands those systems issue are carried in that frame's single STEP message and replayed before their own sub-step. Collision/contact-force events (both modes) are delivered by `flushPhysicsEvents` at the start of the next sub-step — after held-key polling, before `APP_PHYSICS_STEP` — an order gameplay code (e.g. the dynamic character's moving-platform logic, `features/character/controllers/dynamic/`) depends on. `APP_POST_PHYSICS` is where physics state syncs into ECS transforms; `APP_RENDER_SYNC` is where ECS transforms sync into Three.js `Object3D`s.
- **The loop** (`kernel/loop/MainLoop.ts`, p612 D10): one frame function, `runFrame`, in every build (not `async`; the stats behind `IS_DEBUG_ENV`, which a production build folds, the editor view branch a boolean check). Every frame request goes through `requestMainLoopFrame()` (`@internal`), which asks for one unless one is queued or the loop is stopped (`stopMainLoop()`), so the start, `toggleMainPlay` and the Loop controls tab never run two chains. The max FPS cap (`VITE_MAX_FPS`, or the Loop controls tab's `maxFPS`) skips only the render, `LATE_MAIN` and the late scene loopers of a frame it holds back: the stages before them run on every frame, so no game time is lost. Worlds are iterated from `getAllECSWorlds()`, a read-only array rebuilt on world create and delete (no copy per frame). The window listeners are `onVisibilityChange(fn)`, `onBeforeUnload(fn)` and `onWindowBlur(fn)` (`@internal`, Sets, each returning its remover).

### Scene/asset data pipeline (JSON → generated code)

Scenes and assets are authored as JSON files under `src/app/**` (and the toolkit's under `src/toolkit/**`), named by suffix (e.g. `*.scene.json`, `*.mesh.json`, `*.camera.json`, `*.light.json`, `*.geometry.json`, `*.texture.json`, `*.textureArray.json`, `*.textureAtlas.json`, `*.material.json`, `*.importedAsset.json`, `*.skybox.json`, `*.postFx.json`, `*.impostor.json`; `GATHERED_SUFFIXES`). `devTools/gatherAppData.ts` runs it (`gatherSceneData({ pipeline?, profiles?, isProduction?, srcDir?, outDir? })`, the repo's by default; its steps in `devTools/gather/`, one module each: `gatheredJson.ts` the suffixes, schemas and `validateGatheredJson`; `context.ts` the registries, the id spaces and `readAssetJsons`, the one pass-1 reader for every type, which `registries.ts` and `textures.ts` use; `scenePass.ts` and `sceneAssets.ts` the scenes, `sources.ts` the files an asset points at; `saveEntries.ts`; `shipChecks.ts`; `output.ts`; `jsonSchemas.ts`):

1. Walks `src/`, finds files matching those suffixes.
2. Validates each against a Zod schema in `src/_engine/schemas/*.ts`, or next to its feature (`features/skybox/SkyBoxSchema.ts`, `features/lod/LodSchema.ts`, `features/lod/impostors/ImpostorSchema.ts`; all on `aekasha/schemas`). The scene and mesh schemas are composed (p607 D10): the kernel's fields plus each feature's `FeatureSchemaPart` (`skyBoxSchemaPart`, `postFxSchemaPart`, `spatialSchemaPart`, `lodSchemaPart`; `createSceneAssetSchema` / `createMeshAssetSchema`, `schemas/FeatureSchemas.ts`, which throws on a field two owners give), composed for the gatherer in `devTools/gather/engineSchemas.ts` (`ENGINE_SCHEMA_PARTS`, in the JSON Schemas' property order, so `.schemas/` didn't change; its test fails on an engine `*SchemaPart` missing from it, whose fields zod would strip). The gather fails on a file that doesn't parse or validate, an id two files of a type give (the first file keeps it) and an id a scene lists that no asset JSON has (p619 G1, G2, G12).
3. Emits `src/generated/`: `generatedAppData.json`, `generatedAppFns.ts` (a loader per id, `() => import(…)`, for the scene, TSL material and PostFX files: a scene's file loads with its scene, a TSL material's with its scene load's assets or by `loadTslMaterialFileAsync` (`createMaterial` throws naming it for a file nobody loaded), a PostFX pass's in `postFx()`'s `created` hook; each its own chunk in a build) and `index.ts`, whose `appData` `src/index.ts` passes to `InitEngine({ data })`. Each embed profile of `sbp.config.ts` gets the same three files with only its scenes in `src/generated/profiles/<id>/`, which its entry module binds (p611 D7, `devTools/gather/output.ts`; see `devTools/sbp/CLAUDE.md`). The engine never imports the folder: it keeps the data in `kernel/scene/AppData.ts` (`getAppData`, `@internal`; apps read it with `getGeneratedAppData` / `getGeneratedSceneData`), and `kernel/scene/Scene.ts`'s `registerScenesFromGeneratedData()` builds the scenes from it. Each gathered scene gets the feature manifest `__features` (`getSceneFeatureIds` in `devTools/gather/engineSchemas.ts`: the features whose part's fields the resolved scene or one of its meshes uses, given and not an empty list; always written, `[]` included). `InitEngine`'s `checkSceneFeatures` throws on a scene that needs a feature `features` doesn't list, naming each scene and the factory; a scene without the key (data from before it) isn't checked. Only data counts: a sky box or LOD made in scene code isn't in it.
4. Also compiles the Zod schemas to plain JSON Schema files in `.schemas/*.schema.json` (used for editor autocomplete/validation on the asset JSON files themselves): `writeJsonSchemas` (`gather/jsonSchemas.ts`), run by `yarn gatherAppData`, `yarn assets` and the dev plugin's (re)start, writing a file only when it changed; importing `gatherAppData.ts` writes nothing (nor does importing `copyDecoders.ts`).

Per-scene overrides live in each asset file's `__saveData` (`{ [sceneId]: [latest, ...older] }`; only the latest entry is applied, its fields replacing the asset's but for `params`, a TSL material's `nodes`, a sky box's definition (`applySkyBoxSaveEntry`) and a mesh's `geo` / `mat` props of the same type, merged key by key; a mesh's merged props are validated again). An entry's `__meta` can carry `engineVersion`/`toolkitVersion`/`appVersion` (`src/_engine/schemas/_SaveDataSchema.ts`); anything that writes save entries should stamp all three, and the gatherer warns when an applied entry comes from another major version.

This runs via `yarn gatherAppData`, and automatically on file add/change/delete during `yarn dev` through the custom `sceneGathererPlugin` Vite plugin (`devTools/sceneGathererPlugin.ts`, its queue `devTools/workQueue.ts`: debounced, one run at a time; triggers a full reload, or surfaces a Vite error overlay if validation or an asset fails). A gather writes a generated file only when its content changed (`writeFileIfChanged`, atomic, p619 G7; `gatherSceneData` returns `{ isGathered, changedFiles }`), so a gather that changes nothing reloads no page. Each gather the plugin runs first sends the custom HMR event `aek:gather` (`DevDataGatheredEvent` in `debug/DevFilesProtocol.ts`: `done` / `failed`, the changed files, the asset errors, `willReload`), which the dev files' `onDevDataGathered` delivers; the page reloads when the generated data changed or a source file did (one served as it is changes no `__url`), and a failed gather keeps it. Both run the asset pipeline (`_DONE_p300`) first, cached: the gather needs its run for the `__url`s. The plugin builds only what a change touched (an asset JSON, a source file, `assets.config.json`, `assets.optimization` in `src/CONFIG.ts`) and reuses its last run when nothing the pipeline reads changed.

Scene loads (`loadScene`, `kernel/scene/SceneLoader.ts`, p613 D3) run one at a time: a call during a load waits for it, and a later call replaces the waiting one, which resolves `false` without loading. `loadScene` resolves `true` once the scene is current and `false` when it failed or was replaced, and never rejects, so scene code and scene hooks never await it (the call would wait for the load it runs in). The steps: `resolveLoadTarget` (an unknown scene, scene code or loader throws before anything changes), `beginLoad`, `tearDownPrevScene`, `loadNextSceneAsync`, `enterSceneAsync`, then `finishLoad` for both outcomes: a failed load turns the inputs, the canvas's pointer events and the debugger back on, hands the asset owner back to the current scene and leaves that scene current. It's a promise chain, not a `try`, so its debug-gated calls fold. What a load builds from the scene's data is in `kernel/scene/SceneDataLoader.ts` (`@internal`): `createCameras` first, `loadNextSceneAssets` (a material's texture ids resolved into a copy, never into the cached generated params), and after the scene code `createNextSceneObject3Ds` (the lights and meshes). The glTF import path (`kernel/assets/import/ImportRegistry.ts`) loads with an `import()` only for a scene whose data names an imported asset, by id or inline (p613 D4), and hands `SceneAssetRelease.ts` its release on its first import (`setSceneImportRelease`), so a scene file's own `importAssetAsync` is released with its scene too.

`src/index.html` → `src/index.ts` (imports `aekasha`, the feature factories and `./AppECSPlugins`' `appECSPlugins`) → `InitEngine({ config, data, features, start })` (`src/_engine/kernel/init/InitEngine.ts`, p606: the engine imports nothing of the app; every `IS_*` flag reads as production before it, and the debug flags are set only when `__AEK_DEBUG__`), takes `config` (`loadConfig`, `src/CONFIG.ts`; `Config.ts` holds no defaults, each module that reads a key defaults it, p612 D4, and the env var and debug LS overrides go into copies of `physics`, `assets` and `ecs`), checks `features` (`checkFeatures`) and the scenes' manifests against them (`checkSceneFeatures`), keeps `data` (`setAppData`, `kernel/scene/AppData.ts`: `appData` from `src/generated/`), adds the window listeners, registers the built-in icons (debug env / prod test only), creates the root Three.js scene, installs the kernel (`installKernel`, cameras and lights included), `initECSWorld()`, creates the HUD container, `initAssets()`, (debug env, `bootKernelDebugAsync`) loads the 3D symbols, the camera and light debug GUIs and the debug camera, installs `features` in list order (`installFeaturesAsync`; `physics()` inits Rapier and creates the first world when `physics.enabled`), registers the scenes from the data (after the installs, so the features' `sceneRegistered` hooks see them), then (`bootDebugToolsAsync`; only if `IS_DEBUG_ENV`) registers the debug tooling/stats/GUIs and runs the features' `onDebug` hooks, (`IS_DEBUG_ENV`/`IS_PROD_TEST_MODE`) the debug tools, profiler, on-screen tools and the test bridge — and then awaits the app's `start` before starting the main loop when the root scene has children (otherwise the first scene that adds one starts it, `setCurrentScene`; a development or test build warns when no load is running then). After `start` (`bootDebugAfterStartAsync`, debug env): the debug GUIs that need the renderer, the features' `onDebugAfterStart` hooks and the debug toaster; then, in every build, the after-start hooks of the modules in use (`runBootAfterStartHooks`, `kernel/init/BootHooks.ts`: a module adds one on its first use, never at load, and one added after this step is refused; the draggable windows' restore of their saved states, p613 D5), and `restoreSavedView()` (debug env, not awaited).

The embed boot, `mountAekasha({ target, … })` (`kernel/init/Mount.ts`, on `aekasha`, p611 Phase 3), runs the same `bootEngineAsync` into a container it adds to an element of a page it doesn't own: without `page.scss` (the full-page boot's normalize, `html` and `body` rules), with the canvas sized by the container (`getCanvasSize`, `kernel/render/CanvasSize.ts`), input scoped to `NONE` or the canvas, files resolved against `assetBaseUrl`, its own scene loader without UI, and its handle (`pause`, `resume`, `loadScene`, `unmount`; `unmount()` also runs the features' `onUnmount` hooks). An app builds it as an embed profile (`devTools/sbp/CLAUDE.md`); the Hub's SBP feature page runs one live.

### Engine features

`kernel/init/Features.ts` (p607, the install contract): `InitEngine` installs the kernel (`kernel/init/Kernel.ts`' `installKernel`, right before `initECSWorld`: the core systems, frustum culling, meshes, groups, raycasting, then the cameras' and lights' hooks, `installCameras` / `installLights`, whose debug GUIs load in the boot's debug step; the input devices register nothing at boot: each adds its listeners on its first binding), then each `EngineFeature` (`{ id, requires?, install(ctx) }`, public on `aekasha`) of the required `features`, in list order, each awaited, after the debug camera. `[]` is the kernel alone; `checkFeatures` throws, before anything installs, on a missing list, an id listed twice or a `requires` id not listed earlier (`character()` requires `physics()`). The nine engine features are factories on their entries, each in a `<Name>Feature.ts` next to its code: `physics()` (`features/physics/PhysicsFeature.ts`), `character()`, `skyBox()`, `lod()`, `spatial()` (with light culling), `instancing()`, `lines()`, `postFx()`, `viewports()` (`features/viewports/ViewportsFeature.ts`). The template lists all nine in that order, then `appECSPlugins`.

- `FeatureContext` is a feature's only way into the kernel: the ECS registrations (`registerPlugin`, `registerCorePlugin`, `registerComponentHooks`, `registerTransformResetListener`), `addSceneHooks` (`kernel/scene/SceneHooks.ts`: `loadStart`, `exit` (reverse install order, so characters before physics), `worldCleared`, `beforeAssets`, `created`, `entered` and `loadSettled` at their places in `loadScene`; `sceneRegistered` from `Scene.ts` (`sceneDeleted` is deprecated, never called); `retainedTextures`: what `releaseSceneOwnedAssets` and a material's last release keep, with the root scene's background and environment, `getKeptTextures` in `kernel/assets/Material.ts`), `setFixedStepDriver` (`MainLoop.ts`' `FixedStepDriver`: `latch`, `step`, `flushEvents`, `isStepping`; physics'; without one the loop polls held keys once per frame), `setRenderPipeline` and `addAfterRender` (`kernel/render/RenderHooks.ts`: PostFX's pipeline, which `MainLoop.renderScene`, `Snapshot.ts` and the profiler read; the viewports' hook), `registerImportExtension` (`kernel/assets/import/ImportExtensions.ts`: physics' spawn of imported bodies, LOD's chain reads; each member one provider), `onDebug` / `onDebugAfterStart` (kept only when `__AEK_DEBUG__`; run at the end of `InitEngine`'s first debug block and after `start`, in install order) and `onUnmount` (p614 D6: synchronous, run by `mountAekasha`'s teardown right after `stopMainLoop`, in reverse install order, through `Boot.ts`' `stopEngineFeatures`; never under `InitEngine`; physics' `stopPhysics` deletes the world or terminates the worker through its transport and rejects the pending requests; the sky box's `stopSkyBox` clears it, its bakes and lights, and drops its listeners). Two internal setters aren't on the context: `setSpatialDomainMembership` (`spatial()`) and `setAutoLodResolverLoader` (`lod()`). Feature → feature, only character → physics imports at runtime: the LOD targets and spatial radius providers are kernel registries (`kernel/ecs/LodTargets.ts`, `kernel/ecs/SpatialMembership.ts`).
- Install order is registration order, which breaks system ties: the scene runner's system order baseline (`devTools/verify/CLAUDE.md`) catches a moved registration. A `_dbg__` module another one imports statically registers at its first importer's load, so a debug module whose systems tie with the app's registers from an install function (`_installPhysicsWireframes`, called by physics' `onDebug`).
- Production builds: a call to `ctx.onDebug*` stays in the bundle with the closure it's handed and every wrapper that names (only the context's functions fold), so every call sits inside `if (IS_DEBUG_ENV)` (p612 D9); `yarn verify:baselines` fails on an ungated one in a build. Rollup keeps a `try` block's calls whole: no debug-gated call inside one (`InitEngine` and `mountAekasha` catch `bootEngineAsync`'s promise, and `installFeaturesAsync` each feature's).
- Without its feature, the API says so: `createLines` and `createViewport` throw naming it; `lod: 'AUTO'`, an import's physics nodes or `lodChain`, and a pool's `spatialDomain` warn instead; the engine's debug tools that draw lines or viewports are off with one log line each (`isLinesInstalledFor`, `isViewportsInstalledFor`). A scene whose data needs a missing feature fails the boot (the manifest, see the data pipeline).
- The assets worker can't be handed code, so it `import()`s each job's module on its first job (`kernel/assets/worker/`'s `AssetsSwitchTexture` and `AssetsSwitchGLTF`, `features/lod/worker/AssetsSwitchSimplify`, LOD's), and the GLTF job `LodChainGLTF` only for a request with `readLodChains` (set while LOD's import extension is registered).

### Debug system (dual-layer, lazy-loaded)

Debug tooling (Tweakpane-based) is split into two layers so it tree-shakes out of production builds:

- `src/_engine/debug/*.ts` and other engine modules (e.g. `kernel/render/Renderer.ts`'s `createRendererDebugGUI`) are thin public entry points that, only when `IS_DEBUG_ENV` is true, dynamically `import()` the real implementation via `loadDebugModuleAsync`/`useDebug` (`src/_engine/kernel/config/DebugModules.ts`, next to `Config.ts`: shipping code calls them, so they aren't in a debug folder, p608 D2).
- `__AEK_DEBUG__` (p607 D7, see Build config) is false in a production build: `initEnvironment` never sets the debug flags there, so every `IS_DEBUG_ENV` branch, the `debug/*.ts` wrappers it was the only user of and their `_dbg__` chunks fold away (`yarn verify:baselines` fails on any left: a `_dbg__` module, or any module in an engine folder named `debug`, the entry aside), and both loaders return `null` first. A feature registers its debug tools with `ctx.onDebug` / `onDebugAfterStart` (see Engine features).
- The actual Tweakpane implementations live in files prefixed `_dbg__`, next to the code they debug: the debugger framework's in `debug/` (`_dbg__DebuggerGUI.ts`), a kernel area's or a feature's in its own `debug/` subfolder (`kernel/render/debug/_dbg__Renderer.ts`, `kernel/camera/debug/`, `features/skybox/debug/`). A debug folder holds nothing that ships (p608 D4: the production check above). Follow this `_dbg__` + dynamic-import pattern when adding new debug panels for engine-level features.
- The debug drawer itself is toggled in-app with the `h` key (bound in `src/CONFIG.ts`) via `toggleDrawer()`.
- Draggable windows are the UI kit's (`src/_engine/ui/CLAUDE.md`: kinds, registration, LS, scene loads). A debug module's edit window per entity is a window kind, registered at its `_dbg__` module's load.

Detail: `src/_engine/debug/CLAUDE.md` (the About dialog, debug keys, the test bridge, the profiler, GPU memory, drawer tabs) and `devTools/devFiles/CLAUDE.md` (dev files).

### Physics

The `physics()` feature (`features/physics/`, on `aekasha/physics`): Rapier behind an engine-agnostic Physics API, on a worker thread by default (`AppConfig.physics.workerTarget`, `'WORKER_THREAD'` or `'MAIN_THREAD'`), with every message through one transport and the transforms back through one shared triple buffer. Bodies are ECS components made by `createPhysicsEntity` (`async`, the entry point app code uses), and simulation tiers let a large world freeze, disable or remove bodies. The layout, the worker targets, the deterministic loads and the probe, the tiers and imported physics: `src/_engine/features/physics/CLAUDE.md`.

Scene loads are deterministic (p101): physics is held for the whole load, the world is replaced with a fresh one, and stepping resumes only after every `createPhysicsEntity` call of the load has finished. So a scene simulates identically on every visit, in both worker targets. The rules for simulation code:

- No physics entity survives a scene switch, and any body/collider reference from the previous scene is stale. Deleting one is a quiet no-op.
- Physics writes (poses, velocities, impulses, kinematic targets) go in `APP_PHYSICS_STEP` systems or in scene-load code. Writes from per-frame stages depend on frame timing. In `WORKER_THREAD` mode, `APP_PHYSICS_STEP` commands are captured per sub-step and cloned at capture, so reusing scratch vectors is safe.
- `getPhysicsSubStepIndex()` is the step clock for `APP_PHYSICS_STEP` systems (-1 outside a sub-step), and `addPhysicsStepGate(step)` makes stepping wait for something.
- Characters (the dynamic controller, `features/character/controllers/dynamic/`) are deterministic on `MAIN_THREAD` (p610): durations count fixed steps (`getPhysicsSubStepIndex`; the configured durations stay in ms), the tumble start draws from the seeded stream `character:<id>`, the casts are synchronous, and the sensor callbacks only record (the tick writes the body). Their brains run right before the controllers in the same step and read action maps sampled right before it (`kernel/input/`), so a recorded input replays step for step. In `WORKER_THREAD` mode they aren't: the tick runs on the main thread against the latched snapshot and async casts (p428). Detail: `src/_engine/features/character/CLAUDE.md`.
- Randomness in simulation code comes from a named stream (`getRandomStream(name)`, `utils/RandomStreams.ts`, on `aekasha`): seeded from the world seed (`setRandomSeed`) and the name, restarted by every `loadScene` (right before the physics world is replaced), so a scene draws the same numbers on every visit.
- The simulation lint (`SIMULATION_FILES` in `eslint.config.js`: the physics and character files (the engine's brains included), `movingPlatform/`, `MutualGravity.ts`, the gym's `GymDummyBrain.ts`; not the input devices, which time DOM events) makes `Math.random`, `performance.now()`, `Date.now()` and `new Date` errors there. Profiling reads go through `readStatsClock` (`utils/StatsClock.ts`, measurement only); the known violations are allow-listed per file with their plan (`features/physics/PhysicsWallClock.ts` under the deprecated `getPhysGameTime`, which no simulation code reads, removed in engine 6.0.0), never disabled inline. A new simulation file goes on the list.

### Viewports

`src/_engine/features/viewports/Viewports.ts` renders extra rectangles over the canvas, each with its own scene and camera (picture-in-picture, minimaps, item previews), after the main render and PostFX. Each enabled viewport renders into its own render target, then a quad composites it with the renderer's tone mapping and colour space neutralised (the `RenderPipeline.render()` contract), so it works on both backends with PostFX on or off. `renderViewports()` is the `viewports()` feature's after-render hook (`kernel/render/RenderHooks.ts`, p607), which `MainLoop.renderScene()` runs once per frame, and is a single count check while no viewport is enabled. A viewport is render configuration, not ECS: `createViewport({ id, scene, camera, anchor | rect, ... })`, where `camera` can be a resolver (eg. `getActiveCamera`; one returning `null` or `undefined` skips the viewport that frame), and `sceneId` deletes it on that scene's exit.

- Placement is DOM-driven. Each viewport owns a slot element in `#aekViewportsLayer` (created on the first viewport), either in a corner stack (`anchor` + `order`, 0 = in the corner; global class `aekViewportStack_<ANCHOR>` for consumer SCSS) or at an explicit `rect` (px or %). The rendered rect is the slot's box, re-read only on create/enable, canvas resize, `<body>` class changes, while a CSS transition runs in the layer, or on `invalidateViewportLayout()`.
- `interactive` slots take pointer events, so those never reach the canvas, OrbitControls or `MouseInput`; raycast into the viewport with `getViewportPointerNDC`, switch it with `setViewportInteractive`. Other slots let everything through.
- `renderViewports` restores what it changes on the renderer (target, viewport, tone mapping, output colour space) in a `finally`: a throw in a viewport's `onBeforeRender` or render still ends the frame, but leaves the renderer as it was (p613 VP1). `syncCameraAspect` compares with the camera's own projection every frame, never a cache: the camera resizer sets every camera entity back to the canvas's aspect on a resize. A mount's `unmount()` removes the layer with its container, and the `<body>` `MutationObserver` disconnects on its next callback once the layer has left the document.
- The first consumer is the debug-only axes gizmo (`debug/AxesGizmo.ts` → `debug/_dbg__AxesGizmo.ts`): top right, follows the active camera, F10 and two Debug Tools options. With the debug camera, clicking a bubble aligns it and dragging orbits it.
- The environment ball (`debug/EnvBall.ts` → `debug/_dbg__EnvBall.ts`) sits left of the gizmo (`order: 1`): an unlit sphere sampling `getActiveEnvironmentTexture()` along the reflection vector (with a direct-path cube's `flipY` and the scene's `environmentRotation`), following the active camera, F9 and three Debug Tools options. A new PMREM texture gets a new node, never a `.value` swap. In an editor view it shows the view scene's `environment` (see Views).

### Snapshots

`kernel/render/Snapshot.ts`: `takeSnapshotAsync({ width, height, scene?, camera?, postFx?, hideDebugHelpers?, transparent?, samples? })` renders a scene through a camera into an image off screen and reads it back as a `Snapshot` (`{ width, height, data, postFx }`: RGBA8, sRGB encoded as the canvas shows it, straight alpha, top row first), for thumbnails, the Hub's example images (the debug drawer's Hub tab) and save game pictures. By default it's what the canvas shows: the current view's scene and camera (the debug camera too), through the scene's PostFX, without the viewports, and with the debug helpers hidden (`isDebugHelperObject`, `kernel/render/Object3DHelpers.ts`: `markDebugHelper`'s flag, the 3D symbols, three's `*Helper`s; the profiler's census reads the same predicate). `snapshotToBlobAsync` encodes one through a canvas (PNG, WebP, JPEG; a fully transparent pixel loses its colour), the dev files' `encodePNG` byte for byte. `readRenderTargetRGBA8Async` (`@internal`) is its readback (top row first on both backends), which the texture preview shares.

- Direct path (any scene and camera, PostFX off, or `transparent`): the scene renders into a HalfFloat target, then a quad with `renderOutput()` and the renderer's tone mapping and output colour space (the viewports' contract) into an RGBA8 target. The canvas isn't touched. `transparent` clears to alpha 0 and leaves the scene's background out for the render.
- PostFX path (the root scene with the active camera, its pipeline on): three's `pass()` sizes itself from the drawing buffer, so the renderer is resized to the snapshot (pixel ratio 1) for the render and put back, and `renderFrameNow()` (`MainLoop.ts`) draws the canvas again in the same task, so the browser never shows it cleared.
- Both start a new node frame first: three r186 updates `FRAME` nodes (a `pass()`, a shadow map) once per node frame, so a snapshot after the frame's own render would reuse them at the canvas's size and aspect (the PostFX snapshot came out stretched).
- The camera's aspect (an orthographic camera's width, keeping its height) is set for the snapshot and put back, like everything else it changes, before the readback starts.

### Views

`kernel/render/Views.ts` (`_DONE_p083`, the editor/creator view epic): a view is what the whole canvas shows and what the main loop ticks, and exactly one is active. The built-in **Runtime** view (`RUNTIME_VIEW_ID = 'runtime'`, no `ViewDef`) is the loaded scene with the game/app debugger. Editor views (the material editor, `_DONE_p084`, `_DONE_p085`) are registered by debug modules with `registerView({ id, title, icon, orderNr?, scene, getCamera, getCameraRig?, onEnter?, onExit?, mainUpdate?, update?, toggleDrawer? })` and switched with `setActiveView(id)`: calls run one after another, and a failed `onEnter` returns to the Runtime view and resolves `false`. Views aren't viewports: viewports are composited over whichever view is active. Only the debug env registers views so far; in production the loop pays one boolean check.

- Suspension: while an editor view is active (`loopState.isSceneSuspended`, from the start of a switch to one until the switch back has finished; `isRuntimeViewActive()`), the frame (`runFrame`) runs none of the scene's per-frame work. That means no world's ECS stages (`MAIN` and `LATE_MAIN` included, so `object3DSyncSystem`, `skyBoxSystem` and `debugCameraSystem` stop too), no scene loopers, no held keys, and no physics: `stepPhysics` treats it as a pause and resumes without catching up, so a switch keeps a scene deterministic. `getElapsedTime()` stands still. The loop instead runs the view's `mainUpdate(delta)` and, while the view plays, `update(delta)`, then renders `view.scene` with `view.getCamera()` (no PostFX) and the viewports. Work outside the loop (timers, audio, DOM events, TSL's `time` node) keeps going, so per-frame game logic belongs in ECS systems or scene loopers. A scene loaded meanwhile (app code, HMR) is suspended as soon as it exists.
- Debug tools that must run in every view add `addViewFrameListener(fn, 'BEFORE_UPDATE' | 'AFTER_RENDER')`, called only in editor views (the axes gizmo, the env ball, the profiler's frame and GPU memory samplers), next to their ECS system for the Runtime view. `addViewChangeListener` runs after every finished switch.
- Input: `setAppInputsSuspended` (`kernel/input/InputState.ts`; apart from `setAllInputsEnabled`, so a scene load's end doesn't lift it) stops mouse, touch, held keys, every key binding without `isDebugKey` and every action map outside the `DEBUG` context (the engine's debug keys and CONFIG.ts `debugKeys` are `DEBUG` maps). The scene debug camera's OrbitControls are gated off (`setSceneDebugCameraInputEnabled`). `h` calls `toggleActiveViewDrawer()` (the view's `toggleDrawer`). F1 and F5 do nothing. F7 and the pause button call `toggleViewPlay()`, the view's own play flag (in the Runtime view, `toggleAppPlay`). The master loop button stops every view.
- HUD: `<body>` gets `aekEditorView` and `aekView_<id>`, and `body.aekEditorView #hudRoot > :not(.aekKeepInViews)` hides the scene's HUD (drawer, switch tools, draggable windows, scene loader, app HUD) with `display: none`, so it comes back as it was. `KEEP_IN_VIEWS_CLASS` (`ui/HUD.ts`) keeps an element: the top on-screen rows (centred and top left), stats, the toaster, the viewports layer, debug dialogs with a backdrop, and windows of a kind registered with `keepInViews: true` (the profiler). An editor view's own UI needs it too. The scene drawer keeps its open state (`setDrawerSuspendedByView`) and leaves `debugDrawerOpen` to the editor view, whose own right drawer sets it, so the rules keyed on that class (top row, viewport stack) shift for it too.
- On-screen tools: the view tools group (tool type `'VIEW'`) sits right of the About and undo / redo group in the top left row (`onScreenTopLeftRow`); the play group is alone in the centred top row (`onScreenTopRow`). Runtime comes first, then `getViews()` (by `orderNr`, then registration order; a `ViewDef`'s `iconSize: 'small'` shrinks an icon that fills its box). The group shows only when an editor view is registered, and every switch shows a toast. An editor view builds no prod-test play button and no switch tools.
- Camera rig: `ViewCameraRig` (`{ camera, controls, setControlsSuspended, onMoveEnd? }`). The gizmo and the env ball resolve the camera they follow and drive through `kernel/camera/debug/_dbg__CameraRig.ts`: in the Runtime view the active camera, and the debug camera's rig while it is active; in an editor view its `getCameraRig()`, or its `getCamera()` treated like the main camera. The profiler census reads `getActiveViewCamera()` (`Views.ts`) instead, since it also loads in prodTest.
- Undo: `perScene` actions recorded in an editor view go to the bucket `__view:<id>`; `global` ones show in every view.
- Refresh: `AEK_debugViews` (`{ activeViewId, viewPlay }`) is written on every finished switch and every editor view play toggle. `restoreSavedView()` runs at the end of `InitEngine` (debug env, not awaited), after the first scene and the debug GUIs exist, so register views before that (in `kernel/init/InitEngine.ts`'s debug block). A saved view that isn't registered falls back to the Runtime view and clears the key. Each view restores its own state.
- The editor views' own code (`createViewCamera`, the material editor): `src/_engine/debug/editors/CLAUDE.md`.

### Build config notes (`vite.config.ts`)

- `root: './src'`, output to `../dist`.
- `vite-plugin-wasm` for Rapier's WASM binary.
- `worker: { format: 'es' }`: ES module workers, so a worker can load chunks on demand (an IIFE worker can't be code-split, and a dynamic `import()` in one fails `vite build`). The dev server loads workers as modules either way.
- `server.fs.allow: [<repo root>]`: `/@fs/` serves the repo (`node_modules`, `.tools/`) but nothing outside it, since the dev server is on the LAN (`--host`).
- `crossOriginIsolationPlugin`: the COOP / COEP headers on every dev server response (`SharedArrayBuffer`, physics' shared transform buffer); `basicSsl()` only under `AEK_DEV_HTTPS=true`.
- The dev-only `sceneGathererPlugin` (see data pipeline above), the dev-only `devFilesPlugin` (see Debug system), the dev-only `hubPlugin` (after `devFilesPlugin`; `/hub/`, see Ækasha Hub) and an `html-transform` plugin that injects `%APP_NAME%`/`%VERSION_CHECKSUM%`/etc. placeholders (sourced from `package.json`'s `app_metadata`/`engine_metadata`/`toolkit_metadata` through `devTools/projectMetadata.ts`) into `index.html`. In a build, `assetOutputsBuildPlugin` copies the asset outputs the production data loads into `dist/aek-assets/`; with `AEK_EMBED_PROFILE=<id>` the config is merged with the embed's (`getEmbedBuildConfig`, `embedOutputsPlugin` in its place; `devTools/sbp/CLAUDE.md`).
- `define`: `__PROJECT_METADATA__` and `__AEK_DEBUG__` (p607 D7): true when `VITE_APP_ENV` is `development` or `test` (read from `process.env`; `yarn build` sets none, which is production), false otherwise, dev server and workers included; `vitest.config.ts` defines it `true`, `types/typings.d.ts` declares it. False folds the debug flags and the code behind them (see Debug system).
- `rollup-plugin-visualizer` writes a bundle treemap to `dist-stats/bundle-stats.html`, and `devTools/sbp/moduleSizesPlugin.ts` (in `plugins` and `worker.plugins`, p619) each module's size after minification, the worker builds' too, to `dist-stats/module-sizes.json`: what `yarn sbp`'s groups and the production debug check read (`devTools/sbp/CLAUDE.md`).
- The public entries' aliases (`aekasha`, `aekasha/<feature>`, `aekasha/toolkit/<category>`, p606) come from one list, `devTools/aliases.ts`: `resolve.alias` here and in `vitest.config.ts`, and `tsconfig.json`'s `paths` (a copy `devTools/aliases.test.ts` checks). Each alias is exact (`^aekasha$`), so an entry not in the list fails to resolve. The toolkit, the app, `src/*.ts` and the generated code import the engine only through them; engine code imports engine code by relative path (both are lint rules, see Three-folder split).
- `package.json`'s `"sideEffects": ["**/*.scss", "**/*.css"]` (p607 D13): every other module is side-effect free, so the build keeps only what's used of a module (the entries' re-exports included) and drops a module none of whose names are used, with its top-level code. Vite applies it to the project's own files through its resolver (relative imports, in a build), and that wins over Rollup's `treeshake.moduleSideEffects` (the entries' function it replaced made no difference with it). So nothing may register at module load outside `_dbg__` modules (`moduleSideEffects.test.ts`), and an entry file holds only named `export … from` (`aliases.test.ts`). esbuild reads the field too, where Vite bundles `vite.config.ts` with its `devTools/` imports, so a devTools module the config loads registers nothing at load either (p619 H6: the Hub's directives are a list `createHubMarkdown` takes; `./devTools/**` was listed for them). The dev server doesn't tree-shake, so there importing an entry runs every module it re-exports.

## Coding standards

The full text, with examples, is the Hub page `hub/pages/documentation/coding-standards/` (`intro.md`, `jsdoc.md`). In one line each:

- Layering: engine ← toolkit ← app, enforced by the lint; outside the engine only `aekasha*` entries, inside it only relative paths; the kernel imports a feature's types only (`import type`); a feature owns its folder; debug code in colocated `_dbg__` modules, reached only through the debug loader.
- Public API: entry points only (an entry file is named `export … from` lines only), everything else `@internal`; options objects past two parameters or any optional one; no internal types in public signatures.
- Naming: `create`/`delete`, `register`/`unregister`, `get`/`set`, `*Async`, `on*` returning the remover, `is`/`has`; PascalCase files (an asset id's file keeps the id); no `Manager` suffix; no names differing only in case.
- Size: about 800 lines per file and 150 per function or closure, or the file's header says why not.
- Async and disposal: re-check the scene / entity / request after every `await`, and say in the JSDoc which overlapping call wins; one owner disposes each resource; listeners and timers return or register their cleanup.
- Per-frame code: no allocations, storages read once per frame, no redundant GPU state changes (`perf-auditor` agent).
- Smallest build: no module-level side effects (register in an install; `moduleSideEffects.test.ts`, and a top-level `const x = register()` it can't see is still one), debug code behind the folded debug flags and out of `try` blocks, heavy dependencies behind `import()`, no `Addons.js` barrel.
- Simulation (`APP_PHYSICS_STEP`, physics, controllers, AI): step-index time, seeded RNG, intents as the only input, state read at the step (never synced `TRANSFORM`s or interpolated poses), plain-data messages, `import type` across the boundary, data components, one Rapier build.
- Type hygiene: no `any`; `eslint-disable` with `-- reason`; a TODO names its issue file or plan.
- Dev tools (p619 D8, K3): they import the engine by path, only the schemas entry file (`src/_engine/schemas/index.ts`; the `aekasha/schemas` alias doesn't resolve in Vite's bundle of `vite.config.ts`), the modules `devTools/engineImports.test.ts` lists with their reasons (each loads zod at most, or the packages its entry names; `TestBridge.ts` with `import type` only), and types from any entry with `import type`; the test fails on anything else. The repo's folders come from `devTools/paths.ts` (the Hub's from `devTools/hub/paths.ts`, built on it), `sha256`, atomic and changed-only writes and the source walk from `devTools/files.ts`, git from `devTools/git.ts`. A `never` helper is a `function` declaration (an arrow's call doesn't narrow). A command's `main()` runs only when its file is the script run (a test or the Vite config imports it). New tool code names promises `*Async` (K4: older tool code isn't renamed).
- JSDoc: a summary on every export saying what the signature can't; `@param name text` (no hyphen, no type) and `@returns` only where they add; `@example` on entry APIs; `@remarks` for traps; `@template` for type parameters; empty `@internal` on its own line; `@deprecated` with its replacement and removal major; `{@link}` only to public names (on an entry; an internal export in backticks, or the Hub warns); Zod types documented on the alias and on each shape key. `eslint-plugin-jsdoc` checks the shape as errors (`eslint.config.js`; no `require-*` rule: presence is the ratchet's). It's pinned at 63.3.3, the last version that runs on `.nvmrc`'s Node 22.13.0 (64+ needs ≥ 22.22.2). Its `empty-tags` and `no-types` fixers delete text, and the hooks run `--fix` on every edit: write an `@internal` reason in the summary and a `@returns` with words first (`@returns {@link X}` reads as a type, and its fix leaves `@returns` empty).

## Versioning

`package.json` holds four semver versions (`MAJOR.MINOR.PATCH`: major = breaking, minor = new feature, patch = fix):

- `engine_metadata.version` — the engine (`src/_engine/`).
- `toolkit_metadata.version` — the toolkit (`src/toolkit/`), which ships with the engine. Its own scale: additions are minor, fixes/updates are patch, and a major bump happens only when an engine-level change requires it.
- `app_metadata.version` — the example app (`src/app/` and the app-level files in `src/`: `AppECSPlugins.ts`, `AppECSRegistry.ts`, `CONFIG.ts`).
- `version` (the project/package version) — **always identical to `engine_metadata.version`**. App-only changes bump `app_metadata.version` and never touch the project version.

Rules:

- Bump once per branch merged to `main` (in the PR), not per commit, at the level of the biggest change on that side since the last merge. Reset the lower parts to 0 (e.g. `1.4.2` → minor bump → `1.5.0`).
- Engine, toolkit and app are bumped independently; a side with no changes keeps its version.
- A major bump gets a new codename. Engine codenames follow the sun's path (Dawn → Sunrise → Morning → Zenith → Afternoon → Golden Hour → …); toolkit codenames follow the moon's phases (Crescent → Half Moon → Gibbous → Full Moon → …); app codenames follow life stages (Toddler → Preschooler → Kid → Teen → …).
- Each PR adds an entry to `CHANGELOG.md` with a section per part it bumped (Engine / Toolkit / App, plus Project for repo tooling).
- Before opening the PR, `yarn checkVersions --against main` must pass. The Stop hook runs the base check (project version = engine version, valid semver) whenever `package.json` changes.
- After merging to `main`, run `yarn tagRelease` and push the tags it prints.
- The `x-version-checksum` meta tag hashes every part's version and codename plus the project version.

## Workflow

- **Always run Node with the version in `.nvmrc` (22.13.0).** The shell's default Node can be older than `package.json`'s `engines` (≥ 22.13.0); yarn then refuses to run, and checks fail or silently do nothing. Every Bash command that runs `yarn`, `npx`, `node` or `tsx` starts with `source .claude/hooks/use-node.sh &&` (from the repo root; it works in bash and zsh and stops the command when that Node isn't installed), eg. `source .claude/hooks/use-node.sh && yarn build`. The hooks source it too. Never report a check result from another Node version.
- **Watching a long run.** A command whose result you wait for and that takes more than a few seconds (`yarn verify:*`, `yarn build`, `yarn hub:build`, `yarn assets`, a long Vitest run) runs in the background with its output in a log under the gitignored `.cache/`: the verify commands write `.cache/verify/progress.log` themselves, anything else is redirected to `.cache/runs/<name>.log`. Give the user a command to copy that starts from the repo root's absolute path on the current machine (the user works on several), eg. `cd /path/to/repo && tail -f .cache/verify/progress.log`. Don't poll the log: the background task reports when it ends. `yarn test` takes about a second: run it in the foreground.
- A Stop hook runs lint (`--fix`, then fails on the errors left; warnings don't block) and type-check (`tsc` and `tsc -p hub`) when `src/`, `hub/`, `devTools/` or `vite.config.ts` changed, the unit tests when `src/`, `devTools/` or `vitest.config.ts` did, the docs ratchet (`yarn verify:baselines --docs`, naming each new undocumented export) when `src/_engine/` or `src/toolkit/` did, plus the version rule check when `package.json` changed. Leave the tree compiling and lint-clean. An edit to a `.ts` file is linted the same way right away (`tool-lint.sh`), showing the file's remaining errors.
- **Keep the Ækasha Hub current.** A change that adds, changes or removes an engine or toolkit feature or public API updates its Hub content (`hub/pages/`) in the same branch: the feature page, the example page and its scene, and the snippets they include. Run `yarn hub:build` after a Hub change: it fails on a dead `hub:` link.
- **Keep the nested `CLAUDE.md` files current.** A change to a subsystem that has one (the map under Architecture) updates it in the same branch; project-wide rules stay here. A new nested file starts with one line naming what it covers, gets a line in the map, and its `## ` sections are Hub sections like the Architecture ones (see Ækasha Hub).
- `readme.md` (root) is the project's public face. Update it in the same branch when a change alters what it lists: a new engine subsystem or toolkit module (Features), a new asset JSON type, a new command or URL flag, a changed runtime/browser requirement, a changed signature of an API its Examples use (`InitEngine`, `createRenderer`, `createSceneLoader`/`loadScene`, `createMeshEntity`, `createPhysicsEntity`, `addSystem`/`registerPlugin`, `AppConfig`), or a Roadmap item that lands (move it into Features). Physics objects in the scene JSON schema, the procedural sky/day-night cycle, the editor/material editor and the LOD system are the ones that call for a new highlight or example. Keep version numbers out of it (they live in `CHANGELOG.md`).
- `docs/plans/` holds specs for unstarted work. Never treat one as current state or implement one unless I reference it explicitly.
