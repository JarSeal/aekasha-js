Notes for authoring the Ækasha Hub (`hub/`: pages, layout, assets; the generator's are in `devTools/hub/CLAUDE.md`); the root `.claude/CLAUDE.md` keeps the project-wide rules, commands and workflow.

## Ækasha Hub

- Sources: `hub.config.ts` (title, description, `coverageIgnore` (see Features and homepage); the menu comes from the pages, the GitHub links from `package.json`'s repository), `_layout/shell.html` (the frame every page goes into: `{{name}}` placeholders filled by `shell.ts`) and `_layout/404.html` (the 404 page's body), `_assets/` (`scss/hub.scss` and its partials through `sass`: `_tokens.scss` loads the UI kit's `src/_engine/ui/styles/tokens.css` (p801 Phase 5): the shell's `<html>` is a kit root (`aekUi`) whose theme is the kit's `data-aek-theme` (the toggle's, saved in `localStorage.aekHubTheme`; the homepage hero forces `dark` with it), each `--hub-*` role is an alias of a `--aek-*` token and only the Hub's own (the gradient, the header's background, the code colours, the layout sizes) have values, `devTools/hub/tokens.test.ts` keeping them so and the colours the Hub's but for p801 D2's changes; the focus ring and the transitions read the kit's tokens too; every `ts/*.ts` not starting with `_` is an entry bundled by Vite's `build()` (the `_` ones are `hub.ts`' lazy chunks, `_search.ts`, `_embed.ts` and the dev-only `_components.ts`, and `_devClient.ts`, the dev build's second entry; `_componentChecks.ts` is no chunk: plain data `yarn verify:ui` reads, which no page imports; `_kit/` holds the component library's stand-ins: the script build in `devTools/hub/CLAUDE.md`); `icons/` and `images/` copied as they are, and `_assets/fonts/` the engine's `src/_engine/ui/fonts/` woff2 and licence files (p801 D8: the UI kit's IBM Plex, which `scss/_base.scss`' `@font-face` rules name and its copy of `fonts.css`' opt-in puts in `--aek-font-sans` / `--aek-font-mono`, which `--hub-font` / `--hub-font-mono` alias; `devTools/hub/fonts.test.ts` keeps them the same as the engine's `fonts.css`)), `pages/` (one folder per URL), and `tsconfig.json` (`tsc -p hub`, DOM lib: the root `tsconfig.json` doesn't include `hub/`). The Stop hook runs on changes in `hub/` too and runs `tsc -p hub` after the root `tsc`.
- Pages: a folder under `hub/pages/` with an `index.html` is a page at its folder's path (`examples/physics/index.html` → `/hub/examples/physics/`), and needs its parent page. The `<head>` has `<title>` and `aek:` metas (`aek:menu` (label, default the title), `aek:order`, `aek:tags`, `aek:description`, `aek:icon` (top-level items), `aek:featured`, `aek:image` (see Scenes and examples), `aek:group`, `aek:covers` (see Features and homepage), `aek:dev` (see Dev pages)); an unknown `aek:` name warns. The nav is rendered per page at build time from these alone (children by `aek:order`, then label). The `<body>` is the page's markup: every empty element with an `id` is a slot, filled by `<id>.md` in the same folder. An `.md` without a slot, or in a folder without an `index.html`, fails the build; a slot without its `.md` warns.
- Markdown (markdown-it, `markdown.ts`): heading ids (never one the page's markup has: a `quick-start` slot's "Quick start" heading gets `quick-start-2`) with a `#` anchor, and the "On this page" TOC (h2 and h3, from 3 headings, not on the homepage); `hub:` links (`[physics](hub:examples/physics#setup)`, also `href="hub:…"` / `src="hub:…"` in a page's markup) resolved to relative URLs and checked, a missing page or `#hash` failing the build with its file and line; `repo:` links (`[budgets](repo:docs/techniques/asset-optimization.md#budgets)`): a repo file, checked with its `#heading` (GitHub's slug, `readMarkdownHeadings` in `repoFiles.ts`) or `#L<line>`, linking GitHub at the build's commit in `public` and the editor in `dev`; `::: tip|note|warning|danger|do|dont [title]` callouts (`do` / `dont`: a rule's example pair), and the other `::: name args` directives (`code-group`, `scene`, `embed`, `cards`, `claude-md`, `dev-only`; nest with a longer marker on the outer one): a `HubDirective` (`{ open, close, devOnly? }`) exported by its module and listed in `build.ts`' `HUB_DIRECTIVES`, which `createHubMarkdown` takes (nothing registers at load); `::: dev-only [title]` (p601) is content only the dev server's Hub shows: a directive with `devOnly: true` has its lines skipped before parsing in `public`, so none of it is in the built Hub (nor its TOC entries or search text) and `hub:build` doesn't check its links. The test and verify commands (the Quick start's "Check your changes") and the debug suite's test bridge are in such blocks; relative images, which must be inside the page's folder, copied to `_assets/images/pages/<page path>` (PNG and JPEG to WebP by sharp). A page's markup (not its Markdown) has `{{root}}`, `{{icon:name}}` (the SVG from `_assets/icons/` inlined, `currentColor`) and `{{asset:path}}` (a static asset's URL with its `?v=`); the shell also `{{link:path}}` (a checked page URL). An unknown icon, asset or page fails the build. `{{sbp:<profile>.<measure>}}` (p611, `devTools/hub/sbp.ts`) works in both a page's markup and its Markdown (filled before parsing, code blocks too): a gzip size from the last `yarn sbp` report, `.cache/sbp/report.json` (`initial`, `lazy`, `lazyFiles` (a count), `chunk:<key>`, `group:<group>`, `budget:<key>`; written `300.6 KiB`), so a page never states a size by hand. An unknown profile, measure or key fails the build; a report without the profile fails `public` and warns in `dev`. `yarn build` runs `yarn sbp` right before the Hub.
- Dev pages (p802 D1-D4, `pages.ts`, `devPages.test.ts`): `<meta name="aek:dev" content="true">` makes a page and every page under it dev only (`HubPage.isDev`; another value warns and leaves it public, a dev homepage and a generated page under a dev one are errors). The dev server's Hub shows them with "Local only" in their breadcrumbs; `public` drops them right after the coverage check, which counts their `aek:covers` (`removeDevPages`: no page, nav item, card or search entry). A top-level dev page isn't a nav item but a filled button between the nav and the tools (`renderDevNav`, the shell's `{{devNav}}`, empty in `public`). The header's desktop breakpoints (`_header.scss`) are where its contents fit with 16 px to spare, in the public and the dev header (measured at every 5 px from 960 to 1800, p802 Phase 1 step 6): a change to the header's contents re-measures them. A public page's `hub:` link to a dev page is an error in both modes unless it's inside `::: dev-only` (`HubLinkRef.isInDevOnly`; a generator writing a dev-only link passes it to `resolveHubLink`), and so is its `::: cards` of a dev page. The Project section, `hub/pages/project/`, is the first (p802).
- The Project section (`hub/pages/project/`, p802 D5): `project/` (the philosophy: the brand and core principles, how the project is developed, what the section is), `project/aekasha/` (Developing Ækasha: its `conventions` and `workflow` slots, and `::: cards project/aekasha` for its children: the design document, the component library and the code blocks reference) and `project/app/` (the app's conventions; its child is the app's design document). The prose is the root `CLAUDE.md`'s, `docs/plans/CLAUDE.md`'s and the coding standards page's, rewritten for a reader, not copied: each page names its sources, and a change to one is a reason to read its page. `aek:covers` ties only part of it (`project/aekasha/` covers `Plans logic and structure`, `Verify commands` and `Ækasha Hub`; the root's `##` sections, Coding standards, Versioning and Workflow, can't be named).
  - The design document (`project/aekasha/design/`): the prose in `<topic>-text.md` slots (`colours-text.md`, so a slot's id never takes its heading's), each rule with a `::: do` / `::: dont` pair, and seven `generated-design-*` slots (colours, type, space, elevation, motion, focus, icons) that `devTools/hub/generated/design.ts` fills from `src/_engine/ui/styles/tokens.css`, `fonts.css` and `BuiltInIcons.ts`: a token's value, a contrast ratio or the icon list is never written by hand. A kit root token no table shows warns at its line in `tokens.css`, so a new token's prefix gets a group in `design.ts` in the same change. Styles: `_design.scss` (in the public `hub.css` too).
  - The app's design document (`project/app/design/`): the same headings, each holding a `::: note To decide` and a link to the same section of Ækasha's. It's the app's document itself, not a template to copy: a fork replaces the notes with its decisions in place, starting from Ækasha's tokens.
  - The component library (`project/aekasha/components/`, p802 D9): the UI kit's pieces live, without the engine, for developing Ækasha (p803's public page is to reuse its script). Its `[data-hub-components]` element holds the settings form (theme and density on the HUD root; they look the same until p803 maps the kit's styles to the tokens) and, per piece, a `<piece>-text` slot, a `[data-hub-demo="<key>"]` box and a `generated-components-<piece>` slot (the "Used by" list, `devTools/hub/generated/components.ts`). `hub.ts` imports `_assets/ts/_components.ts` only on a page with `[data-hub-components]` and only in `dev` (`__HUB_DEV__`): it makes one HUD root over the viewport (`createHudRoot`, which brings the kit's global styles), registers the built-in icons and fills each box from `DEMOS` (a key's function adds the Hub buttons, `.hubButton` in `addGroup`'s labelled groups, that open the piece's states; a piece drawn in the page, a button or a key hint, draws in a kit root of its own in its box, `addKitRoot`, which the theme and density switches set with the HUD root). The env flags stay false, so a debug window doesn't open there, and the windows' storage is in memory (the stand-ins, `devTools/hub/CLAUDE.md`). A new component: the three elements in `index.html`, its `<piece>-text.md` (what it is, its states, what the page can't show, notes for its plan), a `Demo` in `DEMOS`, its functions in `COMPONENT_USES`, and its checks in `_componentChecks.ts` (p803 D11): `yarn verify:ui` opens each of the box's Hub buttons (`.hubButton`, `addButton`) as a state (axe-core and a screenshot in both themes and densities), so the table lists only the states a button alone doesn't open (a list open) and the keyboard scripts (what a keyboard user does and sees, step by step; `devTools/verify/CLAUDE.md`). A demo's button texts name its states and their screenshots: renaming one starts its screenshots again. `build-text.md` gives the kit's size with `{{sbp:…}}` (the SBP report measures the kit as a whole, so there's no line per piece). Styles: `_components.scss`.
- Code blocks (`code.ts`; the reference page is the dev page `hub/pages/project/aekasha/code-blocks/`): shiki highlights at build time with two themes of our own (`codeThemes.ts`, every colour AA on the code background and its line tints, which `codeThemes.test.ts` checks against `_tokens.scss`), both in the HTML as CSS variables, so pages ship no highlighter. The fence meta (`title="…"`, `{3,5-7}`, `startLine=N`, `showLineNumbers` / `noLineNumbers`, `wrap`, `collapse`; an unknown word warns) and shiki's notation comments (`// [!code ++|--|highlight|focus|error|warning]`) add the rest; `` `fn()`{ts} `` highlights inline code. `::: code-group` turns its fences into tabs. An unknown language renders plain with a warning. `hub.ts` adds copy (the DOM's clean source: no numbers, notation or `--` lines), collapse and the tabs; without JS every line and block shows.
- Snippet includes (`snippets.ts`): `<<< path/from/repo/root.ts#region {meta}` (or the whole file, or `#L10-L24`) on a line of its own becomes an ordinary fence token, titled with its path. Regions are `#region name` / `#endregion name` in any comment style; a `.json` file has none. Included files go into the build's `files`, so in dev an edit to one rebuilds the Hub and reloads the pages that show it.
- Scenes and examples (`devTools/hub/scenes.ts`, `cards.ts`): a Hub page shows the app's scenes, which `?startScene` opens (see Commands).
  - `::: scene <sceneId>` … `:::` is a panel: the scene's Hub image (webp at 800 and 1600 wide), the directive's content, then in `dev` "Open in debug" / "Open in prod test" buttons (`/?isDebug=true&startScene=<id>`), in `public` a note on running it locally (the public Hub runs no engine but `::: embed`'s). The ids come from `src/generated/generatedAppData.json` (`yarn build` gathers the development data again before `hub:build`): an unknown id fails the build in both modes, a missing image warns.
  - `::: embed <profile> [height]` … `:::` (p611 D9, `devTools/hub/embed.ts`; the browser side `_assets/ts/_embed.ts`, a chunk `hub.ts` loads only on a page with one) runs an embed profile of `sbp.config.ts` live, the one place the public Hub runs the engine (the SBP feature page and the embedding example). The panel shows the profile's first scene's Hub image as the poster, at `height` (a CSS length) or the poster's aspect, with the content as the caption; near the viewport the profile's entry is imported and mounted over it (`INLINE`, `input: 'NONE'`, paused out of view), with a pause button. Reduced motion keeps the poster with a play button; no WebGPU or WebGL2 keeps it with a line saying why. `public` imports the build copied into `_assets/embed/<id>/` (`yarn hub:build --no-embed`: the poster and a note), `dev` the entry's source from the dev server. One per page (the engine mounts once per page load), and an unknown or non-embed profile fails the build.
  - A scene's Hub image is `src/app/<sceneFile's folder>/<sceneId>.hub.png` (app scenes only; the same rule in `getHubImagePath`, `app/examples/_dbg__exampleHub.ts`, and `loadAppScenes`). It's written by the debug drawer's scene-scoped "Hub" tab, **Save Hub image**: a `takeSnapshotAsync` of what the canvas shows (active camera, PostFX, no viewports or debug helpers) at `CARD` 1600 × 1000 or `HERO` 1560 × 960, `encodePNG`, `writeDevFiles` (an unchanged PNG isn't written; without the dev files it's downloaded, with the path to put it at). A PNG isn't gathered, so a save doesn't reload the app, and the dev Hub watches the path (also before it exists), so it rebuilds. `registerExampleHubTabs()` (called from `src/index.ts` in the debug env) gives the tab, on enter, to every scene whose file is under `src/app/examples/` and to `OTHER_HUB_SCENES` (`lodShowcase`, `banner`; `TRANSPARENT_HUB_SCENES` saves the banner's without its background, the embed's poster), so no example scene file holds debug code.
  - `aek:image` in a page's head (`scene:<sceneId>`, or an image path from the repo root) is checked into `HubPage.imageFile`, every page's before any page renders. `::: cards <page path>` (no content) renders a card per child page in the nav: its `aek:image` (else its `aek:icon`), nav label and `aek:description`, linking it, out of the search (`hubSearchSkip`). Filters after the path: `featured` (children with `aek:featured`; the list gets `hubCards_featured`) and `group=<name>` (children with that `aek:group`). With no image among its cards the list gets `hubCards_icons`: `.hubCards_featured.hubCards_icons` are the homepage's icon columns, laid out by container query on the cards' parent. A page's markup shows a scene's image with `<img data-aek-scene="<sceneId>" src="<fallback>" …>`: the build swaps in the webp (`srcset`, real size) and the class `hubSceneRender`, and keeps the fallback (with a warning) until the PNG is saved; the homepage hero is `exampleHubHero`'s.
  - The example scenes (`src/app/examples/<name>/`: `<id>.scene.json` named "Example: …", `<id>.ts`, its own camera, lights and asset ids, since `createGeometry` returns an id that's registered already with its old params) are ordinary app scenes in every build. Each page under `hub/pages/examples/` includes its scene's regions (and `AppECSPlugins.ts`'s for the ECS example): a scene file holds only the example. The embedding example's scene is the banner profile's (`src/app/profiles/banner/`), and its site page is `devTools/verify/embedExample.html`, which `yarn verify:embed` runs: change its regions there. `exampleHud.ts` is their HUD line, removed by an all-scenes exit hook. `exampleHubHero` (`SPACE` sky box, toolkit asteroids, a bloom PostFX) has no page: it's the homepage hero's render. Changing an example changes its page: run `yarn hub:build`, and save its Hub image again when it looks different.
- Features and homepage:
  - Feature pages: `hub/pages/features/<slug>/` (rendering, ecs, physics, scenes-and-assets, input, smallest-build, asset-optimization, sky-box, lod, spatial-index, viewports, lines, debug-suite, characters, toolkit, ui-kit), each an `index.html` with an `intro` slot (the summary and the example's `::: scene` panel) and a `guide` slot (how it works, key APIs as `api:` links, related issues, "Read more"). `aek:group` puts each in one of the Features page's groups (Core, World, Performance, Tools, a `::: cards features group=<name>` each), and `aek:featured` (`content="true"`) marks the homepage's four, one per core principle (rendering, physics, ecs, smallest-build; four columns, so a fifth would sit alone). The content is checked against the code like the CLAUDE.md files, and a feature change updates its page (see Workflow).
  - `aek:covers` (comma-separated) names the CLAUDE.md sections a page covers (the root's Architecture `###` sections and each nested `CLAUDE.md`'s `##` ones), by heading without its parenthetical (`Debug system`). `::: claude-md` (`claudeMd.ts`, no content) renders the dev-only "Read more" line linking them in the editor (nothing in `public`). The coverage check (`checkClaudeMdCoverage`, right after page discovery) makes an unknown `aek:covers` name an error, and a section that no page covers and that isn't in `hub.config.ts`'s `coverageIgnore` (empty since p802 Phase 2: the Project pages cover the plans, the verify commands and the Hub sections) a warning at its line. The check reads the files through `readClaudeMdSections` (`repoFiles.ts`; the nested ones are what `git ls-files` lists, untracked ones included), is skipped where the root file isn't there (a build outside the repo), and adds them to the build's files, so in dev saving a new section warns.
  - The homepage is a generated section (`generated/home.ts`, path `''`): `generated-hero-side` (`engine_metadata.description`), `generated-hero-project` (under it, in `dev` only: the Project section's links, `PROJECT_LINKS`, the app's design document first, then the app, Ækasha's design document, the component library, Developing Ækasha, the plan workflow and the code blocks, each passed to `resolveHubLink` as dev-only; empty in `public`, p802 D6), `generated-whats-new` (`CHANGELOG.md`'s latest entry: date, branch, a row per part with version and codename, linked to its Version page anchor by a checked `hub:` link built from the heading's `slugify`, since the homepage renders before the changelog fills `latestChange.hash`) and `generated-quick-links` (Documentation, Examples, Issues, GitHub from `package.json`'s repository). Its featured features and examples are `::: cards … featured` slots (`featured-features.md`, `featured-examples.md`); the quick start is its own page (`examples/quick-start/`) so it can be a card.
- Issue files (`docs/issues/*.md`): `**Title:** …` on line 1, then from line 3 a block of `Key: value` lines, `Status:` first (`open`, `not filed yet`, `fixed`, …; text after a `|` is a detail shown next to the badge: `Status: open | fixed upstream on dev`), then the others that apply (`File at`, `Category`, `Found`, `Our workaround`), then a blank line and the issue itself. `fixed`, `closed`, `resolved`, `done` and `won't fix` are listed last. A file without a `**Title:**` line warns, and one without `Status:` is shown as "Status not stated".
