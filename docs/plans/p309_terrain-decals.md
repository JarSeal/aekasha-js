# Terrain Decals

Decals add unique, non-repeating detail where it matters: tyre tracks, cracks, stains, leaks, footprints, scorch marks, wet patches. They break up tiling more cheaply than any shader technique, because they cost only where they're placed.

This plan delivers:

- **Decal atlases**: imported CC0 decals plus procedural ones exported from p304's baker, as p299 atlases with a `DECAL` packing.
- **A decal material**: alpha-blended or alpha-tested, polygon offset, render order, wet-aware, with an optional puddle-mask channel (ruts that fill with water).
- **Mesh decals** authored in Blender (`*.decalSet.json`, owned by terrain blocks).
- **Runtime decals** projected onto terrain blocks and meshes: footprints, impacts, tyre ribbons. One `BATCHED` merge group (p375) per pool, with fade-out.

## Context (grounded)

- **No decal support exists** (no `DecalGeometry` usage; p301 survey).
- **`MeshProps`** (`kernel/mesh/Mesh.ts`, on `aekasha`) has no `renderOrder`, nor does the mesh schema (`schemas/MeshSchema.ts`). Lines have one (`LineTypes.ts`), and LOD's fade copies carry the mesh's (`features/lod/LodFades.ts`).
  - `polygonOffset`, `polygonOffsetFactor`/`Units`, `transparent`, `depthWrite`, `alphaTest` and `alphaToCoverage` are material params, so the material JSON can already set them through `params`.
- **The forward renderer** (`WebGPURenderer`) has no G-buffer. Screen-space/deferred decals would need the depth prepass that today lives only inside the PostFX chain (the lazy non-MSAA depth + normal pre-pass in `features/postfx/PostFX.ts`' pipeline, `getPrePass`, built only when a pass reads depth or normals, not reachable from materials). **Mesh decals are the fit.**
- **Atlases exist** (p299 Phase 3, `kernel/assets/TextureAtlas.ts`, `schemas/TextureAtlasSchema.ts`): a `*.textureAtlas.json` with named map slots (one KTX2 output each, built by `yarn assets`), cells placed by `rect` or a shelf packer on the block grid, `padding` with edge extension (the mip chain stops at the level it protects, or `mipChain: "FULL"`), a slot `fill`, `optimize.alphaCoverage` per slot (`_DONE_p341`), a free-form per-cell `data` that the gatherer passes through, and the cell table (`__atlas.cells`: UV rect, pixel size, `data`) in the generated data. A cell's slot source is an image or a texture asset's id, and a texture asset can be packed from several source images (`pack`, `schemas/TextureSchema.ts`). The `textureAtlases` scene (`src/app/scenes/textureAtlases/`) draws the test atlases. On `aekasha`: `getAtlasCell` (a cell's UV rect, size and `data`), `sampleAtlasCell` (the cell as an id, a UV rect or a `vec4` node, eg. a per-instance attribute: one material for many cells; clamped half a texel inside it by default) and `remapUVsToAtlasCell` (a geometry's UVs into a cell). Since p299 Phase 5 a material JSON samples a fixed cell without code: an input `{ "atlas": id, "slot", "cell", "clampToCell"? }`, which the gather checks against the atlas and whose slot it adds to the scene. Rules D1 must follow (p299 Phase 3): a slot's colour space is its `texOpts.colorSpace` (`"srgb"`; the slot schema is strict), a slot is KTX2 only, so a `data` slot (codec `none`) needs a codec set, and an explicit `rect` includes the padding and isn't snapped (off the 4 px grid it's an error; off the packer's grid, `4 · 2^⌊log2 padding⌋` px, it shortens the mip chain with a warning).
- **Terrain blocks** (p306) are regular grids with `getHeightAt` for generated geometry, or the extracted heightfield (p306 D3) for imported geometry. A small grid patch around a point is cheap to build, so runtime decals never need to clip the whole block.
- **ambientCG decal and atlas assets** (checked via the API, 2026-10-02):

| Asset                                                 | Maps                                        | Use                                         |
| ----------------------------------------------------- | ------------------------------------------- | ------------------------------------------- |
| `TireTracks001` (Decal)                               | colour, normal, roughness, AO, displacement | Tyre tracks                                 |
| `AsphaltDamage001` (Decal)                            | + opacity                                   | Cracks and damage                           |
| `AsphaltDamageSet001` (Atlas)                         |                                             | Crack set                                   |
| `Leaking012A` / `Leaking017B` / `Leaking019A` (Decal) | colour, normal, roughness, metalness        | Streaks on concrete and cliffs              |
| `LeafSet024` (Atlas)                                  |                                             | Leaf litter; p308 uses it for scatter cards |

Searches for footprint, crack and stain decals found nothing, so those come from procedural generators (D5).

## Design

### D1 — Decal atlas and packing

- **`DECAL` packing** (2 textures, same channels for imported and procedural):
  - `albedoAlpha`: RGB albedo (sRGB), A opacity;
  - `normalRough`: RG normal XY, B roughness, A **puddle mask** (where water collects, e.g. tyre ruts; 0 for most decals).
- **Built on p299's 2D atlases** (p299 D3, built): the atlas is a `*.textureAtlas.json` with the `albedoAlpha` (`texOpts.colorSpace: "srgb"`) and `normalRough` (`optimize: { "slot": "data", "textures": { "data": { "codec": "uastc" } } }`, `fill` `[0.5, 0.5, 1, 0]`) slots, so the composition, padding, block-aligned rects, per-slot encoding and the generated cell table are p299's. `decalsGround`'s 4 × 4 cells of 512 are explicit rects with the padding inside them (480² of content at 16 px), on the packer's 64 px grid, so the chain keeps levels 0-4. No decal build script and no `*.decalAtlas.json`.
- **Per cell** (the atlas JSON's `cells`):
  - `id`, and a `rect` in the atlas grid (or packed);
  - its slot sources: each a packed texture asset (`pack`) that puts the decal's maps into the `DECAL` channels (colour + opacity → `albedoAlpha`; normal XY + roughness + puddle mask → `normalRough`), from an imported asset's maps or an exported procedural PNG;
  - in its `data`: `physicalSize`, `tileAlong: 'U' | 'NONE'` (tyre tracks tile along their length) and `opacitySource` (an opacity map, or derived from height/colour with a threshold where the asset has none; if `pack` can't threshold, D1's first phase adds that step to the pack, not a separate tool).
- Fetching uses p303's `source.json` + `yarn fetchTextureSources`; `yarn assets` encodes (UASTC) and records the outputs in `assets.lock.json`.
- **Toolkit atlases:**
  - `decalsGround` (2K, 4 × 4 cells of 512): tyre tracks, cracks ×2, mud splatter, wet patch, stains ×2, footprints ×4 (boot, bare, paw, snow-boot), scorch, leaf patch, ice crack.
  - `decalsStructure` (2K): leaks ×4, cracks ×2, stains ×2, form-work marks.

### D2 — Decal material (toolkit: `src/toolkit/materials/decal/`, `decal.tsl.ts` with its `decal.material.json`, `setup` entry; its nodes in `src/toolkit/terrain/decals/`)

- **Sampling:** the atlas cell is sampled with the mesh's UV. Blender decals are UV'd straight into atlas space; runtime decals get UVs computed into their cell's rect from the cell table (`getAtlasCell`); the material samples with `sampleAtlasCell`, which clamps half a texel inside the rect (p299 D4, on `aekasha`). A runtime pool's instances pass their cell as a per-instance `vec4` rect attribute, so one material draws every cell; a material JSON fixed to one cell can use p299 D5's `{ "atlas", "slot", "cell" }` input instead.
- **Opacity:** opacity × an edge fade (a UV border falloff, so hard quad edges never show) × a per-instance fade (runtime pool).
- **Two modes:**

| Mode              | Settings                                                                                               | Use                         | Cost                                                          |
| ----------------- | ------------------------------------------------------------------------------------------------------ | --------------------------- | ------------------------------------------------------------- |
| `BLEND` (default) | `transparent`, `depthWrite: false`, `polygonOffset` (factor −1, units −4), `renderOrder` after terrain | Soft decals: stains, tracks | Sorted with other transparents; overdraw where decals overlap |
| `CUTOUT`          | `alphaTest` + `alphaToCoverage` when MSAA is on                                                        | Footprints, cracks, leaves  | Cheaper: opaque pass, no sorting                              |

- **Lighting:** the decal's normal and roughness replace the surface's inside its opacity, which is correct for a forward mesh decal.
- **Wetness:** `applySurfaceWetness` (p307) with the decal's own response. The **puddle mask** channel raises local puddle level, so ruts fill first.
- **Shadows:** decals don't cast; they receive.
- **Engine addition:** `renderOrder` in `MeshProps` and the mesh schema (`schemas/MeshSchema.ts`; small, generic), applied by `createMeshEntity` and kept by the LOD's level swaps and fade copies.

### D3 — Mesh decals from Blender (`*.decalSet.json`, engine asset type, in `terrain()`)

```json
{
  "id": "showcaseMud_decals",
  "importedAsset": "showcaseMud_decals",
  "material": "decalsGround_blend",
  "renderOrder": 10
}
```

- Spawned with the owning terrain block (p306's `decals` ids) or by `spawnDecalSet(id)`.
- **Merging:** `CUTOUT` mesh decals are opaque, so a block's mesh decals can join a p372 merge group (one draw per decal material per block). `BLEND` decals are transparent: a `BAKED` group refuses them (p372 §5), a `BATCHED` one (p375 Phase 3) takes them and draws them in join order (`transparentOrder: 'JOIN'`) or back to front, so a block's `BLEND` decals can share one batch per material (one render object; on WebGPU one draw per decal, see D4).
- **Engine-level, but tiny:** a typed wrapper around `spawnImportedAsset` with material, render order and no physics, in p306's `terrain()` feature (`features/terrain/DecalSetSchema.ts` on `aekasha/schemas`, `spawnDecalSet` on `aekasha/terrain`, the suffix in `GATHERED_SUFFIXES`). It exists so a terrain block's manifest can list decals as data.
- **Blender workflow** (`terrain_decals.blend`):
  - **Quad decals:** a plane UV'd onto an atlas cell. The template has one pre-UV'd quad per cell, so you duplicate the cell you want.
  - **Strip decals** (tyre tracks): a plane with Array + Curve modifiers along a path curve, UV'd along the length (`tileAlong: 'U'`).
  - **Conforming:** subdivide to about the terrain grid spacing, then _Shrinkwrap_ (Target: block, Wrap Method: Project along −Z / Nearest Surface Point, Offset 0.01–0.02 m), then apply.
  - **Export:** a separate GLB per block (geometry only, same locked settings as blocks, no colliders), into the block folder.

### D4 — Runtime decals (toolkit: `src/toolkit/terrain/decals/RuntimeDecals.ts`, on `aekasha/toolkit/terrain`)

- **`createDecalPool({ atlas, mode, maxDecals = 128 })`:** an explicit `BATCHED` merge group (p375, `aekasha/merging`; decided by p375 Phase 3's stand-in, its S5 results):
  - **the pool's decals are member entities**: each a mesh entity with its own registered geometry (its patch) and the pool's material, joined with `addToMergeGroup` (not the `merge` prop, which only queues it until the build: `setMergeMemberColor` needs a member). The group owns scene scope, `DISABLED`, per-member culling, the Merging tab and picking (`getMergeMemberAtBatchId`);
  - **FIFO by rewriting**: the pool keeps `maxDecals` entities; a spawn takes the oldest, writes the new patch into its geometry, moves it (`setTransform`) and calls `updateMergeMember`, which rewrites its geometry slot in place and puts it last in the join order. Deleting the oldest entity and creating one works too (the freed slot is reused by fit, and a spawn before the frame's build, `APP_RENDER_SYNC`, is never drawn on its own) but cost 0.15-0.19 ms more a spawn in the stand-in;
  - **the group's settings**: `geometryReserve` sized for the largest patch (every slot alike, so the buffers stop growing: 36 000 spawns over 10 minutes kept one size), `transparentOrder: 'JOIN'` for `BLEND` (the newest on top; its sort was ~0.1 ms cheaper a pass than three's depth sort at 512), `castShadow: false`. `CUTOUT` is an opaque batch (no sort);
  - **draws**: one render object per pool; on WebGL2 one multi-draw, on WebGPU one draw per visible decal (r187 merges only instances of one geometry, and every patch is its own). The win is the CPU's (render objects, not draw calls): 35-58 % of the CPU frame at 128 decals and 49-81 % at 512 against a mesh per decal, on both backends; WebGPU's GPU time the same. **The single-geometry pool is dropped**: it would buy WebGPU one draw where the draws cost no measured GPU time, for its own code (fixed vertex slots, a per-vertex fade attribute, whole-range rewrites). Revisit only if WebGPU gains multi-draw-indirect (p375 §5) or a profile shows the per-decal draws;
  - **tint and fades**: `setMergeMemberColor(entityId, { color?, opacity? })` (its alpha fades a `BLEND` decal; with `CUTOUT` it erodes the cut-out shape), written only on a change. It costs ~1-1.5 µs a call, so a fade that changes many decals a frame is the spawner's main cost (the stand-in faded by FIFO place, rewriting the oldest quarter on each spawn: 0.17-0.25 ms a spawn at 512): fade by time over `fadeSec` and write only the decals fading;
  - **WebGL2's GPU time**: the stats timer read 5.7-8.0 ms for the batch against 5.0-5.3 for separate meshes in every run (WebGPU: the same or lower). That timer is unreliable (p375 §2), so this is unproven: profile it in Phase 4 before relying on WebGL2's GPU budget;
  - per-frame work (the fades) allocates nothing and writes only the decals that changed.
- **`spawnDecal(pool, { target, position, normal, size, rotation, cell, lifetimeSec?, fadeSec? })`:**
  - **On a terrain block:** build a conforming patch from the block's grid (heights in a size-bounded window; spacing = block spacing, or half of it for small decals) and offset it along the normal. O(cells under the decal), not O(block).
  - **On other meshes:** three's `DecalGeometry` (`three/examples/jsm/geometries/DecalGeometry.js`, never the `Addons.js` barrel), loaded by `import()` on the first such decal, clipped against the target mesh. Costly on big meshes, fine on props. Documented.
- **`spawnRibbonDecal(pool, { target, points[], width, cell })`:** a strip conformed along a path. Use it for tyre tracks behind a vehicle, appended in segments.
- **Wet footprints:** the footprint cells' puddle mask × wetness gives wet prints in mud, and snow-boot cells (height-only normal) give prints in snow. This is the "T15" item of p307.
- **Determinism:** runtime decals are visual only and never touch physics. Spawn variation (rotation, cell pick) draws from a named stream (`getRandomStream('decals')`), so a replayed scene stamps the same decals.

### D5 — Procedural decals (toolkit, p304 generators)

| Generator          | Output                                                                                                                      |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------- |
| `decalCracks`      | Worley F2−F1 edges with radial falloff and branching noise; dark albedo, normal from edges                                  |
| `decalStain`       | fbm blotch, darkening, roughness change                                                                                     |
| `decalScorch`      | Radial burn with soot noise                                                                                                 |
| `decalMudSplatter` | Splat-drop SDFs + fbm                                                                                                       |
| `decalFootprint`   | Boot, bare, paw and snow-boot shapes as SDFs + tread pattern; height-driven normal; puddle mask in the heel/toe depressions |
| `decalWetPatch`    | Soft fbm mask, darkening + low roughness + puddle mask                                                                      |
| `decalIceCrack`    | Thin, bright crack lines + subsurface-looking halo                                                                          |

- **Exported** through p304 D5 into the atlas sources (committed, since they aren't re-downloadable).
- **Optional runtime path:** bake per-seed variants into an array (`bakeTexture` layers) for endless unique footprints. The decal material then has an `ARRAY` source mode. Only if the gallery shows repetition matters.

## Handbook content (`docs/techniques/terrain-decals.md`)

1. **What it is:** mesh decals in a forward renderer, and why not screen-space here.
2. **"Best for":**
   - every camera type;
   - first- and third-person benefit most (close-up unique detail);
   - top-down/RTS use them for roads, scorch and tracks (very visible from above);
   - stylized: hand-painted decal atlases.
   - **Poor fit:** thousands of overlapping blend decals in one spot (overdraw). Use CUTOUT or bake them into a colour map (p305 D7) instead.
3. **Performance:**
   - BLEND vs CUTOUT;
   - draw calls (one per decal set or pool);
   - overdraw;
   - runtime spawn cost (patch vs `DecalGeometry`);
   - atlas VRAM (2K UASTC ≈ 5.6 MB for 2 maps with mips);
   - gallery numbers.
4. **Maps:** the `DECAL` packing table; opacity sources; the puddle mask, and why.
5. **Blender, step by step:** atlas cell quads, strips along curves, Shrinkwrap settings, apply, UV check, export.
6. **Import and set-up:** `*.decalSet.json`, block `decals`, materials (BLEND and CUTOUT variants).
7. **Runtime:** pools, `spawnDecal`, ribbons, lifetimes, wet footprints.
8. **Variations, each with why and cost:**
   - baking static decals into a colour map (zero runtime cost, no lighting response);
   - CUTOUT instead of BLEND;
   - procedural arrays for variety.
9. **Making your own decals:** from photos (opacity from a mask painted in Krita/GIMP), from the baker, and from Blender (bake a sculpted crack to a plane: colour, normal, height → opacity).
10. **Pitfalls:**
    - z-fighting (offset and polygon offset);
    - mip bleeding (atlas padding);
    - decals floating on steep slopes (subdivide);
    - sorting with other transparents.

## Phases

### Phase 1 — Atlas tooling (D1) — done

1. The packed texture JSONs per decal (the `DECAL` channels), the two atlas JSONs in `src/toolkit/textures/decalsGround/` and `src/toolkit/textures/decalsStructure/` (p301 §2: shared textures by id), and the `opacitySource` derivation if `pack` lacks it (an asset pipeline change, its test next to it).

Found when it started (2026-11-18), and decided:

- **ambientCG, by its API:** `TireTracks001` has colour, normal, roughness, AO and displacement, no opacity, 180 × 45 cm (stored stretched in a square cell, its UVs over the whole cell: about 280 px/m along the track). `Leaking012A` / `017B` / `019A` have colour, normal, roughness, metalness and displacement, no opacity. `AsphaltDamage001` has an opacity map (120 × 120 cm). So two `decalsGround` cells (tyre tracks, one crack) and three `decalsStructure` cells (leaks) come from ambientCG; the rest are placeholders (cells without sources: the slots' `fill`) until Phase 5.
- **`AsphaltDamageSet001` dropped:** it's an atlas of several potholes, and `pack` can't crop; the second crack is Phase 5's `decalCracks`.
- **Opacity derivation needs no pack step:** `remap: [t0, t1]` with the output's clamp to 0-1 is a soft threshold, so a recipe derives a missing opacity from its displacement or colour; the cell's `opacitySource` in `data` only records it.
- **Fetching:** `yarn fetchTextureSources` took only texture-set folders. A `source.json` without a set beside it is now a source folder (a decal's, `decalsGround/<decal>/`), named by its folder, with an `opacity` map type, the `.gitignore` pattern `src/toolkit/textures/**/source/raw/` and its row in `CREDITS.md`.
- **Atlas-only sources:** every `*.texture.json` is encoded on its own, so a decal's two pack recipes would each ship an unused 2K output. A texture JSON gets a flag that makes it an atlas cell's source only, never encoded on its own.
- **The gallery's Decals row** shows each atlas's two slots as whole-atlas quads with cell labels; per-cell quads come with Phase 2's material.

Sections:

1. Source folders in `yarn fetchTextureSources` (`textureSources.ts`, its tests) — done.
2. The atlas-source-only texture flag (the pipeline, its test) — done. As built: `sourceOnly: true` on a `*.texture.json` (`TextureAssetSchema`, build time only; named for both uses, an atlas cell's or a texture array layer's source). `collectPipelineAssets` skips it; the gather keeps it in pass 1's lookup, leaves it out of the development data's `textures` and drops it from a texture's data, and fails a scene listing it, a material naming it (the closure) and a texture set slot naming it (`getSourceOnlyTextureError`, `gather/context.ts`). An engine schema change: the engine's minor (Phase 6) covers it.
3. The decals' `source.json`s and pack recipes, the two atlas JSONs; fetch, `yarn assets`, the cell tables — done. As built:
   - **Source folders** (each a `source.json`, its two `sourceOnly` recipes `<decal>_albedoAlpha` / `<decal>_normalRough`, its gitignored `source/raw/`): `decalsGround/decalTireTracks01/` (TireTracks001), `decalsGround/decalAsphaltDamage01/` (AsphaltDamage001: a square patch of damaged asphalt, not a crack line, so its cell is `asphaltDamage`), `decalsStructure/decalLeak01-03/` (Leaking012A, 017B, 019A), all 2K-JPG.

AsphaltDamage001: colour, its opacity map, puddle the inverted height (`remap [0.2, 0.6]`, its deepest dips). The Leaking downloads hold their streaks only in the displacement (colour near-white greyscale, metalness 1 everywhere, normal flat, roughness low): a constant stain colour (linear 0.06, 0.05, 0.04), opacity the displacement over its full range (`remap: "auto"`) × 0.85, no puddle mask. A single-channel target from a greyscale JPG needs `"channel": "r"` (a target `a` reads the source's `a` by default).

Both slots `profile: "hero"` (the default `maxSize` is 1024), `normalRough` UASTC RDO 1; levels 0-4.

4. The gallery's Decals row — done. As built: `src/app/scenes/terrainGallery/decalsRow.ts` (`createDecalsRow`, `DECALS_ROW_BOUNDS`, `DECALS_PANELS`), right of the Live block (x 130-168, z −24…−6, in the ground's extent): an atlas per row from the back, a flat 8 m panel per view (`ALBEDO` over a ground colour by its alpha, `OPACITY`, `NORMAL_ROUGH`, `PUDDLE`), `BASICNODEMATERIAL` showing the stored values (the data views through `sRGBTransferEOTF`), every cell outlined and named by a `CanvasTexture` drawn from the slot's cell table (`getTextureAtlasInfo`), registered with `saveTexture` (the scene's). ### Phase 2 — Decal material (D2) — done

1. BLEND, CUTOUT, edge fade, wet response, puddle mask; `renderOrder` in `MeshProps` and the mesh schema (an engine minor, with its JSDoc and a test).

**Exit:** decal quads on a gallery block show no z-fighting at 200 m, no visible quad edges, and get wet.

Found when it started (2026-11-18), and decided:

- **D2's per-instance rect is stale:** D4 replaced the single-geometry pool with a `BATCHED` group of separate geometries, which has no per-instance attribute. So the material reads atlas-space UVs only (a Blender decal's, `remapUVsToAtlasCell`'s, Phase 4's patches'), and the edge fade a **second UV set (`uv1`), 0..1 over the decal**. Finding the cell in the shader from the cell table was the alternative (a loop over every cell).
- **`CUTOUT` needs the polygon offset too** (D2's table gave it to `BLEND` only): a coplanar cut-out quad z-fights the same way.
- **The puddle mask is a relief** for `applySurfaceWetness`'s puddles (`0.5 − mask × puddleDepth`), not its `regional` input, which keeps a place wet in any weather. `Wet.ts` is unchanged.
- **The mode's flags are the setup's** (`transparent`, `depthWrite`, `alphaToCoverage`, `polygonOffset`), so a JSON can't contradict its mode; the numbers stay tunable through `params`. The toolkit ships a JSON per atlas and mode over one TSL file.
- `renderOrder`: LOD level swaps never touched it and `LodFades.ts` already copied it into the fade copies, so LOD needed a test, not code. A `BATCHED` merge group already refuses a member with another `renderOrder` (`MergeEligibility.ts`) and draws at its first member's.

Sections:

1. `renderOrder` in the engine — done.    - **Not `spawnDecal`: `spawnMeshDecalAsync(pool, opts)`** → `Promise<entity | null>`. `spawnDecal` is synchronous and the `import()` isn't, so a mesh decal has its own call (`*Async`), loading `three/examples/jsm/geometries/DecalGeometry.js` with its first call (one promise kept). `SpawnMeshDecalOpts` is `SpawnDecalOpts` less `target`, `position`, `normal`, plus `target: { entityId }`, `position: { x, y, z }`, `normal` (required, world space, normalized here) and `depth` (the projector box's along the normal, default the decal's larger side). 4. Ribbons: `spawnRibbonDecal` (segments as members, the tiles along U, the ends' fade in metres) — done. As built:
   - **Files:** the pool module passed 800 lines, so each spawn beyond the block's has its own module over the pool's internals (`@internal` exports of `RuntimeDecals.ts`: `PoolState`, `DecalPlace`, `DecalLook`, `createLook`, `getLiveState`, `readDecalBlockTarget` with `DecalBlockTarget`, `resolveLook`, `pickCell`, `takePlace`, `createPlace`, `releasePlace`, `finishSpawn`, which now takes the patch counts): `MeshDecals.ts` (section 3's `spawnMeshDecalAsync` and `SpawnMeshDecalOpts`, moved), `DecalRibbonPatch.ts` (the strip's geometry, pure), `DecalRibbons.ts` (`spawnRibbonDecal`, `createDecalTrail`). `RuntimeDecals.ts` 720 lines. The pool's state has `isRibbonWarned`.
   - **`DecalRibbonPatch.ts`' `writeRibbonPatch(surface, spec, arrays, out)`** → `{ vertexCount, indexCount, stride, length }`: the path's points in world space (`pointCount` of them; a repeated point takes its neighbour's direction), rows at stations at most `step` apart (each segment cut evenly, the path's points kept), columns as close across `width` (at least 2), each vertex sampled on the block (`sampleBlockSurface`) and lifted along that normal. The tiles: `tileLength` metres a tile from `along`; a station where a tile ends is two rows (u at the cell's right, then its left), no faces between them; the path's start a tile's start, its end a tile's end. `uv1`: v across 0..1 (1 on the frame's v side: −z for a path along +x), u the fade coordinate `min(0.5, share · s / endFadeMeters, share · (length − s) / endFadeMeters)` at a faded end (`edgeShareU` the material's share; 0 or no fade: 0.5). A row at a path's point turns to the bisector, widened by the miter (at most 2); a row at an end turns to `startDirection` / `endDirection` when given, at its plain width, so a ribbon joined to another (its start the other's own last direction) shares its last row exactly. Past the arrays the step grows by 1.25 until the rows fit (`stride` its factor, rounded up); none fits (eg. tile ends every few centimetres) → 0 vertices. The stations go into module lists, reused.

The step is half the block's grid spacing, the lift 0.015 m (Phase 3's offset, since the faces aren't the block's), the end fade 0.5 m at the share of the material's `decal_edgeFade` uniform's x (`userData.uniforms`; 0.1 without one). Only the cell is drawn from the random stream (`pickCell`: no rotation drawn).    - **`createDecalTrail(pool, { target, cell, segmentLength?, minSpacing?, … })`** → `DecalTrail { addPoint(x, z), end() }` (`CreateDecalTrailOpts`: `SpawnRibbonDecalOpts` less `points`, `along`, `fadeStart`, `fadeEnd`; `segmentLength` default 2 m, `minSpacing` 0.1 m).    - Tests: `DecalRibbonPatch.test.ts` (5: rows, columns and doubled tile ends with their u, v across, faces up; the fade coordinate; `along` and a relief block's surface with the lift; the miter at a right angle and a joined ribbon's shared row; longer steps, no fit, no length, a repeated point), `DecalRibbons.test.ts` (7, the pool test's stand-ins: the physical size, the material's share at the ends, a tile's end; the cut at the block's edge and the `null`s; the width and tile length refusals; a ribbon too long gives its place back; a trail's segments joined with their tiles running on and its ends; a point off the block and `minSpacing`; a gone pool, quietly).

## Risks

| Risk                                                                                             | Mitigation                                                                                                                          |
| ------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- |
| `BatchedMesh` behaviour on the WebGPU backend (per-instance colour, geometry slot reuse) | Answered by p375 (r187). Phase 0: per-member colour and visibility work on both backends; `deleteGeometry` + `addGeometry` leaks buffer space. Phase 3 (its S5 results): a `BATCHED` merge group is the pool (D4), with geometry slots that are freed and reused by fit, `geometryReserve`, transparent members in join order, `setMergeMemberColor`; a stand-in pool of 128 and 512 conformed patches beat a mesh per decal by 35-81 % of the CPU frame on both backends, its buffers the same size over 10 minutes of churn, and `BLEND` decals pixel-identical to separate meshes. WebGPU draws one per decal (one render object); the single-geometry pool is dropped (D4) |
| Transparent sorting conflicts with other transparents (water later, particles)                   | `renderOrder` bands documented: terrain 0, decals 10, scatter cards (CUTOUT) opaque, transparents ≥ 20                              |
| Polygon offset differs between depth ranges or backends                                          | Offsets in the material are tunable; the gallery checks at 1, 50 and 200 m                                                          |
| Atlas mip bleeding                                                                               | Cell padding (≥ 16 px at 2K) with edge extension; mips are generated per atlas, so padding scales                                   |
