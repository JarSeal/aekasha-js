# Sky Box KTX2 Cube Textures and Pre-filtered Environments — Plan

A `CUBE_TEXTURE` sky box base loads six images (`fileNames`, `layers/Base.ts`' `loadCubeTexture`,
through the engine's texture loader) and bakes its PMREM at runtime (`getPMREMTexture`,
`SkyEnvironment.ts`). three r187 makes two things possible that weren't on WebGPU:

- **KTX2 cube textures** (`CompressedCubeTexture`, #35083): before r187 a KTX2 cube rendered black
  on the WebGPU backend (uploaded as 1 × 1 × 6). With uncompressed data in compressed textures
  (#35082), UASTC-HDR or half-float KTX2 uploads on WebGPU too (an RGBA half fallback): an option
  for HDR skies, which load as uncompressed `.hdr` equirects today.
- **Pre-filtered environments:** `PMREMNode.updateBefore` uses a texture with `isPMREMTexture` as
  it is, and `updateFromTexture` reads a `CompressedCubeTexture`'s face mips, so a cube whose mips
  are already the PMREM's roughness levels skips the runtime bake (three's
  `webgl_materials_envmaps_fasthdr` example does this).

Not urgent: no sky box needs it today. It cuts a texture sky's download (six PNGs → one KTX2) and
its first-frame bake.

## Grounding (2026-11-05)

- `SkyBoxCubeBaseSchema` (`SkyBoxSchema.ts`): `fileNames` (six), `flipY`, `colorSpace`, `rotate`,
  `intensity`.
- `loadCubeTexture` sets `generateMipmaps = true`: wrong for a compressed cube (its mips come in
  the file, and a compressed format can't generate them).
- The asset pipeline (`devTools/assetPipeline/`, `yarn assets`) encodes 2D textures and texture
  arrays with KTX-Software's `ktx`; it skips cube textures (`textureArrays.ts`: "the texture is a
  cube texture"). `ktx create --cubemap` takes six faces.
- r187's PMREM is a `CubeRenderTarget` with only the prefiltered mips down to 8 texels, at least
  256 per face (p057 D1): a pre-filtered KTX2 has to match that layout and its roughness ramp
  (`PMREMGenerator.lodToRoughness`), or PMREMNode samples the wrong roughness per level.

## Design (to refine)

1. **A KTX2 cube base:** `fileName` (one `.ktx2`) as the alternative to `fileNames` in the cube
   base schema; the loader goes through the KTX2 path (the engine's `KTX2Loader` setup) and skips
   `generateMipmaps`; `flipY` and `rotate` as for six images.
2. **The pipeline encodes cubes:** a texture JSON whose `fileName` is six faces gets
   `optimize.ktx2`, encoded with `ktx create --cubemap` (ETC1S or UASTC, mips generated by the
   encoder), recorded in `assets.lock.json` like any output.
3. **Pre-filtered (optional, after 1-2):** a build step that bakes a cube's PMREM (in a headless
   browser, or `PMREMGenerator` against the WebGL backend) and writes its levels as a KTX2 cube,
   marked `isPMREMTexture` at load. Only if the runtime bake shows up in a scene's first frame
   (measure it in Phase 0).

## Phases

### Phase 0: Measure — done

A texture sky's first-frame cost (the PMREM bake) and its download, six PNGs against one KTX2
cube, on WebGPU and WebGL2.

As built (2026-11-20; a throwaway Playwright script, not committed):

- Subject: scene01's `desert-dunes` cube, six 2048² RGB PNGs. KTX2 cubes made from them with the
  repo's `ktx` 4.4.2 (`ktx create --cubemap --format R8G8B8_SRGB --generate-mipmap`, the
  pipeline's default codec settings: ETC1S `--qlevel 128`; UASTC level 2, RDO 2, zstd 18), at 2048
  and at 1024 (`--scale 0.5`). Encode times: ETC1S 8 s / 4 s, UASTC 40 s / 11 s.
- Method: the scene runner's dev server and the Windows Chrome 157 on the real GPU (AMD RDNA 3);
  WebGL2 forced through the renderer's debug LS key (`debugRenderer`). A page per case on
  `exampleQuickStart`, in the page: `loadTextureAsync`, `renderer.initTexture`, then
  `getPMREMTexture`, each timed on the CPU and until the GPU finished (WebGPU
  `queue.onSubmittedWorkDone()`, WebGL2 a 1-pixel `readPixels`). Six runs per case: the first
  (cold), then the median of five (warm). The first page per API was a warm-up (WebGL2 caches
  its programs across pages; WebGPU didn't).
- Both APIs load a KTX2 cube as a `CompressedCubeTexture` and bake its PMREM with `fromCubemap`
  unchanged: r187's support works.
- **Download:** PNGs 22.6 MB; ETC1S 2048 2.09 MB (with mips), UASTC 2048 13.5 MB; ETC1S 1024
  0.64 MB, UASTC 1024 3.74 MB.
- **Load** (warm; fetch from the local dev server plus decode or transcode; the KTX2 transcode is
  in KTX2Loader's workers): PNG ~185 ms; ETC1S 2048 ~128 ms, 1024 ~40 ms; UASTC 2048 ~1.1 s,
  1024 ~275 ms (zstd and the UASTC transcode: slow for a sky).
- **Upload** (main thread; the PNG cube with `generateMipmaps`, as `loadCubeTexture` sets it):
  PNG 160-190 ms CPU on both APIs; a KTX2 2048 cube 4-5 ms (WebGPU) / 23-25 ms (WebGL2), 1024
  under 3 ms. The largest first-frame cut Phase 1 gives.
- **PMREM bake** (warm, GPU done): WebGPU 28 ms at 1024, 47-50 ms at 2048 (9-15 ms of it CPU);
  WebGL2 50 ms at 1024, 139-145 ms at 2048 (all of it blocking the main thread). The source format
  makes no difference, only the face size. Cold, WebGPU's first bake in a page took 480-500 ms
  on every page (its pipelines' creation), WebGL2's 243 ms on the warm-up page only.
- **The PMREM's size is the source's face size** (r187's `_fromTexture`: a cube's face width,
  floored to a power of two, at least 256; an equirect's width / 4), and it's HalfFloat RGBA. So
  the 2048 PNG cube keeps a 2048-per-face PMREM of about 268 MB on the GPU (9 levels down to 8
  texels), plus a transient source target of ~200 MB during the bake; at 1024 it's 67 MB, at 512
  17 MB. `env.size` doesn't apply to a texture base (only the composite path's bake). A sky
  texture's face size is its memory and its bake time, so the cube's size should be a choice:
  the pipeline's default `maxSize` (1024) would make it one in Phase 2.

Decision for Phase 3 (pre-filtered cubes): the warm bake (28-50 ms GPU on WebGPU, 50-145 ms
on WebGL2) is smaller than what Phases 1-2 cut (the PNG upload's 160-190 ms main-thread block and
~20 MB of download). WebGPU's ~0.5 s first bake is pipeline creation, which a pre-filtered cube
skips only when nothing else in the page makes a PMREM (a composite sky's env bake uses the same
pipelines), and a pre-filtered cube needs a browser build step and an HDR-capable encode to match
the HalfFloat PMREM. Recommended: drop Phase 3 for now (a follow-up if a scene's first frame shows
the pipeline creation).

### Phase 1: KTX2 cube bases — done

Design 1, with an example sky box in the app.

As built:

- The key is `file`, not `fileName`: the equirect base's single file is `file` already, and the
  flat base overrides schema and `BASE_STRUCTURAL_KEYS` have it. `SkyBoxCubeBaseSchema` takes
  `fileNames` (six) or `file` (one `.ktx2`, its query and hash ignored), exactly one of them
  (refinements; the overrides schema didn't change).
- `loadCubeTexture` (`layers/Base.ts`) loads `file ?? fileNames` through `loadSkyTextureAsync`;
  a texture that isn't a cube (a KTX2 without six faces) is reported and shows black, like a
  failed load. A compressed cube keeps KTX2Loader's filter, its own mips and the file's colour
  space; the base's `colorSpace` replaces it only when set. Six images are as before.
- Debug tab: the base folder shows `File` for a KTX2 cube and `Files` for six images
  (`_dbg__BaseFolder.ts`); the proxy's `fileNames` copes with a cube without them.
- The app's example: scene01's JSON lists `desertDunesKtx2` (`scenes/scene01/desertDunesKtx2.skybox.json`),
  the desert-dunes cube as one ETC1S KTX2 at 1024 per face
  (`src/public/debugger/assets/testTextures/cubemap02.ktx2`, 640 KB, Phase 0's encode in the
  faces' order scene01 lists them, `flipY` as desert-dunes), switched to in the sky box tab;
  scene01's default stays the PNG cube, so its scene baseline doesn't change.
- Tests: `SkyBox.test.ts`' "a KTX2 cube base (p311)" (the one file loaded, the file's mips,
  filter and colour space kept, `colorSpace` over it, a non-cube shown black) and
  `SkyBoxSchema.test.ts` (six images or one `.ktx2`; both, neither and a non-`.ktx2` refused).
- Checked in the Windows Chrome (WebGPU and WebGL2): scene01 switches between the PNG cube and
  the KTX2 cube with no error, the same orientation and colours.
- `SkyBoxDef`'s public type changed (`fileNames` optional, `file` added): the API baseline
  (`yarn verify:baselines`) is updated with Phase 4's versioning.

Notes from Phase 0's reading of the code (the plan before Phase 1):

- `loadTextureAsync` already loads a single `.ktx2` `fileName` through the shared KTX2Loader,
  which gives a `CompressedCubeTexture` for a six-face file (`generateMipmaps` false, the colour
  space read from the file); `isPMREMSourceReady` accepts it. So the base needs the `fileName`
  branch (schema, the overrides schema, `BASE_STRUCTURAL_KEYS`, `loadCubeTexture`), no forced
  `generateMipmaps` / `minFilter` on a compressed cube, and the file's colour space kept unless
  the base sets `colorSpace` (today `resolveColorSpace` defaults to sRGB).
- `flipY` is a lookup turn (`turnUpsideDown`), not a texture flip, so it works on a KTX2 cube as
  on six images. The KTX2's faces are stored unflipped (`ktx create --cubemap`, as above).

### Phase 2: The pipeline's cube encode

Design 2. Phase 0 found a gap the design must close first: a `*.texture.json` can't describe a
cube (`TextureAssetSchema`'s `fileName` is one string; `textureArrays.ts`' cube check only guards
an array layer), and a sky box base never goes through a texture asset (its files are `src/public`
URLs; the gatherer adds no sky box file to a scene's texture closure; a cube base can't name a
registered texture, its `textureId` is only the id it registers under). So Phase 2 needs a cube
form for a texture JSON, a way for a base to name that texture asset (so its `__url` loads), and
the encode, with the faces stored unflipped (the pipeline stores 2D textures flipped).

Decisions (2026-11-20):

- **D1: a cube texture asset.** `*.texture.json` gets `faces`: six sources in the order +x, −x,
  +y, −y, +z, −z (each what `fileName` takes: `./` relative to the JSON, or a `src/public` URL
  path), in place of `fileName` and `pack` (exactly one of the three; the schema refuses two).
  The pipeline encodes it as one KTX2 cube (`ktx create --cubemap`, mips generated by the
  encoder), its faces stored unflipped (`texOpts.flipY` is refused with `faces`), each face
  resized to the profile's `maxSize` (default 1024: Phase 0's memory figures, a 1024 cube's
  PMREM is 67 MB against 2048's 268 MB). Recorded in `assets.lock.json` like any output; its
  key covers the six files. An array layer or atlas cell naming a cube texture stays refused
  (`textureArrays.ts`' check, now reading `faces`).
- **D2: a base names the texture asset.** A `CUBE_TEXTURE` base with only `textureId` (no `file`,
  no `fileNames`) shows that texture asset; the schema's one-of becomes `fileNames`, `file` or a
  lone `textureId`. The gatherer adds the id to the textures of each scene that lists the sky box
  (the texture closure, as a material's textures), so the scene's load registers it, `__url`
  and all, before the sky box activates; `loadCubeTexture` takes it with `getTexture(textureId)`
  (as the equirect base's `textureId` does), and a texture that isn't a cube is reported and
  black, as in Phase 1. In the development data, a cube asset without an output falls back to
  its six sources (as `__sourceUrl` does for one file, with the same warning), loaded as today's
  six-image cube; a production build fails without the output, like any texture's.
- **D3: cubes default to ETC1S** (Phase 0: UASTC + zstd took ~1.1 s to load at 2048, 6.5× ETC1S's
  bytes). A texture with `faces` is encoded as ETC1S unless its `optimize` names a codec (how: a
  built-in default or a profile in `assets.config.json`, whichever the settings code takes
  cleanly; say which in "As built").

Steps (a section each, stopped for review):

1. Schema and encode: `faces` in `TextureAssetSchema` (D1's refusals, the generated JSON schema),
   the pipeline's cube job (`ktxEncode.ts`: a `--cubemap` encode of six faces; the source walk,
   cache key and lock entry for six files; D3's codec), `textureArrays.ts`' cube check on
   `faces`. Tests next to each (`ktxEncode.test.ts`, `textures.test.ts`, `assets.test.ts`,
   `TextureSchema.test.ts`).
2. Gather and runtime: the base's lone `textureId` (schema, `loadCubeTexture`), the texture
   closure from a scene's sky boxes, the development data's six-source fallback and
   `loadTextureAsync`'s path for it (`kernel/assets/Texture.ts`). Tests: `gather.test.ts`,
   `SkyBox.test.ts`, `SkyBoxSchema.test.ts`.
   As built (step 1):
   - `TextureAssetSchema` takes `faces` (a six-tuple of what `fileName` takes; `path` applies to
     public faces as to `fileName`). Its refinements (`superRefine`): at most one of `fileName`,
     `pack`, `faces` (the issue at the second); with `faces`, any `texOpts.flipY` (true too) and
     `optimize.alphaCoverage` are refused. The refinements sit on the exported schema over an
     unrefined object (`TextureAssetObjectSchema`), which `InlineTextureSchema` omits from (zod 4
     can't `omit` a refined object); an inline texture has no `faces`. `RuntimeTypes.test.ts` lists
     `faces` as a build-time key.
   - `devTools/assetPipeline/textureCubes.ts` (new, beside `textureArrays.ts` and
     `textureAtlases.ts`): `CubeSource` (`kind: 'cube'`, the JSON as `repoPath`, like a pack),
     `resolveCubeSource` (each face through `textureArrays.ts`' now-exported `resolveFileLayer`:
     an error per face, `faces[4] (+z): …`), `listCubeFiles` (the key's files, in face order) and
     `encodeCubeTexture` (faces square and of one size, else an error naming the face; fit to
     `maxSize`; RGBA when a face has alpha; not flipped). `ktxEncode.ts`' `encodeKtx2Cube` /
     `getKtxCubeArgs`: `getKtxCreateArgs` then `--cubemap`. Output `<json path>.cube.<hash>.ktx2`
     (`getCubeLogicalPath`); key params `kind: 'cubeTexture'`, the slot, the settings, `isSrgb`,
     the output. No `PIPELINE_VERSION` bump (no existing output changes).
   - The pipeline key is `texture:<json>:cube:<json>:srgb|linear` (`getPipelineAssetKey`); a cube
     use is never `:unflipped`, whatever a scene entry's `texOpts` says. A cube with its textures
     side off is `skipped` (no output, like an array); codec `none` throws ("a cube texture is a
     KTX2 file", `getTextureArraySlotSettings`).
   - D3: a built-in level in `settings.ts` (`CUBE_LEVEL`, `textures.default.codec: 'etc1s'`, input
     `isCubeSource`), applied after the profile like the collider default: only the JSON's own
     `optimize.textures` names another codec (a rule's or profile's codec doesn't, nor
     `assets.config.json`'s `defaults`, which say `uastc`). The budget's ceiling uses it too.
   - `EncodedTexture.isCube`: the VRAM figures and the budget count six faces
     (`getTextureImageCount`, `generated.ts`).
   - Tests: `textureCubes.test.ts` (not `textures.test.ts`: next to the new module),
     `ktxEncode.test.ts`, `settings.test.ts`, `assets.test.ts`, `TextureSchema.test.ts`. Checked
     with the real `ktx`: scene01's cubemap01 PNGs (2048²) → 6 faces at 1024, 11 levels, ETC1S
     sRGB, 785 KB, 8.6 s.
   - Open for step 2: a cube has no output when its textures are kept as they are, so with the
     project switch off a production build using one fails its output check (a plain texture gets
     a copy of its file then).

3. The example on the pipeline: `desertDunesKtx2` names a `desertDunes` cube texture asset (its
   six faces from the PNGs scene01's desert-dunes loads) in place of Phase 1's hand-made
   `cubemap02.ktx2`, which is removed; `yarn assets` builds it and the lock is committed with
   it. Checked in the browser as Phase 1 was (WebGPU and WebGL2, against the PNG cube).
