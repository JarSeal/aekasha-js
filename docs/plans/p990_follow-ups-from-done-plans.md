## Physics and interpolation

- **`NONE` interpolation shows each step one frame late** (p059). `object3DSyncSystem` copies TRANSFORM → Object3D at `MAIN`, before physics writes that frame's pose. Syncing the mesh after physics would remove it; it was left as is so `NONE` stays byte-identical to the old behaviour.
- **The Physics API tab's position editor streaks once under interpolation** (p059). It doesn't go through `setTransform`, so the interpolation history isn't reset.
- **`FIXED_PHYSICS` + worker at matched 60/60 Hz has ~17% jitter** (p059, headless). The pairing is unsupported and warned about.
- **Unchanged p059 non-goals**: `FollowTool`'s write-direction lag, smoothing `camera.lookAt`, an `EXTRAPOLATION` interpolation mode.
- **The other shared buffers can tear** (p063 non-goal): the debug-state buffer (wireframe colour states) and the step-stats buffer are `SharedArrayBuffer`-backed like the transform buffer, but read without its triple-buffer latch. Debug-only, per field, and right again on the next write; the same latch fixes them if they ever matter.
- **`MESSAGE_BATCH` still copies each push** (p063 non-goal): it carries only the used slots (`copyUsedBank`), but a transfer-and-return ping-pong would drop the copy. A protocol change with its own trade-offs.
- **A reused slot shows the deleted body's pose for up to a frame** (p063 risk): a slot reused in a bank latched before the new body's first write-back still holds the old pose. If it shows, the fix is at body creation (the creation pose as a pending write visible from the creation step), not in the buffer.
- **A `REMOVED` body's proxies and collision events** (p352 Phase 3). While a body is `REMOVED` (detached: `features/physics/CLAUDE.md`'s Simulation tiers), calls on a body or collider proxy the app holds fail as on a deleted body, and the removal sends no "stopped" collision event (a delete doesn't either), so an app counting contacts, a trigger zone, must treat the tier change as an exit itself. **What it takes:** the detach (`detachRigidBody`, `backends/rapier/RapierBodies.ts`) emitting the stopped events of the body's active contacts and intersections before taking it out, or Simulation tiers documenting the gap.

## Large worlds: LOD, instancing, spatial index and streaming

- **Origin rebasing for worlds past a few km** (p350 §9 Q3, p353 §8; p420 asks it too). Rapier, the physics transform buffer (`features/physics/PhysicsTransformBuffer.ts`) and three's matrices are 32-bit floats, so positions jitter a few km from the origin: a streamed world larger than about 4 km across needs a floating origin. **What it takes:** a plan of its own. Past a threshold, shift every world position by a cell-sized step on a fixed step (the determinism probe still holds): physics bodies in both worker targets, cameras, the sky, lights, the spatial domains' cells, the streaming focus and cell keys, instance sets' buffers and the interpolation history.
- **A LOD fade's first frame below about 4 fps** (p351 Phase 5). `lodFadeSystem` (`features/lod/LodFades.ts`) and `stepLodInstanceState` (`utils/LodRules.ts`, the instance sets' rules and their TSL port) advance a new fade by the frame's dt in the frame it starts, so a frame longer than `fadeSeconds` (0.25 s by default: WebGL2 on SwiftShader) ends the fade before it's drawn once and the switch pops (46 of 175 changes in `lodShowcase` at 3-4 fps). **What it takes:** skip the start frame's dt in the ECS path and the sets' rules and port together; `lodShowcase`'s dolly is the no-pop check, and every fade moves by a frame, so the scene baselines move too.
- **Impostor bakes off the main thread** (p351 §5 Q2). A runtime bake (`generateOctahedralImpostor`, `generateCrossQuads`) runs synchronously on the main renderer: 40-115 ms for a 12 × 12 octahedral bake. Exports (`*.impostor.json`) remove it for shipped content; procedural content still pays it. **What it takes:** a bake in the assets worker on an `OffscreenCanvas` with a second WebGPU device (device memory doubled for the bake, the source geometry and material serialized across), or a bake split over frames (`generateCrossQuads` returning a promise: an API change).
- **Alpha-coverage scaling for runtime impostor bakes** (p341 open Q2). Exports keep level 0's coverage at every mip (`devTools/assetPipeline/alphaCoverage.ts`), but a runtime bake (`ImpostorBake.ts`) uses three's GPU mips, which overshoot (the tree: level 4 at 1.04 × level 0's coverage, 3×2 at 1.84, 1×1 at 3.92), so a bake draws 1-11 % more area far away than its export. **What it takes:** a GPU pass after the bake's mipmaps scaling each level to level 0's coverage at the material's `alphaTest` (`measureAlphaCoverage` / `scaleAlphaForCoverage` ported, or read back and run on the CPU). Only if scenes ship runtime bakes.
- **Instanced LOD pools: no pre-warm, no colours across levels** (p348 Phase 3). `createInstancedLodPool` (`features/instancing/InstancedMeshPool.ts`) compiles each level on the first frame it's drawn (instance sets have `preWarm`), and an instance's `instanceColor` isn't carried when it moves to another level's mesh (only the swap-remove inside one mesh copies it). Less pressing since instance sets took the large static cases (p354); a pool is still the path for instances that need entities.
- **Spatial index defaults and scope** (p346 §7 Q1, p349 §6 and §3.7). `DEFAULT`'s grid is sized for `world.maxEntities` members: about 4.5 MB of typed arrays for a grid that usually holds a few hundred (p349 frees it between scenes). `AppConfig.spatial.defaultCellSize` / `defaultMaxMembers` as the template every `DEFAULT` build starts from would answer it. Also open (`features/spatial/CLAUDE.md`): a registration during a scene load defaulting to that scene's scope, as sky boxes do (a major); a "save to scene JSON" button in the Spatial index tab for a tuned cell size (`spatialDomains` is in `SceneOverridesSchema`); a world-level domain freeing its grid when empty, as `DEFAULT` does; a later major dropping `DEFAULT` for grids every scene declares (light culling then needs a fallback). The deferred grid optimizations stay in `_DONE_p050_spatial-index.md`.
- **Streaming: several focuses, 3D cells, deterministic tiers** (p353 §11 Q1 and Q3, Phase 4 D2). The state machine takes one focus (`setStreamingFocus`): split screen or a remote drone needs the union of several focuses' rings. Cells are 2D (the key format already carries `y`); caves under terrain need 3D cells. A cell's body tiers follow the frames (`decideStreamingCells` every N frames, requests on the next sub-step), so a streaming scene with tiers isn't deterministic as the tier policy's `STEPS` cadence is: a step path needs the focus read on a fixed step (for a body focus in `WORKER_THREAD`, the policy's position read and step gate in `PhysicsTierPolicy.ts` through a seam). The rest of streaming's limits: `features/streaming/CLAUDE.md` (Limits) and the Hub's Streaming guide ("Not yet").
- **Instance sets: occlusion culling, chunks on WebGL2, past 1M** (p354 §5; `features/instancing/CLAUDE.md`'s Instance sets, the bench `npx tsx devTools/bench/instanceStress.ts`). No occlusion culling: a Hi-Z pyramid from the previous frame's depth on top of the frustum cull (Phase 0 drew 9-40k instances in the open, where it has little to win; measure it for dense content seen from inside). No spatial chunks on the CPU backend (WebGL2): one `InstancedMesh` per level for the whole set, so three culls a level only whole; past about 20k spread-out instances it draws more than tiled pools (at 100k a 7.0 ms GPU frame against 5.1, 1.8M triangles against 1.1M), and a level mesh per (chunk, level) fixes it, when a WebGL2 device shows a set's GPU frame as the limit. The compute with the sun's slot is 1.07 ms at 1M instances (Apple M2): one dispatch for every slot, or a coarse cell pre-cull, pays past about 2 ms. No visibility fade for a streamed range (`addInstances(…, { fade })`, D1): cells load from a ring past the set's cull distance instead.

## Terrain

- **A heightmap terrain block in JSON** (p306 Phase 4, deferred there on 2026-11-17). Phase 4 gives the code API: `loadTerrainHeightmapAsync` and `generateTerrain(Async)`'s `heightmap` option (`aekasha/toolkit/geometry`). A `*.terrainBlock.json` can't name a heightmap yet: a `.r16` / `.r32` URL in a generator's `params` isn't an asset the gather knows, so `yarn build` (`assetOutputsBuildPlugin`) wouldn't copy it and an embed's prune would drop it. **What it takes:** a heightmap asset kind the gather writes with a `__url` (a JSON next to the raw file: format, size, height range, extent), its file copied into the build like the other outputs, and a toolkit `heightmapTerrain` generator reading it, each block sampling its own part of one map. Until then an app registers its own generator, reaching the file with `new URL('./map.r16', import.meta.url)`.

- **The rain occlusion map tilted by the wind** (p307 Phase 6, decided at its start). The map (`features/surface/RainOcclusion.ts`, `src/_engine/features/surface/CLAUDE.md`) looks straight down, so rain falls vertically: a wall's leeward foot is as wet as its windward one, and the ground under a roof's edge is dry exactly to the edge. **What it takes:** the map's camera tilted against the surface conditions' `wind` (a direction and an angle from its speed against a fall speed), its texel snap and move thresholds in the tilted frame, and the node's matrix following; a change of wind past a threshold requests a render. The streaks stay vertical (running water follows gravity).

- **A decal mode that keeps the ground's colour** (p309 Phase 5). A decal's albedo replaces the ground's (`decals/DecalMaterial.ts`, `src/toolkit/terrain/CLAUDE.md`'s decal material), so a decal reads only on grounds it suits: the tyre tracks are pressed into `mud02` but pale strips on `mud01` (lit 2.6 times as bright), fixed today by a tint per ground (a spawn's `color`, a material JSON's `tint`). **What it takes:** a mode whose decal adds only its darkening, relief (the normal), roughness and puddle mask over the surface under it, so one track reads on any ground. A forward decal can't read the ground's albedo, so one way (not tried) is a multiplying blend with the albedo slot as the darkening factor, the generators' and recipes' albedo becoming that factor.

- **A mirror for `spawnDecal`** (p309 Phase 5): a left and a right foot from one cell (`footprintBare` is a left foot; the boot prints are symmetric, so the walk doesn't show it). A `mirror` option flipping the patch's u (`DecalPatch.ts`' frame), and the same on `spawnMeshDecalAsync`.

- **Runtime decal pools: the start's hitch and two per-spawn savings** (p309 Phase 4, `decals/RuntimeDecals.ts`). A pool's first decal on a block reads the block's whole grid (`readBlockSurface`) and its first `maxDecals` spawns each make an entity and join the group: a `prewarm` option (the places made and joined at the pool's creation, the block read then) would move it to the load. A pool's colour writes could go through a component handle (one `getComponent` less each: the FIFO band's 16 writes a spawn at the default `fifoFade`), and `sampleBlockSurface` could skip the colour a decal never reads.

- **Decal sets on structures, and the atlas in Blender** (p309 Phase 3, the terrain add-on). The add-on's decal set is a block's (its origin and its Shrinkwrap target), so a wall's or bunker's decals of `decalsStructure` are exported by hand or spawned with `spawnMeshDecalAsync`: a set whose origin is any object's. Blender can't read the atlases' KTX2 outputs, so its decals draw a stand-in (`AEK Decal Preview`): `yarn assets` writing a PNG preview of each atlas slot would let the preview show the cells.

- **Structures placed with their block** (p310 §3.6, deferred in its Phase 2). `terrainShowcase`'s bunker and its leak decals are spawned by the scene file at a fixed world transform on the wetlands block's pad (`spawnImportedAsset` with `structureBunker`, then `spawnDecalSet`), so they don't follow the block's grid place and a streamed cell wouldn't carry them. **What it takes:** a `structures` list in `*.terrainBlock.json` (an import, its material and a transform relative to the block, its decal sets), spawned and deleted with the block as its scatters and decals are (`TerrainBlocks.ts`), and the add-on exporting a structure's place on its block.

- **Snow on scatter rocks** (p310 Phase 3). `rockScatter` (`setupRockMaterial`) gets wet and frosted with the ground but has no snow input, so under `terrainShowcase`'s Snowfall the scatter rocks and boulders stand bare on white ground (the decal material takes an optional `snow` set; the showcase's decal set materials name one). **What it takes:** the same optional `snow` input on the rock material, the cover on the rock's up-facing side by the surface conditions' snow.

- **Git LFS for the terrain binaries** (p301 §9, question 1: "not now, revisit if binary churn grows"). On 2026-11-20 the repo holds 16.3 MB of `.blend` files, 4.4 MB of source GLBs in the app and toolkit and 65 MB of asset outputs in `src/public/aek-assets/`; `terrainShowcase`'s blocks are 7.5 MB of it. A `.blend` changes whole on every save, so rebuilding the showcase's blocks or the templates (`buildShowcaseBlocks.py`, `buildTerrainTemplates.py`) adds their full size to the history each time. Revisit when a clone's size gets in the way.

- **Terrain blocks as streamed cell content** (p301 out of scope and §7, p306 D2). A `*.terrainBlock.json` already follows the streaming conventions (a `2^n + 1` grid placed at `grid × size` with shared edge vertices and a `skirt` for neighbours of another resolution; world-space tiling, noise and seeds; its own maps, scatter, decals and `HEIGHTFIELD` collider), but `streaming()` has no path for blocks: the manifest (`devTools/gather/streamingManifest.ts`) cuts only meshes and lights into cells, a scene's `terrainBlocks`, `scatters` and `decalSets` load in its base and are spawned by scene code, and `streamingGrid` generates its ground as code content. **What it takes:** the gather cutting a streaming scene's blocks into cells at their `grid` place (each block's import, material variant textures, scatters and decal sets owned by its cell), the cell's load spawning them through `spawnTerrainBlock` and its unload deleting them, the collider joining the cells' bodies and tiers, and a far form (a coarser block with a skirt, or whole-block LOD levels; crack-free stitching between levels is unplanned). D2 also left open a scene load spawning its listed blocks without scene code. "Structures placed with their block" depends on this.

- **Grass blades and water bodies** (p301 non-goals; no plan has them). Grass and foliage blades: instanced cards or GPU-generated blades bent by the surface conditions' `wind` (the one wind vector p427's question 4 wants). Water surfaces (lakes, rivers): a body with its own shading, its level perhaps `waterLevel`. p307's puddles are a material effect, and p308's leaf cards are the nearest thing that exists.

- **A surface query for gameplay: what's under a point, and how wet** (p307 T14, wet friction; `features/surface/CLAUDE.md` calls it a follow-up). Nothing tells gameplay which ground is under a point or how wet it is: wet friction, tyre grip (p423), footstep sounds and footprint choice. **What it takes:** a `getSurfaceAt(x, z)`-style query returning the block's layer weights there (the material's blend on the CPU: `ScatterLayerWeights.ts`' `createScatterLayerWeigher` over `blocks/BlockSurface.ts`' `sampleBlockSurface`) and the local wetness (the global value × the exposure, plus puddles from each set's `surface` response). Simulation reads come from step-clock state and seeded streams, not the frame-time surface clock (p427's question 5).

- **The terrain material's `MIP` and `HEIGHT` debug views** (p305 D10 listed nine; seven were built). `TERRAIN_DEBUG_VIEWS` (`src/toolkit/terrain/material/TerrainMaterialConfig.ts`) lacks `MIP`, the mip level picked (it would check the explicit-gradient paths, HEX, the slots' gradients, biplanar and gated planes, for mip seams, done by eye today), and `HEIGHT`, the blended height the height blend works on. **What it takes:** both values in `TerrainDebugViewContext` and a branch each in `src/toolkit/terrain/debug/_dbg__DebugViews.ts` (the mip level is log2 of the larger UV derivative × the texture size, per layer or slot, blended by the weights as `TEXEL_DENSITY` is), then the enum, `TerrainDefine.ts` and its test, and the view lists in `src/toolkit/terrain/CLAUDE.md` and the root `CLAUDE.md`. Smaller, from the same plan: a `PROCEDURAL_LIVE` layer's set is still baked (1024² `LITE` ≈ 10.7 MB) though no tier samples the bake; a marker on the input that the gather and `features/texturesets/TextureSetBakes.ts` both read would skip it.

- **The scatter generator off the main thread** (p308 Phase 3 §3). `terrainScatter` (`src/toolkit/terrain/scatter/TerrainScatter.ts`) runs on the main thread at a block's spawn, about 4 µs a candidate: a dense 64 m block at 0.4 m spacing is 15.6k candidates and 68-69 ms on Windows Chrome, mostly Bridson's sampling (`PoissonDisk.ts`). Fine in a load, a hitch once blocks with scatters stream (`docs/techniques/terrain-scatter.md`, Performance). **What it takes:** p306 Phase 4's pattern, a toolkit module worker like `TerrainWorker.ts` loaded on first use, given the block's grid heights, normals and colours and the read-back splat and noise texels (`readTextureTexelsAsync` stays on the main thread) and returning the matrices, items and colours as transferables, with identical placements (the same seed and per-candidate streams). A cheaper first step: Bridson's k from 30 to 15 halves its time for 3.5 % fewer points.

- **An "Export Scatter" operator in the terrain add-on** (p308 Phase 5 §1). A scatter's glTF node carries its object's offset and the `IMPORTED` source adds the block's centre again, so an export is right only with the block at grid (0, 0) and the scatter at the origin (the handbook's workaround). **What it takes:** an operator beside Export Block (`src/toolkit/terrain/blender/aekasha_terrain_tools.py`) exporting relative to the block's centre with the import's settings (GPU Instances, Geometry Nodes Instances, Point Clouds, Attributes), checking for applied scale and unrealized instances, and writing the `*.importedAsset.json` (`optimize.mesh.quantize: false`) and the `IMPORTED` `*.scatter.json`. It fits beside the decal set item above.

- **Scatter on blocks that aren't a regular grid** (p308 D4's raycast path, not built). `ScatterSurface.ts` reads the target as a grid, so a `TRIMESH` or overhanging block throws (a handbook pitfall). Rays weren't built: three's `Raycaster` has no BVH and the engine's casts aren't public (`docs/issues/i270_three-ray-casting-not-public.md`). **What it takes:** a BVH over the block mesh (or physics ray casts against its `TRIMESH`) for the height, normal and colour at each candidate, with barycentrics in place of the grid's diagonal.

- **`terrainGallery` on SwiftShader WebGL2** (p306 Phase 3's exit, unverified since). Under `yarn verify:scenes --webgl` a gallery shader failed to link and the context was lost; a real GPU is fine on both backends. **What it takes:** run `--only terrainGallery --webgl` again; if it still fails, find the shader (`src/toolkit/terrain/CLAUDE.md`'s TSL branch traps) and file an issue, or mark the scene real-GPU-only in `scenes.config.ts`.

- **A debug key for "Center and fit all windows"** (p094): `fitAllDraggableWindowsToScreen` (`aekasha/ui`) exists and the Debug tools tab's button calls it (`debug/_dbg__DebugTools.ts`); a `DefaultDebugKeyBindings.ts` entry with a `category` would add the key. - **Dev files: saving without a reload, and delete / rename** (p342 §5 questions 1-3). Every write that changes the generated data reloads the page after its gather (`devTools/devFiles/CLAUDE.md`; the debug state survives the reload). A tool that would rather keep the page (the material editor saving into its JSON, p355) needs the runtime taking new generated data in place (`import.meta.hot.accept` on `src/generated/index.ts`, the data handed to the engine again, `kernel/scene/AppData.ts`, and whatever caches it) and the gatherer (`devTools/sceneGathererPlugin.ts`) skipping its `full-reload` for writes that ask for it. The server can't delete or rename (`POST commit` only writes): needed once an exporter replaces a set of files whose names change. LAN writes stay opt-in (`AEK_DEV_FILES_LAN=true`); revisit if working from a phone becomes common. Seen once, not chased (p341 Phase 2): after the gather an impostor export triggered, the reloaded page had both `SceneLoader.ts` and `SceneLoader.ts?t=…` in one stack and failed ("KTX2 textures can only be loaded after the renderer has been created"); a fresh load was clean. If it comes back, find which import keeps the old module URL after the reload, in an issue file.
- **The material editor's edits don't reach a palette group** (p374's risk row, never built). A palette group draws the merge material, whose parameter table and texture arrays come from the palette's data the gather bakes into the scene (`MergeMaterial.ts`' `packMergeMaterialTable`, `createMergeMaterialTable`), so an edit, or a saved override, to one of its member materials changes only the meshes drawn with that material on their own. **What it takes:** a hook from a member material's edit to its table entry (that row of the table texture rewritten, `needsUpdate`). A map edit can't follow: an array layer is a build-time encode.
- **A window for any mesh entity** (p373's open question 2). The Merging tab's member window opens only for a merge member; a plain mesh entity has no window. A Meshes tab (or an entry from the ECS tab) listing mesh entities would open the member window for a merged one. The editor's future select and transform tools (Editor views, below) resolve a hit to its member with `getMergeMemberAtFace` / `getMergeMemberAtBatchId` and move it through an edit session (`beginMergeMemberEdit`).
- **A cached import's LOD levels keep their first owner** (p347 Phase 2). `retagImportOwner` (`kernel/assets/import/ImportRegistry.ts`) re-tags a cached import's geometries and textures to the scene getting it, but not their chain levels (`<id>#lod<n>`), so the GPU memory tab's "By owner" lists the levels under the scene that generated them. Nothing leaks (the chain's ref keeps them from that scene's sweep, and they go with the base). **The fix:** re-tag each geometry's levels too, through `lod()`'s import extension (`LodImport.ts`), since the kernel imports no LOD code.
- **GPU memory figures after a device loss** (p345 §5 Q1). The engine has no device-loss handling (`GPUDevice.lost`) at all; whether three's `renderer.info.memory` resets or double-counts on a lost device is unknown, and the tab (`debug/gpuMemory/`) says its figures are since boot. Check it when device-loss handling lands, a plan of its own.

## ECS

- **`object3DSyncSystem` visits every mesh entity each frame** (p378 Phase 0 step 1 and D4; its Phase 2 was dropped for it). The sync (`kernel/ecs/ECSCoreSystems.ts`, `MAIN`) loops over every `OBJECT3D` entity to find the dirty ones (`isDisabled`, the typed store's slot and dirty flag or the `TRANSFORM`'s version), so a static mesh costs 55-60 ns a frame for no work. **Measured** (Apple M2, Chrome, both backends, p377's far field, `devTools/bench/hlodSpike.ts --step draws --cases p378`, its systems table): 1.15-1.25 ms a frame at 400 sites (20,770 baked members), 0.35-0.39 ms at 150 (7,987). After p378 took the members out of the scene graph it's all they still cost: 0.6-0.85 ms over the same draws without members (its Phase 3). A merging-side skip can't avoid it (a member is still in the storage the sync walks), so **the fix** is the kernel's, for every static mesh, and worth a plan of its own: the sync walking only the dirty transforms (a list filled where a `TRANSFORM` is marked dirty or its version bumped, both storage modes), or static entities kept apart. Keep what reads the copy: `OBJECT3D._lastVersion`, the count the copy bumps in `TYPED_ARRAY` storage for the merge batch's sync (p375 S3), `DISABLED` and its re-enable, and the sync's place in the frame (Physics and interpolation's first item). **Smaller shares, figures only:** with the same 20,770 members, `spatialIndexRebuildSystem` 0.06-0.07 ms a frame more and the moved-member check (`mergeMoveCheckSystem`, debug env only) 0.08-0.09 ms on average.

## Per-frame allocations

- **The ECS storage's `for … of` makes an entry array per entity** (p808): `IComponentStorage` (`kernel/ecs/ECSComponentStorage.ts`) is only `Iterable`, with no `forEach`.
- **`getCanvasSize()` makes two objects a call** (p808, `kernel/render/CanvasSize.ts`): an `out` argument, or a public resize listener, would end it for per-frame callers.
- **The kit tables allocate per render on a scheduler** (p807): `readRows`' arrays and closure, `place`, `placeElems`; 14-18 kB/s in the profiler's Objects and GPU memory tabs at 4 and 2 Hz. A "rows unchanged" path in the kit's table (`ui/data/`) would remove it.
- **The 3D debug symbols and the light helpers allocate every frame** (p807, measured): `debug/symbols/_dbg__Symbols.ts` about 21 kB/s, the light helpers 9 kB/s, in any debug session.
- **The debug tabs' leftovers** (p806, measured by p807): the Physics tab 14 kB/s (its list and the tiers' readout), the character state window 18-22 kB/s (its every-frame default interval and the `OTHER` rows).
- **The time series schedules one empty animation frame after each draw** (p807): p805's design for an app pushing every frame; at the stats panels' 30 Hz about 180 empty callbacks a second for six panels.

## Characters

- **`isMovingTowardsImpossibleSlope` is a dead field** (p067): the dynamic controller's data declares it (`features/character/controllers/dynamic/DynamicCharacterData.ts`), but nothing writes it, and the character state window shows it as it is. Implement it or remove it.
- **Rebuilding the body for baked config keys** (p069's Phase 4, dropped): the character state window keeps the keys baked into the colliders (`config.bakedKeys`, eg. `_radius`) locked. A rebuild swaps the colliders in place (async in `WORKER_THREAD` mode; the physics API (`aekasha/physics`) has no helper that adds colliders to an existing entity), must keep the character on a moving platform, and must rebuild back on undo. Saved values are applied after the colliders exist, so saved baked values would need a rebuild right after creation, or to be read before `getDimensions` and kept out of `initialConfig`. The app owns the visual, so a resized capsule wouldn't match the model.
- **Saving tuned character values into the scene source** (p069): there's no character JSON schema yet, so the state window's copy-out (as code) is the bridge.
- **Configurable character gizmo colours** (p068): they're constants (`GIZMO_COLORS` in `features/character/debug/_dbg__CharacterGizmos.ts`).
- **More controllers and body plans** (p066 non-goals): a flying controller (lift for gravity, a 3D intent, landing for "grounded") and a quadruped body plan next to `HUMANOID_CAPSULE` (`features/character/CharacterBodyPlans.ts`). Each reuses the registry, the component, the intent, the input schemes, the locomotion-state events and the state window. The kinematic controller, the animation state graph and the ragdoll hand-off have plans (p421, p422; p250's joints).
- **A `CameraIntent`** (p603 C3, a direction with no plan): the camera rig's look input as an intent, as `CharacterIntent` is the character's. Today `createFollowObjectCameraRig`'s `getMouseMoveInput` callback pulls a look delta from the app, and nothing passes one; the vehicle side (`VehicleIntent`) is p423's.

## Smallest build

- **A "lite" embed profile without TSL** (p611 §7.3, decided against for now): about 110 KiB gzip less on the banner (three 237.7 → 128.3 KiB), with classic materials only: no sky box, PostFX, viewports, fat lines, impostors, LOD fades or texture arrays. Revisit when three ships its node system apart from `WebGPURenderer`, or when a real embed needs well under 200 KiB. three r187 made `three/tsl` tree-shakeable (#34533) and dropped unused maths classes (#34619): the banner's `three` group went from 251.7 to 231.1 kB gzip (p057), so the gap is smaller; measure it again before deciding. Its shape: a lite flag in `sbp.config.ts` aliasing `three/webgpu` to `three`, a classic `createRenderer`, and the gatherer failing a lite profile's TSL scene.
- **Every scene's JSON is in the first download** (p377 Phase 3). `src/generated/index.ts` imports `generatedAppData.json` statically, so the app's first download carries every scene's data, a streaming scene's whole manifest included. p377's ruin kit in `streamingGrid` (meshes with their transforms, far groups, cells' lists and bounds) cost about 30 bytes gzip a mesh: 384 meshes in 64 cells were +11.6 KiB on the initial download, so it shipped with 96 in 16 cells (+3.4 KiB, the budgets raised: initial 398, `assets/index.js` 394, the `app` group 19 KiB). Streaming scenes are where it grows fastest: a world's content is in its JSON by design. The fix: the first scene's data in the first download and each other scene's loaded with its scene (a chunk per scene's data, as its `sceneFile` already is, or the manifest fetched by `created`), a gather and boot change (the registries, `__features` checks and the Hub's scene list read the data before a load). Smaller on the way: the cells' `bounds` unrounded (17 digits a number; to the centimetre saves 0.55 KiB of the 64-cell kit's 12.5).

## Ækasha Hub

- **The first real deploy** (p550, p551): check that the host's CDN keys its cache on the `?v=<hash>` query strings the Hub's `_assets/` references carry (`_headers` caches them as immutable). If it ignores them, switch to hashed file names. A host other than Netlify needs its own headers file.
- **A ringed-planet mark?** (p550): the homepage design's logo is a ringed planet, the brand's is the Æ. A combined mark (the Æ inside a ring) is a brand decision.

- **A shared nav partial** (p551): every page renders its own copy of the nav. If a full rebuild gets slow with the API pages, the nav could become a partial the pages include.
